# 第 2 章 — 方法论

> *授人以鱼，供其一日之食。  
> 授人以渔，供其终身之需。*

中国谚语（英文对应）

我作为一名初级系统管理员开始了我的技术职业生涯，我认为我可以通过单独研究命令行工具和指标来学习性能。我错了。我从上到下阅读了手册页，了解了缺页异常、上下文切换和各种其他系统指标的定义，但我不知道如何处理它们：如何从信号转向解决方案。

我注意到，每当出现性能问题时，资深系统管理员心中都有一套排查流程，能够迅速运用工具和指标找到根因。他们知道哪些指标重要、何时表明存在问题，以及如何利用这些指标缩小排查范围。手册页中缺少的正是这种*实践经验*——通常需要在资深管理员或工程师身旁观察他们的操作才能学到。

从那时起，我收集、记录、分享并开发了我自己的性能*方法论*。本章介绍这些方法，以及系统性能所需的其他基础知识：概念、术语、统计数据和可视化。这些内容构成理论基础，后续章节再深入讨论实现。

本章的学习目标是：

- 了解关键性能指标：延迟、利用率和饱和度。
- 培养对测量时间尺度（小至纳秒）的感觉。
- 了解调优中的权衡、目标以及何时停止分析。
- 识别工作负载与架构的问题。
- 考虑资源与工作负载分析。
- 掌握不同的性能分析方法，包括 USE 方法、工作负载特征分析、延迟分析、静态性能调优和性能箴言。
- 了解统计学和排队论的基础知识。

在本书的所有章节中，这一章自第一版以来变化最小。在我的职业生涯中，软件、硬件、性能工具和性能可调参数都发生了变化。保持不变的是理论和方法：本章涵盖的持久技能。

本章分为三个部分：

- **背景**介绍术语、基本模型、关键性能概念和观点。其中大部分内容将作为本书其余部分的假定知识。
- **方法论**讨论性能分析方法，包括观测和实验、建模以及容量规划。
- **指标**引入性能统计、监控和可视化。

这里介绍的许多方法将在后面的章节中进行更详细的探讨，包括[第 5 章](#ch05-ch05)至[第 10 章](#ch10-ch10)中的方法论部分。

## 2.1 术语

以下是系统性能的关键术语。后面的章节提供了额外的术语，并在不同的上下文中描述了其中的一些术语。

- **IOPS**：每秒输入/输出操作是数据传输操作速率的度量。对于磁盘 I/O，IOPS 是指每秒的读取和写入次数。
- **吞吐量**：执行工作的速率。特别是在通信中，该术语用于指“数据速率”（每秒字节数或每秒位数）。在某些情况下（例如数据库），吞吐量可以指*[操作速率](#gloss-glo-113)*（每秒操作数或每秒事务数）。
- **响应时间**：完成操作的时间。这包括等待所花费的时间和服务所花费的时间（*服务时间*），包括传输结果的时间。
- **延迟**：操作等待获得服务所花费的时间。在某些上下文中，它也可以指操作的完整耗时，相当于响应时间。示例请参见[第 2.3 节](#ch02-ch02lev3)、[概念](#ch02-ch02lev3)。
- **利用率**：对于服务请求的资源，利用率是衡量资源繁忙程度的指标，基于给定时间间隔内资源主动执行工作的时间。对于提供存储的资源，利用率可以指消耗的容量（例如，内存利用率）。
- **饱和度**：资源将其无法服务的工作排队的程度。
- **[瓶颈](#gloss-glo-021)**：在系统性能中，瓶颈是限制系统性能的资源。识别并消除系统瓶颈是系统性能分析的关键工作。
- **[工作负载](#gloss-glo-199)**：系统的输入或施加的负载就是工作负载。对于数据库，工作负载由客户端发送的数据库查询和命令组成。
- **缓存**：快速存储区域，可以复制或缓冲有限数量的数据，以避免直接与较慢的存储层通信，从而提高性能。出于经济原因，缓存通常小于较慢的层。

如果需要，术语表包含更多术语供参考。

## 2.3 概念

以下是系统性能的重要概念，并且是本章其余部分和本书的假定知识。在后面章节的架构部分介绍特定于实现的细节之前，先以通用方式描述这些主题。

<!-- source-id: ch02#ch02lev3sec1 -->
### 2.3.1 延迟

对于某些环境，延迟是性能分析唯一关注的指标；对于另一些环境，它与吞吐量并列为最重要的一两个指标。

以延迟为例，[图 2.3](#ch02-ch02fig03)显示了网络传输（例如 HTTP GET 请求），其中耗时分为延迟和数据传输两部分。

<!-- source-id: ch02#ch02fig03 -->
![图 2.3 网络连接延迟](../images/02fig03.jpg)

延迟是执行操作之前等待的时间。在此示例中，该操作是传输数据的网络服务请求。在执行此操作之前，系统必须等待网络连接建立，这是此操作的延迟。 *响应时间*跨越该延迟和操作时间。

由于延迟可以从不同的位置测量，因此通常会注明测量目标。例如，网站的加载时间可能由从不同位置测量的三个时段组成：*DNS 延迟*、*TCP 连接延迟*，以及*TCP 数据传输时间*。DNS 延迟指整个 DNS 操作；TCP 连接延迟则仅指初始化阶段（TCP 握手）。

在更高的层面上，所有这些，包括 TCP 数据传输时间，都可以被视为其他事物的延迟。例如，从用户单击网站链接到结果页面完全加载的时间可以称为“延迟”，其中包括浏览器通过网络获取网页并呈现它的时间。由于“延迟”一词可能含糊不清，因此最好包含限定术语来解释其测量的内容：请求延迟、TCP 连接延迟等。

由于延迟是基于时间的度量，因此可以进行各种计算。性能问题可以使用延迟进行量化，然后进行排名，因为它们使用相同的单位（时间）来表示。通过考虑哪些延迟可以减少或消除，还可以计算预测的加速比。例如，使用 IOPS 指标无法准确执行这些操作。

作为参考，[表 2.1](#ch02-ch02tab01) 列出了时间的数量级及其缩写。

### 2.3.2 时间尺度

虽然可以用数值比较不同的时间，但建立时间尺度的直觉，以及对不同来源的延迟形成合理预期，同样很有帮助。系统组件运行在差异极大的时间尺度上（相差多个数量级），以至于人们很难真正把握这种差异有多大。[表 2.2](#ch02-ch02tab02) 给出了示例延迟，从 3.5 GHz 处理器的 CPU 寄存器访问开始。为了直观展示这些时间尺度的差异，表中还把每种操作可能耗费的平均时间换算到一个假想系统中：现实中的一个 CPU 周期为 0.3 ns（约为十亿分之一秒的三分之一[^fn-ch02-ch02-footnote-1]），在假想系统中则需要整整 1 秒。

**表 2.2 系统延迟的时间尺度示例**

| **事件** | **延迟** | **换算后的时间** |
| --- | --- | --- |
| 1 个 CPU 周期 | 0.3 ns | 1 s |
| 1 级缓存访问 | 0.9 ns | 3 s |
| 2 级缓存访问 | 3 ns | 10 s |
| 3 级缓存访问 | 10 ns | 33 s |

| 固态硬盘 I/O（闪存） | 10–100 μs | 9–90 小时 |
| 旋转磁盘 I/O | 1–10 毫秒 | 1–12 个月 |
| 互联网：旧金山到纽约 | 40 毫秒 | 4 年 |
| 互联网：旧金山至英国 | 81 毫秒 | 8 年 |
| 轻量级硬件虚拟化启动 | 100 毫秒 | 11 年 |
| 互联网：旧金山至澳大利亚 | 183 毫秒 | 19 年 |
| 操作系统虚拟化系统启动 | \< 1 s | 105 年 |
| 基于 TCP 定时器的重传 | 1–3 秒 | 105–317 年 |

### 2.3.3 权衡

您应该了解一些常见的性能权衡。[图 2.4](#ch02-ch02fig04) 展示了“好、快、便宜三选二”的权衡，以及针对 IT 项目调整后的术语。

<!-- source-id: ch02#ch02fig04 -->
![图 2.4 权衡：三选二](../images/02fig04.jpg)

许多 IT 项目选择准时且成本低廉，而将性能问题留到以后修复。当早期决策阻碍性能提高时，例如选择不理想的存储架构并将数据存入其中、使用实现效率低下的编程语言或操作系统，或者选择缺乏全面性能分析工具的组件，这种选择可能会出现问题。

性能调优中的一个常见权衡是 CPU 和内存之间的权衡，因为内存可用于缓存结果，从而减少 CPU 使用率。在具有大量 CPU 的现代系统上，这种权衡也可能反过来：CPU 时间可能会花在压缩数据以减少内存使用上。

可调参数通常需要权衡。这里有几个例子：

- **文件系统记录大小**（或块大小）：较小的记录大小，接近应用程序 I/O 大小，对于随机 I/O 工作负载性能更好，并在应用程序运行时更有效地利用文件系统缓存。大记录大小将改善流工作负载，包括文件系统备份。
- **网络缓冲区大小**：较小的缓冲区大小将减少每个连接的内存开销，有助于系统扩展。大尺寸将提高网络吞吐量。

在对系统进行更改时，请考虑此类权衡。

<!-- source-id: ch02#ch02lev3sec4 -->
### 2.3.4 调优工作

性能调优在最接近工作实际执行的位置进行时最有效。对于应用程序驱动的工作负载，这意味着在应用程序本身中进行调优。[表 2.3](#ch02-ch02tab03) 展示了一个可供调优的示例软件栈。

在应用程序层调优，可能可以消除或减少数据库查询，从而大幅提升性能（例如速度达到原来的 20 倍）。如果一直调优到存储设备层，虽然可能消除或改善存储 I/O，但执行更高层操作系统栈代码的开销已经付出，因此最终应用性能可能只能获得百分比量级的提升（例如 20%）。

<!-- source-id: ch02#ch02tab03 -->
**表 2.3 调优目标示例**

| **层** | **调优目标示例** |
| --- | --- |
| 应用程序 | 应用程序逻辑、请求队列大小、执行的数据库查询 |
| 数据库 | 数据库表布局、索引、缓冲 |
| 系统调用 | 内存映射或读/写、同步或异步 I/O 标志 |
| 文件系统 | 记录大小、缓存大小、文件系统可调参数、日志记录 |
| 存储 | RAID 级别、磁盘数量和类型、存储可调参数 |

在应用程序级别获得巨大性能提升还有另一个原因。当今的许多环境都以快速部署特性和功能为目标，每周或每天将软件更改推送到生产中。[^fn-ch02-ch02-footnote-2] 因此，应用程序开发和测试往往关注正确性，在生产部署之前几乎没有时间进行性能测量或优化。当性能成为问题时，这些活动才会进行。

虽然应用程序层可能是调优最有效的位置，却不一定是观测最有效的出发点。要理解慢查询，最好考察它在 CPU 上执行所花的时间，或者它引发的文件系统和磁盘 I/O。这些都可以通过操作系统工具观测。

在许多环境（尤其是云计算）中，应用程序级别不断发展，每周或每天将软件更改推入生产。随着应用程序代码的更改，经常会发现巨大的性能提升，包括回归修复。在这些环境中，操作系统的调整和操作系统的可观测性很容易被忽视。请记住，操作系统性能分析还可以识别应用程序级别的问题，而不仅仅是操作系统级别的问题，在某些情况下比单独从应用程序中更容易。

<!-- source-id: ch02#ch02lev3sec5 -->
### 2.3.5 适用程度

不同的组织和环境对性能有不同的要求。您可能加入了一个组织，在该组织中，进行比您以前见过的更深入的分析是常态，甚至超出了您此前认为可能达到的深度。或者您可能会发现，在您的新工作场所，您认为的基本分析被认为是高级的，并且以前从未进行过（好消息：唾手可得的成果！）。

这并不一定意味着有些组织做得对、有些组织做得错。这取决于性能专业知识的投资回报率（ROI）。拥有大型数据中心或大型云环境的组织，可能会聘请性能工程师团队来分析一切，包括内核内部结构和 CPU 性能计数器，并经常使用各种跟踪工具。他们还可以正式建立性能模型，为未来增长做出准确预测。对于每年在计算上花费数百万美元的环境，聘请这样的性能团队很容易证明是值得的，因为他们找到的性能收益就是投资回报。计算支出有限的小型初创公司，可能只做表面检查，依靠第三方监控解决方案检查性能并提供告警。

然而，正如[第 1 章](#ch01-ch01)中所介绍的，系统性能不仅仅与成本有关：它还关系到最终用户体验。初创公司可能需要投资性能工程来改善网站或应用程序延迟。这里的投资回报率不一定体现为成本降低，也可能体现为让客户更满意、避免客户流失。

最极端的环境包括证券交易所和高频交易者，其中性能和延迟至关重要，并且需要付出大量的努力和费用。举个例子，纽约和伦敦交易所之间的跨大西洋电缆计划耗资 3 亿美元，以将传输延迟减少 6 毫秒 [\[Williams 11\]](#ch02-ch02ref14)。

在进行性能分析时，适用程度也会影响何时停止分析的决定。

<!-- source-id: ch02#ch02lev3sec6 -->
### 2.3.6 何时停止分析

进行性能分析时面临的一个挑战是知道何时停止。有这么多的工具，有这么多的东西需要检查！

当我讲授性能课程时（最近又重新开始了），我会给学生一个由三个因素共同造成的性能问题，然后发现有些学生找到一个原因就停止，有些找到两个原因就停止，还有些找到了全部三个原因。也有学生继续追查，试图找出更多原因。谁做得对？找到全部三个原因后，似乎很容易说应该停止；但在真实问题中，你并不知道原因究竟有多少。

以下是您可以考虑停止分析的三种情况，并提供一些个人示例：

- **当您已经解释了性能问题的大部分成因时**。某个 Java 应用程序的 CPU 消耗达到了原来的 3 倍。我首先发现了异常处理调用栈消耗 CPU 的问题，随后量化这些调用栈中的耗时，发现它们只占 CPU 总消耗的 12%。如果这个比例接近 66%，我就可以停止分析，因为这已足以解释那 3 倍的性能下降。但实际比例只有 12%，因此我需要继续寻找其他原因。
- **当潜在投资回报低于分析成本时**。我处理的一些性能问题，每年可以带来数千万美元的收益，因此值得花上几个月的工程时间进行分析。另一些性能优化，例如针对很小的微服务，收益可能只有几百美元，甚至不值得投入一小时的工程时间。也有例外：例如公司没有更值得我做的工作时（实际中从未出现过），或者我怀疑这可能是未来更大问题的预警信号，因而值得在问题扩大前排查。
- **当其他地方有更大的投资回报率时**。即使前两种情况没有得到满足，其他地方也可能有更大的投资回报率需要优先考虑。

如果您是一名全职性能工程师，那么根据潜在的投资回报率对不同问题进行优先分析可能是一项日常任务。

<!-- source-id: ch02#ch02lev3sec7 -->
### 2.3.7 时间点建议

由于更多用户、更新的硬件以及更新的软件或固件的添加，环境的性能特征随着时间的推移而变化。当前受 10 Gbit/s 网络基础设施限制的环境在升级到 100 Gbit/s 后可能会开始遇到磁盘或 CPU 性能瓶颈。

性能建议，尤其是可调参数的取值，仅在特定的“时间点”有效。性能专家本周提出的最佳建议，可能在软件或硬件升级、或增加更多用户后，于下周就失效。

在某些情况下，通过互联网搜索找到的可调参数值可以带来快速收益。如果它们不适合你的系统或工作负载，或者过去适用而现在已经不适用，或者只是某个软件缺陷在后续升级中被正确修复之前的临时绕过方案，那么这些参数也可能拖垮性能。这就像翻找别人的药柜并服用不一定适合你、可能已经过期，或本来只应短期服用的药物。

浏览此类建议只是为了查看存在哪些可调参数以及过去需要更改哪些参数，这可能很有用。然后，您的任务就变成查看是否以及如何针对您的系统和工作负载进行调整。但是，如果其他人之前不需要调整该参数，或者已经调整了它但没有在任何地方分享他们的经验，那么您可能仍然会错过一个重要的参数。

更改可调参数时，将它们存储在具有详细历史记录的版本控制系统中会很有帮助。（使用 Puppet、Salt、Chef 等配置管理工具时，你可能已经在做类似的事情。）这样，之后就能检查参数何时以及为何发生变化。

### 2.3.8 负载与架构

应用程序可能会由于软件配置和运行它的硬件（即其架构和实现）存在问题而表现不佳。然而，应用程序也可能只是因为施加了过多负载而表现不佳，导致排队和长延迟。负载和架构如[图 2.5](#ch02-ch02fig05)所示。

<!-- source-id: ch02#ch02fig05 -->
![图 2.5 负载与架构](../images/02fig05.jpg)

如果架构分析显示工作排队，但工作执行方式没有问题，则问题可能是施加了过多的负载。在云计算环境中，此时可以按需引入更多服务器实例来处理工作。

例如，架构问题可能是 CPU 上繁忙的单线程应用程序，请求排队，而其他 CPU 可用且空闲。在这种情况下，性能受到应用程序的单线程架构的限制。架构的另一个问题可能是多线程程序争夺单个锁，这样只有一个线程可以向前推进，而其他线程则等待。

负载问题可能是多线程应用程序在所有可用 CPU 上都很忙，并且请求仍在排队。在这种情况下，性能受到可用 CPU 容量的限制，或者换句话说，性能受到超出 CPU 处理能力的负载的限制。

### 2.3.9 可扩展性

系统在负载增加时所表现出的性能特征就是其*可扩展性*。[图 2.6](#ch02-ch02fig06) 展示了系统负载增加时典型的吞吐量曲线。

<!-- source-id: ch02#ch02fig06 -->
![图 2.6 吞吐量与负载](../images/02fig06.jpg)

在一段时间内，系统呈现线性可扩展性。随后会到达一个由虚线标记的点，此时资源争用开始降低吞吐量。这个点可以称为*拐点*，因为它是两种函数的分界。超过该点后，随着资源争用加剧，吞吐量曲线偏离线性可扩展性。最终，争用和一致性维护带来的额外开销会使完成的工作减少，吞吐量下降。

当组件达到 100% 利用率时，可能会出现此点：*饱和点*。当组件接近 100% 利用率且排队开始频繁、明显时，也可能会发生这种情况。

一个可能呈现这种曲线的系统，是执行大量计算并通过增加线程来提高负载的应用程序。当 CPU 利用率接近 100% 时，CPU 调度器延迟增加，响应时间开始变差。达到峰值性能后，在 100% 利用率附近继续增加线程会导致更多上下文切换；上下文切换消耗 CPU 资源，实际完成的工作反而减少，于是吞吐量下降。

如果把 x 轴上的“负载”替换成 CPU 核心数等资源，也能看到相同的曲线。有关此主题的更多信息，请参阅[第 2.6 节](#ch02-ch02lev6)、[建模](#ch02-ch02lev6)。

[图 2.7](#ch02-ch02fig07) 展示了以平均响应时间或延迟表示的非线性可扩展性性能下降情况 [\[Cockcroft 95\]](#ch02-ch02ref3)。

<!-- source-id: ch02#ch02fig07 -->
![图 2.7 性能下降](../images/02fig07.jpg)

当然，响应时间越长越糟糕。当系统开始把内存页移到磁盘以释放主内存时，内存负载可能呈现“快速”降级曲线；CPU 负载则可能呈现“缓慢”降级曲线。

另一个“快速”降级曲线的例子是磁盘 I/O。随着负载（以及由此产生的磁盘利用率）增加，I/O 更可能排在其他 I/O 后面。空闲的旋转式（非固态）磁盘可以以约 1 ms 的响应时间处理 I/O；但负载增加后，响应时间可能接近 10 ms。[第 2.6.5 节](#ch02-ch02lev6sec5)、[排队论](#ch02-ch02lev6sec5)中的 M/D/1、60% 利用率示例对此进行了建模；[第 9 章](#ch09-ch09)、[磁盘](#ch09-ch09)将进一步讨论磁盘性能。

如果应用程序在资源不可用时开始返回错误而不是排队工作，则可能会出现响应时间的线性可伸缩性。例如，Web 服务器可能会返回 503“服务不可用”，而不是将请求添加到队列中，以便可以以一致的响应时间执行所服务的那些请求。

### 2.3.10 指标

性能指标是系统、应用程序或附加工具生成的、用于度量关注活动的统计量。它们用于性能分析和监控，既可以在命令行中以数值查看，也可以借助可视化图表查看。

常见的系统性能指标类型包括：

- **吞吐量**：每秒的操作数或数据量
- **IOPS**：每秒 I/O 操作数
- **利用率**：资源的繁忙程度（百分比）
- **延迟**：操作时间，平均值或百分位数

吞吐量的含义取决于上下文。数据库吞吐量通常以每秒查询或请求（操作）数衡量；网络吞吐量则以每秒传输的比特数或字节数（数据量）衡量。

IOPS 是仅针对 I/O 操作（读取和写入）的吞吐量指标。同样，必须结合上下文，具体定义可能有所不同。

<!-- source-id: ch02#ch02lev3_1 -->
#### 开销

性能指标并非没有代价：收集和存储它们必然要消耗 CPU 周期。这会产生开销，可能反过来影响被测对象的性能，这称为*观察者效应*。（它经常与海森堡不确定性原理混淆；后者描述的是位置、动量等成对物理属性能够被同时知晓的精度极限。）

<!-- source-id: ch02#ch02lev3_2 -->
#### 问题

您可能会认为软件供应商提供的指标经过精心挑选，没有错误，并且提供完整的可见性。事实上，指标可能会令人困惑、复杂、不可靠、不准确，甚至完全错误（由于错误）。有时，某个指标在一个软件版本中是正确的，但没有进行更新以反映新代码和代码路径的添加。

有关指标问题的更多信息，请参阅[第 4 章](#ch04-ch04)、[可观测性工具](#ch04-ch04)、[第 4.6 节](#ch04-ch04lev6)、[观察可观测性](#ch04-ch04lev6)。

<!-- source-id: ch02#ch02lev3sec11 -->
### 2.3.11 利用率

术语*利用率*[^fn-ch02-ch02-footnote-3] 通常用于操作系统来描述设备使用情况，例如 CPU 和磁盘设备。利用率可以是基于时间的或基于容量的。

<!-- source-id: ch02#ch02lev3_3 -->
#### 基于时间

基于时间的利用率在排队论中被正式定义。例如[\[Gunther 97\]](#ch02-ch02ref4)：

服务器或资源繁忙的平均时间

并可表示为以下比值：

*U* = *B*/*T*

其中 *U* = 利用率，*B* = 观察期 *T* 期间系统繁忙的总时间。

这也是操作系统性能工具最容易提供的“利用率”指标。磁盘监控工具 iostat(1) 将其称为“繁忙百分比”`%b`，这个名称更准确地传达了底层指标：*B*/*T*。

该利用率指标告诉我们组件的繁忙程度：当组件利用率接近 100% 时，如果存在资源争用，性能可能会严重下降。可以检查其他指标来确认并查看该组件是否因此成为系统瓶颈。

某些组件可以并行处理多个操作。对它们而言，即使利用率达到 100%，性能也可能不会明显下降，因为它们仍能接受更多工作。想想建筑物里的电梯：电梯在楼层之间移动时可视为处于利用状态，停着等待时则不是。但即便电梯为了响应呼叫而 100% 忙碌（也就是利用率达到 100%），它仍可能有能力容纳更多乘客。

100% 繁忙的磁盘也可能能够接受和处理更多工作，例如，通过缓冲磁盘缓存中稍后完成的写入操作。存储阵列经常以 100% 的利用率运行，因为“某些”磁盘在 100% 的时间内都处于繁忙状态，但该阵列有大量空闲磁盘并且可以接受更多工作。

<!-- source-id: ch02#ch02lev3_4 -->
#### 基于容量

IT 专业人员在容量规划中使用利用率的另一个定义 [\[Wong 97\]](#ch02-ch02ref5)：

系统或组件（例如磁盘驱动器）能够提供一定量的吞吐量。在任何性能级别，系统或组件都以其容量的一定比例工作。该比例称为利用率。

这定义了容量而不是时间的利用率。这意味着利用率为 100% 的磁盘*无法*接受任何更多工作。根据基于时间的定义，100% 利用率仅意味着 100% 的时间处于繁忙状态。

100% 繁忙并不意味着 100% 容量。

以电梯为例，100% 容量可能意味着电梯处于其最大有效负载能力，无法容纳更多乘客。

在理想的情况下，我们将能够测量设备的两种类型的利用率，这样，例如，您就会知道磁盘何时 100% 繁忙并且性能因争用而开始下降，以及何时处于 100% 容量且无法接受更多工作。不幸的是，这通常是不可能的。对于磁盘，需要了解磁盘的板载控制器正在做什么并预测容量。磁盘当前不提供此信息。

在本书中，“利用率”通常指的是基于时间的版本，您也可以将其称为“非空闲时间”。容量版本用于某些基于容量的指标，例如内存使用情况。

<!-- source-id: ch02#ch02lev3sec12 -->
### 2.3.12 饱和度

资源所接收到的工作量超过其处理能力的程度就是*饱和度*。当基于容量的利用率达到 100% 时，额外工作无法处理并开始排队，饱和也就开始出现。[图 2.8](#ch02-ch02fig08) 展示了这一点。

<!-- source-id: ch02#ch02fig08 -->
![图 2.8 利用率与饱和度](../images/02fig08.jpg)

图中，负载继续增加并越过基于容量的利用率 100% 这一界限后，饱和度随之线性增长。任何程度的饱和都是性能问题，因为工作需要花时间等待（产生延迟）。对于基于时间的利用率（繁忙时间百分比），排队及随之出现的饱和未必从利用率达到 100% 时才开始，这取决于资源能够在多大程度上并行处理工作。

### 2.3.13 性能剖析

性能剖析通过采样构建出一个可供研究和理解的目标图景。在计算机性能领域，性能剖析通常是在固定时间间隔对系统状态进行*[采样](#gloss-glo-143)*，然后研究得到的样本集合。

与之前介绍的指标（包括 IOPS 和吞吐量）不同，采样的使用提供了目标活动的“粗略”视图。粗略程度取决于采样率。

以性能剖析为例，可以通过频繁采样 CPU 指令指针或堆栈跟踪，收集消耗 CPU 资源的代码路径统计信息，从而相当详细地了解 CPU 使用情况。[第 6 章](#ch06-ch06)、[CPU](#ch06-ch06)介绍了这一主题。

<!-- source-id: ch02#ch02lev3sec14 -->
### 2.3.14 缓存

缓存经常用于提高性能。缓存将较慢存储层的结果存储在较快存储层中，以供参考。一个示例是在主内存 (RAM) 中缓存磁盘块。

可以使用多层缓存。CPU 通常为主内存配备多个硬件缓存（第 1、2、3 级），从非常快但很小的缓存（第 1 级）开始，缓存容量和访问延迟逐级增加。这是密度与延迟之间的经济权衡；缓存级别和大小经过选择，以便在可用片上空间内取得最佳性能。[第 6 章](#ch06-ch06)、[CPU](#ch06-ch06)介绍了这些缓存。

系统中还存在许多其他缓存，其中许多是使用主内存存储数据的软件缓存。有关缓存层次的列表，请参阅[第 3 章](#ch03-ch03)、[操作系统](#ch03-ch03)、[第 3.2.11 节](#ch03-ch03lev2sec11)、[缓存](#ch03-ch03lev2sec11)。

了解缓存性能的一个指标是每个缓存的*命中率*，即在缓存中找到所需数据的次数（命中）与总访问次数（命中 + 未命中）的比值：

命中率=命中数/（命中数+未命中数）

命中率越高越好，因为较高的比率意味着更多数据能够从更快的介质成功读取。[图 2.9](#ch02-ch02fig09)显示了提高缓存命中率带来的预期性能改进。

<!-- source-id: ch02#ch02fig09 -->
![图 2.9 缓存命中率与性能](../images/02fig09.jpg)

98% 与 99% 之间的性能差异远大于 10% 与 11% 之间的差异。这是一条非线性曲线，因为缓存命中与未命中所涉及的两个存储层速度不同；速度差异越大，曲线斜率越陡。

了解缓存性能的另一个指标是*缓存未命中率*，即每秒未命中的次数。它与每次未命中的性能损失成正比（呈线性关系），因而更容易解释。

例如，工作负载 A 和 B 使用不同算法执行同一任务，并使用主内存缓存来避免从磁盘读取。工作负载 A 的缓存命中率为 90%，工作负载 B 的缓存命中率为 80%。仅凭这一信息，似乎 A 的性能更好。但如果 A 的未命中率为 200/s，而 B 为 20/s 呢？从这个角度看，B 执行的磁盘读取次数只有 A 的十分之一，完成任务的速度可能反而比 A 快。要准确判断，可以计算每个工作负载的总运行时间：

运行时间 = (命中率 × 命中延迟) + (未命中率 × 未命中延迟)

此计算使用平均命中和未命中延迟，并假设工作是串行执行的。

<!-- source-id: ch02#ch02lev3_5 -->
#### 算法

缓存管理算法和策略决定在缓存可用的有限空间中存储什么内容。

*最近使用*（MRU）指一种缓存*保留策略*：优先保留最近使用过的对象。*最近最少使用*（LRU）可以指与之等效的缓存*淘汰策略*，决定需要更多空间时从缓存中移除哪些对象。还有*最常使用*（MFU）和*最不常使用*（LFU）策略。

您可能会遇到“不经常使用”（NFU），这可能是 LRU 的廉价但不太彻底的版本。

<!-- source-id: ch02#ch02lev3_6 -->
#### 热、冷与温缓存

这些词通常用来描述缓存的状态：

- **冷**：*冷缓存*为空，或填充了不需要的数据。冷缓存的命中率为零（或在开始预热时接近于零）。
- **温**：*温缓存*已填充有用数据，但命中率还不够高，尚不能称为热缓存。
- **热**：*热缓存*已填充经常请求的数据，并且命中率很高，例如超过 99%。
- **温度**：缓存温度描述了缓存的热度或冷度。提高缓存热度的活动旨在提高缓存命中率。

缓存首次初始化时是冷的，随后会随时间逐渐变热。当缓存很大、下一级存储很慢，或两者兼有时，缓存可能需要很长时间才能填充并预热。

例如，我曾经处理过一台存储设备：它用 128 GB DRAM 作为文件系统缓存、600 GB 闪存作为二级缓存，并使用旋转磁盘存储数据。在随机读工作负载下，磁盘读取速度约为 2,000 次/秒。I/O 大小为 8 KB 时，缓存的预热速度只有 16 Mbytes/s（2,000 × 8 KB）。两个缓存都处于冷状态时，DRAM 缓存需要两个多小时才能预热，闪存缓存则需要十多个小时。

<!-- source-id: ch02#ch02lev3sec15 -->
### 2.3.15 已知—未知

前言中介绍的“已知—已知”、“已知—未知”和“未知—未知”的概念对于性能领域非常重要。细分如下，并举例进行系统性能分析：

- **已知—已知**：这是你知道的事情：你知道应该检查某个性能指标，也知道它当前的值。例如，你知道应该检查 CPU 利用率，也知道它的平均值为 10%。
- **已知—未知**：这些是你知道自己不知道的事情。你知道可以检查某个指标或子系统是否存在，但还没有观察过它。例如，你知道可以使用性能剖析来检查 CPU 繁忙的原因，但尚未这样做。
- **未知—未知**：这是你不知道自己不知道的事情。例如，你可能不知道设备中断会大量消耗 CPU，因此根本不会去检查它们。

性能领域正是“知道得越多，越知道自己不知道得多”。你对系统了解越多，就会意识到更多的未知—未知；这些未知—未知随后会变成可以检查的已知—未知。

## 2.4 视角

性能分析有两种常见视角，每种视角面向不同的受众，使用不同的指标和方法：*工作负载分析*与*资源分析*。如[图 2.10](#ch02-ch02fig10)所示，它们也可以分别看作对操作系统软件栈的自上而下分析和自下而上分析。

<!-- source-id: ch02#ch02fig10 -->
![图 2.10 分析视角](../images/02fig10.jpg)

[第 2.5 节](#ch02-ch02lev5)、[方法论](#ch02-ch02lev5)提供了适用于两种视角的具体策略。下面将更详细地介绍这两种视角。

<!-- source-id: ch02#ch02lev4sec1 -->
### 2.4.1 资源分析

资源分析从分析系统资源开始：CPU、内存、磁盘、网络接口、总线和互连。它很可能由系统管理员（负责物理资源的人员）执行。活动包括

- **性能问题调查**：确认某类资源是否是问题根源
- **容量规划**：为新系统确定合适的规模，并判断现有系统资源何时可能耗尽

此视角侧重于利用率，以确定资源何时达到或接近其极限。某些资源类型（例如 CPU）具有随时可用的利用率指标。可以根据可用指标来估计其他资源的利用率，例如，通过将每秒发送和接收的兆比特数（吞吐量）与已知或预期的最大带宽进行比较来估计网络接口利用率。

最适合资源分析的指标包括：

- IOPS
- 吞吐量
- 利用率
- 饱和度

这些指标衡量资源被要求完成的工作，以及它在给定负载下的利用率或饱和度。其他指标（包括延迟）也有助于了解资源在给定工作负载下的响应情况。

资源分析是性能分析的常用方法，部分归功于该主题的广泛可用文档。此类文档重点关注操作系统“stat”工具：vmstat(8)、iostat(1)、mpstat(1)。当您阅读此类文档时，重要的是要了解这是一种视角，但不是唯一的视角。

<!-- source-id: ch02#ch02lev4sec2 -->
### 2.4.2 工作负载分析

工作负载分析（见[图 2.11](#ch02-ch02fig11)）考察应用程序的性能：施加了什么工作负载，以及应用程序如何响应。它最常由负责应用程序软件和配置的开发人员及支持人员使用。

<!-- source-id: ch02#ch02fig11 -->
![图 2.11 工作负载分析](../images/02fig11.jpg)

工作负载分析的目标是：

- **请求**：施加的工作负载
- **延迟**：应用程序的响应时间
- **完成状态**：寻找错误

研究工作负载请求通常包括检查并汇总其属性，这一过程称为*工作负载特征分析*（详见[第 2.5 节](#ch02-ch02lev5)、[方法论](#ch02-ch02lev5)）。对于数据库，这些属性可能包括客户端主机、数据库名称、表和查询字符串。这些数据有助于发现不必要或不均衡的工作。即使系统当前能够很好地处理工作负载（延迟低），检查这些属性也可能找到减少或消除所施加工作的方法。请记住，最快的查询就是根本不执行的查询。

延迟（响应时间）是表达应用程序性能最重要的指标。对于 MySQL 数据库，它是查询延迟；对于 Apache，它是 HTTP 请求延迟，依此类推。在这些上下文中，“延迟”的含义与响应时间相同（有关上下文的更多信息，请参阅[第 2.3.1 节](#ch02-ch02lev3sec1)、[延迟](#ch02-ch02lev3sec1)）。

工作负载分析的任务包括识别和确认问题（例如，通过查找超出可接受阈值的延迟），然后找到延迟的来源并确认应用修复后延迟是否得到改善。请注意，起点是应用程序。调查延迟通常涉及更深入地研究应用程序、库和操作系统（内核）。

可以通过研究与事件完成相关的特征（包括其错误状态）来识别系统问题。虽然请求可能很快完成，但它可能会出现错误状态，导致请求重试，从而累积延迟。

最适合工作负载分析的指标包括：

- 吞吐量（每秒事务数）
- 延迟

这些衡量请求率和最终的性能。

<!-- source-id: ch02#ch02lev5sec1 -->
### 2.5.1 路灯反方法

这种方法实际上是*没有*刻意采用方法论。用户选择熟悉的、从互联网找到的，或干脆随机选择的可观测性工具来分析性能，看看是否能发现明显问题。这种做法碰运气，可能遗漏许多类型的问题。

也可以用类似的试错方式进行性能调优：把熟悉的可调参数改成不同的值，看看是否有帮助。

即使这种方法发现了一个问题，过程也可能很慢，因为人们会仅仅由于工具或调优手段熟悉，就尝试与问题无关的工具或调整。因此，这种方法以一种称为*路灯效应*的观测偏差命名，寓言如下：

一天晚上，一名警察看到一名醉汉在路灯下搜寻地面，询问他在找什么。醉汉说他丢了钥匙。警察也找不到，问道：“你确定是在路灯下丢的吗？”醉汉回答：“不是，但这里光线最好。”

对应到性能分析，就是查看 top(1)，不是因为它一定有意义，而是因为用户不知道如何解读其他工具。

这种方法找到的可能是*一个*问题，却不是当前要解决的*那个*问题。其他方法会量化调查结果，以便更快排除误报，并优先处理影响更大的问题。

<!-- source-id: ch02#ch02lev5sec2 -->
### 2.5.2 随机修改反方法

这是一种实验性的反方法。用户随机猜测问题可能在哪里，然后不断改动配置，直到问题消失。为了判断每次改动是否改善了性能，需要观察某个指标，例如应用程序运行时间、操作耗时、延迟、操作速率（每秒操作数）或吞吐量（每秒字节数）。步骤如下：

1. 选择一个随机项目进行更改（例如，可调参数）。
2. 朝一个方向改变它。
3. 测量性能。
4. 朝另一个方向改变它。
5. 测量性能。
6. 步骤 3 或步骤 5 中的结果是否优于基线？如果是，请保留更改并返回步骤 1。

虽然这个过程最终可能找到适用于测试工作负载的调优方案，但它非常耗时，也可能留下从长远看毫无意义的调优。例如，应用程序改动可能因为绕过了一个后来被修复的数据库或操作系统缺陷而提升性能；但这项已经失去意义的调优仍会留在应用中，而且从一开始就没有人真正理解它。

另一个风险是，未被正确理解的改动可能在生产高峰负载下引发更严重的问题，届时还需要回滚改动。

<!-- source-id: ch02#ch02lev5sec3 -->
### 2.5.3 责备他人反方法

这种反方法论遵循以下步骤：

1. 找到您不负责的系统或环境组件。
2. 假设问题出在该组件上。
3. 将问题重定向至负责该组件的团队。
4. 如果证明错误，请返回步骤 1。

“也许是网络的问题。你能向网络团队核实一下他们是否有丢包之类的情况吗？”

这种方法的使用者没有调查性能问题，而是把问题推给别人；如果最终证明问题根本不在那个团队，这就浪费了对方的资源。这种反方法的特征是：提出假设时没有数据支撑。

为了避免成为“责备他人”的受害者，可以要求指责者提供截图，说明运行过哪些工具以及如何解读输出；再把这些截图和解读交给其他人征求第二意见。

<!-- source-id: ch02#ch02lev5sec4 -->
### 2.5.4 临时检查清单法

当支持专业人员被要求检查和调整系统时（通常是在很短的时间内），逐步完成预设的清单是一种常见的方法。典型的场景涉及在生产中部署新服务器或应用程序，并且支持专业人员在系统处于实际负载下时花费半天时间检查常见问题。这些清单是临时的，是根据该系统类型的最新经验和问题构建的。

以下是一个清单条目示例：

运行 `iostat –x 1` 并检查 `r_await` 列。如果负载期间该值持续超过 10 ms，则磁盘读取缓慢或磁盘过载。

一个检查表可能由十几个这样的检查组成。

虽然这些清单能在最短时间内提供很大价值，但它们属于特定时点的建议（参见[第 2.3 节](#ch02-ch02lev3)、[概念](#ch02-ch02lev3)），必须经常更新才能保持有效。它们也往往关注容易记录、已有已知修复方案的问题，例如可调参数设置，而不是源代码或环境中的定制修复。

如果您管理着一支由支持专业人员组成的团队，则临时检查表可能是确保每个人都知道如何检查常见问题的有效方法。可以编写清晰、明确规定操作步骤的清单，显示如何识别每个问题以及解决方案。但请记住，该列表必须不断更新。

<!-- source-id: ch02#ch02lev5sec5 -->
### 2.5.5 问题陈述

明确问题陈述是支持人员首次响应问题时的一项例行任务。通常通过询问客户以下问题来完成：

1. 是什么让您认为存在性能问题？
2. 这个系统曾经表现良好吗？
3. 最近发生了什么变化？软件、硬件，还是负载？
4. 问题可以用延迟或运行时间来表达吗？
5. 该问题是否影响其他人或应用程序（或者只是您）？
6. 环境是什么样的？使用了哪些软件和硬件？版本和配置是什么？

只要提出并回答这些问题，通常就能指出直接原因和解决方案。因此，本书将问题陈述作为一种独立方法介绍；解决新问题时，应该首先采用这种方法。

我仅使用问题陈述方法通过电话解决了性能问题，无需登录任何服务器或查看任何指标。

<!-- source-id: ch02#ch02lev5sec6 -->
### 2.5.6 科学方法

科学方法通过提出假设然后进行测试来研究未知事物。可以概括为以下几个步骤：

1. 问题
2. 假设
3. 预测
4. 测试
5. 分析

问题是性能问题陈述。由此您可以推测性能不佳的原因可能是什么。然后，您构建一个测试，可以是观测性的或实验性的，用于测试基于假设的预测。您将完成对收集到的测试数据的分析。

例如，你可能发现应用程序迁移到主内存更少的系统后性能下降，于是假设原因是文件系统缓存更小。可以使用*观测性测试*测量两台系统的缓存未命中率，并预测较小系统的未命中率更高。*实验性测试*则是增加缓存大小（添加 RAM），并预测性能会改善。另一种也许更容易的实验性测试，是人为减小缓存大小（使用可调参数），并预测性能会变差。

以下是更多示例。

<!-- source-id: ch02#ch02lev3_7 -->
#### 示例（观测）

1. 问：什么原因导致数据库查询速度慢？
2. 假设：吵闹的邻居（其他云计算租户）正在执行磁盘 I/O，与数据库磁盘 I/O 竞争（通过文件系统）。
3. 预测：如果在查询期间测量文件系统 I/O 延迟，则将表明文件系统是造成查询缓慢的原因。
4. 测试：将数据库文件系统延迟与查询延迟的比率进行跟踪，结果显示不到 5% 的时间用于等待文件系统。
5. 分析：文件系统和磁盘不是查询缓慢的原因。

尽管问题仍未解决，但环境的一些重要组成部分已被排除。进行此项调查的人员可以返回步骤 2 并提出新的假设。

<!-- source-id: ch02#ch02lev3_8 -->
#### 示例（实验）

1. 问：为什么从主机 A 到主机 C 的 HTTP 请求比从主机 B 到主机 C 花费的时间更长？
2. 假设：主机 A 和主机 B 位于不同的数据中心。
3. 预测：将主机 A 移至与主机 B 相同的数据中心将解决该问题。
4. 测试：移动主机 A 并测量性能。
5. 分析：性能问题已解决，这与假设一致。

如果问题没有得到解决，请在开始新的假设之前逆转实验更改（在本例中将主机 A 移回原处）——同时更改多个因素会使确定哪个因素重要变得更加困难！

<!-- source-id: ch02#ch02lev3_9 -->
#### 示例（实验）

1. 问：为什么文件系统性能会随着文件系统缓存大小的增大而下降？
2. 假设：较大的缓存可以存储更多的记录，与较小的缓存相比，管理较大的缓存需要更多的计算。
3. 预测：使记录大小逐渐变小，从而导致使用更多记录来存储相同数量的数据，将使性能逐渐“变差”。
4. 测试：使用逐渐减小的记录大小来测试相同的工作负载。
5. 分析：结果用图表表示，与预测一致。现在对缓存管理例程执行下钻分析。

这是一个*负向测试*的例子——故意损害性能，以便进一步了解目标系统。

<!-- source-id: ch02#ch02lev5sec7 -->
### 2.5.7 诊断周期

与科学方法类似的是*诊断周期*：

假设 → 插桩 → 数据 → 假设

与科学方法一样，这种方法也通过收集数据来有意检验假设。这个循环强调，数据可以很快导出新的假设，随后不断测试、完善，如此反复。这类似于医生进行一系列小检查来诊断病人，并根据每次检查的结果完善假设。

这两种方法都很好地平衡了理论和数据。应尽快从假设转向数据，及早识别并抛弃错误的理论，再提出更好的理论。

<!-- source-id: ch02#ch02lev5sec8 -->
### 2.5.8 工具方法

面向工具的方法如下：

1. 列出可用的性能工具（可以选择安装或购买更多工具）。
2. 对于每个工具，列出它提供的有用指标。
3. 对于每个指标，列出解释它的可能方法。

结果是一份规定性清单，说明该运行哪个工具、读取哪些指标以及如何解读它们。虽然这种方法可能相当有效，但它完全依赖现有（或已知）的工具，而这些工具只能提供不完整的系统视图，类似于路灯反方法。更糟的是，用户并不知道自己的视图不完整，甚至可能一直意识不到。需要定制工具（例如动态跟踪）才能发现和解决的问题，可能永远不会被识别。

在实践中，工具方法确实能够识别某些资源瓶颈、错误及其他问题，只是效率可能不高。

当有大量工具和指标可用时，迭代它们可能会非常耗时。当多个工具似乎具有相同的功能并且您花费额外的时间试图了解每个工具的优缺点时，情况会变得更糟。在某些情况下，例如文件系统微基准测试工具，有十几种工具可供选择，而您可能只需要一个。[^fn-ch02-ch02-footnote-4]

<!-- source-id: ch02#ch02lev5sec9 -->
### 2.5.9 USE 方法

应在性能调查的早期使用利用率、饱和度和错误 (USE) 方法来识别系统瓶颈 [\[Gregg 13b\]](#ch02-ch02ref15)。它是一种关注系统资源的方法论，可以概括为：

对每个资源检查利用率（Utilization）、饱和度（Saturation）和错误（Errors）。

这些术语定义如下：

- **资源**：服务器的所有物理功能组件（CPU、总线……）。如果指标有意义，也可以检查某些软件资源。
- **利用率**：在设定的时间区间内，资源忙于处理工作的时间百分比。资源繁忙时可能仍能接受更多工作；饱和度反映的是超出其处理能力的工作量。
- **饱和度**：资源收到但无法服务的额外工作量，通常表现为工作在队列中等待。另一个术语是“压力”。
- **错误**：错误事件的计数。

对于某些资源类型（包括主内存），利用率指已使用的资源“容量”。这不同于基于时间的定义，前文[第 2.3.11 节](#ch02-ch02lev3sec11)、[利用率](#ch02-ch02lev3sec11)已经解释过。一旦容量型资源达到 100% 利用率，就无法接受更多工作；资源要么将工作排队（饱和），要么返回错误，而这些情况也可以使用 USE 方法识别。

应调查错误，因为它们会降低性能，但在故障模式可恢复时可能不会立即被注意到。这包括失败并重试的操作，以及冗余设备池中失败的设备。

与工具方法相比，USE 方法涉及迭代系统资源而不是工具。这可以帮助您创建完整的问题列表，然后您才可以搜索工具来回答这些问题。即使无法找到工具来回答某些问题，了解这些问题尚未得到解答对于性能分析师来说也非常有用：它们现在是“已知—未知”。

USE 方法还将分析引导到有限数量的关键指标，以便尽快检查所有系统资源。此后，如果没有发现问题，则可以使用其他方法。

<!-- source-id: ch02#ch02lev3_10 -->
#### 实施步骤

USE 方法的流程如[图 2.12](#ch02-ch02fig12)所示。首先检查错误，因为错误通常容易解释（通常是客观而非主观的指标），在调查其他指标前排除错误可以节省时间。其次检查饱和度，因为它比利用率更容易解释：任何程度的饱和都可能是问题。

<!-- source-id: ch02#ch02fig12 -->
![图 2.12 USE 方法流程图](../images/02fig12.jpg)

这种方法能发现可能构成系统瓶颈的问题。但系统可能同时存在多个性能问题，因此首先发现的可能是*一个*问题，却不是当前要解决的*那个*问题。每项发现都可以用其他方法进一步调查，再按需回到 USE 方法，继续检查更多资源。

<!-- source-id: ch02#ch02lev3_11 -->
#### 表达指标

USE 方法的指标通常表示如下：

- **利用率**：一段时间间隔内的百分比（例如，“一个 CPU 的利用率为 90%”）
- **饱和度**：以等待队列长度表示（例如，“CPU 的平均运行队列长度为 4”）
- **错误**：报告的错误数量（例如，“此磁盘驱动器有 50 个错误”）

尽管这似乎有悖常理，但短暂的高利用率可能会导致饱和和性能问题，即使整体利用率在很长一段时间内“较低”。一些监控工具报告以 5 分钟为区间的平均利用率。例如，CPU 利用率每秒都会发生巨大变化，因此 5 分钟平均值可能会掩盖短期的 100% 利用率，从而掩盖饱和度。

考虑高速公路上的收费站。利用率可以定义为正忙于服务车辆的收费窗口数。利用率达到 100% 意味着找不到空窗口，必须排在别人后面（饱和）。如果我告诉你这些窗口全天平均利用率为 40%，你能判断当天是否曾有车辆排队吗？高峰时段利用率可能达到 100% 并出现排队，但日平均值看不出这一点。

<!-- source-id: ch02#ch02lev3_12 -->
#### 资源列表

USE 方法的第一步是创建资源列表。尝试尽可能完整。以下是服务器硬件资源的通用列表以及具体示例：

- **CPU**：处理器插槽、CPU 核心、硬件线程（虚拟 CPU）
- **[主内存](#gloss-glo-098)**：DRAM
- **网络接口**：以太网端口、Infiniband
- **存储设备**：磁盘、存储适配器
- **加速器**：GPU、TPU、FPGA 等（如果使用）
- **控制器**：存储、网络
- **互连**：CPU、内存、I/O

每个组件通常属于一种资源类型。例如，主内存是*容量*资源，网络接口是*[I/O](#gloss-glo-078)*资源（可以指 IOPS 或吞吐量）。有些组件可能同时属于多种资源类型：例如，存储设备既是 I/O 资源，也是容量资源。要考虑所有可能导致性能瓶颈的类型。还要注意，I/O 资源可以进一步作为*排队系统*研究：它们先将请求排队，再为请求提供服务。

某些物理组件，例如硬件缓存（例如 CPU 缓存），可以排除在清单之外。 USE 方法对于在高利用率或饱和情况下性能下降、导致瓶颈的资源最有效，而缓存在高利用率下“提高”性能。这些可以使用其他方法进行检查。如果您不确定是否包含某个资源，请将其包含在内，然后查看指标在实践中的效果如何。

<!-- source-id: ch02#ch02lev3_13 -->
#### 功能框图

遍历资源的另一种方法，是查找或绘制系统的功能框图，例如[图 2.13](#ch02-ch02fig13)所示的框图。这种图还展示组件之间的关系，对于寻找数据流中的瓶颈很有用。

<!-- source-id: ch02#ch02fig13 -->
![图 2.13 双处理器系统功能框图示例](../images/02fig13.jpg)

CPU、内存、I/O 互连和总线常常被忽视。幸运的是，它们不是常见的系统瓶颈，因为它们在设计时通常预留了充足的吞吐能力。不幸的是，如果是的话，问题可能很难解决。也许你可以升级主板，或者减少负载；例如，“零拷贝”软件技术减轻了内存总线负载。

要调查互连，请参阅[第 6 章](#ch06-ch06)、[CPU](#ch06-ch06)中的 CPU 性能计数器，见[第 6.4.1 节](#ch06-ch06lev4sec1)、[硬件](#ch06-ch06lev4sec1)。

#### 软件资源

可以类似地检查某些软件资源。这通常适用于软件的较小组件（而不是整个应用程序），例如：

- **互斥锁**：利用率可以定义为锁被持有的时间，饱和度则由排队等待该锁的线程衡量。
- **线程池**：利用率可以定义为线程忙于处理工作的时间，饱和度则由等待线程池处理的请求数量衡量。
- **进程/线程容量**：系统可能具有有限数量的进程或线程，其当前使用情况可定义为利用率；等待分配的情况可以表示饱和度；错误是指分配失败（例如“无法创建子进程”）。
- **文件描述符容量**：与进程/线程容量类似，但针对文件描述符。

如果这些指标适合您的情况，请使用它们；否则，可以应用延迟分析等替代方法。

<!-- source-id: ch02#ch02lev3_16 -->
#### 建议的解释

以下是解释指标类型的一些一般建议：

- **利用率**：100% 的利用率通常是瓶颈的标志（检查饱和度及其影响以确认）。利用率超过 60% 可能会因几个原因成为问题：根据统计间隔，它可能掩盖利用率短暂达到 100% 的峰值。此外，某些资源（例如硬盘，但不包括 CPU）在操作期间通常不能被中断，即使面对更高优先级的工作也是如此。随着利用率提高，排队延迟会变得更加频繁和明显。关于 60% 左右的利用率，请参阅[第 2.6.5 节](#ch02-ch02lev6sec5)、[排队论](#ch02-ch02lev6sec5)。
- **饱和度**：任何饱和度（非零）都可能成为问题。它可以以等待队列的长度或在队列上等待所花费的时间来衡量。
- **错误**：非零错误计数器值得研究，特别是当它们在性能较差时增加时。

这些指标的排除结果很容易解释：利用率低、没有饱和、没有错误。这种结果的作用比看起来更大：确认问题很可能*不在*资源上，便能缩小调查范围，快速聚焦问题所在。这就是排除法。

<!-- source-id: ch02#ch02lev3_17 -->
#### 资源控制

在云计算和容器环境中，软件资源控制可能会限制或限流共享同一系统的租户。这些控制可以限制内存、CPU、磁盘 I/O 和网络 I/O。例如，Linux 容器使用 cgroup 限制资源使用。每项资源限制都可以像物理资源一样使用 USE 方法检查。

例如，“内存容量利用率”可以定义为租户内存使用量相对于内存上限的比例。即使主机系统没有内存压力，租户也可能因达到限制而出现分配错误或交换，这就是“内存容量饱和”。[第 11 章](#ch11-ch11)、[云计算](#ch11-ch11)将讨论这些限制。

<!-- source-id: ch02#ch02lev3_18 -->
#### 微服务

微服务架构带来了与资源指标过多类似的问题：每个服务可能都有大量指标，逐一检查十分费力，而且还会遗漏尚未有指标覆盖的区域。USE 方法同样可以处理微服务中的这些问题。例如，对于典型的 Netflix 微服务，USE 指标是：

- **利用率**：整个实例集群的平均 CPU 利用率。
- **饱和度**：可以用延迟的第 99 百分位数与平均延迟之差来近似衡量（假设第 99 百分位数主要受饱和影响）。
- **错误**：请求错误。

Netflix 已使用 Atlas 云范围监控工具对每个微服务检查这三个指标 [\[Harrington 14\]]。

有一种专门为服务设计的类似方法：RED 方法。

<!-- source-id: ch02#ch02lev5sec10 -->
### 2.5.10 RED 方法

这种方法关注服务，通常是微服务架构中的云服务。它从用户视角确定三个用于监控健康状况的指标，可概括为 [\[Wilkie 18\]](#ch02-ch02ref19)：

对每项服务检查请求率（Rate）、错误（Errors）和耗时（Duration）。

指标是：

- **请求率**：每秒的服务请求数
- **错误**：失败的请求数
- **持续时间**：请求完成所需的时间（除平均值外，还应考虑百分位数等分布统计信息：请参阅[第 2.8 节](#ch02-ch02lev8)、[统计](#ch02-ch02lev8)）

你的任务是绘制微服务架构图，并确保每项服务都监控这三个指标。（分布式跟踪工具可能会为你提供这样的图。）它的优点与 USE 方法类似：RED 方法快速、易于执行，而且覆盖全面。

RED 方法由 Tom Wilkie 创建。他还借助 Grafana 仪表板，为 Prometheus 开发了 USE 和 RED 方法指标的实现 \[Wilkie 18\]。这两种方法互为补充：USE 方法关注机器健康，RED 方法关注用户健康。

纳入请求率能为调查提供重要的早期线索：判断性能问题来自负载还是架构（请参阅[第 2.3.8 节](#ch02-ch02lev3sec8)、[负载与架构](#ch02-ch02lev3sec8)）。如果请求率保持稳定而请求持续时间增加，则说明问题在架构，即服务本身。如果请求率和持续时间都增加，则问题可能来自施加的负载。可以使用工作负载特征分析进一步调查。

<!-- source-id: ch02#ch02lev5sec11 -->
### 2.5.11 工作负载特征分析

工作负载特征分析是一种简单而有效的方法，用于识别由所施加负载造成的问题。它关注系统的“输入”，而不是由此产生的性能。系统可能不存在架构、实现或配置问题，只是承受了超出合理处理能力的负载。

工作负载可以通过回答以下问题来表征：

- **谁**造成负载？进程ID、用户ID、远程IP地址？
- **为什么**会产生这些负载？代码路径、堆栈跟踪？
- **负载特性是什么**？ IOPS、吞吐量、方向（读/写）、类型？在适当的情况下包括方差（标准差）。
- **负载随时间如何变化？** 是否存在日周期模式？

即使您对答案抱有强烈期望，检查所有这些内容也很有用，因为您可能会感到惊讶。

考虑这样的场景：你的数据库出现性能问题，客户端是一组 Web 服务器。你是否应该检查正在使用数据库的客户端 IP 地址？按配置来看，你本来会认为它们都是 Web 服务器；但检查后却发现，整个互联网似乎都在向数据库施加负载，破坏了数据库性能。原来你正遭受拒绝服务（DoS）攻击！

最大的性能收益来自*消除不必要的工作*。有时，不必要的工作源于应用程序故障，例如线程陷入循环，产生不必要的 CPU 工作；也可能源于错误配置，例如高峰时段运行的系统级备份，甚至前面所述的 DoS 攻击。工作负载特征分析可以识别这些问题，并通过维护或重新配置消除它们。

如果无法消除所识别的工作负载，另一种方法可能是使用系统资源控制来限制它。例如，系统备份任务可能会消耗 CPU 资源来压缩备份，然后消耗网络资源来传输备份，从而干扰生产数据库。可以使用资源控制（如果系统支持它们）来限制 CPU 和网络的使用，以便备份运行得更慢，而不会损害数据库。

除了识别问题，工作负载特征还可以作为设计模拟基准的输入。如果工作负载测量结果是平均值，理想情况下还应收集分布和变化的细节。这一点对于模拟预期的多种工作负载很重要，而不是只测试平均工作负载。有关平均值和变异（标准差）的更多信息，请参见[第 2.8 节](#ch02-ch02lev8)、[统计](#ch02-ch02lev8)；基准测试见[第 12 章](#ch12-ch12)、[基准测试](#ch12-ch12)。

通过识别负载本身，工作负载分析还有助于把负载问题与架构问题区分开来。[第 2.3.8 节](#ch02-ch02lev3sec8)、[负载与架构](#ch02-ch02lev3sec8)介绍过这种区分。

用于工作负载特征分析的具体工具和指标取决于目标。一些应用程序会记录客户端活动的详细日志，可将其作为统计分析的数据源；它们也可能已经提供客户使用情况的日报或月报，可以从中挖掘细节。

### 2.5.12 下钻分析

下钻分析从高层次检查问题开始，然后根据之前的发现缩小范围，排除看起来无关紧要的区域，深入检查值得调查的区域。必要时，这一过程会沿软件栈逐层向下，直至硬件，以找出问题根因。

下面是用于系统性能分析的三阶段下钻分析方法 \[McDougall 06a\]：

1. **监控**：用于随着时间的推移持续记录高层统计数据，并识别可能存在的问题或发出警报。
2. **识别**：鉴于可疑问题，这会将调查范围缩小到特定资源或感兴趣的领域，从而识别可能的瓶颈。
3. **分析**：对特定系统区域进行进一步检查，以尝试找出根本原因并量化问题。

监控可以在整个公司范围内进行，并汇总所有服务器或云实例的结果。用于此目的的一项早期技术是简单网络管理协议（SNMP），它可以监控任何支持该协议的联网设备。现代监控系统使用*导出器*：运行在各系统上的软件代理，负责收集并发布指标。监控系统记录这些数据，再由前端 GUI 可视化。这样可以揭示短时间使用命令行工具时容易错过的长期模式。许多监控方案会在疑似出现问题时告警，推动分析进入下一阶段。

通过直接分析服务器并检查系统组件（CPU、磁盘、内存等）来进行识别。历史上，它是使用命令行工具（例如 vmstat(8)、iostat(1) 和 mpstat(1)）执行的。如今，有许多 GUI 仪表板公开相同的指标以实现更快的分析。

分析阶段会使用基于跟踪或性能剖析的工具，对可疑区域进行更深入的检查。这可能包括创建定制工具和检查源代码（如果有）。大部分逐层深入都发生在这里：按需剥开软件栈各层，直到找到根因。Linux 中可用于此目的的工具包括 strace(1)、perf(1)、BCC 工具、bpftrace 和 Ftrace。

下面是 Netflix 云采用这套三阶段方法的一个实现示例：

1. **监控**：Netflix Atlas：面向整个云环境的开源监控平台 \[Harrington 14\]。
2. **识别**：Netflix perfdash（以前称为 Netflix Vector）：用于使用仪表板分析单个实例的 GUI，包括 USE 方法指标。
3. **分析**：Netflix FlameCommander，用于生成不同类型的火焰图；以及通过 SSH 会话使用的命令行工具，包括基于 Ftrace 的工具、BCC 工具和 bpftrace。

以 Netflix 使用这套流程为例：Atlas 可能识别出有问题的微服务，perfdash 随后把问题缩小到某个资源，FlameCommander 再显示消耗该资源的代码路径；最后可以使用 BCC 工具和定制的 bpftrace 工具对这些路径进行插桩。

<!-- source-id: ch02#ch02lev3_19 -->
#### 五个为什么

在下钻分析阶段可以使用的另一种方法是“五个为什么”技术 [\[Wikipedia 20\]](#ch02-ch02ref21)：问自己“为什么？”然后回答问题，总共重复五次（或更多）。下面是一个示例过程：

1. 数据库处理许多查询时开始表现不佳。为什么？
2. 数据库因内存分页产生的磁盘 I/O 而被拖慢。为什么？
3. 数据库的内存使用量增长得过大。为什么？
4. 内存分配器消耗的内存超过应有水平。为什么？
5. 内存分配器存在内存碎片问题。

这是一个真实案例，最终意外促成了系统内存分配库的修复。正是持续追问并深入到核心问题，才找到了修复方案。

### 2.5.13 延迟分析

延迟分析检查完成操作所需的时间，然后将其分解为更小的组件，继续细分延迟最高的组件，以便可以识别和量化根本原因。与下钻分析类似，延迟分析可以深入软件栈的各层以找到延迟问题的根源。

分析可以从施加的工作负载开始，检查应用程序如何处理它，然后逐层深入操作系统库、系统调用、内核和设备驱动程序。

例如，MySQL 查询延迟的分析可能涉及回答以下问题（此处给出了示例答案）：

1. 是否存在查询延迟问题？（是）
2. 查询时间主要花在 CPU 上，还是在脱离 CPU 状态下等待？（脱离 CPU）
3. 脱离 CPU 状态下的等待时间是在等待什么？（文件系统 I/O）
4. 文件系统 I/O 时间是由磁盘 I/O 还是锁争用造成的？（磁盘 I/O）
5. 磁盘 I/O 时间主要花在排队，还是花在处理 I/O？（处理 I/O）
6. 磁盘服务时间主要用于 I/O 初始化，还是数据传输？（数据传输）

在这个例子中，流程的每一步都提出一个问题，把延迟分成两部分，然后继续分析较大的一部分——可以把它理解为对延迟进行二分搜索。流程如[图 2.14](#ch02-ch02fig14)所示。

当 A 或 B 中较慢的一个被识别出来后，它会被进一步分成 A 或 B，进行分析，等等。

数据库查询的延迟分析是方法 R 的目标。

### 2.5.14 方法 R

方法 R 是一种针对 Oracle 数据库开发的性能分析方法，重点是基于 Oracle 跟踪事件 [\[Millsap 03\]](#ch02-ch02ref7) 查找延迟的根源。它被描述为“一种基于响应时间的性能改进方法，可为您的业务带来最大的经济价值”，并专注于识别和量化查询期间花费的时间。虽然这是用于数据库的研究，但其方法可以应用于任何系统，并且作为可能的研究途径值得在此提及。

### 2.5.15 事件追踪

系统通过处理离散事件来运行。这些事件包括 CPU 指令、磁盘 I/O 和其他磁盘命令、网络数据包、系统调用、库调用、应用程序事务、数据库查询等。性能分析通常研究这些事件的汇总信息，例如每秒操作数、每秒字节数或平均延迟。有时汇总会丢失重要细节，必须逐个检查事件才能充分理解它们。

- **结果**：错误状态、事件结果（例如，成功传输大小）

### 2.5.16 基线统计

环境通常使用监控方案记录服务器性能指标，并把它们绘制成折线图，时间位于 x 轴（参见[第 2.9 节](#ch02-ch02lev9)、[监控](#ch02-ch02lev9)）。折线图可以显示指标近期是否发生变化，以及现在有何不同，只要观察曲线的变化即可。有时还会增加其他曲线以显示更多历史数据，例如历史平均值，或与当前时间范围对照的历史时间范围。比如，许多 Netflix 仪表板会额外绘制上一周同一时间范围的曲线，这样就能直接把本周二下午 3 点的行为与上周二下午 3 点进行比较。

这些方法与已经监控的指标和可视化它们的 GUI 配合良好。然而，命令行上还有更多系统指标和详细信息可能尚未纳入监控。您可能会遇到不熟悉的系统统计数据，并想知道它们对于服务器来说是否“正常”，或者是否是存在问题的证据。

这并不是新问题。在折线图监控方案尚未普及之前，就有一种解决方法：收集*基线统计数据*。具体可以是在系统处于“正常”负载时收集所有系统指标，并记录到文本文件或数据库中供日后参考。基线程序可以是运行可观测性工具、同时收集其他来源（例如用 cat(1) 读取 /proc 文件）的 shell 脚本。也可以把性能剖析器和跟踪工具纳入基线，提供远多于监控产品通常记录的细节（但要注意工具开销，避免扰动生产环境）。基线可以定期收集（例如每天一次），也可以在系统或应用程序变更前后收集，以分析性能差异。

如果尚未收集基线并且无法进行监视，则某些可观测性工具（基于内核计数器的工具）可以显示自启动以来的平均值摘要，以便与当前活动进行比较。这很粗糙，但总比没有好。

<!-- source-id: ch02#ch02lev5sec17 -->
### 2.5.17 静态性能调优

静态性能调优关注已配置架构中的问题。其他方法关注所施加负载下的性能，即*动态性能* [\[Elling 00\]](#ch02-ch02ref6)。静态性能分析可以在系统空闲、未施加负载时进行。

对于静态性能分析和调优，请逐一检查系统组件，并确认：

- 组件是否合理？（是否过时、性能不足等）
- 配置对于预期工作负载是否合理？
- 组件是否已针对预期工作负载自动配置到最佳状态？
- 组件是否遇到错误，导致其现在处于降级状态？

以下是使用静态性能调优可能发现的一些问题示例：

- 网络接口协商：选择 1 Gbits/s 而不是 10 Gbit/s
- RAID 池中出现故障的磁盘
- 使用旧版本的操作系统、应用程序或固件
- 文件系统几乎已满（可能导致性能问题）
- 文件系统记录大小与工作负载 I/O 大小不匹配
- 应用程序意外地保持在开销很高的调试模式
- 服务器意外配置为网络路由器（启用 IP 转发）
- 服务器配置为使用来自远程数据中心而不是本地的资源，例如身份验证

幸运的是，这些类型的问题很容易检查；困难的部分是记住去做！

<!-- source-id: ch02#ch02lev5sec18 -->
### 2.5.18 缓存调优

应用程序和操作系统可能使用多级缓存来提高 I/O 性能，缓存层次从应用程序一直延伸到磁盘。完整列表参见[第 3 章](#ch03-ch03)、[操作系统](#ch03-ch03)的[第 3.2.11 节](#ch03-ch03lev2sec11)、[缓存](#ch03-ch03lev2sec11)。以下是调优各级缓存的一般策略：

1. 尽可能在栈的高层、靠近工作执行处进行缓存，从而降低缓存命中的操作开销。该位置通常也拥有更多元数据，可用于改进缓存保留策略。
2. 检查缓存是否已启用并且正在工作。
3. 检查缓存命中率、未命中率以及每秒未命中次数。
4. 如果缓存大小是动态的，请检查其当前大小。
5. 针对工作负载调整缓存。此任务取决于可用的缓存可调参数。
6. 针对缓存调优工作负载，包括减少不必要的缓存使用者，为目标工作负载释放更多空间。

留意双重缓存，例如，两个不同的缓存消耗主内存并将相同的数据缓存两次。

还要考虑调优每一级缓存带来的总体性能收益。调优 CPU 一级缓存可能只节省纳秒，因为未命中仍可由二级缓存服务；但改善 CPU 三级缓存可能避免慢得多的 DRAM 访问，从而带来更大的总体收益。（这些 CPU 缓存见[第 6 章](#ch06-ch06)、[CPU](#ch06-ch06)。）

### 2.5.19 微基准测试

微基准测试用于测试简单、人工构造的工作负载的性能。这不同于*宏基准测试*（或*行业基准测试*），后者通常旨在测试真实且自然的工作负载。宏基准测试通过运行工作负载模拟来完成，执行和理解起来可能很复杂。

由于影响因素较少，微基准测试的执行和理解也较简单。常用的微基准是 Linux iperf(1)，它执行 TCP 吞吐量测试：这可以通过在生产工作负载期间检查 TCP 计数器来识别外部网络瓶颈（否则很难发现）。

微基准测试可以由*微基准工具*完成：它施加工作负载并测量性能；也可以使用只施加工作负载的*负载生成器*，把性能测量交给其他可观测性工具（示例负载生成器见[第 12 章](#ch12-ch12)、[基准测试](#ch12-ch12)、[第 12.2.2 节](#ch12-ch12lev2sec2)、[模拟](#ch12-ch12lev2sec2)）。两种方式都可以，但最稳妥的做法是使用微基准工具，并用其他工具再次核对性能。

微基准测试的一些目标示例（包括测试所用的第二个维度）如下：

- **系统调用时间**：fork(2)、execve(2)、open(2)、read(2)、close(2)
- **文件系统读取**：读取已缓存的文件，将每次读取大小从 1 字节变到 1 MB
- **网络吞吐量**：针对不同的套接字缓冲区大小，在 TCP 端点之间传输数据

微基准测试通常会尽快执行目标操作，并测量大量此类操作完成的时间。然后可以计算平均时间（平均时间=运行时间/操作次数）。

后续章节将介绍具体的微基准测试方法，列出要测试的目标和属性。[第 12 章](#ch12-ch12)、[基准测试](#ch12-ch12)将更详细地介绍这一主题。

<!-- source-id: ch02#ch02lev5sec20 -->
### 2.5.20 性能箴言

这是一种调优方法，展示了如何最好地提高性能，并按从最有效到最不有效的顺序列出了可操作的项目。它是：

1. 不要这样做。
2. 做一次，但不要再做一次。
3. 少做。
4. 稍后再做。
5. 在他们不注意的时候做。
6. 并发执行。
7. 以更低成本完成。

以下是每项的一些示例：

1. 不要这样做：消除不必要的工作。
2. 做一次，但不要再做：缓存。
3. 少做：减少刷新、轮询或更新的频率。
4. 稍后再做：回写式缓存。
5. 在他们不注意的时候进行：将工作安排在非高峰时段进行。
6. 并发执行：从单线程切换到多线程。
7. 以更低成本完成：购买更快的硬件。

这是我最喜欢的方法之一，是我从 Netflix 的斯科特·埃蒙斯那里学到的。他将其归功于克雷格·汉森和帕特·克雷恩（尽管我还没有找到已发表的参考文献）。

## 2.6 建模

系统的分析建模可用于各种目的，尤其是*可扩展性分析*：研究性能如何随着负载或资源增加而扩展。资源可以是硬件（例如 CPU 核心），也可以是软件（进程或线程）。

分析建模可以被视为第三类性能评估活动，另外两类是生产系统的可观测性（“测量”）和实验测试（“模拟”）\[Jain 91\]。至少开展其中两类活动，才能更好地理解性能：例如分析建模与模拟，或模拟与测量。

如果分析针对现有系统，可以从测量开始：刻画负载及其产生的性能。如果系统尚未承受生产负载，或者需要测试超出生产范围的工作负载，则可以通过测试工作负载模拟来进行实验分析。分析建模可以预测性能，并以测量或模拟结果为基础。

可扩展性分析可能揭示：由于资源限制，性能在某个点不再线性扩展。这被称为*拐点*，即一种函数切换为另一种函数的地方；在这里，系统从线性扩展转为受争用影响。找出拐点是否存在及其位置，可以帮助定位限制可扩展性的性能问题，并在生产环境遇到问题前修复它们。

有关这些步骤的详细信息，请参阅[第 2.5.11 节](#ch02-ch02lev5sec11)、[工作负载特征分析](#ch02-ch02lev5sec11)和[第 2.5.19 节](#ch02-ch02lev5sec19)、[微基准测试](#ch02-ch02lev5sec19)。

<!-- source-id: ch02#ch02lev6sec1 -->
### 2.6.1 企业与云

虽然建模可以让我们不必承担拥有大型企业系统的费用就模拟其行为，但大规模环境的性能通常很复杂，难以准确建模。

借助云计算，可以按基准测试所需的短时间租用任意规模的环境。与其建立数学模型预测性能，不如刻画并模拟工作负载，再在不同规模的云环境中测试。某些发现（例如拐点）可能相同，但此时它们基于测量数据而非理论模型；测试真实环境还可能发现模型未包含的限制因素。

### 2.6.2 视觉识别

当可以通过实验收集足够多的结果时，把实际性能绘制成扩展参数的函数，可能会显露出某种模式。

[图 2.15](#ch02-ch02fig15)展示了线程数扩展时应用程序的吞吐量。大约在线程数为 8 附近似乎出现拐点，曲线斜率在此发生变化。现在可以进一步调查，例如检查应用程序和系统配置中与数值 8 相关的设置。

<!-- source-id: ch02#ch02fig15 -->
![图 2.15 可扩展性测试结果](../images/02fig15.jpg)

本例中的系统有 8 个核心，每个核心有两个硬件线程。为了进一步确认这与 CPU 核心数有关，可以研究并比较线程数少于或多于 8 时的 CPU 效应（例如 IPC；参见[第 6 章](#ch06-ch06)、[CPU](#ch06-ch06)）。也可以在核心数不同的系统上重复扩展测试，确认拐点是否按预期移动。

有许多可扩展性曲线可以寻找，无需正式模型即可通过视觉识别。[图 2.16](#ch02-ch02fig16)展示了这些曲线。

<!-- source-id: ch02#ch02fig16 -->
![图 2.16 可扩展性曲线](../images/02fig16.jpg)

对于其中每一个，x 轴是可扩展性维度，y 轴是最终的性能（吞吐量、每秒事务数等）。这些模式是：

- **线性可扩展性**：性能随着资源的扩展而按比例增加。这可能不会永远持续下去，而可能是另一种可扩展性模式的早期阶段。
- **[争用](#gloss-glo-034)**：架构中的某些组件是共享的，只能串行使用；对这些共享资源的争用开始降低扩展效果。
- **一致性**：维护数据一致性（包括传播更改）的成本开始超过扩展的好处。
- **拐点**：在可扩展性曲线上的某一点遇到改变曲线形状的因素。
- **可扩展性上限**：已达到硬限制。这可能是设备瓶颈，例如达到最大吞吐量的总线或互连，或软件施加的限制（系统资源控制）。

视觉识别简单而有效，但使用数学模型可以进一步了解系统的可扩展性。模型可能以意外方式偏离数据，这值得调查：要么模型有问题，说明你对系统的理解有误；要么真实系统的可扩展性存在问题。接下来的部分介绍阿姆达尔可扩展性定律、通用可扩展性定律和排队论。

<!-- source-id: ch02#ch02lev6sec3 -->
### 2.6.3 阿姆达尔可扩展性定律

该定律以计算机架构师 Gene Amdahl [\[Amdahl 67\]](#ch02-ch02ref1) 命名，对系统可扩展性进行建模，考虑到不能并行扩展的工作负载的串行组件。它可用于研究 CPU、线程、工作负载等的扩展。

阿姆达尔可扩展性定律在前面的可扩展性曲线中体现为争用，用于描述对串行资源或工作负载组件的争用。它可以定义为\[Gunther 97\]：

*[C](#gloss-glo-026)*(*N*) = *N*/(1 + α(*N* – 1))

相对容量为 *C*(*N*)，*N* 是扩展维度，例如 CPU 数量或用户负载。参数 α（其中 0 \<= α \<= 1）表示串行程度，也表示系统因此偏离线性扩展的程度。

可以通过以下步骤应用阿姆达尔可扩展性定律：

1. 通过观察现有系统或使用微基准测试或负载生成器进行实验，收集 *N* 范围内的数据。
2. 进行回归分析，确定 Amdahl 参数（α）；这可以使用 gnuplot 或 R 等统计软件完成。
3. 呈现结果以供分析。收集的数据点可以与模型函数一起绘制，以预测扩展表现并揭示数据和模型之间的差异。这也可以使用 gnuplot 或 R 来完成。

以下是阿姆达尔可扩展性定律回归分析的示例 gnuplot 代码，旨在让您了解如何执行此步骤：

![点此查看代码图片](../images/pg065.jpg)

```text
inputN = 10                     # rows to include as model input
alpha = 0.1                     # starting point (seed)
amdahl(N) = N1 * N/(1 + alpha * (N - 1))
# regression analysis (non-linear least squares fitting)
fit amdahl(x) filename every ::1::inputN using 1:2 via alpha
```

在 R 中处理此问题需要类似数量的代码，其中涉及用于非线性最小二乘拟合的 nls() 函数来计算系数，然后在绘图过程中使用该系数。请参阅本章末尾参考文献中的性能可扩展性模型工具包，了解 gnuplot 和 R 中的完整代码 [\[Gregg 14a\]](#ch02-ch02ref16)。

下一节将显示阿姆达尔可扩展性定律函数的示例。

### 2.6.4 通用可扩展性定律

通用可扩展性定律（USL）以前称为“超级串行模型”\[Gunther 97\]，由 Neil Gunther 博士开发，其中包含一致性延迟参数。前文将其描述为一致性扩展曲线，其中包括争用的影响。

USL 可以定义为：

*C*(*N*) = *N*/(1 + α(*N* – 1) + β*N*(*N* – 1))

*C*(*N*)、*N* 和 α 与阿姆达尔可扩展性定律相同。 β 是一致性参数。当 β == 0 时，这成为阿姆达尔可扩展性定律。

[图 2.17](#ch02-ch02fig17)绘制了 USL 和阿姆达尔可扩展性定律分析的示例。

![图 2.17 可扩展性模型](../images/02fig17.jpg)

输入数据集的方差很大，因此很难直观地确定可扩展性曲线。前十个数据点以圆圈绘制，作为模型的输入；另外十个数据点以十字绘制，用于将模型预测与现实进行核对。

有关 USL 分析的更多信息，请参阅 \[Gunther 97\] 和 [\[Gunther 07\]](#ch02-ch02ref9)。

### 2.6.5 排队论

排队论是对队列系统的数学研究，提供了分析队列长度、等待时间（延迟）和利用率（基于时间）的方法。计算中的许多组件（无论是软件还是硬件）都可以建模为“排队系统”。多个排队系统的建模称为“排队网络”。

本节总结了排队论的作用并提供了一个示例来帮助您理解该作用。这是一个很大的研究领域，在其他文本中详细介绍了 [\[Jain 91\]](#ch02-ch02ref2)\[Gunther 97\]。

排队论建立在数学和统计学的各个领域之上，包括概率分布、随机过程、Erlang 的 C 公式（Agner Krarup Erlang 发明了排队论）和利特尔定律（Little’s Law）。利特尔定律可以表示为

*L* = λ*W*

它确定系统中的平均请求数 *L*，即平均到达率 λ 乘以系统中的平均请求时间 *W*。这可以应用于队列，其中 L 是队列中的请求数，W 是队列上的平均等待时间。

排队系统可用于回答各种问题，包括：

- 如果负载加倍，平均响应时间是多少？
- 添加额外处理器后对平均响应时间有何影响？
- 当负载加倍时，系统的响应时间第 90 百分位数能否低于 100 ms？

除了响应时间之外，还可以研究其他因素，包括利用率、队列长度和常驻作业数量。

[图 2.18](#ch02-ch02fig18)显示了一个简单的排队系统模型。

<!-- source-id: ch02#ch02fig18 -->
![图 2.18 排队模型](../images/02fig18.jpg)

它有一个处理队列中的作业的服务中心。排队系统可以有多个并行处理工作的服务中心。在排队论中，服务中心通常称为“服务器”。

排队系统可以根据三个因素进行分类：

- **到达过程**：这描述了对排队系统的请求的到达间隔时间，它可以是随机的、固定时间的或诸如泊松（其使用到达时间的指数分布）之类的过程。
- **服务时间分布**：描述服务中心的服务时间。它们可以是固定的（确定性的）、指数的或其他分布类型。
- **服务中心数量**：一个或多个。

这些因子可以用肯德尔符号表示。

<!-- source-id: ch02#ch02lev3_20 -->
#### 肯德尔符号

该表示法为每个属性分配代码。它具有以下形式

*A*/*S*/*m*

它们是到达过程（*A*）、服务时间分布（*S*）和服务中心数量（*m*）。肯德尔符号还有一种扩展形式，其中包含更多因素：系统中缓冲区的数量、顾客源规模和服务规则。

经常研究的排队系统的例子是

- **M/M/1**：马尔可夫到达（指数分布到达时间），马尔可夫服务时间（指数分布），一个服务中心
- **M/M/c**：与 M/M/1 相同，但多服务器
- **M/G/1**：马尔科夫到达，服务时间的一般分布（任意），一个服务中心
- **M/D/1**：马尔科夫到达，确定的服务时间（固定），一个服务中心

M/G/1 通常用于研究旋转硬盘的性能。

<!-- source-id: ch02#ch02lev3_21 -->
#### M/D/1 和 60% 利用率

作为排队论的一个简单示例，请考虑以确定性方式响应工作负载的磁盘（这是一种简化）。模型为 M/D/1。

提出的问题是：随着磁盘利用率的增加，磁盘的响应时间如何变化？

排队论允许计算 M/D/1 的响应时间：

*r* = *s*(2 - ρ)/2(1 - ρ)

其中响应时间 *r* 根据服务时间 *s* 和利用率 ρ 定义。

对于 1 毫秒的服务时间和从 0 到 100% 的利用率，这种关系已在[图 2.19](#ch02-ch02fig19)中绘出。

<!-- source-id: ch02#ch02fig19 -->
![图 2.19 M/D/1 平均响应时间与利用率](../images/02fig19.jpg)

利用率超过 60% 后，平均响应时间会翻倍；达到 80% 时，响应时间会变为三倍。由于磁盘 I/O 延迟通常是限制应用程序性能的因素，平均延迟增加一倍或更多可能会对应用程序性能产生显著负面影响。这就是磁盘利用率在达到 100% 之前就可能成为问题的原因：磁盘是排队系统，请求通常不能被中断，只能等待轮到自己。这一点不同于 CPU，例如 CPU 可以让更高优先级的工作抢占当前工作。

该图可以直观地回答之前的问题——如果负载加倍，平均响应时间是多少？——当利用率与负载相关时。

这个模型很简单，在某些方面代表了最佳情况。服务时间的变化可能会使平均响应时间更长（例如使用 M/G/1 或 M/M/1）。响应时间还具有分布（[图 2.19](#ch02-ch02fig19)中未显示），因此利用率超过 60% 后，第 90 和第 99 百分位数会恶化得快得多。

和前面的阿姆达尔可扩展性定律 gnuplot 示例一样，展示一些实际代码有助于了解可能涉及的内容。这次使用 R 统计软件[\[R Project 20\]](#ch02-ch02ref25)：

![点此查看代码图片](../images/pg069.jpg)

```text
svc_ms <- 1                   # average disk I/O service time, ms
util_min <- 0                 # range to plot
util_max <- 100               # "
ms_min <- 0                   # "
ms_max <- 10                  # "
# Plot mean response time vs utilization (M/D/1)
plot(x <- c(util_min:util_max), svc_ms * (2 - x/100) / (2 * (1 - x/100)),
    type="l", lty=1, lwd=1,
    xlim=c(util_min, util_max), ylim=c(ms_min, ms_max),
    xlab="Utilization %", ylab="Mean Response Time (ms)")
```

前文给出的 M/D/1 方程已传递给 `plot()` 函数。此代码的大部分内容用于设置图表的取值范围、线条属性和轴标签。

## 2.7 容量规划

容量规划考察系统处理负载的能力，以及负载增加时系统如何扩展。它可以通过多种方式进行，包括本节介绍的资源限制和因素分析，以及前面介绍的建模。本节还介绍负载均衡器、分片等扩展方案。有关此主题的更多信息，请参阅*容量规划的艺术* [\[Allspaw 08\]](#ch02-ch02ref10)。

对于特定应用程序的容量规划，最好先确定一个量化的性能目标。如何确定这一目标，已在[第 5 章](#ch05-ch05)、[应用程序](#ch05-ch05)中较早讨论过。

<!-- source-id: ch02#ch02lev7sec1 -->
### 2.7.1 资源限制

该方法用于寻找在负载下会成为瓶颈的资源。对于容器，软件施加的资源限制也可能成为瓶颈。步骤如下：

1. 测量服务器请求的速率，并随时间监控该速率。
2. 测量硬件和软件资源的使用情况，并随时间监控这些利用率。
3. 用所使用的资源来表示服务器请求。
4. 将请求量外推至各项资源的已知上限（或通过实验确定的上限）。

首先确定服务器的角色及其所服务的请求类型。例如，Web 服务器为 HTTP 请求提供服务，网络文件系统 (NFS) 服务器为 NFS 协议请求（操作）提供服务，数据库服务器为查询请求（或命令请求，查询是其子集）提供服务。

下一步是确定每个请求的系统资源消耗。对于现有系统，可以测量当前的请求率以及资源利用率。然后可以使用外推法来查看哪个资源将首先达到 100% 利用率，以及请求率是多少。

对于未来的系统，可以使用微基准测试或负载生成工具在测试环境中模拟预期请求，同时测量资源利用率。如果客户端负载足够，或许可以通过实验找到资源上限。

要监控的资源包括：

- **硬件**：CPU 利用率、内存使用率、磁盘 IOPS、磁盘吞吐量、磁盘容量（已使用的容量）、网络吞吐量
- **软件**：虚拟内存使用、进程/任务/线程、文件描述符

假设您正在查看当前每秒执行 1,000 个请求的现有系统。最繁忙的资源是 16 个 CPU，平均利用率为 40%；您预测，一旦 100% 得到利用，它们将成为该工作负载的瓶颈。问题是：此时每秒的请求率是多少？

每个请求的 CPU% = 总 CPU%/请求 = 16 × 40%/1,000 = 每个请求的 0.64% CPU

最大请求数/秒 = 100% × 16 个 CPU/每个请求的 CPU% = 1,600 / 0.64 = 2,500 个请求/秒

预测为 2,500 个请求/秒，此时 CPU 将 100% 繁忙。这是对容量的粗略最佳情况估计，因为在请求达到该速率之前可能会遇到一些其他限制因素。

此练习仅使用一个数据点：应用程序吞吐量（每秒请求数）为 1,000，而设备利用率为 40%。如果启用了随时间的监控，就可以纳入不同吞吐量和利用率下的多个数据点，以提高估计准确性。[图 2.20](#ch02-ch02fig20)说明了处理这些数据并外推最大应用程序吞吐量的可视化方法。

<!-- source-id: ch02#ch02fig20 -->
![图 2.20 资源限制分析](../images/02fig20.jpg)

2,500 个请求/秒够吗？回答这个问题需要了解峰值工作负载是什么，这会显示在日常访问模式中。对于您长期监控的现有系统，您可能已经了解峰值的样子。

考虑一台每天处理 100,000 次网站点击的 Web 服务器。这个数字听起来很大，但平均下来只有每秒一个请求，并不多。然而，100,000 次点击可能大多集中在新内容发布后的几秒内，因此峰值可能非常明显。

<!-- source-id: ch02#ch02lev7sec2 -->
### 2.7.2 因子分析

购买和部署新系统时，通常有许多因素可以调整才能达到所需的性能。这些可能包括改变磁盘和 CPU 的数量、RAM 的数量、闪存设备的使用、RAID 配置、文件系统设置等。任务通常是以最小的成本实现所需的性能。

测试所有组合将确定哪种组合具有最佳性价比；然而，这很快就会失控：八个二元因素将需要 256 次测试。

解决方案是测试一组有限的组合。这是一种基于了解最大系统配置的方法：

1. 将所有因素配置为最大值来测试性能。
2. 逐个改变因素，每次都测试性能（预计每次改变都会使性能下降）。
3. 根据测量结果以及成本节省，将性能下降的百分比归因于每个因素。
4. 从最大性能（和成本）开始，选择因素来节省成本，同时根据综合性能下降维持每秒所需的请求数。
5. 重新测试计算的配置以确认交付的性能。

对于八因素系统，这种方法可能只需要十次测试。

例如，为新存储系统做容量规划，要求读取吞吐量为 1 GB/s，工作集大小为 200 GB。最高配置达到 2 GB/s，包括四个处理器、256 GB DRAM、2 张双端口 10 GbE 网卡，使用巨型帧，并关闭压缩和加密（开启它们会带来较高开销）。改为两个处理器时，性能下降 30%；改为一张网卡时下降 25%；不使用巨型帧时下降 35%；开启加密时下降 10%；开启压缩时下降 40%；减少 DRAM 时下降 90%，因为此时预计无法将整个工作负载缓存下来。结合这些性能降幅及各项调整带来的已知成本节省，就可以计算出满足要求且性价比最高的配置。例如，两个处理器、一张网卡的系统可能满足吞吐量要求，估计为 2 × (1 – 0.30) × (1 – 0.25) = 1.04 GB/s。随后应测试这套配置，因为这些组件组合使用时的表现可能与预期不同。

<!-- source-id: ch02#ch02lev7sec3 -->
### 2.7.3 扩展解决方案

满足更高的性能需求通常意味着使用更大的系统，这种策略称为“垂直扩展”。将负载分散到多个系统（通常在前端放置称为“负载均衡器”的系统，使它们看起来像一个系统）称为“水平扩展”。

云计算通过构建更小的虚拟化系统而不是整个系统，进一步实现水平扩展。这在购买计算来处理所需负载时提供了更细的粒度，并允许以小而高效的增量进行扩展。由于不需要像企业大型机那样进行初始大量采购（包括支持合同承诺），因此在项目的早期阶段对严格容量规划的需求相对较低。

有一些技术可以根据性能指标自动进行云扩展。用于此目的的 AWS 技术称为“自动扩展组（ASG）”。可以创建自定义扩展策略，根据使用率指标增加或减少实例数量。[图 2.21](#ch02-ch02fig21)展示了这一技术。

<!-- source-id: ch02#ch02fig21 -->
![图 2.21 弹性伸缩组](../images/02fig21.jpg)

Netflix 通常使用的 ASG 的目标是 CPU 利用率为 60%，并且会随负载变化增加或减少实例数，以维持该目标。

容器编排系统也支持自动扩展。例如，Kubernetes 提供水平 Pod 自动扩缩器（HPA），可以根据 CPU 利用率或其他自定义指标调整 Pod（容器）的数量 [\[Kubernetes 20a\]](#ch02-ch02ref24)。

对于数据库，常见的扩展策略是“分片”，其中数据被分割为逻辑组件，每个组件由自己的数据库（或冗余数据库组）管理。例如，可以通过将客户名称分成按字母顺序排列的范围来将客户数据库分成多个部分。选择有效的分片键对于在数据库之间均匀分布负载至关重要。

## 2.8 统计

充分了解如何使用统计数据及其局限性非常重要。本节讨论使用统计数据（指标）和统计类型（包括平均值、标准差和百分位数）来量化性能问题。

<!-- source-id: ch02#ch02lev8sec1 -->
### 2.8.1 量化性能增益

量化问题及其潜在性能改进，有助于比较问题并确定优先级。这项工作可以通过观察或实验完成。

<!-- source-id: ch02#ch02lev3_22 -->
#### 基于观察

使用观察来量化性能问题：

1. 选择一个可靠的指标。
2. 估计解决问题所带来的性能提升。

例如：

- 观察到：应用程序请求需要 10 毫秒。
- 观察到：其中，9 毫秒是磁盘 I/O。
- 建议：将应用程序配置为在内存中缓存 I/O，预计 DRAM 延迟约为 10 μs。
- 估计增益：10 ms → 1.01 ms（10 ms - 9 ms + 10 μs）= 约 9 倍增益。

正如[第 2.3 节](#ch02-ch02lev3)、[概念](#ch02-ch02lev3)中所介绍的，延迟（时间）非常适合用于此目的，因为它可以在组件之间直接比较，从而能够进行这样的计算。

使用延迟时，请确保将其作为应用程序请求的同步组件进行测量。有些事件是异步发生的，例如后台磁盘 I/O（写入刷新到磁盘），并且不会直接影响应用程序性能。

<!-- source-id: ch02#ch02lev3_23 -->
#### 基于实验

通过实验量化性能问题：

1. 应用修复。
2. 使用可靠的指标量化修复前后的情况。

例如：

- 观察结果：应用程序事务延迟平均为 10 毫秒。
- 实验：增加应用程序线程数以允许更多并发而不是排队。
- 观察结果：应用程序事务延迟平均为 2 毫秒。
- 增益：10 ms → 2 ms = 5x。

如果在生产环境中尝试修复成本高昂，则此方法可能不合适！对于这种情况，应使用基于观测的方法。

<!-- source-id: ch02#ch02lev8sec2 -->
### 2.8.2 平均值

平均值通过单个值表示数据集：集中趋势指标。最常见的平均值类型是“算术平均值”（或简称“平均值”），它是值的总和除以值的数量。其他类型包括几何平均数和调和平均数。

<!-- source-id: ch02#ch02lev3_24 -->
#### 几何平均值

*几何平均值* 是各个值乘积的 *n* 次方根（其中 *n* 是值的数量）。\[Jain 91\]对此有详细描述，其中包括使用几何平均值进行网络性能分析的示例：如果分别测量内核网络栈每一层带来的性能改进，平均性能改进是多少？由于各层共同处理同一个数据包，性能改进具有“乘法”效应，最适合用几何平均值概括。

<!-- source-id: ch02#ch02lev3_25 -->
#### 调和平均值

*调和平均值*是值的数量除以它们倒数之和。它更适合计算速率的平均值。例如，对于 800 Mbytes 数据，前 100 Mbytes 以 50 Mbytes/s 发送，剩余 700 Mbytes 以受限速率 10 Mbytes/s 发送；用调和平均值得到的答案是 800/(100/50 + 700/10) = 11.1 Mbytes/s。

<!-- source-id: ch02#ch02lev3_26 -->
#### 一段时间内的平均值

在性能分析中，我们研究的许多指标都是一段时间内的平均值。CPU 永远不会“处于 50% 利用率”；它只是在某个时间间隔（可以是一秒、 一分钟或一小时）内有 50% 的时间被使用。每当考虑平均值时，都必须检查统计间隔。

例如，我遇到了一个问题，客户遇到了由 CPU 饱和（调度程序延迟）引起的性能问题，尽管他们的监控工具显示 CPU 利用率从未高于 80%。监控工具报告“5 分钟平均值”，其中掩盖了 CPU 利用率一次达到 100% 的时间段（持续数秒）。

<!-- source-id: ch02#ch02lev3_27 -->
#### 衰减平均值

系统性能分析有时会使用*衰减平均值*。例如，uptime(1) 等工具报告的系统“平均负载”就属于这种情况。

衰减平均值仍然是在一段时间间隔内测量的，但最近时间的权重比更远的过去时间的权重更大。这减少（抑制）平均值的短期波动。

有关详细信息，请参阅[第 6 章](#ch06-ch06)、[CPU](#ch06-ch06)、[第 6.6 节](#ch06-ch06lev6)、[可观测性工具](#ch06-ch06lev6)中的“平均负载”。

<!-- source-id: ch02#ch02lev3_28 -->
#### 限制

平均值是会隐藏细节的汇总统计量。我分析过许多磁盘 I/O 延迟偶尔超过 100 毫秒的异常值案例，而平均延迟却接近 1 毫秒。要更好地理解数据，可以使用[第 2.8.3 节](#ch02-ch02lev8sec3)、[标准差、百分位数、中位数](#ch02-ch02lev8sec3)（下一节）介绍的其他统计量，以及[第 2.10 节](#ch02-ch02lev10)、[可视化](#ch02-ch02lev10)介绍的可视化方法。

<!-- source-id: ch02#ch02lev8sec3 -->
### 2.8.3 标准差、百分位数、中位数

标准差和百分位数（例如第 99 百分位数）用于描述数据的*分布*。标准差衡量数据的*离散程度*；数值越大，数据相对于平均值（均值）的偏离就越大。第 99 百分位数是分布中覆盖 99% 数据的分界点。[图 2.22](#ch02-ch02fig22)以*正态分布*为例展示这些统计量，以及最小值和最大值。

<!-- source-id: ch02#ch02fig22 -->
![图 2.22 统计值](../images/02fig22.jpg)

第 90、95、99 和 99.9 等百分位数用于请求延迟的性能监控，以量化总体中最慢的一部分请求。这些数值也可以在服务级别协议（SLA）中指定，用来衡量性能是否为大多数用户所接受。

第 50 个百分位数称为“中位数”，可用来查看大多数数据所在的位置。

<!-- source-id: ch02#ch02lev8sec4 -->
### 2.8.4 变异系数

标准差需要结合平均值来理解，因此判断数据的离散程度时应同时考虑标准差和平均值。单说标准差是 50，提供的信息很有限；再知道平均值是 200，就能了解得更多。

可以用单一指标表示数据的相对离散程度：标准差与平均值之比，称为*变异系数*（CoV 或 CV）。本例中，CV 为 25%。CV 越低，表示相对离散程度越小。

用单一指标表达离散程度的另一种方式是 z 值，它表示一个值偏离平均值多少个标准差。

<!-- source-id: ch02#ch02lev8sec5 -->
### 2.8.5 多峰分布

均值、标准差和百分位数存在问题，从上一张图表中可以明显看出：它们适用于“正态”类或单峰分布。系统性能通常是“双峰”的，快速代码路径返回低延迟，慢速代码路径返回高延迟，或者缓存命中返回低延迟，缓存未命中返回高延迟。也可以有两个以上的峰。

[图 2.23](#ch02-ch02fig23)显示了读写混合工作负载（包括随机 I/O 和顺序 I/O）的磁盘 I/O 延迟分布。

<!-- source-id: ch02#ch02fig23 -->
![图 2.23 延迟分布](../images/02fig23.jpg)

它以直方图形式呈现，显示出两种模式。左侧峰的延迟小于 1 毫秒，表示磁盘缓存命中；右侧峰值约为 7 毫秒，表示磁盘缓存未命中，即随机读取。平均 I/O 延迟为 3.3 毫秒，以垂直线绘出。这个平均值并不是集中趋势指标（如前所述）；事实上，情况几乎相反。作为指标，该分布的平均值极具误导性。

“还有人会在平均深度只有 6 英寸的小溪中溺水。”——W. I. E. Gates

每当看到平均值被用作性能指标（尤其是平均延迟）时，都要问：分布是什么？[第 2.10 节](#ch02-ch02lev10)、[可视化](#ch02-ch02lev10)提供了另一个示例，并展示了不同可视化方法和指标在呈现该分布方面的效果。

<!-- source-id: ch02#ch02lev8sec6 -->
### 2.8.6 异常值

另一个统计问题是*异常值*的存在：极少数极高或极低的值似乎不符合预期分布（单峰或多峰）。

磁盘 I/O 延迟异常值就是一个例子：当大多数磁盘 I/O 介于 0 到 10 毫秒之间时，极少数 I/O 可能耗时超过 1,000 毫秒。这样的延迟异常值可能导致严重的性能问题，但除了最大值之外，很难从大多数指标类型中识别它们。另一个例子是由基于 TCP 计时器的重传造成的网络 I/O 延迟异常值。

对于正态分布，异常值的存在可能会稍微改变均值，但不会改变中位数（考虑这一点可能有用）。标准差和第 99 个百分位数更有可能识别异常值，但这仍然取决于它们的频率。

要更好地理解多峰分布、异常值及其他复杂但常见的行为，应检查完整分布，例如使用直方图。有关更多方法，请参阅[第 2.10 节](#ch02-ch02lev10)、[可视化](#ch02-ch02lev10)。

## 2.9 监控

系统性能监控记录一段时间内的性能统计数据（*时间序列*），以便比较过去与现在，并识别基于时间的使用模式。这对于容量规划、量化增长和了解峰值使用情况非常有用。历史值还可以显示过去的“正常”范围和平均值，为理解当前性能指标提供背景。

包括图中所示的各种行为周期通常可以在历史数据中看到，包括：

- **每小时**：应用程序环境中的活动可能每小时发生一次，例如监视和报告任务。这些以 5 或 10 分钟为周期执行也很常见。
- **每日**：可能存在与工作时间（上午 9 点至下午 5 点）一致的每日使用模式，如果服务器适用于多个时区，则可能会延长。对于互联网服务器，当全球用户活跃时，可能会遵循这种模式。其他日常活动可能包括夜间日志轮换和备份。
- **每周**：除了每日模式外，还可能存在基于工作日和周末的每周模式。
- **季度**：财务报告按季度完成。
- **每年**：每年的负荷模式可能取决于学校的时间表和假期。

其他活动可能会导致负载不规则增加，例如在网站上发布新内容和促销活动（美国的黑色星期五/网络星期一）。由于外部活动，例如大面积停电或互联网中断以及体育决赛（每个人都观看比赛而不是使用您的产品），可能会出现负载不规则的下降。[^fn-ch02-ch02-footnote-6]

### 2.9.2 监控产品

有许多用于系统性能监控的第三方产品。典型功能包括归档数据并将其呈现为基于浏览器的交互式图表，以及提供可配置的警报。

其中一些通过在系统上运行*代理*（也称为*导出器*）来收集统计数据。这些代理要么执行操作系统可观测性工具（例如 iostat(1) 或 sar(1)）并解析输出文本（这种方式效率较低），要么直接从操作系统库和内核接口读取。监控产品还支持一组自定义代理，用于从特定目标导出统计信息，例如 Web 服务器、数据库和语言运行时。

随着系统变得更加分布式以及云计算的使用不断增长，您将更频繁地需要监控大量系统：数百、数千甚至更多。这就是集中式监控产品特别有用的地方，它允许从一个界面监控整个环境。

举一个具体的例子：Netflix 云由超过 200,000 个实例组成，并使用 Atlas 云范围监控工具进行监控。该工具由 Netflix 定制开发，面向这一规模运行，并且是开源的 [\[Harrington 14\]](#ch02-ch02ref17)。其他监控产品在[第 4 章](#ch04-ch04)、[可观测性工具](#ch04-ch04)、[第 4.2.4 节](#ch04-ch04lev2sec4)、[监控](#ch04-ch04lev2sec4)中讨论。

### 2.9.3 自启动以来的汇总

如果尚未执行监控，请检查操作系统是否至少提供了 *自启动以来的汇总*值，以便与当前值比较。

## 2.10 可视化

可视化允许检查比文本更丰富的数据，而这些数据往往难以用文本理解、甚至无法完整显示。可视化还支持模式识别和模式匹配。它可以有效识别不同指标来源之间的相关性：这件事用程序实现可能很难，但通过视觉观察却很容易。

<!-- source-id: ch02#ch02lev10sec1 -->

折线图（也称为*线图*）是一种常见的基础可视化图表，通常用于检查一段时间内的性能指标，并在 x 轴上显示时间的推移。

[图 2.27](#ch02-ch02fig27)是一个示例，显示 20 秒时间段内的平均磁盘 I/O 延迟。该数据测量于一台运行 MySQL 数据库的生产云服务器，当时怀疑磁盘 I/O 延迟导致查询缓慢。

### 2.10.2 散点图

[图 2.29](#ch02-ch02fig29)以散点图形式显示同一时间范围内的磁盘 I/O 事件，使所有数据可见。每个磁盘 I/O 都绘制为一个点，其完成时间位于 x 轴，延迟位于 y 轴。

<!-- source-id: ch02#ch02fig29 -->
![图 2.29 散点图](../images/02fig29.jpg)

现在可以完全理解平均延迟高于预期的根源了：有很多磁盘 I/O 的延迟达到 10 ms、20 ms，甚至超过 50 ms。散点图显示了所有数据，揭示了这些异常值的存在。

许多 I/O 都是亚毫秒级的，显示在 x 轴附近。这就是散点图的分辨率开始成为问题的地方，因为点重叠并且变得难以区分。随着数据的增加，情况会变得更糟：想象一下，在一个散点图上绘制整个云中的事件，涉及数百万个数据点：这些点可以合并并成为“油漆墙”。另一个问题是必须收集和处理的数据量：每个 I/O 的 x 和 y 坐标。

<!-- source-id: ch02#ch02lev10sec3 -->
### 2.10.3 热图

热图（更准确地称为“列量化”）可以通过将 x 和 y 范围量化为称为“桶”的组来解决散点图可扩展性问题。它们显示为大像素，并根据该 x 和 y 范围内的事件数量进行着色。这种量化还解决了散点图视觉密度限制，允许热图以相同的方式显示来自单个系统或数千个系统的数据。热图之前曾用于磁盘偏移等位置（例如，TazTool [\[McDougall 06a\]](#ch02-ch02ref8)）；我率先将它们用于计算机系统的延迟、利用率及其他指标。延迟热图首次包含在 2008 年发布的 Sun Microsystems ZFS 存储设备的 Analytics 分析功能中 [\[Gregg 10a\]](#ch02-ch02ref11)[\[Gregg 10b\]](#ch02-ch02ref12)，现在在 Grafana 等性能监控产品中很常见[\[Grafana 20\]](#ch02-ch02ref22)。

前面绘制的同一数据集在[图 2.30](#ch02-ch02fig30)中以热图显示。

<!-- source-id: ch02#ch02fig30 -->
![图 2.30 热力图](../images/02fig30.jpg)

高延迟异常值可以被识别为热图中较高的块，通常为浅色，因为它们对应的 I/O 事件很少（通常是单个 I/O）。大量数据中的模式开始出现，这可能无法通过散点图看到。

这次磁盘 I/O 跟踪的完整秒数范围（前面未显示）见[图 2.31](#ch02-ch02fig31)热图。

<!-- source-id: ch02#ch02fig31 -->
![图 2.31 热图：全范围](../images/02fig31.jpg)

尽管跨越了九倍的范围，可视化仍然非常具有可读性。在大部分范围内都可以看到双峰分布，一些 I/O 返回的延迟接近于零（可能是磁盘缓存命中），而其他 I/O 的返回时间略小于 1 毫秒（可能是磁盘缓存未命中）。

本书后面还有其他热图示例，包括[第 6 章](#ch06-ch06)、[CPU](#ch06-ch06)、[第 6.7 节](#ch06-ch06lev7)、[可视化](#ch06-ch06lev7)；[第 8 章](#ch08-ch08)、[文件系统](#ch08-ch08)、[第 8.6.18 节](#ch08-ch08lev6sec18)、[可视化](#ch08-ch08lev6sec18)；以及[第 9 章](#ch09-ch09)、[磁盘](#ch09-ch09)、[第 9.7.3 节](#ch09-ch09lev7sec3)、[延迟热图](#ch09-ch09lev7sec3)。我的网站还有延迟、利用率和亚秒偏移热图的示例 [\[Gregg 15b\]](#ch02-ch02ref18)。

### 2.10.4 时间线图表

时间线图表将一组活动显示为时间线上的条形图。这类图表通常用于前端性能分析（Web 浏览器），也称为“瀑布图”，用于显示网络请求的时间。[图 2.32](#ch02-ch02fig32)展示了 Firefox Web 浏览器中的一个示例。

在[图 2.32](#ch02-ch02fig32)中，第一个网络请求被突出显示：除了用水平条显示其持续时间外，还用彩色条显示该持续时间的组成部分。右侧面板也解释了这些组成部分：第一个请求最慢的部分是“等待”，即等待服务器的 HTTP 响应。第二到第六个请求在第一个请求开始接收数据后才开始，并且可能依赖于这些数据。如果图表中包含显式依赖箭头，它就成为甘特图的一种。

<!-- source-id: ch02#ch02fig32 -->
![图 2.32 Firefox 时间线图](../images/02fig32.jpg)

对于后端性能分析（服务器），也使用类似图表显示线程或 CPU 的时间线。示例软件包括 KernelShark [\[KernelShark 20\]](#ch02-ch02ref23) 和 Trace Compass [\[Eclipse 20\]](#ch02-ch02ref20)。有关 KernelShark 屏幕截图的示例，请参阅[第 14 章](#ch14-ch14)、[Ftrace](#ch14-ch14)、[第 14.11.5 节](#ch14-ch14lev11sec5)、[KernelShark](#ch14-ch14lev11sec5)。Trace Compass 还会绘制表示依赖关系的箭头，例如一个线程唤醒另一个线程。

<!-- source-id: ch02#ch02lev10sec5 -->
### 2.10.5 曲面图

这是三维数据的表示形式，呈现为三维表面。当第三维的值从一个点到下一个点不会频繁发生剧烈变化时，效果最好，形成类似连绵起伏山丘的表面。曲面图通常呈现为“线框模型”。

[图 2.33](#ch02-ch02fig33)显示每个 CPU 利用率的线框曲面图。它包含来自许多服务器、持续 60 秒的每秒数据（该图像取自一个覆盖 300 多台物理服务器和 5,312 个 CPU 的数据中心，并经过裁剪）[\[Gregg 11b\]](#ch02-ch02ref13)。

<!-- source-id: ch02#ch02fig33 -->
![图 2.33 线框曲面图：数据中心 CPU 利用率](../images/02fig33.jpg)

每台服务器的表示方式如下：将其 16 个 CPU 在表面上绘制为行，将 60 个每秒利用率测量值绘制为列，然后将表面高度设为利用率值。颜色也反映利用率值。如果需要，可以使用色相和饱和度向可视化中加入数据的第四维和第五维。（如果分辨率足够，还可以用图案表示第六维。）

然后，这些 16 × 60 服务器矩形将作为棋盘映射在整个表面上。即使没有标记，图像中也可以清楚地看到一些服务器矩形。右侧显示为升高的平台表明其 CPU 几乎始终处于 100%。

网格线突出了高度的细微变化。可以看到一些微弱的线条，表明某个 CPU 持续以较低利用率（几个百分点）运行。

<!-- source-id: ch02#ch02lev10sec6 -->
### 2.10.6 可视化工具

Unix 性能分析历来侧重于使用基于文本的工具，部分原因是图形支持有限。此类工具可以通过登录会话快速执行并实时报告数据。可视化的访问更加耗时，并且通常需要跟踪和报告周期。在处理紧急性能问题时，访问指标的速度可能至关重要。

现代可视化工具提供系统性能的实时视图，可通过浏览器和移动设备访问。有许多产品可以做到这一点，其中许多能够监控整个云。[第 1 章](#ch01-ch01)、[介绍](#ch01-ch01)、[第 1.7.1 节](#ch01-ch01lev7sec1)、[计数器、统计数据和指标](#ch01-ch01lev7sec1)中包含此类产品 Grafana 的示例屏幕截图；其他监控产品在[第 4 章](#ch04-ch04)、[可观测性工具](#ch04-ch04)、[第 4.2.4 节](#ch04-ch04lev2sec4)、[监控](#ch04-ch04lev2sec4)中讨论。

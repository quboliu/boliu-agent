# 第 3 章 — 操作系统

了解操作系统及其内核对于系统性能分析至关重要。您经常需要针对系统行为提出并检验假设，例如系统调用如何执行、内核如何在 CPU 上调度线程、有限的内存如何影响性能，或者文件系统如何处理 I/O。这些活动要求您运用对操作系统和内核的知识。

本章的学习目标是：

- 学习内核术语：上下文切换、交换、分页、抢占等。
- 了解内核和系统调用的作用。
- 获得内核内部的实用知识，包括：中断、调度程序、虚拟内存和 I/O 栈。
- 了解从 Unix 到 Linux 的发展过程中，内核逐步加入了哪些性能功能。
- 对扩展 BPF 有基本的了解。

本章概述了操作系统和内核，其内容是阅读本书其余部分所需的基础知识。如果您错过了操作系统课程，您可以将其视为速成课程。请留意您的知识差距，因为最后会有考试（我开玩笑的；这只是一个测验）。有关内核内部结构的更多信息，请参阅本章末尾的参考资料。

本章分为三个部分：

- **术语**列出了基本术语。
- **背景**总结了关键操作系统和内核概念。
- **内核** 总结了 Linux 和其他内核的实现细节。

与性能相关的领域，包括 CPU 调度、内存、磁盘、文件系统、网络和许多特定的性能工具，将在后续章节中进行更详细的介绍。

## 3.1 术语

作为参考，这里是本书中使用的核心操作系统术语。其中许多也是本章和后续章节中更详细解释的概念。

- **操作系统**：这是指安装在系统上以便引导和执行程序的软件和文件。它包括内核、管理工具和系统库。
- **[内核](#gloss-glo-088)**：内核是管理系统的程序，包括（取决于内核模型）硬件设备、内存和 CPU 调度。它以允许直接访问硬件的特权 CPU 模式运行，这种模式称为“内核模式”。
- **进程**：用于执行程序的操作系统抽象和环境。程序在*用户模式*下运行，并通过系统调用或陷阱进入内核，以请求特权操作（例如执行设备 I/O）。
- **[线程](#gloss-glo-176)**：可以安排在 CPU 上运行的可执行上下文。内核有多个线程，一个进程包含一个或多个线程。
- **[任务](#gloss-glo-173)**：Linux 可运行实体，可以指进程（具有单线程）、多线程进程中的线程或内核线程。
- **BPF 程序**：运行在 BPF[^fn-ch03-ch03-footnote-1] 执行环境中的内核模式程序。
- **主内存**：系统的物理内存（例如RAM）。
- **[虚拟内存](#gloss-glo-197)**：支持多任务和超额分配的主内存抽象。实际上，它是一种无限的资源。
- **内核空间**：内核的虚拟内存地址空间。
- **用户空间**：进程的虚拟内存地址空间。
- **用户层**：用户级程序和库（/usr/bin、/usr/lib...）。
- **上下文切换**：从运行一个线程或进程到另一个线程或进程的切换。这是内核 CPU 调度程序的正常功能，涉及将正在运行的 CPU 寄存器组（线程上下文）切换到新组。
- **模式切换**：内核模式和用户模式之间的切换。
- **系统调用（syscall）**：一种定义明确的协议，供用户程序请求内核执行特权操作，包括设备I/O。
- **处理器**：不要与*进程*混淆，处理器是包含一个或多个CPU的物理芯片。
- **陷阱**：发送到内核以请求系统例程（特权操作）的信号。陷阱类型包括系统调用、处理器异常和中断。
- **硬件中断**：物理设备发送到内核的信号，通常用于请求 I/O 服务。中断是一种陷阱。

如需参考，词汇表还包含本章涉及的更多术语，包括 *[地址空间](#gloss-glo-005)*、*[缓冲区](#gloss-glo-024)*、*[CPU](#gloss-glo-037)*、*[文件描述符](#gloss-glo-060)*、*[POSIX](#gloss-glo-128)* 和 *[寄存器](#gloss-glo-136)*。

### 3.2.1 内核

内核是操作系统的核心软件。它的作用取决于内核模型：包括 Linux 和 BSD 在内的类 Unix 操作系统采用*单体内核*，负责管理 CPU 调度、内存、文件系统、网络协议和系统设备（磁盘、网络接口等）。该内核模型显示在 [图 3.1](#ch03-ch03fig01) 中。

<!-- source-id: ch03#ch03fig01 -->
![图 3.1 单体操作系统内核的作用](../images/03fig01.jpg)

还显示了系统库，它们通常用于提供比单独的系统调用更丰富、更简单的编程接口。应用程序包括所有正在运行的用户级软件，包括数据库、Web 服务器、管理工具和操作系统 shell。

系统库在这里被描绘成一个带缺口的环，以表明应用程序可以直接调用系统调用（*syscalls*）。[^fn-ch03-ch03-footnote-2] 例如，Golang 运行时有自己的系统调用层，不需要系统库 libc。传统上，该图是用完整的环绘制的，反映了从中心内核开始的特权级别递减（该模型起源于 Multics [\[Graham 68\]](#ch03-ch03ref1)，Unix 的前身）。

还存在其他内核模型：*微内核*采用小型内核，将功能移到用户模式程序；*unikernel* 将内核和应用程序代码一起编译成单个程序。还有*混合内核*，例如 Windows NT 内核，同时采用单体内核和微内核的方法。这些内容总结在 [第 3.5 节](#ch03-ch03lev5)、[其他主题](#ch03-ch03lev5) 中。

Linux 最近改变了它的模型，允许一种新的软件类型：扩展 BPF。它支持安全的内核模式应用程序，并提供自己的内核 API——BPF helper。这使得一些应用程序和系统功能可以用 BPF 重写，从而提供更高的安全性和性能，如 [图 3.2](#ch03-ch03fig02) 所示。

<!-- source-id: ch03#ch03lev3_1 -->
#### 内核执行

内核是一个大型程序，通常有数百万行代码。它主要在用户级程序进行系统调用或设备发送中断时按需执行。一些内核线程异步执行内务处理任务，其中可能包括内核时钟例程和内存管理任务，但这些任务尽量保持轻量，并消耗很少的 CPU 资源。

执行频繁 I/O 的工作负载（例如 Web 服务器）主要在内核上下文中执行。计算密集型工作负载通常在用户模式下运行，不会被内核打断。人们可能会认为内核不会影响这类工作负载的性能，但实际上有很多例外。最明显的是 CPU 争用：当其他线程竞争 CPU 资源时，内核调度器需要决定哪些线程运行、哪些线程等待。内核还会选择线程运行在哪个 CPU 上，并可为进程选择硬件缓存更“热”或内存局部性更好的 CPU，从而显著提高性能。

<!-- source-id: ch03#ch03lev2sec2 -->
### 3.2.2 内核和用户模式

内核在称为“内核模式”的特殊 CPU 模式下运行，允许完全访问设备并执行特权指令。内核仲裁设备访问以支持多任务处理，防止进程和用户访问彼此的数据，除非明确允许。

用户程序（进程）在“用户模式”下运行，它们通过系统调用向内核请求特权操作，例如 I/O。

内核和用户模式在处理器上使用*特权环*（或*保护环*）实现，遵循 [图 3.1](#ch03-ch03fig01) 中的模型。例如，x86 处理器支持四个特权环，编号为 0 到 3。通常仅使用两个或三个：用于用户模式、内核模式和虚拟机管理程序（如果存在）。访问设备的特权指令只允许在内核模式下使用；在用户模式下执行它们会导致*异常*，然后由内核处理（例如，生成权限被拒绝错误）。

在传统的内核中，系统调用是通过切换到内核模式，然后执行系统调用代码来执行的。这显示在 [图 3.3](#ch03-ch03fig03) 中。

<!-- source-id: ch03#ch03fig03 -->
![图 3.3 系统调用执行模式](../images/03fig03.jpg)

用户模式和内核模式之间的切换是“模式切换”。

所有系统调用都会导致模式切换。一些系统调用还会导致*上下文切换*：阻塞型系统调用（例如磁盘和网络 I/O）会进行上下文切换，使第一个线程阻塞时另一个线程可以运行。

由于模式切换和上下文切换会带来少量开销（CPU 周期），[^fn-ch03-ch03-footnote-3] 人们采用了各种优化来避免它们，包括：

- **用户模式系统调用**：可以单独在用户模式库中实现一些系统调用。 Linux 内核通过导出映射到进程地址空间的虚拟动态共享对象 (vDSO) 来实现此目的，其中包含 gettimeofday(2) 和 getcpu(2) [\[Drysdale 14\]](#ch03-ch03ref19) 等系统调用。
- **内存映射**：内存映射用于按需分页（请参阅 [第 7 章](#ch07-ch07)、[内存](#ch07-ch07)、[第 7.2.3 节](#ch07-ch07lev2sec3)、[按需分页](#ch07-ch07lev2sec3)），也可用于数据存储和其他 I/O，从而避免系统调用开销。
- **内核旁路**：这允许用户模式程序直接访问设备，绕过系统调用和典型的内核代码路径。例如，网络领域的 DPDK（数据平面开发套件）。
- **内核模式应用程序**：其中包括在内核中实现的 TUX Web 服务器 [\[Lever 00\]](#ch03-ch03ref8)，以及最近在 [图 3.2](#ch03-ch03fig02) 中展示的扩展 BPF 技术。

内核和用户模式有自己的软件执行上下文，包括堆栈和寄存器。某些处理器架构（例如 SPARC）为内核使用单独的地址空间，这意味着模式切换还必须更改虚拟内存上下文。

### 3.2.3 系统调用

系统调用请求内核执行特权系统例程。有数百个可用的系统调用，但内核维护者努力让这个数量尽可能少，以保持内核简单（Unix 哲学；\[Thompson 78\]）。更复杂的接口可以在用户层以系统库的形式构建，这样更易于开发和维护。操作系统通常包含一个 C 标准库，为许多常见的系统调用提供更易用的接口（例如 libc 或 glibc 库）。

系统调用都有详细的文档记录，每个系统调用通常都随操作系统附带一个手册页。它们的接口通常简单且一致，并在需要时使用错误代码描述错误（例如，ENOENT 表示“没有此类文件或目录”）。[^fn-ch03-ch03-footnote-4]

许多系统调用的用途很直观。下面列出几个常见但不太直观的用法：

- **ioctl(2)**：它通常用于向内核请求各种操作，尤其适用于系统管理工具，因为其他（更直观的）系统调用无法满足需求。请参阅下面的示例。
- **mmap(2)**：它通常用于将可执行文件和库映射到进程地址空间，以及映射文件。有时也用它来分配进程的工作内存，替代基于 brk(2) 的 malloc(2)，以降低系统调用率并提高性能（但由于内存映射管理的权衡，这并不总是有效）。
- **brk(2)**：用于扩展堆指针，定义进程工作内存的大小。当堆中的现有空间无法满足 malloc(3)（内存分配）调用时，它通常由系统内存分配库执行。请参见 [第 7 章](#ch07-ch07)、[内存](#ch07-ch07)。
- **futex(2)**：此系统调用用于处理用户空间锁的一部分：可能阻塞的部分。

如果系统调用不熟悉，您可以在其手册页中了解更多信息（这些内容位于手册页的第 2 节：系统调用）。

ioctl(2) 系统调用可能是最难学习的，因为它的性质不明确。以其用法为例，Linux perf(1) 工具（在 [第 6 章](#ch06-ch06)、[CPU](#ch06-ch06) 中介绍）执行特权操作来协调性能插桩。与其为每个操作添加一个系统调用，不如只添加一个系统调用：perf\_event\_open(2)，它返回一个供 ioctl(2) 使用的文件描述符。然后可以使用不同的参数调用 ioctl(2)，执行不同的操作。例如，ioctl(fd, PERF\_EVENT\_IOC\_ENABLE) 会启用插桩。开发人员可以更容易地添加和修改本例中的参数 PERF\_EVENT\_IOC\_ENABLE。

### 3.2.4 中断

*中断*是向处理器发出的信号，表明发生了某些需要处理的事件，并中断处理器的当前执行以处理该事件。它通常会导致处理器进入内核模式（如果尚未进入），保存当前线程状态，然后运行*中断服务例程*（ISR）来处理事件。

有外部硬件产生的异步中断和软件指令产生的同步中断。这两类中断如 [图 3.4](#ch03-ch03fig04) 所示。

#### 异步中断

硬件设备可以向处理器发送“中断服务请求”(IRQ)，该请求异步到达当前正在运行的软件。硬件中断的示例包括：

- 磁盘设备发出磁盘 I/O 完成信号
- 指示故障情况的硬件
- 网络接口发出数据包到达信号
- 输入设备：键盘和鼠标输入

为了解释异步中断的概念，[图 3.5](#ch03-ch03fig05) 中描绘了一个示例场景，显示了在 CPU 0 上运行的数据库 (MySQL) 从文件系统读取数据时的时间流逝。文件系统内容必须从磁盘获取，因此调度器会在数据库等待时进行上下文切换，转而执行到另一个线程（Java 应用程序）。一段时间后，磁盘 I/O 完成，但此时数据库不再在 CPU 0 上运行。完成中断与数据库异步发生，如 [图 3.5](#ch03-ch03fig05) 中的虚线所示。

#### 同步中断

同步中断由软件指令产生。下面使用“陷阱”、“异常”和“故障”这些术语描述不同类型的软件中断；不过，这些术语经常可以互换使用。

- **陷阱**：有意调用内核，例如通过 int（中断）指令。系统调用的一种实现方式，是使用系统调用处理程序的向量调用 int 指令（例如 Linux x86 上的 int 0x80）。int 会引发软件中断。
- **异常**：异常情况，例如某条指令执行除以零操作。
- **故障**：这个术语常用于描述内存事件，例如访问没有 MMU 映射的内存位置而触发的*缺页异常*。请参见 [第 7 章](#ch07-ch07)、[内存](#ch08-ch08)。

对于这些中断，负责的软件和指令仍在 CPU 上运行。

<!-- source-id: ch03#ch03lev3_4 -->
#### 中断线程

中断服务例程 (ISR) 旨在尽可能快地运行，以减少对被中断活动线程的影响。如果中断需要执行不止少量的工作，尤其是可能因锁而阻塞，就可以交给由内核调度的中断线程处理。如 [图 3.6](#ch03-ch03fig06) 所示。

<!-- source-id: ch03#ch03fig06 -->
![图 3.6 中断处理](../images/03fig06.jpg)

具体实现取决于内核版本。在 Linux 上，设备驱动程序可以分成两半：上半部快速处理中断，并把工作安排给下半部稍后处理 [\[Corbet 05\]](#ch03-ch03ref12)。快速处理中断很重要，因为上半部运行在*禁用中断*模式下，会推迟新中断的传递；如果运行时间过长，就可能导致其他线程出现延迟问题。下半部可以是 *tasklet* 或*工作队列*；后者是可由内核调度、必要时可以休眠的线程。

例如，Linux 网络驱动程序的上半部处理入站数据包的 IRQ，然后调用下半部把数据包推入网络协议栈。下半部以*softirq*（软件中断）的形式实现。

从中断到达，到它得到服务之间的时间称为*中断延迟*，取决于硬件和实现。这是实时或低延迟系统研究的主题。

<!-- source-id: ch03#ch03lev3_5 -->
#### 中断屏蔽

内核中的某些代码路径无法安全地被中断。例如，系统调用期间获取自旋锁的内核代码，可能与同样需要该锁的中断发生冲突。在持有此类锁时处理中断可能导致死锁。为防止这种情况，内核可以设置 CPU 的*中断屏蔽*寄存器，临时屏蔽中断。禁用中断的时间应尽可能短，因为它会干扰被其他中断唤醒的应用程序及时执行。对于具有严格响应时间要求的*实时*系统，这是一个重要因素。禁用中断的时间也是性能分析的目标（Ftrace irqsoff 跟踪器直接支持此类分析，见 [第 14 章](#ch14-ch14)、[Ftrace](#ch14-ch14)）。

一些高优先级事件不应被忽略，因此被实现为*不可屏蔽中断* (NMI)。例如，Linux 可以使用智能平台管理接口 (IPMI) 看门狗定时器，根据一段时间内没有中断来检查内核是否疑似卡死。如果是这样，看门狗可以发出 NMI 中断来重新启动系统。[^fn-ch03-ch03-footnote-5]

### 3.2.5 时钟和空闲

原始 Unix 内核的核心组件是由定时器中断执行的 clock() 例程。历史上它的执行速度为每秒 60、100 或 1,000 次[^fn-ch03-ch03-footnote-6]（通常以赫兹表示：每秒周期数），每次执行称为一个 *tick*。[^fn-ch03-ch03-footnote-7] 其功能包括更新系统时间、使计时器和线程调度时间片到期、维护 CPU 统计信息以及执行已调度的内核例程。

时钟存在性能问题，在后来的内核中得到了改进，包括：

- **滴答延迟**：对于 100 赫兹时钟，定时器在等待下一个滴答时处理时可能会遇到最多 10 毫秒的额外延迟。已使用高分辨率实时中断修复了此问题，以便立即执行。
- **滴答开销**：滴答会消耗 CPU 周期并稍微扰乱应用程序，并且是所谓的“操作系统抖动”的原因之一。现代处理器还具有动态电源功能，可以在空闲期间关闭部件。时钟例程会中断此空闲时间，这会不必要地消耗功率。

现代内核已将许多功能从时钟例程转移到按需中断，以努力创建“无滴答内核”。这允许处理器更长时间地保持睡眠状态，从而减少开销并提高电源效率。

Linux 的时钟例程是 scheduler\_tick()；在没有 CPU 负载时，Linux 可以省略对时钟例程的调用。时钟本身通常以 250 Hz 运行（由 CONFIG\_HZ Kconfig 选项及其变体配置），而 NO\_HZ 功能（由 CONFIG\_NO\_HZ 及其变体配置）会减少调用次数；该功能现在通常处于启用状态 [\[Linux 20a\]](#ch03-ch03ref38)。

<!-- source-id: ch03#ch03lev3_6 -->
#### 空闲线程

当 CPU 没有工作需要执行时，内核会调度一个等待工作的占位线程，称为“空闲线程”。简单的实现可以在循环中检查是否有新工作可用。在现代 Linux 中，“空闲任务”可以调用 hlt（halt）指令，让 CPU 停止执行，直到收到下一个中断，从而节省电能。

### 3.2.6 进程

进程是执行用户级程序的环境。它由内存地址空间、文件描述符、线程堆栈和寄存器组成。在某些方面，进程就像一台虚拟的早期计算机，其中只有一个程序使用自己的寄存器和堆栈执行。

进程由内核执行多任务处理，通常支持在单个系统上执行数千个进程。它们通过其*进程 ID* (PID) 进行单独标识，这是一个唯一的数字标识符。

一个进程包含一个或多个“线程”，它们在进程地址空间中运行并共享相同的文件描述符。线程是由堆栈、寄存器和指令指针（也称为*程序计数器*）组成的可执行上下文。多个线程允许单个进程在多个 CPU 上并行执行。在 Linux 上，线程和进程都是“任务”。

内核启动的第一个进程称为“init”，来自 /sbin/init（默认情况下），PID 为 1，用于启动用户空间服务。在 Unix 中，这涉及从 /etc 运行启动脚本，这种方法现在称为 SysV（以 Unix System V 命名）。 Linux 发行版现在普遍使用 systemd 软件来启动服务并跟踪它们的依赖关系。

<!-- source-id: ch03#ch03lev3_7 -->

在 Unix 系统上，进程通常是使用 fork(2) 系统调用创建的。在 Linux 上，C 库通常通过包装通用的 clone(2) 系统调用来实现 fork 函数。这些系统调用创建进程的副本，并具有自己的进程 ID。然后可以调用 exec(2) 系统调用（或其变体，例如 execve(2)）来开始执行不同的程序。

[图 3.7](#ch03-ch03fig07) 展示了一个 bash shell (`bash`) 执行 `ls` 命令时的进程创建示例。

<!-- source-id: ch03#ch03fig07 -->
![图 3.7 进程创建](../images/03fig07.jpg)

fork(2) 或 clone(2) 系统调用可以使用写时复制（COW）策略来提高性能。这会添加对原有地址空间的引用，而不是复制全部内容。一旦任一进程修改了被多个进程引用的内存，就会为修改部分创建一个单独的副本。此策略推迟或消除了复制内存的需要，从而减少了内存和 CPU 使用量。

### 3.2.7 堆栈

堆栈是临时数据的内存存储区域，按后进先出 (LIFO) 列表组织。它用于存储无法放入 CPU 寄存器组、重要性低于寄存器数据的数据。当函数被调用时，返回地址会保存到堆栈中；如果调用后还需要某些寄存器的值，这些寄存器也会保存到堆栈中。[^fn-ch03-ch03-footnote-10] 被调用函数完成后，会恢复所需的寄存器，并从堆栈取出返回地址，把执行权交还给调用函数。堆栈还可以用于向函数传递参数。与函数执行相关的堆栈数据集合称为 *[堆栈帧](#gloss-glo-162)*。

通过检查线程堆栈中所有堆栈帧里保存的返回地址，可以看到当前执行函数的调用路径（这个过程称为*堆栈遍历*）。[^fn-ch03-ch03-footnote-11] 这条调用路径称为*堆栈回溯*或*[堆栈跟踪](#gloss-glo-163)*。在性能工程中，它通常简称为“堆栈”。堆栈可以回答某段代码“为什么”正在执行，是调试和性能分析不可或缺的工具。

<!-- source-id: ch03#ch03lev3_10 -->
#### 如何读取堆栈

以下示例内核堆栈（来自 Linux）显示了 TCP 传输所采用的路径，由跟踪工具打印：

![点此查看代码图片](../images/pg102.jpg)

```text
    tcp_sendmsg+1
    sock_sendmsg+62
    SYSC_sendto+319
    sys_sendto+14
    do_syscall_64+115
    entry_SYSCALL_64_after_hwframe+61
```

堆栈通常按从叶到根的顺序打印，因此打印的第一行是当前正在执行的函数，下面是其父函数，然后是其祖父函数，依此类推。在此示例中，tcp\_sendmsg() 函数正在执行，由 sock\_sendmsg() 调用。在此堆栈示例中，函数名称右侧是指令偏移量，显示函数内的位置。第一行显示 tcp\_sendmsg() 偏移量 1（这将是第二条指令），由 sock\_sendmsg() 偏移量 62 调用。仅当您希望对所采用的代码路径有深入了解（直至指令级别）时，此偏移量才有用。

由于堆栈揭示了经过源代码的内部路径，这些函数通常没有代码之外的文档；对于这个示例堆栈，相关文档就是 Linux 内核源代码。例外情况是函数属于某个 API，并且 API 已为其提供文档。

### 3.2.8 虚拟内存

虚拟内存是主内存的一种抽象，为进程和内核提供各自的、几乎无限的[^fn-ch03-ch03-footnote-12] 主内存私有视图。它支持多任务处理，让进程和内核可以在各自的私有地址空间中运行，而不必担心相互争用。它还支持主内存的超额分配，使操作系统可以按需在主内存和辅助存储（磁盘）之间透明地映射虚拟内存。

虚拟内存的作用如 [图 3.11](#ch03-ch03fig11) 所示。主存储器就是主内存（RAM），辅助存储器则是存储设备（磁盘）。

<!-- source-id: ch03#ch03fig11 -->
![图 3.11 虚拟内存地址空间[^fn-ch03-ch03-footnote-13]](../images/03fig11.jpg)

处理器和操作系统的支持使虚拟内存成为可能。它不是真实内存；大多数操作系统只在内存首次被填充（写入）时，才按需将虚拟内存映射到物理内存。

有关虚拟内存的更多信息，请参阅 [第 7 章](#ch07-ch07)、[内存](#ch07-ch07)。

<!-- source-id: ch03#ch03lev3_12 -->
#### 内存管理

虽然虚拟内存允许使用辅助存储来扩展主内存，但内核努力将最活跃的数据保留在主内存中。为此有两种内核方案：

- **进程交换** 在主内存和辅助存储之间移动整个进程。
- **分页**移动称为 [页](#gloss-glo-116) 的小内存单元（例如 4 KB）。

进程交换是原始的 Unix 方法，会导致严重的性能损失。分页效率更高，并通过引入分页虚拟内存而添加到 BSD 中。在这两种情况下，最近最少使用（或最近未使用）的内存都会移至辅助存储，并仅在再次需要时移回主内存。

在 Linux 中，术语“交换”用于指代“分页”。 Linux 内核不支持整个线程和进程的（较旧的）Unix 风格的进程交换。

有关分页和交换的更多信息，请参阅 [第 7 章](#ch07-ch07)、[内存](#ch07-ch07)。

### 3.2.9 调度程序

Unix 及其衍生系统是分时系统，通过划分执行时间来允许多个进程同时运行。处理器和各个 CPU 上的进程调度由操作系统内核的关键组件“调度程序”执行。调度程序的作用如 [图 3.12](#ch03-ch03fig12) 所示，它显示调度程序在线程（在 Linux 中为*任务*）上运行，将它们映射到 CPU。

<!-- source-id: ch03#ch03fig12 -->
![图 3.12 内核调度器](../images/03fig12.jpg)

基本目的是在活动进程和线程之间分配 CPU 时间，并维护“优先级”概念，以便更重要的工作可以更快执行。调度程序跟踪处于就绪状态的所有线程，传统上位于称为*运行队列* [\[Bach 86\]](#ch03-ch03ref4) 的按优先级队列上。现代内核可以为每个 CPU 实现这些队列，并且还可以使用除队列之外的其他数据结构来跟踪线程。当想要运行的线程多于可用 CPU 时，优先级较低的线程将等待轮到它们。大多数内核线程的运行优先级高于用户级进程。

调度程序可以动态修改进程优先级，以提高某些工作负载的性能。工作负载可以分为以下几类：

- **CPU 密集型**：执行繁重计算的应用程序，例如科学和数学分析，通常运行很长时间（数秒、数分钟、数小时、数天，甚至更久），因而受 CPU 资源限制。
- **I/O 密集型**：执行 I/O 且计算量很少的应用程序，例如 Web 服务器、文件服务器和交互式 shell；这类应用需要低延迟响应。当负载增加时，它们会受限于存储或网络资源的 I/O。

一种可追溯到 UNIX 的常用调度策略会识别 CPU 密集型工作负载并降低其优先级，从而让更需要低延迟响应的 I/O 密集型工作负载更快运行。这可以通过计算最近的计算时间（在 CPU 上执行的时间）与实际时间（经过的时间）的比率，并降低该比率较高的进程的优先级来实现 \[Thompson 78\]。这种机制优先考虑运行时间较短的进程，而这些通常正是执行 I/O 的进程，包括人机交互进程。

现代内核支持多个“调度类”或“调度策略”（Linux），它们应用不同的算法来管理优先级和可运行线程。这些可能包括*实时调度*，它使用高于所有非关键工作（包括内核线程）的优先级。实时调度结合抢占支持（稍后描述），为需要它的系统提供可预测的低延迟调度。

有关内核调度程序和其他调度算法的更多信息，请参阅 [第 6 章](#ch06-ch06)、[CPU](#ch06-ch06)。

### 3.2.10 文件系统

文件系统负责把数据组织成文件和目录。它们提供基于文件的访问接口，通常以 POSIX 标准为基础。内核支持多种文件系统类型和实例。提供文件系统是操作系统最重要的作用之一，甚至曾被称为操作系统*最*重要的作用 [\[Ritchie 74\]](#ch03-ch03ref2)。

操作系统提供一个全局文件命名空间，组织成从根目录（“/”）开始的自上而下的树形拓扑。文件系统通过*挂载*加入这棵树，把自己的目录树附加到某个目录（*挂载点*）。这样，最终用户无需关心底层文件系统类型，就能透明地浏览整个文件命名空间。

典型的操作系统的组织方式如 [图 3.13](#ch03-ch03fig13) 所示。

<!-- source-id: ch03#ch03fig13 -->
![图 3.13 操作系统文件层次结构](../images/03fig13.jpg)

### 3.2.12 网络

现代内核提供一组内置网络协议，使系统能够通过网络通信并参与分布式系统环境。这套协议通常称为*网络协议栈*或*TCP/IP 协议栈*，名称来自常用的 TCP 和 IP 协议。用户级应用程序通过称为*套接字*的可编程端点访问网络。

连接到网络的物理设备称为*网络接口*，通常由*网络接口卡* (NIC) 提供。过去，系统管理员需要将 IP 地址关联到网络接口，使其能够与网络通信；如今这些映射通常通过动态主机配置协议 (DHCP) 自动完成。

网络协议不会经常改变，但有一种新的传输协议得到越来越多的采用：QUIC（总结在 [第 10 章](#ch10-ch10)、[网络](#ch10-ch10) 中）。协议增强功能和选项更频繁地更改，例如更新的 TCP 选项和 TCP 拥塞控制算法。较新的协议和增强功能通常需要内核支持（用户空间协议实现除外）。另一个变化是对不同网络接口卡的支持，这需要内核的新设备驱动程序。

有关网络和网络性能的更多信息，请参阅 [第 10 章](#ch10-ch10)、[网络](#ch10-ch10)。

<!-- source-id: ch03#ch03lev2sec13 -->
### 3.2.13 设备驱动程序

内核必须与各种物理设备通信。这种通信通过*设备驱动程序*实现：设备驱动程序是用于设备管理和 I/O 的内核软件，通常由硬件设备供应商提供。某些内核支持*可插拔*设备驱动程序，可以在不重启系统的情况下加载和卸载。

设备驱动程序可以为设备提供*字符*和/或*块*接口。字符设备也称为“原始设备”，根据设备不同，可提供任意 I/O 大小（最小到单个字符）的无缓冲顺序访问。此类设备包括键盘和串行端口（在早期 Unix 中还包括纸带和行式打印机设备）。

块设备以块为单位执行 I/O，历史上每个块为 512 字节。可以根据块偏移量随机访问这些块，偏移量从块设备开头的 0 开始。在早期 Unix 中，块设备接口还会缓存块设备缓冲区以提高性能，缓存位于主内存中一个称为*缓冲区缓存*的区域。在 Linux 中，这个缓冲区缓存现在是页缓存的一部分。

<!-- source-id: ch03#ch03lev2sec14 -->
### 3.2.14 多处理器

多处理器支持允许操作系统使用多个 CPU 实例并行执行工作。它通常以*对称多处理* (SMP) 的形式实现，其中所有 CPU 都被平等对待。这在技术上很难实现，因为并行运行的线程需要访问和共享内存及 CPU。在多处理器系统上，还可能存在连接到不同插槽（物理处理器）的多组主内存，形成*非一致性内存访问* (NUMA) 架构；这同样带来性能挑战。有关调度和线程同步等详情，请参阅 [第 6 章](#ch06-ch06)、[CPU](#ch06-ch06)；有关内存访问和架构的详情，请参阅 [第 7 章](#ch07-ch07)、[内存](#ch07-ch07)。

<!-- source-id: ch03#ch03lev3_15 -->
#### IPI

在多处理器系统中，CPU 有时需要协调工作，例如维护内存转换条目的缓存一致性（通知其他 CPU：某个已缓存的条目现在已经过时）。CPU 可以使用处理器间中断 (IPI)（也称为 *SMP call* 或 *[CPU 交叉调用](#gloss-glo-038)*），请求其他 CPU 或所有 CPU 立即执行此类工作。IPI 是为快速执行而设计的处理器中断，以最大限度地减少对其他线程的干扰。

IPI 也可用于实现抢占。

<!-- source-id: ch03#ch03lev2sec15 -->
### 3.2.15 抢占

内核抢占支持允许高优先级用户级线程打断内核并执行。这使实时系统能够在给定的时间约束内完成工作，包括飞机和医疗设备使用的系统。支持抢占的内核称为*完全可抢占*，尽管实际上仍有一些很短的关键代码路径无法被打断。

Linux 支持的另一种方法是*自愿内核抢占*：内核代码中的逻辑停止点可以检查并执行抢占。这避免了支持完全抢占式内核的一些复杂性，并为常见工作负载提供低延迟抢占。Linux 中通常通过 CONFIG\_PREEMPT\_VOLUNTARY Kconfig 选项启用自愿内核抢占；CONFIG\_PREEMPT 允许除关键区段外的所有内核代码被抢占；CONFIG\_PREEMPT\_NONE 则禁用抢占，以更高延迟为代价提高吞吐量。

<!-- source-id: ch03#ch03lev2sec16 -->
### 3.2.16 资源管理

操作系统可以提供各种可配置的控制，用于微调对 CPU、内存、磁盘和网络等系统资源的访问。这些*资源控制*可用于管理运行不同应用程序或托管多个租户（云计算）的系统性能。此类控制可以对每个进程（或进程组）的资源使用施加固定限制，也可以采用更灵活的方式，让它们共享未使用的资源。

Unix 和 BSD 的早期版本具有基本的按进程资源控制，包括通过 nice(1) 设置 CPU 优先级，以及通过 ulimit(1) 设置一些资源限制。

对于 Linux，控制组 (cgroup) 在 Linux 2.6.24 (2008) 中开发并集成，此后又添加了各种控制项。这些内容记录在内核源代码的 Documentation/cgroups 下。还有一种改进的统一分层方案，称为 *cgroup v2*，在 Linux 4.5 (2016) 中提供，并记录在 Documentation/admin-guide/cgroup-v2.rst 中。

具体的资源控制将在后面的章节中酌情提及。管理操作系统虚拟化租户性能的示例用例见 [第 11 章](#ch11-ch11)、[云计算](#ch11-ch11)。

<!-- source-id: ch03#ch03lev2sec17 -->
### 3.2.17 可观测性

操作系统由内核、库和程序组成。这些程序包括用于观察系统活动和分析性能的工具，通常安装在 /usr/bin 和 /usr/sbin 中。系统上也可以安装第三方工具，提供额外的可观测性。

可观测性工具及其所依赖的操作系统组件将在 [第 4 章](#ch04-ch04) 中介绍。

### 3.3.1 Unix

Unix 是由 Ken Thompson、Dennis Ritchie 和 AT&T 贝尔实验室的其他人在 1969 年及随后的几年中开发的。它的确切起源在*UNIX 分时系统* \[Ritchie 74\] 中进行了描述：

当我们中的一个人（汤普森）对可用的计算机设施不满意时，发现了很少使用的 PDP-7 并开始创建一个更友好的环境，从而编写了第一个版本。

UNIX 的开发人员之前曾开发过多路信息和计算机服务 (Multics) 操作系统。 UNIX 是作为“轻量级”多任务操作系统和内核而开发的，最初名为 UNIplexed 信息和计算服务 (UNICS)，是 Multics 的双关语。来自 *UNIX 实现* [\[Thompson 78\]](#ch03-ch03ref3)：

内核是唯一不能由用户根据自己的喜好进行替换的 UNIX 代码。因此，内核应该做出尽可能少的实际决策。这并不意味着允许用户有一百万个选项来做同样的事情。相反，它意味着只允许一种方法来做一件事，但让这种方法成为可能提供的所有选项的最小公约数。

虽然内核很小，但它确实提供了一些高性能功能。进程具有调度程序优先级，可以减少高优先级工作的运行队列延迟。为了提高效率，磁盘 I/O 在大块（512 字节）中执行，并缓存在内存中的每设备缓冲区高速缓存中。空闲进程可以交换到存储中，从而允许繁忙的进程在主内存中运行。当然，该系统是多任务处理的——允许多个进程同时运行，从而提高作业吞吐量。

为了支持网络、多种文件系统、分页以及其他如今已视为标准的功能，内核不得不不断扩展。随着 BSD、SunOS (Solaris) 以及后来的 Linux 等多个衍生系统出现，内核性能开始相互竞争，进而推动了更多功能和代码的加入。

<!-- source-id: ch03#ch03lev3sec2 -->
### 3.3.2 BSD

伯克利软件发行版 (BSD) 操作系统最初是加州大学伯克利分校对 Unix 第六版所做的增强，并于 1978 年首次发布。由于原始 Unix 代码需要 AT&T 软件许可证，到 20 世纪 90 年代初，这些 Unix 代码已在新的 BSD 许可证下重写为 BSD 代码，从而允许包括 FreeBSD 在内的自由发行版。

主要的 BSD 内核开发，尤其是与性能相关的开发，包括：

- **分页虚拟内存**：BSD 将分页虚拟内存引入 Unix：无需交换出整个进程来释放主内存，而是可以移动（分页）较小的、最近最少使用的内存块。请参见 [第 7 章](#ch07-ch07)、[内存](#ch07-ch07)、[第 7.2.2 节](#ch07-ch07lev2sec2)、[分页](#ch07-ch07lev2sec2)。
- **按需分页**：它把物理内存到虚拟内存的映射推迟到首次写入时，避免为可能永远不会使用的页面过早付出、且有时并不必要的性能和内存成本。BSD 将按需分页引入 Unix。请参见 [第 7 章](#ch07-ch07)、[内存](#ch07-ch07)、[第 7.2.2 节](#ch07-ch07lev2sec2)、[分页](#ch07-ch07lev2sec2)。
- **FFS**：伯克利快速文件系统 (FFS) 将磁盘分配分组为柱面组，大大减少碎片并提高旋转磁盘的性能，并支持更大的磁盘和其他增强功能。 FFS 成为许多其他文件系统（包括 UFS）的基础。请参见 [第 8 章](#ch08-ch08)、[文件系统](#ch08-ch08)、[第 8.4.5 节](#ch08-ch08lev4sec5)、[文件系统类型](#ch08-ch08lev4sec5)。
- **TCP/IP 协议栈**：BSD 为 Unix 开发了第一个高性能 TCP/IP 协议栈，包含在 4.2BSD (1983) 中。 BSD 仍然以其高性能的网络协议栈而闻名。
- **套接字**：Berkeley 套接字是用于连接端点的 API。它们包含在 4.2BSD 中，已成为网络标准。请参见 [第 10 章](#ch10-ch10)、[网络](#ch10-ch10)。
- **Jails**：轻量级操作系统级虚拟化，允许多个隔离实例共享一个内核。 Jails 首次在 FreeBSD 4.0 中发布。
- **内核 TLS**：由于传输层安全 (TLS) 现在在 Internet 上广泛使用，因此内核 TLS 将大部分 TLS 处理移至内核，从而提高了性能[^fn-ch03-ch03-footnote-14] [\[Stewart 15\]](#ch03-ch03ref26)。

虽然 BSD 不像 Linux 那样流行，但它仍用于一些性能关键型环境，包括 Netflix 内容分发网络 (CDN)，以及 NetApp、Isilon 等公司的文件服务器。Netflix 在 2019 年这样总结 FreeBSD 在其 CDN 上的性能 [\[Looney 19\]](#ch03-ch03ref35)：

“使用 FreeBSD 和通用硬件，我们在一颗 16 核、2.6 GHz 的 CPU 上以约 55% 的 CPU 使用率提供了 90 Gb/s 的 TLS 加密连接服务。”

有一本优秀的 FreeBSD 内部结构参考书，出自本书的同一出版商：*FreeBSD 操作系统的设计与实现*（第 2 版）[\[McKusick 15\]](#ch03-ch03ref25)。

<!-- source-id: ch03#ch03lev3sec3 -->
### 3.3.3 Solaris

Solaris 是由 Sun Microsystems 于 1982 年创建的源自 Unix 和 BSD 的内核和操作系统。它最初被命名为 SunOS，并针对 Sun 工作站进行了优化。到 20 世纪 80 年代末，AT&T 基于 SVR3、SunOS、BSD 和 Xenix 的技术开发了新的 Unix 标准，即 Unix System V Release 4 (SVR4)。 Sun 基于 SVR4 创建了新内核，并将操作系统重新命名为 Solaris。

主要的 Solaris 内核开发，尤其是与性能相关的开发，包括：

- **[VFS](#gloss-glo-196)**：虚拟文件系统（VFS）是一个抽象和接口，允许多个文件系统轻松共存。 Sun 最初创建它是为了让 NFS 和 UFS 能够共存。 [第 8 章](#ch08-ch08)、[文件系统](#ch08-ch08) 中涵盖了 VFS。
- **完全可抢占的内核**：这为高优先级工作（包括实时工作）提供了低延迟。
- **多处理器支持**：在 20 世纪 90 年代初，Sun 在多处理器操作系统支持方面投入了大量资金，开发了对非对称和对称多处理（ASMP 和 SMP）的内核支持 [\[Mauro 01\]](#ch03-ch03ref10)。
- **Slab 分配器**：内核 slab 内存分配器取代了 SVR4 伙伴分配器，通过为预分配缓冲区提供每 CPU 缓存来快速重用，从而获得更好的性能。这种分配器及其派生实现已成为包括 Linux 在内的许多内核的标准。
- **DTrace**：静态和动态跟踪框架及工具，在生产环境中实时提供对整个软件栈几乎不受限制的可观测性。Linux 使用 BPF 和 bpftrace 提供同类可观测性。
- **区域（zones）**：一种基于操作系统的虚拟化技术，用于创建共享同一内核的操作系统实例，类似于早期的 FreeBSD jail 技术。如今，操作系统虚拟化作为 Linux 容器得到广泛使用。请参见 [第 11 章](#ch11-ch11)、[云计算](#ch11-ch11)。
- **[ZFS](#gloss-glo-201)**：具有企业级功能和性能的文件系统。它现在可用于其他操作系统，包括 Linux。请参见 [第 8 章](#ch08-ch08)、[文件系统](#ch08-ch08)。

Oracle 于 2010 年收购了 Sun Microsystems，Solaris 现在更名为 Oracle Solaris。本书第一版更详细地介绍了 Solaris。

<!-- source-id: ch03#ch03lev4 -->
## 3.4 Linux

Linux 是由 Linus Torvalds 于 1991 年创建的，作为 Intel 个人计算机的免费操作系统。他在新闻组帖子中宣布了该项目：

我正在为 386(486) AT 克隆做一个（免费）操作系统（只是一个爱好，不会像 gnu 那样庞大和专业）。这个计划从四月份就开始酝酿，现在已经开始准备了。我希望得到关于人们喜欢/不喜欢 minix 的任何反馈，因为我的操作系统有点类似于它（文件系统的物理布局相同（由于实际原因）等）。

这是指 MINIX 操作系统，它是为小型计算机开发的免费小型（迷你）版本 Unix。 BSD 还旨在提供免费的 Unix 版本，尽管当时它遇到了法律问题。

Linux 内核的开发借鉴了许多祖先的一般思想，包括：

- **Unix（和 Multics）**：操作系统层、系统调用、多任务、进程、进程优先级、虚拟内存、全局文件系统、文件系统权限、设备节点、缓冲区高速缓存
- **[BSD](#gloss-glo-023)**：分页虚拟内存、按需分页、快速文件系统 (FFS)、TCP/IP 协议栈、套接字
- **[Solaris](#gloss-glo-155)**：VFS、NFS、页面缓存、统一页面缓存、slab 分配器
- **Plan 9**：资源分叉 (rfork)，用于在进程和线程（*任务*）之间创建不同级别的共享

Linux 现在广泛用于服务器、云实例和包括移动电话在内的嵌入式设备。

<!-- source-id: ch03#ch03lev4sec1 -->
### 3.4.1 Linux 内核开发

Linux 内核的发展，尤其是与性能相关的部分，包括以下内容（许多条目还列出了首次引入该特性的 Linux 内核版本）：

- **CPU 调度类**：已经开发出各种高级 CPU 调度算法，包括调度域 (2.6.7)，以便针对非一致性内存访问 (NUMA) 做出更好的决策。请参见 [第 6 章](#ch06-ch06)、[CPU](#ch06-ch06)。
- **I/O 调度类**：已经开发出不同的块 I/O 调度算法，包括 deadline (2.5.39)、anticipatory (2.5.75) 和完全公平排队 (CFQ) (2.6.6)。这些算法在 Linux 5.0 之前的内核中可用；Linux 5.0 移除了它们，只支持更新的多队列 I/O 调度器。请参见 [第 9 章](#ch09-ch09)、[磁盘](#ch09-ch09)。
- **TCP 拥塞算法**：Linux 允许配置不同的 TCP 拥塞控制算法，并支持 Reno、Cubic 以及本列表后面提到的内核版本中的更多算法。另请参见 [第 10 章](#ch10-ch10)、[网络](#ch10-ch10)。
- **内存超额分配**：结合内存不足 (OOM) killer，这是用更少的主内存完成更多工作的策略。请参见 [第 7 章](#ch07-ch07)、[内存](#ch07-ch07)。
- **Futex** (2.5.7)：“快速用户空间互斥体”的缩写，用于提供高性能的用户级同步原语。
- **大页面** (2.5.36)：这为内核和内存管理单元 (MMU) 预分配的大型内存页提供支持。请参见 [第 7 章](#ch07-ch07)、[内存](#ch07-ch07)。
- **OProfile** (2.5.43)：用于研究内核和应用程序的 CPU 使用情况和其他事件的系统性能剖析器。
- **[RCU](#gloss-glo-134)** (2.5.43)：内核提供了读-复制更新同步机制，允许多个读取与更新同时发生，提高了以读为主的数据的性能和可扩展性。
- **epoll** (2.5.46)：一个系统调用，用于跨多个打开的文件描述符有效等待 I/O，从而提高服务器应用程序的性能。
- **模块化 I/O 调度** (2.6.10)：Linux 提供可插拔的调度算法来调度块设备 I/O。请参见 [第 9 章](#ch09-ch09)、[磁盘](#ch09-ch09)。
- **DebugFS** (2.6.11)：一个简单的非结构化接口，用于内核向用户级别公开数据，由一些性能工具使用。
- **Cpusets** (2.6.12)：为进程提供专用的 CPU 分组。
- **自愿内核抢占** (2.6.13)：此特性提供低延迟调度，而无需完全抢占的复杂性。
- **inotify** (2.6.13)：用于监视文件系统事件的框架。
- **blktrace** (2.6.17)：用于跟踪块 I/O 事件的框架和工具（后来迁移到跟踪点）。
- **splice** (2.6.17)：系统调用，用于在文件描述符和管道之间快速移动数据，而无需穿过用户空间。 （sendfile(2) 系统调用可以有效地在文件描述符之间移动数据，现在是 splice(2) 的包装器。）
- **延迟记账** (2.6.18)：跟踪每个任务的延迟状态。请参见 [第 4 章](#ch04-ch04)、[可观测性工具](#ch04-ch04)。
- **IO 统计** (2.6.20)：测量每个进程的各种存储 I/O 统计数据。
- **DynTicks** (2.6.21)：动态滴答允许内核定时器中断（时钟）在空闲期间不触发，从而节省 CPU 资源和电量。
- **SLUB** (2.6.22)：slab 内存分配器的新简化版本。
- **CFS** (2.6.23)：完全公平的调度程序。请参见 [第 6 章](#ch06-ch06)、[CPU](#ch06-ch06)。
- **cgroups** (2.6.24)：控制组允许测量和限制进程组的资源使用情况。
- **TCP LRO** (2.6.24)：TCP 大型接收卸载 (LRO) 允许网络驱动程序和硬件在将数据包发送到网络协议栈之前将其聚合为更大的大小。 Linux 还支持发送路径的大型发送卸载 (LSO)。
- **latencytop** (2.6.25)：用于观察操作系统中延迟来源的插桩机制和工具。
- **[跟踪点](#gloss-glo-181)** (2.6.28)：静态内核跟踪点（又名*静态探针*），用于在内核中的逻辑执行点进行插桩，供跟踪工具使用（以前称为*内核标记*）。 [第 4 章](#ch04-ch04)、[可观测性工具](#ch04-ch04)中引入了跟踪工具。
- **perf** (2.6.31)：Linux 性能事件 (perf) 是一组用于性能可观测性的工具，包括 CPU 性能计数器剖析以及静态和动态跟踪。有关介绍，请参见 [第 6 章](#ch06-ch06)、[CPU](#ch06-ch06)。
- **无 BKL** (2.6.37)：最终消除大内核锁 (BKL) 性能瓶颈。
- **透明大页面** (2.6.38)：这是一个便于使用大（巨型）内存页的框架。请参见 [第 7 章](#ch07-ch07)、[内存](#ch07-ch07)。
- **KVM**：基于内核的虚拟机 (KVM) 技术是由 Qumranet 为 Linux 开发的，该公司于 2008 年被 Red Hat 收购。KVM 允许创建虚拟操作系统实例，运行它们自己的内核。请参见 [第 11 章](#ch11-ch11)、[云计算](#ch11-ch11)。
- **BPF JIT** (3.0)：伯克利数据包过滤器 (BPF) 的即时 (JIT) 编译器，通过将 BPF 字节码编译为原生机器指令来提高数据包过滤性能。
- **CFS带宽控制**（3.2）：支持CPU配额和限制的CPU调度算法。
- **TCP 防缓冲区膨胀** (3.3+)：从 Linux 3.3 开始，针对缓冲区膨胀问题进行了各种增强，包括用于传输数据包数据的字节队列限制 (BQL) (3.3)、CoDel 队列管理 (3.5)、TCP 小队列 (3.6) 和增强型比例积分控制器 (PIE) 数据包调度程序 (3.14)。
- **[uprobes](#gloss-glo-187)** (3.5)：用于动态跟踪用户级软件的基础设施，由其他工具（perf、SystemTap 等）使用。
- **TCP 早期重传** (3.5)：RFC 5827 用于减少触发快速重传所需的重复确认。
- **TFO**（3.6、3.7、3.13）：TCP 快速打开 (TFO) 可以将 TCP 三次握手减少为带有 TFO cookie 的单个 SYN 数据包，从而提高性能。在 3.13 中它被设为默认值。
- **NUMA 平衡** (3.8+)：这为内核添加了自动平衡多 NUMA 系统上的内存位置的方法，减少了 CPU 互连流量并提高了性能。
- **SO\_REUSEPORT** (3.9)：一个套接字选项，允许多个侦听器套接字绑定到同一端口，从而提高多线程可扩展性。
- **SSD 缓存设备** (3.9)：设备映射器支持 SSD 设备用作速度较慢的旋转磁盘的缓存。
- **bcache** (3.10)：一种用于块接口的 SSD 缓存技术。
- **TCP TLP** (3.10)：TCP 尾部丢失探测 (TLP) 是一种通过在较短的探测超时后发送新数据或最后一个未确认的数据段来避免基于计时器的昂贵重传的方案，以触发更快的恢复。
- **NO\_HZ\_FULL** (3.10, 3.12)：也称为*无定时器多任务*或*无滴答内核*，这允许非空闲线程在没有时钟滴答的情况下运行，避免工作负载扰动 [\[Corbet 13a\]](#ch03-ch03ref13)。
- **多队列块 I/O** (3.13)：这提供了每个 CPU I/O 提交队列而不是单个请求队列，从而提高了可扩展性，特别是对于高 IOPS SSD 设备 [\[Corbet 13b\]](#ch03-ch03ref14)。
- **SCHED\_DEADLINE** (3.14)：实现最早截止时间优先 (EDF) 调度的可选调度策略 [\[Linux 20b\]](#ch03-ch03ref39)。
- **TCP 自动 corking** (3.14)：这允许内核合并小的写入，从而减少发送的数据包；它是 TCP\_CORK setsockopt(2) 的自动版本。
- **MCS 锁和 qspinlocks** (3.15)：高效的内核锁，使用诸如每 CPU 结构之类的技术。 MCS 以最初的锁发明者（Mellor-Crummey 和 Scott）的名字命名 [\[Mellor-Crummey 91\]](#ch03-ch03ref5)[\[Corbet 14\]](#ch03-ch03ref18)。
- **扩展 BPF** (3.18+)：用于运行安全内核模式程序的内核执行环境。大部分扩展 BPF 是在 4.x 系列中添加的。 3.19 中添加了对附加到 kprobes 的支持，4.7 中添加了对跟踪点的支持，4.9 中添加了对软件和硬件事件的支持，4.10 中添加了对 cgroup 的支持。 5.3 中添加了有界循环，这也增加了指令限制以允许复杂的应用程序。请参见 [第 3.4.4 节](#ch03-ch03lev4sec4)、[扩展 BPF](#ch03-ch03lev4sec4)。
- **Overlayfs** (3.18)：Linux 中包含的联合挂载文件系统。它在其他文件系统之上创建虚拟文件系统，而且可以在不修改底层文件系统的情况下修改这些虚拟文件系统。常用于容器。
- **DCTCP** (3.18)：数据中心 TCP (DCTCP) 拥塞控制算法，旨在提供较高的突发流量容忍度、低延迟和高吞吐量 [\[Borkmann 14a\]](#ch03-ch03ref16)。
- **DAX** (4.0)：直接访问 (DAX) 允许用户空间直接从持久内存存储设备读取数据，而无需缓冲区开销。 ext4 可以使用 DAX。
- **排队自旋锁** (4.2)：在争用情况下提供更好的性能，这些成为 4.2 中默认的自旋锁内核实现。
- **TCP 无锁侦听器** (4.4)：TCP 侦听器快速路径变得无锁，从而提高了性能。
- **cgroup v2**（4.5、4.15）：cgroup 的统一层次结构早已存在于早期内核中，并在 4.5 中被认为稳定且正式公开，称为 cgroup v2 [\[Heo 15\]](#ch03-ch03ref24)。cgroup v2 CPU 控制器于 4.15 加入。
- **epoll 可扩展性** (4.5)：为提高多线程可扩展性，epoll(7) 避免每次事件都唤醒等待同一组文件描述符的所有线程；后者会造成惊群性能问题 [\[Corbet 15\]](#ch03-ch03ref22)。
- **KCM** (4.6)：内核连接多路复用器 (KCM) 通过 TCP 提供基于消息的高效接口。
- **TCP NV** (4.8)：New Vegas (NV) 是一种新的 TCP 拥塞控制算法，适用于高带宽网络（以 10+ Gbps 运行的网络）。
- **XDP**（4.8、4.18）：eXpress 数据路径 (XDP) 是基于 BPF 的可编程快速路径，用于高性能网络 [\[Herbert 16\]](#ch03-ch03ref29)。 4.18 中添加了可以绕过大部分网络协议栈的 AF\_XDP 套接字地址族。
- **TCP BBR** (4.9)：瓶颈带宽和 RTT (BBR) 是一种 TCP 拥塞控制算法，可在遭受数据包丢失和缓冲区膨胀的网络上提供改进的延迟和吞吐量 [\[Cardwell 16\]](#ch03-ch03ref27)。
- **硬件延迟跟踪器** (4.9)：Ftrace 跟踪器，可以检测由硬件和固件引起的系统延迟，包括系统管理中断 (SMI)。
- **perf c2c** (4.10)：缓存到缓存 (c2c) perf 子命令可以帮助识别 CPU 缓存性能问题，包括伪共享。
- **英特尔 CAT** (4.10)：支持英特尔缓存分配技术 (CAT)，允许任务拥有专用的 CPU 缓存空间。容器可以利用它帮助解决“吵闹的邻居”问题。
- **多队列 I/O 调度器：BPQ、Kyber** (4.12)：预算公平队列 (BFQ) 多队列 I/O 调度器为交互式应用提供低延迟 I/O，尤其适合较慢的存储设备。BFQ 在 5.2 中得到显著改进。Kyber I/O 调度器适合快速多队列设备 [\[Corbet 17\]](#ch03-ch03ref30)。
- **内核 TLS** (4.13、4.17)：Linux 版本的内核 TLS [\[Edge 15\]](#ch03-ch03ref23)。
- **MSG\_ZEROCOPY** (4.14)：一个 send(2) 标志，用于避免应用程序和网络接口之间的数据包字节的额外副本 [\[Linux 20c\]](#ch03-ch03ref40)。
- **[PCID](#gloss-glo-121)** (4.14)：Linux 添加了对进程上下文 ID (PCID) 的支持，这是一种处理器 MMU 功能，有助于避免上下文切换时的 TLB 刷新。这降低了缓解Meltdown 漏洞所需的内核页表隔离（KPTI）补丁的性能成本。请参见 [第 3.4.3 节](#ch03-ch03lev4sec3)、[KPTI（Meltdown）](#ch03-ch03lev4sec3)。
- **PSI**（4.20、5.2）：压力停滞信息 (PSI) 是一组新指标，用于显示 因 CPU、内存或 I/O 资源压力而停滞的时间。 5.2 中添加了 PSI 阈值通知以支持 PSI 监控。
- **TCP EDT** (4.20)：TCP 协议栈切换到提前离开时间 (EDT)：它使用时间轮调度器发送数据包，从而提高 CPU 效率并缩短队列 [\[Jacobson 18\]](#ch03-ch03ref33)。
- **多队列 I/O** (5.0)：多队列块 I/O 调度器在 5.0 中成为默认调度器，经典调度器则被移除。
- **UDP GRO** (5.0)：UDP 通用接收卸载 (GRO) 允许驱动程序和网卡聚合数据包，再沿协议栈向上传递，从而提高性能。
- **io\_uring** (5.1)：一个通用异步接口，用于应用程序和内核之间的快速通信，利用共享环形缓冲区。主要用途包括快速磁盘和网络 I/O。
- **MADV\_COLD、MADV\_PAGEOUT** (5.4)：这些 madvise(2) 标志向内核提示：内存虽然需要，但近期不会使用。MADV\_PAGEOUT 还提示内核可以立即回收该内存。这些标志对于内存受限的嵌入式 Linux 设备尤其有用。
- **多路径 TCP** (5.6)：可以使用多个网络链接（例如 3G 和 WiFi）来提高单个 TCP 连接的性能和可靠性。
- **启动时跟踪** (5.6)：允许 Ftrace 跟踪早期启动过程。（systemd 可以提供后期启动过程的计时信息：请参阅 [第 3.4.2 节](#ch03-ch03lev4sec2)、[systemd](#ch03-ch03lev4sec2)。）
- **热压力** (5.7)：调度器会考虑因温度过高而降频，以便做出更好的任务放置决策。
- **perf 火焰图** (5.8)：perf(1) 支持火焰图可视化。

这里没有列出锁机制、驱动程序、VFS、文件系统、异步 I/O、内存分配器、NUMA、新处理器指令支持、GPU，以及 perf(1) 和 Ftrace 等性能工具方面的大量小型性能改进。采用 systemd 也改善了系统启动时间。

以下各节更详细地描述了对性能很重要的三个 Linux 主题：systemd、KPTI 和扩展 BPF。

### 3.4.2 systemd

systemd 是 Linux 常用的服务管理器，作为原始 UNIX init 系统的替代品开发。systemd 提供多种功能，包括感知依赖关系的服务启动和服务耗时统计。

系统性能中的一项偶尔任务是调整系统的启动时间，systemd 时间统计信息可以显示要调整的位置。可以使用 systemd-analyze(1) 报告总体启动时间：

![点此查看代码图片](../images/pg120-1.jpg)

```text
# systemd-analyze
Startup finished in 1.657s (kernel) + 10.272s (userspace) = 11.930s
graphical.target reached after 9.663s in userspace
```

此输出显示系统在 9.663 秒内完成启动（本例中到达 graphical.target）。使用 `critical-chain` 子命令可以查看更多信息：

![点此查看代码图片](../images/pg120-2.jpg)

```text
# systemd-analyze critical-chain
The time when unit became active or started is printed after the "@" character.
The time the unit took to start is printed after the "+" character.

graphical.target @9.663s
└─multi-user.target @9.661s
  └─snapd.seeded.service @9.062s +62ms
    └─basic.target @6.336s
      └─sockets.target @6.334s
        └─snapd.socket @6.316s +16ms
          └─sysinit.target @6.281s
            └─cloud-init.service @5.361s +905ms
              └─systemd-networkd-wait-online.service @3.498s +1.860s
                └─systemd-networkd.service @3.254s +235ms
                  └─network-pre.target @3.251s
                    └─cloud-init-local.service @2.107s +1.141s
                      └─systemd-remount-fs.service @391ms +81ms
                        └─systemd-journald.socket @387ms
                          └─system.slice @366ms
                            └─-.slice @366ms
```

此输出显示*关键路径*：导致延迟的步骤序列（在本例中为服务）。最慢的服务是 `systemd-networkd-wait-online.service`，启动时间为 1.86 秒。

还有其他有用的子命令：`blame` 显示最慢的初始化时间，`plot` 生成 SVG 图。有关详细信息，请参阅 systemd-analyze(1) 的手册页。

### 3.4.3 KPTI（Meltdown）

2018 年加入 Linux 4.14 的内核页表隔离 (KPTI) 补丁，是针对名为“Meltdown”的英特尔处理器漏洞的缓解措施。较旧的 Linux 内核版本有用于类似目的的 KAISER 补丁，其他内核也采用了相应的缓解措施。虽然这些措施解决了安全问题，但由于额外的 CPU 周期，以及上下文切换和系统调用时增加的 TLB 刷新，它们也会降低处理器性能。Linux 在同一版本中加入了进程上下文 ID (PCID) 支持；只要处理器支持 PCID，就可以避免部分 TLB 刷新。

我评估过 KPTI 对 Netflix 云生产工作负载的性能影响，结果在 0.1% 到 6% 之间，具体取决于工作负载的系统调用率（系统调用率越高，代价越大）[\[Gregg 18a\]](#ch03-ch03ref32)。进一步调优可以降低这项代价：使用大页面让刷新后的 TLB 更快预热，并使用跟踪工具检查系统调用，以找出降低调用率的方法。许多此类跟踪工具都是用扩展 BPF 实现的。

<!-- source-id: ch03#ch03lev4sec4 -->
### 3.4.4 扩展 BPF

BPF 是 Berkeley Packet Filter 的缩写。这项鲜为人知的技术最初开发于 1992 年，用于提高数据包捕获工具的性能 [\[McCanne 92\]](#ch03-ch03ref6)。2013 年，Alexei Starovoitov 提议对 BPF 进行重大重写 [\[Starovoitov 13\]](#ch03-ch03ref15)；之后他与 Daniel Borkmann 继续开发，并于 2014 年将其纳入 Linux 内核 [\[Borkmann 14b\]](#ch03-ch03ref17)。这使 BPF 变成了一个通用执行引擎，可用于网络、可观测性和安全等多种用途。

BPF 本身是一种灵活高效的技术，由指令集、存储对象（映射）和 helper 函数组成。由于拥有虚拟指令集规范，它可以被视为一台虚拟机。BPF 程序在内核模式下运行（如前面 [图 3.2](#ch03-ch03fig02) 所示），并被配置为响应各种事件：套接字事件、跟踪点、USDT 探针、kprobes、uprobes 和 perf\_events。这些组件显示在 [图 3.16](#ch03-ch03fig16) 中。

<!-- source-id: ch03#ch03fig16 -->
![图 3.16 BPF组件](../images/03fig16.jpg)

BPF 字节码首先必须通过验证器的安全检查，确保 BPF 程序不会使内核崩溃或破坏内核。它还可以使用 BPF 类型格式 (BTF) 系统来理解数据类型和结构。BPF 程序可以通过 perf 环形缓冲区（高效输出每个事件数据的方式）或通过适合统计用途的映射来输出数据。

由于 BPF 驱动着新一代高效、安全且先进的跟踪工具，因此它对系统性能分析十分重要。它为现有内核事件源提供了可编程能力：tracepoints、kprobes、uprobes 和 perf\_events。例如，BPF 程序可以在 I/O 开始和结束时记录时间戳，计算其持续时间，并将结果记录在自定义直方图中。本书包含许多使用 BCC 和 bpftrace 前端的 BPF 程序；这些前端见 [第 15 章](#ch15-ch15)。

## 3.5 其他主题

其他一些值得总结的内核和操作系统主题包括 PGO 内核、unikernel、微内核、混合内核和分布式操作系统。

### 3.5.1 PGO 内核

基于性能剖析的优化 (PGO) 也称为反馈导向优化 (FDO)，它使用 CPU 性能剖析信息改进编译器决策 [\[Yuan 14a\]](#ch03-ch03ref20)。它可以应用于内核构建，过程如下：

1. 在生产环境中采集 CPU 性能剖析数据。
2. 根据这些性能剖析数据重新编译内核。
3. 在生产环境中部署新内核。

这样可以为特定工作负载创建性能更好的内核。JVM 等运行时会自动执行类似操作：结合即时 (JIT) 编译，根据运行时性能重新编译 Java 方法。而创建 PGO 内核仍需手动完成这些步骤。

相关的编译优化是链接时优化 (LTO)，即一次编译整个二进制文件，以便在整个程序范围内进行优化。Microsoft Windows 内核大量使用 LTO 和 PGO；PGO 带来了 5% 到 20% 的性能提升 [\[Bearman 20\]](#ch03-ch03ref36)。Google 也使用 LTO 和 PGO 内核来提高性能 [\[Tolvanen 20\]](#ch03-ch03ref44)。

gcc 和 clang 编译器以及 Linux 内核都支持 PGO。内核 PGO 通常需要运行经过专门插桩的内核来收集剖析数据。Google 发布了 AutoFDO 工具，免去了对这种特殊内核的需求：AutoFDO 允许使用 perf(1) 从普通内核收集剖析数据，然后将其转换为编译器使用的正确格式 [\[Google 20a\]](#ch03-ch03ref37)。

关于使用 PGO 或 AutoFDO 构建 Linux 内核的唯一最新文档是 Microsoft [\[Bearman 20\]](#ch03-ch03ref36) 和 Google [\[Tolvanen 20\]](#ch03-ch03ref44) 在 Linux Plumber’s Conference 2020 上的两场演讲。[^fn-ch03-ch03-footnote-15]

<!-- source-id: ch03#ch03lev5sec2 -->
### 3.5.2 Unikernels

unikernel 是一种单应用机器映像，把内核、库和应用程序软件组合在一起，通常可以在硬件虚拟机或裸机上的单个地址空间中运行。这可能带来性能和安全优势：更少的指令代码意味着更高的 CPU 缓存命中率和更少的安全漏洞。但这也带来一个问题：系统中可能没有 SSH、shell 或性能工具可供登录和调试，也没有办法再把它们添加进去。

若要在生产环境中调优 unikernel 的性能，就必须构建支持它们的新性能工具和指标。作为概念验证，我构建了一个从 Xen dom0 运行的简易 CPU 性能剖析器，用于对 domU unikernel 客户机进行性能剖析，随后生成 CPU 火焰图，只为证明这确实可行 [\[Gregg 16a\]](#ch03-ch03ref28)。

unikernel 的示例包括 MirageOS [\[MirageOS 20\]](#ch03-ch03ref42)。

<!-- source-id: ch03#ch03lev5sec3 -->
### 3.5.3 微内核和混合内核

本章大部分内容讨论类 Unix 内核，也称为*单体内核*，其中所有管理设备的代码作为一个大型内核程序一起运行。对于*微内核*模型，内核软件被压缩到最低限度。微内核支持内存管理、线程管理和进程间通信 (IPC) 等基本功能；文件系统、网络协议栈和驱动程序则作为用户模式软件实现，因此更容易修改和替换这些组件。你不仅可以选择安装哪个数据库或 Web 服务器，还可以选择安装哪个网络协议栈。微内核还具有更高的容错能力：驱动程序崩溃不会导致整个内核崩溃。微内核的例子包括 QNX 和 Minix 3。

微内核的缺点是执行 I/O 和其他功能需要额外的 IPC 步骤，从而降低性能。一种解决方案是*混合内核*，结合微内核和单体内核的优点。混合内核把性能关键型服务移回内核空间（像单体内核一样使用直接函数调用，而非 IPC），同时保留微内核的模块化设计和容错能力。混合内核的例子包括 Windows NT 内核和 Plan 9 内核。

<!-- source-id: ch03#ch03lev5sec4 -->
### 3.5.4 分布式操作系统

分布式操作系统在一组联网的独立计算机节点上运行单个操作系统实例。每个节点上通常使用微内核。分布式操作系统的示例包括贝尔实验室的 Plan 9 和 Inferno 操作系统。

虽然是一种创新设计，但这种模型并未得到广泛应用。Plan 9 和 Inferno 的共同创始人 Rob Pike 描述了其中的各种原因 [\[Pike 00\]](#ch03-ch03ref9)：

“20 世纪 70 年代末和 80 年代初，有人声称 Unix 扼杀了操作系统研究，因为没人愿意尝试其他方案。当时我不相信这种说法。如今我不情愿地承认，它可能确实是真的（微软除外）。”

在云上，当今扩展计算节点的常见模型是在一组相同的操作系统实例之间实现负载平衡，这些实例可以根据负载进行扩展（请参阅 [第 11 章](#ch11-ch11)、[云计算](#ch11-ch11)、[第 11.1.3 节](#ch11-ch11lev1sec3)、[容量规划](#ch11-ch11lev1sec3)）。

## 3.6 内核比较

哪个内核最快？这部分取决于操作系统配置、工作负载以及内核参与了多少工作。总的来说，我预计 Linux 会胜过其他内核，因为它在性能改进、应用和驱动支持方面投入了大量工作，使用广泛，并拥有能够发现和报告性能问题的庞大社区。TOP500 列表自 1993 年开始追踪前 500 台超级计算机；到 2017 年，这些系统已全部采用 Linux [\[TOP500 17\]](#ch03-ch03ref31)。当然也有例外；例如，Netflix 在云端使用 Linux，而在 CDN 上使用 FreeBSD。[^fn-ch03-ch03-footnote-16]

通常使用微基准来比较内核性能，但这很容易出错。此类基准可能发现某个内核在特定系统调用上快得多，但生产工作负载根本没有使用该系统调用（或者确实使用了它，却带有微基准未测试的标志，而这些标志会极大影响性能）。准确比较内核性能是高级性能工程师的任务，可能需要数周时间。可将 [第 12 章](#ch12-ch12)、[基准测试](#ch12-ch12)、[第 12.3.2 节](#ch12-ch12lev3sec2)、[主动基准测试](#ch12-ch12lev3sec2) 作为应遵循的方法。

在本书第一版中，我在本节结尾指出，Linux 没有成熟的动态跟踪器；没有它，读者可能错失巨大的性能收益。第一版之后，我转而从事全职 Linux 性能工作，并帮助开发了 Linux 当时缺少的动态跟踪器：基于扩展 BPF 的 BCC 和 bpftrace。这些内容见 [第 15 章](#ch15-ch15) 以及我的前一本书 [\[Gregg 19\]](#ch03-ch03ref34)。

[第 3.4.1 节](#ch03-ch03lev4sec1)、[Linux 内核开发](#ch03-ch03lev4sec1) 列出了第一版与本版之间发生的许多其他 Linux 性能方面的发展，涵盖内核版本 3.1 到 5.8。前面未列出的一项重大发展是：OpenZFS 现在以 Linux 为主要支持内核，在 Linux 上提供了高性能且成熟的文件系统选项。

然而，Linux 的发展也带来了复杂性。Linux 拥有如此多的性能特性和可调参数，以至于针对每种工作负载分别配置和调优它们变得十分费力。我见过许多未经调优的部署。比较内核性能时请记住这一点：每个内核是否都经过了调优？本书后面的章节及其调优部分可以帮助你解决这个问题。

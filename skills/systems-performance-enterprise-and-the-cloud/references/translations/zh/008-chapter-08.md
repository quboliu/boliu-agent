# 第 8 章 — 文件系统

对于应用程序来说，文件系统性能通常比磁盘或存储设备性能更重要，因为应用程序是与文件系统交互并等待的。文件系统可以使用缓存、缓冲和异步 I/O 来避免应用程序遭受磁盘级（或远程存储系统）延迟。

系统性能分析和监控工具历来关注磁盘性能，而将文件系统性能视为盲点。本章重点介绍文件系统，展示它们的工作原理以及如何测量其延迟和其他细节。这通常可以排除文件系统及其底层磁盘设备作为性能不佳的根源，从而使调查能够转移到其他领域。

本章的学习目标是：

- 了解文件系统模型和概念。
- 了解文件系统工作负载如何影响性能。
- 熟悉文件系统缓存。
- 熟悉文件系统内部结构和性能特征。
- 遵循文件系统分析的各种方法。
- 测量文件系统延迟以识别延迟分布的峰和异常值。
- 使用跟踪工具调查文件系统的使用情况。
- 使用微基准测试文件系统性能。
- 了解文件系统可调参数。

本章由六部分组成，前三部分提供文件系统分析的基础，后三部分展示其在基于 Linux 的系统中的实际应用。各部分如下：

- **背景**介绍文件系统相关术语和基本模型，阐释文件系统原理和文件系统关键性能概念。
- **架构**介绍通用和特定的文件系统架构。
- **方法论**描述观测性和实验性的性能分析方法。
- **可观测性工具**展示基于 Linux 的系统上的文件系统可观测性工具，包括静态和动态插桩。
- **实验**总结文件系统基准测试工具。
- **调优**描述文件系统可调参数。

## 8.1 术语

作为参考，本章中使用的文件系统相关术语包括：

- **文件系统**：将数据组织为文件和目录，具有用于访问它们的基于文件的接口以及用于控制访问的文件权限。附加内容可能包括设备、套接字和管道的特殊文件类型，以及包括文件访问时间戳的元数据。
- **文件系统缓存**：主内存（通常是 DRAM）的一个区域，用于缓存文件系统内容，其中可能包括针对各种数据和元数据类型的不同缓存。
- **操作**：文件系统操作是对文件系统的请求，包括 read(2)、write(2)、open(2)、close(2)、stat(2)、mkdir(2) 等操作。
- **I/O**：输入/输出。文件系统 I/O 可以通过多种方式定义；这里仅指直接读写（执行 I/O）的操作，包括 read(2)、write(2)、stat(2)（读取统计信息）和 mkdir(2)（写入新目录项）。I/O 不包括 open(2) 和 close(2)（尽管这些调用会更新元数据并可能导致间接磁盘 I/O）。
- **逻辑 I/O**：应用程序向文件系统发出的 I/O。
- **物理 I/O**：文件系统直接向磁盘发出 I/O（或通过裸 I/O）。
- **块大小**：也称为*记录大小*，是文件系统在磁盘上使用的数据组大小。请参阅 [第 8.4.4 节](#ch08-ch08lev4sec4)、[文件系统特性](#ch08-ch08lev4sec4) 中的“块与区段”。
- **吞吐量**：应用程序和文件系统之间的当前数据传输速率，以每秒字节数为单位。
- **inode**：索引节点（inode）是包含文件系统对象元数据的数据结构，包括权限、时间戳和数据指针。
- **VFS**：虚拟文件系统，是用于抽象和支持不同文件系统类型的内核接口。
- **卷**：存储实例提供比使用整个存储设备更大的灵活性。卷可以是单个设备的一部分，也可以由多个设备组成。
- **卷管理器**：用于以灵活的方式管理物理存储设备的软件，创建“虚拟卷”以供操作系统使用。

本章将介绍其他术语。术语表包含供参考的基本术语，包括 *[fsck](#gloss-glo-067)*、*[IOPS](#gloss-glo-080)*、*操作速率*和 *POSIX*。另请参阅[第 2 章](#ch02-ch02)和[第 3 章](#ch03-ch03)中的术语部分。

## 8.3 概念

以下是一些重要的文件系统性能概念。

<!-- source-id: ch08#ch08lev3sec1 -->
### 8.3.1 文件系统延迟

文件系统延迟是文件系统性能的主要指标，衡量从逻辑文件系统请求发出到请求完成所经过的时间。它包括在文件系统和磁盘 I/O 子系统中花费的时间，以及等待磁盘设备（物理 I/O）的时间。应用程序线程通常会在处理请求期间阻塞，以等待文件系统请求完成；因此，文件系统延迟会*直接*且*成比例地*影响应用程序性能。

应用程序可能不会直接受到影响的情况包括使用非阻塞 I/O、预取（[第 8.3.4 节](#ch08-ch08lev3sec4)），以及从异步线程（例如后台刷新线程）发出 I/O。如果应用程序提供文件系统使用情况的详细指标，就可以从应用程序中识别这些情况。如果没有，通用方法是使用能够显示引发逻辑文件系统 I/O 的用户态堆栈跟踪的内核跟踪工具。然后可以研究该堆栈跟踪，以确定哪些应用程序例程发出了该 I/O。

操作系统历来没有让文件系统延迟易于观测，而是提供磁盘设备级统计数据。但在很多情况下，此类统计数据与应用程序性能无关，甚至会产生误导。例如，文件系统在后台刷新已写入的数据时，可能表现为高延迟磁盘 I/O 突发。从磁盘设备级统计来看，这很令人担忧；然而，没有应用程序在等待这些操作完成。更多案例请参见[第 8.3.12 节](#ch08-ch08lev3sec12)、[逻辑 I/O 与物理 I/O](#ch08-ch08lev3sec12)。

<!-- source-id: ch08#ch08lev3sec2 -->
### 8.3.2 缓存

文件系统通常会使用主存（RAM）作为缓存以提高性能。对于应用程序来说，这个过程是透明的：应用程序逻辑 I/O 的延迟会显著降低，因为请求可以由主存提供服务，而不必访问慢得多的磁盘设备。

随着时间的推移，缓存会增长，而操作系统可用的内存会减少。这可能会让新用户感到震惊，但完全正常。原则是：如果有空闲主存，就让它发挥作用。当应用程序需要更多内存时，内核应迅速从文件系统缓存中回收内存供其使用。

文件系统使用缓存来提高读取性能，并使用缓存中的缓冲来提高写入性能。文件系统和块设备子系统通常使用多种缓存，其中可能包括[表 8.1](#ch08-ch08tab01)中的缓存。

### 8.3.3 随机与顺序 I/O

根据每个 I/O 的文件偏移量，一系列逻辑文件系统 I/O 可以描述为“随机”或“顺序”。对于顺序 I/O，每个 I/O 偏移量从前一个 I/O 的末尾开始。随机 I/O 之间没有明显的关系，偏移量随机变化。随机文件系统工作负载也可以指随机访问许多不同的文件。

<!-- source-id: ch08#ch08fig04 -->
![图 8.4 顺序和随机文件 I/O](../images/08fig04.jpg)

[图 8.4](#ch08-ch08fig04)说明了这些访问模式，显示了一系列有序的 I/O 和示例文件偏移量。

由于某些存储设备（如[第 9 章](#ch09-ch09)、[磁盘](#ch09-ch09)中所述）的性能特征，文件系统历来尝试通过将文件数据按顺序、连续地放置在磁盘上来减少随机 I/O。“碎片”描述文件系统在这方面做得不好时的结果：文件散落在驱动器上，使顺序逻辑 I/O 产生随机物理 I/O。

文件系统可以测量逻辑 I/O 访问模式，以便识别顺序工作负载，然后使用预取或预读来提高其性能。这对于旋转磁盘很有帮助；对于闪存驱动器，帮助则较小。

<!-- source-id: ch08#ch08lev3sec4 -->
### 8.3.4 预取

常见的文件系统工作负载涉及顺序读取大量文件数据，例如，用于文件系统备份。该数据可能太大而无法放入缓存，或者可能只读取一次并且不太可能保留在缓存中（取决于缓存驱逐策略）。这样的工作负载性能相对较差，因为它的缓存命中率较低。

预取是解决此问题的常见文件系统功能。它可以根据当前和先前的文件 I/O 偏移量检测顺序读取工作负载，然后在应用程序请求磁盘读取之前预测并发出磁盘读取操作。这会填充文件系统缓存，因此，如果应用程序确实执行了预期的读取，则会导致缓存命中（所需的数据已在缓存中）。示例场景如下：

1. 应用程序发出文件 read(2)，将执行传递给内核。
2. 数据没有被缓存，因此文件系统将读取发出到磁盘。
3. 将前一个文件偏移指针与当前位置进行比较，如果它们是连续的，则文件系统发出附加读取（预取）。
4. 第一次读取完成，内核将数据和执行传递回应用程序。
5. 任何预取读取完成，填充缓存以供将来的应用程序读取。
6. 未来的顺序应用程序通过 RAM 中的缓存快速完成读取。

[图 8.5](#ch08-ch08fig05)也说明了这种情况：应用程序读取偏移量 1，然后读取偏移量 2，触发接下来三个偏移量的预取。

<!-- source-id: ch08#ch08fig05 -->
![图 8.5 文件系统预取](../images/08fig05.jpg)

当预取检测工作良好时，应用程序的顺序读取性能会显著提高；磁盘会领先于应用程序请求（前提是磁盘有足够带宽）。当预取检测效果不佳时，会发出应用程序不需要的 I/O，从而污染缓存并消耗磁盘和 I/O 传输资源。文件系统通常允许按需调节预取。

<!-- source-id: ch08#ch08lev3sec5 -->
### 8.3.5 预读

从历史上看，预取也被称为“预读”。 Linux 使用预读术语 readahead(2) 来表示系统调用，它允许应用程序显式预热文件系统缓存。

<!-- source-id: ch08#ch08lev3sec6 -->
### 8.3.6 回写式缓存

文件系统通常使用回写式缓存来提高写入性能。它的工作原理是在传输到主内存后将写入视为已完成，并在稍后*异步*将它们写入磁盘。将这些“脏”数据写入磁盘的文件系统过程称为“刷新”。示例序列如下：

1. 应用程序发出文件 write(2)，将执行传递给内核。
2. 将应用程序地址空间中的数据复制到内核。
3. 内核将 write(2) 系统调用视为已完成，并将执行传递回应用程序。
4. 稍后，异步内核任务找到写入的数据并发出磁盘写入。

权衡是可靠性。基于 DRAM 的主存储器具有易失性，一旦发生电源故障，脏数据可能会丢失。数据也可能“不完整”地写入磁盘，从而留下“损坏的”磁盘状态。

如果文件系统元数据损坏，文件系统可能不再加载。这种状态可能只能通过系统备份来恢复，从而导致停机时间延长。更糟糕的是，如果损坏影响应用程序读取和使用的文件内容，则业务可能会陷入危险。

为了平衡速度和可靠性的需求，文件系统可以默认提供回写缓存，以及“同步写入”选项来绕过此行为并直接写入持久存储设备。

<!-- source-id: ch08#ch08lev3sec7 -->
### 8.3.7 同步写入

仅当完全写入持久存储（例如磁盘设备）时，同步写入才会完成，其中包括写入任何必要的文件系统元数据更改。这些比异步写入（回写缓存）慢得多，因为同步写入会导致磁盘设备 I/O 延迟（并且可能由于文件系统元数据而导致多个 I/O）。同步写入由某些应用程序使用，例如数据库日志写入线程或进程，其中异步写入导致数据损坏的风险是不可接受的。

同步写入有两种形式：同步写入的单个 I/O 和同步提交的先前写入组。

<!-- source-id: ch08#ch08lev3_1 -->
#### 单独的同步写入

当使用标志 O\_SYNC 或其变体之一 O\_DSYNC 和 O\_RSYNC（从 Linux 2.6.31 开始由 glibc 映射到 O\_SYNC）打开文件时，写 I/O 是同步的。某些文件系统具有挂载选项，可强制所有文件的所有写入 I/O 同步。

<!-- source-id: ch08#ch08lev3_2 -->
#### 同步提交先前的写入

应用程序可以使用 fsync(2) 系统调用在代码中的检查点同步提交先前的异步写入，而不是同步写入单个 I/O。这可以通过对写入进行分组来提高性能，还可以通过取消被后续写入覆盖的中间写入来避免多次元数据更新。

还有其他情况会提交以前的写入，例如关闭文件句柄，或者文件上有太多未提交的缓冲区。前者在解压许多文件的存档时通常会出现长时间的暂停，尤其是通过 NFS。

<!-- source-id: ch08#ch08lev3sec8 -->
### 8.3.8 裸 I/O 与直接 I/O

这些是应用程序可以使用的其他类型的 I/O（如果内核或文件系统支持的话）：

**裸 I/O** 直接向磁盘指定偏移量发起 I/O，完全绕过文件系统。一些应用程序，尤其是数据库，会使用这种方式，因为它们能比文件系统缓存更好地管理和缓存自身的数据。缺点是软件更复杂，管理也更困难：常规文件系统工具无法用于备份、恢复或可观测性。

**直接 I/O** 允许应用程序使用文件系统但绕过文件系统缓存，例如，在 Linux 上使用 O\_DIRECT open(2) 标志。这类似于同步写入（但不具备 O\_SYNC 提供的保证），并且同样适用于读取。它不像裸设备 I/O 那样直接，因为文件偏移到磁盘偏移的映射仍须由文件系统代码执行；I/O 还可能被调整大小，以匹配文件系统磁盘布局使用的大小（记录大小），否则可能出错（EINVAL）。根据文件系统的不同，这不仅可能禁用读缓存和写缓冲，也可能禁用预取。

<!-- source-id: ch08#ch08lev3sec9 -->
### 8.3.9 非阻塞 I/O

通常，文件系统 I/O 要么立即完成（例如从缓存中完成），要么在等待之后完成（例如等待磁盘设备 I/O）。如果需要等待，应用程序线程会*阻塞*并脱离 CPU，让其他线程在等待期间执行。虽然被阻塞的线程无法执行其他工作，但这通常不是问题，因为多线程应用程序可以在线程阻塞时创建额外线程执行任务。

在某些情况下需要非阻塞 I/O，例如希望避免创建线程的性能或资源开销时。可以在 open(2) 系统调用中使用 O\_NONBLOCK 或 O\_NDELAY 标志启用非阻塞 I/O；此时读取和写入会返回 EAGAIN 错误而不是阻塞，告知应用程序稍后重试。（是否支持取决于文件系统；文件系统可能只对建议锁或强制锁支持非阻塞。）

操作系统还可以提供单独的异步 I/O 接口，例如 aio\_read(3) 和 aio\_write(3)。Linux 5.1 添加了名为 io\_uring 的新异步 I/O 接口，提高了易用性、效率和性能 [\[Axboe 19\]](#ch08-ch08ref16)。

非阻塞 I/O 也在[第 5 章](#ch05-ch05)、[应用程序](#ch05-ch05)、[第 5.2.6 节](#ch05-ch05lev2sec6)、[非阻塞 I/O](#ch05-ch05lev2sec6)中讨论过。

<!-- source-id: ch08#ch08lev3sec10 -->
### 8.3.10 内存映射文件

对于某些应用程序和工作负载，可以通过将文件映射到进程地址空间并直接访问内存偏移量来提高文件系统 I/O 性能。这避免了调用 read(2) 和 write(2) 系统调用来访问文件数据时产生的系统调用执行和上下文切换开销。如果内核支持直接将文件数据缓冲区映射到进程地址空间，还可以避免数据的双重复制。

内存映射使用 mmap(2) 系统调用创建，使用 munmap(2) 删除。可以使用 madvise(2) 调整映射，详见[第 8.8 节](#ch08-ch08lev8)、[调优](#ch08-ch08lev8)。某些应用程序提供在配置中使用 mmap 系统调用（可能称为“mmap 模式”）的选项。例如，Riak 数据库可以使用 mmap 作为其内存数据存储。

我注意到一种倾向：人们不先分析文件系统性能问题，就尝试使用 mmap(2) 解决它。如果问题是磁盘设备的 I/O 延迟很高，那么即使使用 mmap(2) 避免了微小的系统调用开销，只要高磁盘 I/O 延迟仍然存在并占主导地位，收效就可能甚微。

在多处理器系统上使用映射的一个缺点是保持每个 CPU 的 MMU 同步所需的开销，特别是为删除映射而进行的 CPU 间调用（*TLB shootdown*，使其他 CPU 上的相应 TLB 缓存项失效）。根据内核和映射方式，可以通过延迟 TLB 更新（*lazy shootdown*）[\[Vahalia 96\]](#ch08-ch08ref7) 将这些开销降至最低。

<!-- source-id: ch08#ch08lev3sec11 -->
### 8.3.11 元数据

*data* 描述文件和目录的内容，而 *metadata* 描述有关它们的信息。元数据可以指从文件系统接口（POSIX）读取的信息，也可以指实现文件系统磁盘布局所需的信息。这两类信息分别称为逻辑元数据和物理元数据。

<!-- source-id: ch08#ch08lev3_3 -->
#### 逻辑元数据

逻辑元数据是消费者（应用程序）读取和写入文件系统的信息，可以是：

- **显式：** 读取文件统计信息（stat(2)），创建和删除文件（creat(2)、unlink(2)）及目录（mkdir(2)、rmdir(2)），设置文件属性（chown(2)、chmod(2)）。
- **隐式：** 更新文件系统访问时间戳、目录修改时间戳、已用块位图，以及可用空间统计信息。

“元数据密集型”工作负载通常是指逻辑元数据，例如网络服务器以远高于读取文件内容的频率对文件执行 stat(2)，以确保文件自缓存以来没有发生变化。

<!-- source-id: ch08#ch08lev3_4 -->
#### 物理元数据

物理元数据是指记录所有文件系统信息所需的磁盘布局元数据。使用的元数据类型取决于文件系统，可能包括超级块、索引节点、数据指针块（主、辅助......）和空闲列表。

逻辑和物理元数据是逻辑 I/O 和物理 I/O 之间存在差异的原因之一。

<!-- source-id: ch08#ch08lev3sec12 -->
### 8.3.12 逻辑 I/O 与物理 I/O

尽管看起来违反直觉，但由于多种原因，应用程序向文件系统请求的 I/O（逻辑 I/O）可能与磁盘 I/O（物理 I/O）不匹配。

文件系统的功能远不止将持久存储（磁盘）呈现为基于文件的接口。它们会缓存读取、缓冲写入、将文件映射到地址空间，并产生额外的 I/O 来维护记录所有内容所需的磁盘物理布局元数据。与应用程序 I/O 相比，这可能导致磁盘 I/O 与应用程序无关、间接、隐式、膨胀或缩减。示例如下。

<!-- source-id: ch08#ch08lev3_5 -->
#### 不相关

这是与应用程序无关的磁盘 I/O，可能是由于：

- **其他应用**
- **其他租户**：磁盘 I/O 来自另一个云租户（通过某些虚拟化技术下的系统工具可见）。
- **其他内核任务**：例如，内核正在重建软件 RAID 卷或执行异步文件系统校验和验证时（请参阅[第 8.4 节](#ch08-ch08lev4)、[架构](#ch08-ch08lev4)）。
- **管理任务**：例如备份。

<!-- source-id: ch08#ch08lev3_6 -->
#### 间接

这是由应用程序引起的磁盘 I/O，但没有立即对应的应用程序 I/O。这可能是由于：

- **文件系统预取**：增加应用程序可能使用、也可能不使用的额外 I/O。
- **文件系统缓冲**：使用回写缓存来推迟和合并写入以便稍后刷新到磁盘。某些系统可能会在写入之前缓冲写入数十秒，然后这些写入会显示为大的、不频繁的突发。

<!-- source-id: ch08#ch08lev3_7 -->
#### 隐式

这是由应用程序事件直接触发的磁盘 I/O，而不是显式文件系统读写，例如：

- **内存映射加载/存储**：对于内存映射（mmap(2)）文件，加载和存储指令可能触发磁盘 I/O 来读取或写入数据。写入可能被缓冲，稍后才写入磁盘。在分析文件系统操作（read(2)、write(2)）却找不到 I/O 来源时，这可能令人困惑，因为 I/O 是由指令而不是系统调用触发的。

<!-- source-id: ch08#ch08lev3_8 -->
#### 缩减

磁盘 I/O 少于应用程序 I/O，甚至完全不存在。这可能是由于：

- **文件系统缓存**：从主存而不是磁盘满足读取请求。
- **文件系统写入取消**：相同的字节偏移量在一次刷新到磁盘之前被修改多次。
- **压缩**：减少从逻辑到物理 I/O 的数据量。
- **合并**：在将顺序 I/O 发送到磁盘之前合并它们（这会减少 I/O 计数，但不会减少总大小）。
- **内存中文件系统**：可能永远不会写入磁盘的内容（例如，tmpfs[^fn-ch08-ch08-footnote-1]）。

<!-- source-id: ch08#ch08lev3_9 -->
#### 膨胀

磁盘 I/O 大于应用程序 I/O。这是典型情况，原因如下：

- **文件系统元数据**：添加额外的 I/O。
- **文件系统记录大小**：将 I/O 大小向上取整（增加字节数），或拆分 I/O（增加次数）。
- **文件系统日志**：如果采用，这可以使磁盘写入加倍，一次写入日志，另一次写入最终目的地。
- **卷管理器奇偶校验**：读取-修改-写入周期，添加额外的 I/O。
- **RAID 膨胀**：写入额外的奇偶校验数据，或向镜像卷写入数据。

<!-- source-id: ch08#ch08lev3_10 -->
#### 示例

为了展示这些因素如何同时发生，以下示例描述了 1 字节应用程序写入时可能发生的情况：

1. 应用程序对现有文件执行 1 字节写入。
2. 文件系统将该位置标识为 128 KB 文件系统记录的一部分，该记录尚未缓存（但引用它的元数据已缓存）。
3. 文件系统请求从磁盘加载记录。
4. 磁盘设备层将 128 KB 读取分解为适合设备的较小读取。
5. 磁盘执行多次较小的读取，总计 128 KB。
6. 文件系统现在用新字节替换记录中的 1 个字节。
7. 稍后，文件系统或内核请求将 128 KB 脏记录写回磁盘。
8. 磁盘写入 128 KB 记录（如果需要，则进行分解）。
9. 文件系统写入新的元数据，例如，更新引用（用于写入时复制）或访问时间。
10. 磁盘执行更多写入操作。

因此，虽然应用程序仅执行一次 1 字节写入，但磁盘执行多次读取（总共 128 KB）和更多写入（超过 128 KB）。

<!-- source-id: ch08#ch08lev3sec13 -->
### 8.3.13 操作代价并不相同

从前面的部分可以清楚地看出，文件系统操作的性能取决于操作类型。仅从速率无法了解“每秒 500 次操作”的工作负载。某些操作可能以主存速度从文件系统缓存返回；另一些操作则可能从磁盘返回，速度慢几个数量级。其他决定因素包括操作是随机还是顺序、读取还是写入、同步写入还是异步写入、I/O 大小、是否包含其他操作类型、CPU 执行成本（以及系统的 CPU 负载）以及存储设备特性。

通常的做法是对不同的文件系统操作进行微基准测试，以确定这些性能特征。例如，[表 8.2](#ch08-ch08tab02)中的结果来自运行在空闲 Intel Xeon 2.4 GHz 多核处理器上的 ZFS 文件系统。

<!-- source-id: ch08#ch08tab02 -->
**表 8.2 文件系统操作延迟示例**

| **操作** | **平均值 (μs)** |
| --- | --- |
| open(2)（缓存[^fn-ch08-ch08-footnote-2]） | 2.2 |
| close(2)（干净[^fn-ch08-ch08-footnote-3]） | 0.7 |
| read(2) 4 KB（缓存） | 3.3 |
| read(2) 128 KB（缓存） | 13.9 |
| write(2) 4 KB（异步） | 9.3 |
| write(2) 128 KB（异步） | 55.2 |

这些测试不涉及存储设备，而是测试文件系统软件和 CPU 速度。一些特殊文件系统从不访问持久存储设备。

这些测试也是单线程的。并行 I/O 性能可能会受到所使用的文件系统锁的类型和组织的影响。

### 8.3.14 特殊文件系统

文件系统的目的通常是持久存储数据，但 Linux 上有一些特殊的文件系统类型用于其他目的，包括临时文件 (/tmp)、内核设备路径 (/dev)、系统统计信息 (/proc) 和系统配置 (/sys)。[^fn-ch08-ch08-footnote-4]

<!-- source-id: ch08#ch08lev3sec15 -->
### 8.3.15 访问时间戳

许多文件系统都支持访问时间戳，用于记录每个文件和目录被访问（读取）的时间。这会导致每次读取文件时都更新文件元数据，从而产生消耗磁盘 I/O 资源的写入工作负载。[第 8.8 节](#ch08-ch08lev8)、[调优](#ch08-ch08lev8)展示了如何关闭这些更新。

某些文件系统通过推迟和分组访问时间戳写入来优化访问时间戳写入，以减少对活动工作负载的干扰。

<!-- source-id: ch08#ch08lev3sec16 -->
### 8.3.16 容量

当文件系统填满时，性能可能会因多种原因而降低。首先，写入新数据时，可能需要更多的 CPU 时间和磁盘 I/O 来查找磁盘上的空闲块。[^fn-ch08-ch08-footnote-5] 其次，磁盘上的空闲空间区域可能更小且位置更稀疏，从而由于较小的 I/O 或随机 I/O 而降低性能。

这个问题的严重程度取决于文件系统类型、磁盘布局、写时复制的使用及其存储设备。下一节将介绍各种文件系统类型。

### 8.4.3 文件系统缓存

Unix 最初只有缓冲区缓存来提高块设备访问性能。如今，Linux 有多种不同的缓存类型。[图 8.8](#ch08-ch08fig08)概述了 Linux 上的文件系统缓存，显示了标准文件系统类型可用的通用缓存。

<!-- source-id: ch08#ch08fig08 -->
![图 8.8 Linux 文件系统缓存](../images/08fig08.jpg)

##### 缓冲区高速缓存

Unix 在块设备接口上使用缓冲区缓存来缓存磁盘设备块。这是一个独立的固定大小缓存；后来加入页面缓存后，在平衡两者之间的不同工作负载，以及处理双重缓存和同步开销时，出现了调优问题。这些问题在很大程度上通过使用页面缓存存储缓冲区缓存得到了解决。这种方法由 SunOS 引入，称为“统一缓冲区缓存”。

Linux 最初和 Unix 一样使用缓冲区缓存。从 Linux 2.4 开始，缓冲区缓存也存储在页面缓存中（因此[图 8.8](#ch08-ch08fig08)中的虚线边框），避免了双重缓存和同步开销。缓冲区缓存功能仍然存在，可以提高块设备 I/O 性能；该术语仍会出现在 Linux 可观测性工具中（例如 free(1)）。

缓冲区高速缓存的大小是动态的，可以从 /proc 中观察到。

##### 页面缓存

页面缓存于 1985 年虚拟内存重写期间首次引入 SunOS，并加入 SVR4 Unix \[Vahalia 96\]。它缓存虚拟内存页面，包括映射的文件系统页面，从而提高文件和目录 I/O 的性能。相较于每次查找都必须将文件偏移量转换为磁盘偏移量的缓冲区缓存，页面缓存访问文件更高效。多种文件系统类型都可以使用页面缓存，包括最初的使用者 UFS 和 NFS。它的大小是动态的：页面缓存会增长以利用可用内存，并在应用程序需要时再次释放内存。

Linux 也有具备相同属性的页面缓存。Linux 页面缓存的大小同样是动态的，并提供可调参数来设置从页面缓存逐出和交换之间的平衡（swappiness；请参阅[第 7 章](#ch07-ch07)、[内存](#ch07-ch07)）。

已变脏（已修改）且属于文件系统的内存页面由内核线程刷新到磁盘。在 Linux 2.6.32 之前，系统使用一个脏页刷新（*pdflush*）线程池，按需运行 2 到 8 个线程。此后，这些线程被回写线程（*flusher* 线程，名为 *flush*）取代；后者按设备创建，以更好地平衡各设备工作负载并提高吞吐量。页面因以下原因刷新到磁盘：

- 间隔一段时间后（30 秒）
- sync(2)、fsync(2)、msync(2) 系统调用
- 脏页太多（dirty\_ratio 和 dirty\_bytes 可调参数）
- 页面缓存中没有可用页面

如果系统内存不足，另一个内核线程——页面换出守护进程（*kswapd*，也称为*页面扫描器*）——也可能查找并安排脏页写入磁盘，以便释放内存页供重用（请参阅[第 7 章](#ch07-ch07)、[内存](#ch07-ch07)）。在可观测性方面，kswapd 和 flush 线程会作为内核任务出现在操作系统性能工具中。

有关页面扫描器的更多详细信息，请参阅[第 7 章](#ch07-ch07)、[内存](#ch07-ch07)。

##### 目录项缓存

*dentry 缓存*（Dcache） 会记住从目录条目（struct dentry）到 VFS inode 的映射，类似于早期的 Unix *目录名称查找缓存*（DNLC）。 Dcache 提高了路径名查找的性能（例如，通过 open(2)）：当遍历路径名时，每个名称查找都可以检查 Dcache 的直接 inode 映射，而不是单步遍历目录内容。 Dcache 条目存储在哈希表中，以便进行快速且可扩展的查找（按父目录项和目录条目名称进行哈希处理）。

多年来，性能得到了进一步提高，包括使用 *read-copy-update-walk*（RCU-walk）算法 [\[Corbet 10\]](#ch08-ch08ref11)。该算法尝试在不更新 dentry 引用计数的情况下遍历路径名；在多 CPU 系统上，路径名查找率较高时，缓存一致性会导致可扩展性问题。如果遇到不在缓存中的 dentry，RCU-walk 会退回较慢的引用计数遍历（ref-walk），因为文件系统查找和阻塞期间需要引用计数。对于繁忙工作负载，dentry 数据通常可能已经缓存，RCU-walk 方法也就能成功。

Dcache 还执行“负缓存”，它会记住对不存在条目的查找。这提高了查找失败的性能，这种情况在搜索共享库时通常会发生。

Dcache 会动态增长；当系统需要更多内存时，它通过 LRU（最近最少使用）收缩。其大小可以通过 /proc 看到。

##### 索引节点缓存

该缓存包含 VFS inode（struct inode），每个 inode 描述一个文件系统对象的属性，其中许多属性由 stat(2) 系统调用返回。文件系统工作负载经常访问这些属性，例如打开文件时检查权限，或在修改期间更新时间戳。这些 VFS inode 存储在哈希表中，以便快速、可扩展地查找（按 inode 编号和文件系统 superblock 哈希），不过大多数查找会通过 dentry 缓存完成。

inode 缓存动态增长，至少保存 Dcache 映射的所有 inode。当系统存在内存压力时，inode 缓存会收缩，丢弃没有关联 dentry 的 inode。其大小可以通过 /proc/sys/fs/inode\* 文件查看。

<!-- source-id: ch08#ch08lev4sec4 -->
### 8.4.4 文件系统特性

此处描述了影响性能的其他关键文件系统功能。

<!-- source-id: ch08#ch08lev3_11 -->
#### 块与区段

基于块的文件系统将数据存储在固定大小的块中，由存储在元数据块中的指针引用。对于大文件，这可能需要许多块指针和元数据块，而且块的位置可能变得分散，从而导致随机 I/O。一些基于块的文件系统尝试连续放置块来避免这种情况。另一种方法是使用*可变块大小*，这样随着文件增长可以使用更大的块，也能减少元数据开销。

基于区段的文件系统为文件预先分配连续空间（区段），并按需扩展这些区段。区段长度可变，可以表示一个或多个连续块。这样可以提高流式访问性能；由于文件数据更集中，也可以提高随机 I/O 性能。它还减少了需要跟踪的对象数量，从而改善元数据性能，同时不会像固定区段那样浪费未使用块的空间。

<!-- source-id: ch08#ch08lev3_12 -->
#### 日志记录

文件系统日志（或 *log*）记录对文件系统的更改，以便在系统崩溃或电源故障时原子地重放这些更改——要么全部成功，要么全部失败。这使文件系统能够快速恢复到一致状态。如果与更改相关的数据和元数据写入不完整，非日志文件系统可能在系统崩溃期间损坏。从此类崩溃中恢复需要遍历所有文件系统结构；对于大型（数 TB）文件系统，可能需要数小时。

日志会同步写入磁盘；对于某些文件系统，可以将其配置为使用单独的设备。有些日志同时记录数据和元数据，这会消耗更多存储 I/O 资源，因为所有 I/O 都会写入两次。另一些只写入元数据，并通过采用写时复制来维护数据完整性。

有一种文件系统类型几乎只包含日志：*日志结构文件系统*，其中所有数据和元数据更新都写入连续、循环的日志。这能优化写入性能，因为写入始终是顺序的，并且可以合并成更大的 I/O。

<!-- source-id: ch08#ch08lev3_13 -->
#### 写入时复制

写时复制 (COW) 文件系统不会覆盖现有块，而是遵循以下步骤：

1. 将块写入新位置（新副本）。
2. 更新对新块的引用。
3. 将旧块添加到空闲列表中。

这有助于在系统发生故障时保持文件系统的完整性，并且还可以通过将随机写入转变为顺序写入来提高性能。

当文件系统接近容量时，COW 可能会导致文件的磁盘数据布局碎片化，从而降低性能（尤其是 HDD）。文件系统碎片整理（如果可用）可能有助于恢复性能。

<!-- source-id: ch08#ch08lev3_14 -->
#### 数据清洗（scrubbing）

这是一项文件系统功能，会异步读取所有数据块并验证校验和，以尽早检测故障驱动器；理想情况下，此时由于 RAID 的存在，故障仍然可以恢复。但是，scrub 的读取 I/O 可能损害性能，因此应以低优先级运行，或安排在工作负载较低时运行。

<!-- source-id: ch08#ch08lev3_15 -->
#### 其他功能

其他可能影响性能的文件系统功能包括快照、压缩、内置冗余、重复数据删除、修剪支持等。以下部分描述了特定文件系统的各种此类功能。

### 8.4.5 文件系统类型

本章的大部分内容描述了可应用于所有文件系统类型的通用“特征”。以下各节总结了常用文件系统的具体性能特征。它们的分析和调整将在后面的章节中介绍。

<!-- source-id: ch08#ch08lev3_16 -->
#### FFS

许多文件系统最终都基于 Berkeley *快速文件系统*（FFS），该系统旨在解决原始 Unix 文件系统的问题。[^fn-ch08-ch08-footnote-6] 了解一些背景有助于解释当今文件系统的状态。

原始 Unix 文件系统的磁盘布局由 inode 表、512 字节存储块，以及分配资源时使用的信息超级块组成 [\[Ritchie 74\]](#ch08-ch08ref1)[\[Lions 77\]](#ch08-ch08ref2)。inode 表和存储块将磁盘分区分成两个区域，导致在两者之间寻道时出现性能问题。另一个问题是采用较小的固定块大小（512 字节），这限制了吞吐量，并增加了存储大文件所需的元数据（指针）数量。[\[McKusick 84\]](#ch08-ch08ref3)描述了将块大小加倍到 1024 字节的实验，以及随后遇到的瓶颈：

尽管吞吐量增加了一倍，旧文件系统仍然只使用了大约 4% 的磁盘带宽。主要问题是，尽管空闲列表最初按最佳访问顺序排列，但随着文件的创建和删除，它很快变得混乱。最终，空闲列表变得完全随机，导致文件块在磁盘上随机分配，从而迫使每次访问块之前都进行寻道。尽管旧文件系统刚创建时传输速率最高可达每秒 175 KB，但由于数据块位置随机化，适度使用几周后，速率会下降到每秒 30 KB。

这段摘录描述了空闲列表的*碎片化*：随着文件系统被使用，性能会随时间下降。

FFS 通过将分区划分为许多*柱面组*来提高性能，如[图 8.9](#ch08-ch08fig09)所示；每个柱面组都有自己的 inode 数组和数据块。文件 inode 和数据尽可能保留在同一个柱面组内，如[图 8.9](#ch08-ch08fig09)所示，从而减少磁盘寻道。其他相关数据也放在附近，包括目录及其目录项的 inode。inode 的设计类似，具有指针和数据块的层次结构，如[图 8.10](#ch08-ch08fig10)所示（三重间接块，即具有三级指针的块，此处未显示）[\[Bach 86\]](#ch08-ch08ref4)。

<!-- source-id: ch08#ch08fig09 -->
![图 8.9 柱面组](../images/08fig09.jpg)

<!-- source-id: ch08#ch08fig10 -->
![图 8.10 inode 数据结构](../images/08fig10.jpg)

块大小增加到至少 4 KB，从而提高了吞吐量。这减少了存储文件所需的数据块数量，因而减少了引用这些数据块所需的间接块数量。所需的间接指针块数量还因指针块变大而进一步减少。为了提高小文件的空间效率，每个块可以分成 1 KB 的片段。

FFS 的另一项性能特性是*块交错*：将连续文件块放置在磁盘上，并在它们之间留出一个或多个块的间隔 [\[Doeppner 10\]](#ch08-ch08ref12)。这些额外的块为内核和处理器发出下一次顺序文件读取争取了时间。如果没有交错，下一个块可能在系统准备发出读取之前就转过（旋转）磁头，导致系统等待磁盘完整旋转而产生延迟。

<!-- source-id: ch08#ch08lev3_17 -->
#### ext3

Linux 扩展文件系统（ext）于 1992 年开发，是 Linux 及其 VFS 的第一个文件系统，基于原始 Unix 文件系统。第二个版本 ext2（1993）加入了 FFS 的多种时间戳和柱面组。第三个版本 ext3（1999）加入了文件系统扩展和日志记录。

主要性能特性（包括自发布以来添加的特性）包括：

- **日志记录**：可以是仅记录元数据的*有序模式*，也可以是同时记录元数据和数据的*日志模式*。日志记录可提高系统崩溃后的启动性能，避免运行 fsck；还可以通过合并元数据写入来改善某些写入工作负载的性能。
- **日志设备**：可以使用外部日志设备，使日志工作负载不与读取工作负载争用。
- **Orlov 块分配器**：这会将顶级目录分布在柱面组之间，以便子目录和内容更有可能位于同一位置，从而减少随机 I/O。
- **目录索引**：这些将散列 B 树添加到文件系统中以加快目录查找速度。

mke2fs(8) 手册页中记录了可配置的功能。

<!-- source-id: ch08#ch08lev3_18 -->
#### ext4

Linux ext4 文件系统于 2008 年发布，通过新功能和性能改进扩展了 ext3：区段、大容量、使用 fallocate(2) 预分配、延迟分配、日志校验和、更快的 fsck、多块分配器、纳秒级时间戳和快照。

主要性能特性（包括自发布以来添加的特性）包括：

- **区段**：区段改善了连续放置，减少随机 I/O，并增大顺序 I/O 的 I/O 大小。相关内容见[第 8.4.4 节](#ch08-ch08lev4sec4)、[文件系统特性](#ch08-ch08lev4sec4)。
- **预分配**：通过 fallocate(2) 系统调用，应用程序可以预分配很可能连续的空间，从而提高后续写入性能。
- **延迟分配**：块分配延迟到数据刷新至磁盘时进行，允许将写入分组（通过*多块分配器*），从而减少碎片。
- **更快的 fsck**：标记未分配的块和 inode 条目，减少 fsck 时间。

某些功能的状态可以通过 /sys 文件系统查看。例如：

mke2fs(8) 手册页中记录了可配置的功能。某些功能（例如区段）也可以应用于 ext3 文件系统。

<!-- source-id: ch08#ch08lev3_19 -->
#### XFS

XFS 由 Silicon Graphics 于 1993 年为其 IRIX 操作系统创建，旨在解决此前 IRIX 文件系统 EFS（基于 FFS）的可扩展性限制 [\[Sweeney 96\]](#ch08-ch08ref6)。XFS 补丁在 2000 年代初合并进 Linux 内核。如今，大多数 Linux 发行版都支持 XFS，并可将其用作根文件系统。例如，Netflix 将 XFS 用于 Cassandra 数据库实例，因为它在该工作负载下性能很高（根文件系统则使用 ext4）。

主要性能特性（包括自发布以来添加的特性）包括：

- **分配组**：分区分为大小相等、可并行访问的分配组（AG）。为限制争用，每个 AG 的 inode 和空闲块列表等元数据独立管理，而文件和目录可以跨越多个 AG。
- **区段**：（请参阅前面对 ext4 的描述。）
- **日志记录**：日志记录提高了系统崩溃后的启动性能，避免运行 fsck(8)；还可以通过合并元数据写入来改善某些写入工作负载的性能。
- **日志设备**：可以使用外部日志设备，这样日志工作负载就不会与数据工作负载发生冲突。
- **条带分配**：如果文件系统创建在条带化 RAID 或 LVM 设备上，可以为数据和日志提供条带单元，以确保针对底层硬件优化数据分配。
- **延迟分配**：区段分配延迟到数据刷新至磁盘时进行，允许将写入分组并减少碎片。系统会在内存中为文件预留块，以便刷新时有可用空间。
- **在线碎片整理**：XFS 提供可在文件系统正常使用时运行的碎片整理工具。虽然 XFS 使用区段和延迟分配来防止碎片，但某些工作负载和条件仍可能造成文件系统碎片化。

mkfs.xfs(8) 手册页中记录了可配置的功能。XFS 的内部性能数据可以通过 /proc/fs/xfs/stat 查看。该数据专为高级分析而设计；有关详细信息，请参阅 XFS 网站 [\[XFS 06\]](#ch08-ch08ref9)[\[XFS 10\]](#ch08-ch08ref13)。

<!-- source-id: ch08#ch08lev3_20 -->
#### ZFS

ZFS 由 Sun Microsystems 开发并于 2005 年发布，将文件系统与卷管理器相结合，并包含众多企业级功能，因此成为文件服务器（*filer*）的有吸引力的选择。ZFS 以开源方式发布，并被多个操作系统使用，但通常作为附加组件提供，因为它采用 CDDL 许可证。大多数开发都发生在 OpenZFS 项目中；该项目于 2019 年宣布 Linux 为主要支持的操作系统 [\[Ahrens 19\]](#ch08-ch08ref15)。虽然 ZFS 在 Linux 中得到越来越多的支持和使用，但由于其源代码许可证，仍然存在阻力，其中包括 Linus Torvalds 的反对 [\[Torvalds 20a\]](#ch08-ch08ref20)。

ZFS 的主要性能特性（包括自发布以来添加的特性）包括：

- **池化存储**：所有分配的存储设备都放入一个池中，并从池中创建文件系统。这允许并行使用所有设备，以获得最大吞吐量和 IOPS。可以使用不同的 RAID 类型：0、1、10、Z（基于 RAID-5）、Z2（双重校验）和 Z3（三重校验）。
- **COW**：复制被修改的块，然后将它们分组并按顺序写入。
- **日志记录**：ZFS 将更改组成*事务组*（TXG）批量刷新；事务组整体成功或失败，从而使磁盘上的格式始终保持一致。
- **ARC**：自适应替换缓存同时使用多种缓存算法来获得高缓存命中率：最近使用（MRU）和最常使用（MFU）。系统根据两种算法的表现，在它们之间平衡主存；为此维护额外的元数据（*幽灵列表*），以了解如果某种算法占用全部主存时会有怎样的表现。
- **智能预取**：ZFS 会按需应用不同类型的预取：针对元数据、针对 znode（文件内容）以及针对 vdev（虚拟设备）。
- **多个预取流**：同一文件上的多个流式读取器可能使文件系统在它们之间寻道，从而产生随机 I/O 工作负载。ZFS 跟踪各个预取流，允许新的流加入已有流。
- **快照**：由于 COW 架构，快照几乎可以立即创建，从而将新块的复制推迟到需要时为止。
- **ZIO 流水线**：设备 I/O 由多个阶段组成的流水线处理，每个阶段由线程池提供服务，以提高性能。
- **压缩**：支持多种算法，但由于 CPU 开销，通常会降低性能。lzjb（Lempel-Ziv Jeff Bonwick）选项很轻量，通过减少 I/O 负载（因为数据被压缩）可能略微提高存储性能，但会消耗一些 CPU。
- **SLOG**：ZFS 独立意图日志允许将同步写入写到独立设备，从而避免与池磁盘工作负载争用。仅在系统发生故障时，才会读取写入 SLOG 的数据以进行重放。
- **L2ARC**：二级 ARC 是主存之后的第二级缓存，用于在基于闪存的固态硬盘（SSD）上缓存随机读取工作负载。它不缓冲写入工作负载，只包含已经驻留在存储池磁盘上的干净数据。它还可以复制 ARC 中的数据，使系统在主存刷新扰动后更快恢复。
- **重复数据删除**：一种文件系统级功能，可避免记录相同数据的多个副本。此功能对性能有显著影响，既有好处（减少设备 I/O），也有坏处（主存无法容纳哈希表时，设备 I/O 可能显著膨胀）。初始版本仅适用于预期哈希表始终能装入主存的工作负载。

与其他文件系统相比，ZFS 的一种行为可能降低性能：默认情况下，ZFS 向存储设备发出缓存刷新命令，以确保断电时写入已经完成。这是 ZFS 的完整性功能之一；但它有代价：必须等待缓存刷新的 ZFS 操作会产生延迟。

<!-- source-id: ch08#ch08lev3_21 -->
#### btrfs

B 树文件系统（btrfs）基于写时复制 B 树。这是一种现代的文件系统与卷管理器组合架构，类似于 ZFS，预计最终会提供类似的功能集。当前功能包括池化存储、大容量、区段、COW、卷扩展和收缩、子卷、块设备添加和删除、快照、克隆、压缩以及各种校验和（包括 crc32c、xxhash64、sha256 和 blake2b）。Oracle 于 2007 年开始开发它。

主要性能特点包括：

- **池化存储**：存储设备放置在组合卷中，并从中创建文件系统。这允许并行使用所有设备，以获得最大吞吐量和 IOPS。可以使用 RAID 0、1 和 10。
- **COW**：按顺序分组和写入数据。
- **在线平衡**：对象可以在存储设备之间移动以平衡其工作负载。
- **区段**：改善顺序布局和性能。
- **快照**：由于 COW 架构，快照几乎可以立即创建，从而将新块的复制推迟到需要时为止。
- **压缩**：支持 zlib 和 LZO。
- **日志记录**：可以为每个子卷创建日志树，以记录同步 COW 工作负载。

计划的性能相关功能包括 RAID-5 和 6、对象级 RAID、增量转储和重复数据删除。

<!-- source-id: ch08#ch08lev4sec6 -->
### 8.4.6 卷和池

从历史上看，文件系统构建在单个磁盘或磁盘分区上。卷和池允许在多个磁盘上构建文件系统，并可使用不同的 RAID 策略进行配置（请参阅[第 9 章](#ch09-ch09)、[磁盘](#ch09-ch09)）。

*卷*将多个磁盘呈现为一个虚拟磁盘，文件系统构建在该虚拟磁盘上。当基于整个磁盘（而不是切片或分区）构建时，卷可以隔离工作负载，减少争用带来的性能问题。

卷管理软件包括用于基于 Linux 的系统的逻辑卷管理器 (LVM)。卷或虚拟磁盘也可以由硬件 RAID 控制器提供。

*池化存储*包括存储池中的多个磁盘，可以从中创建多个文件系统。[图 8.11](#ch08-ch08fig11)展示了这种方式，并以卷作比较。池化存储比卷存储更灵活，因为无论底层设备如何，文件系统都可以扩展和收缩。现代文件系统（包括 ZFS 和 btrfs）都采用这种方式，LVM 也可以采用。

<!-- source-id: ch08#ch08fig11 -->
![图 8.11 卷和池](../images/08fig11.jpg)

池化存储可以让所有文件系统使用全部磁盘设备，从而提高性能。工作负载不会被隔离；在某些情况下，可以牺牲一定的灵活性使用多个池来分离工作负载，因为磁盘设备一开始必须放入某个池。请注意，池中的磁盘可以具有不同类型和大小，而卷中的磁盘可能被限制为统一规格。

使用软件卷管理器或池存储时的其他性能注意事项包括：

- **条带宽度**：将其与工作负载相匹配。
- **可观测性**：虚拟设备利用率可能会令人困惑；检查单独的物理设备。
- **CPU 开销**：特别是在执行 RAID 奇偶校验计算时。对于现代、更快的 CPU，这个问题已较少造成影响。 （奇偶校验计算也可以卸载到硬件 RAID 控制器。）
- **重建**：也称为*重新同步*（resilvering），指将空磁盘添加到 RAID 组（例如替换故障磁盘），并填入加入该组所需的数据。这会显著影响性能，因为它消耗 I/O 资源，可能持续数小时甚至数天。

重建是一个日益严重的问题，因为存储设备容量增长快于吞吐量，导致重建时间增加，也使重建期间发生故障或介质错误的风险更大。如果可能，对未挂载的驱动器执行离线重建可以缩短重建时间。

### 8.5.1 磁盘分析

常见的故障排除策略是忽略文件系统，关注[磁盘](#gloss-glo-047)性能。该策略假设最差的 I/O 是磁盘 I/O，因此只分析磁盘就能方便地聚焦于预期的问题根源。

对于更简单的文件系统和更小的缓存，这通常有效。如今，这种方法会造成混淆，并遗漏一整类问题（请参阅[第 8.3.12 节](#ch08-ch08lev3sec12)、[逻辑 I/O 与物理 I/O](#ch08-ch08lev3sec12)）。

<!-- source-id: ch08#ch08lev5sec2 -->
### 8.5.2 延迟分析

对于延迟分析，首先测量文件系统操作的延迟。这应该包括所有对象操作，而不仅仅是 I/O（例如包括 sync(2)）。

操作延迟 = 时间（操作完成）− 时间（操作请求）

这些时间可以从四个层级之一进行测量，如[表 8.4](#ch08-ch08tab04)所示。

<!-- source-id: ch08#ch08tab04 -->
**表 8.4 用于分析文件系统延迟的目标（层）**

| **层** | **优点** | **缺点** |
| --- | --- | --- |
| 应用程序 | 文件系统延迟对应用程序影响的最接近测量；还可以检查应用程序上下文以确定应用程序的主要功能期间是否发生延迟，或者是否是异步的。 | 技术因应用程序和应用程序软件版本而异。 |
| 系统调用接口 | 文档齐全的接口，通常可以通过操作系统工具和静态跟踪来观察。 | 系统调用会捕获所有文件系统类型，包括非存储文件系统（统计信息、套接字），除非过滤，否则可能造成混淆。更令人困惑的是，同一文件系统函数还可能对应多个系统调用。例如对 read 而言，可能有 read(2)、pread64(2)、preadv(2)、preadv2(2) 等，都需要测量。 |
| VFS | 适用于所有文件系统的标准接口；对文件系统操作的一次调用（例如 vfs\_write()） | VFS 跟踪所有文件系统类型，包括非存储文件系统，除非经过过滤，否则可能会造成混淆。 |
| 文件系统上层入口 | 仅跟踪目标文件系统类型；可获取文件系统内部上下文和扩展细节。 | 依赖具体文件系统；跟踪技术可能随文件系统软件版本而异（不过文件系统可能提供映射到 VFS 的类似接口，因此不会频繁变化）。 |

选择层可能取决于工具的可用性。检查以下内容：

- **应用程序文档**：某些应用程序已经提供文件系统延迟指标或启用其收集的能力。
- **操作系统工具**：操作系统还可以提供指标，理想情况下作为每个文件系统或应用程序的单独统计数据。
- **动态插桩**：如果您的系统具有动态插桩（Linux kprobes 和 uprobes，由各种跟踪器使用），则可以通过自定义跟踪程序检查所有层，而无需重新启动任何内容。

延迟可以表示为每个时间间隔的平均值、分布（例如直方图或热图；请参阅[第 8.6.18 节](#ch08-ch08lev6sec18)），也可以表示为每个操作及其延迟的列表。对于缓存命中率很高（超过 99%）的文件系统，每个时间间隔的平均值可能由缓存命中延迟主导。当存在孤立的高延迟实例（异常值）时，这很不理想：异常值很重要，却很难从平均值中看出。检查完整分布或逐操作延迟，可以调查这些异常值以及不同延迟层的影响，包括文件系统缓存命中和未命中。

发现高延迟后，继续深入分析文件系统以确定来源。

<!-- source-id: ch08#ch08lev3_22 -->
#### 事务开销

表示文件系统延迟的另一种方法是应用程序事务（例如数据库查询）期间等待文件系统所花费的总时间：

文件系统中的时间百分比 = 100 \* 总阻塞文件系统延迟 / 应用程序事务时间

这允许根据应用程序性能来量化文件系统操作的成本，并预测性能改进。该度量可以表示为某个时间间隔内所有事务或单个事务的平均值。

[图 8.12](#ch08-ch08fig12)展示了为事务提供服务的应用程序线程所花费的时间。该事务发出一次文件系统读取；应用程序阻塞并等待其完成，转而脱离 CPU。在这种情况下，总阻塞时间就是这次文件系统读取的时间。如果事务期间调用了多个阻塞 I/O，总时间就是它们的总和。

<!-- source-id: ch08#ch08fig12 -->
![图 8.12 应用程序和文件系统延迟](../images/08fig12.jpg)

作为一个具体示例，应用程序事务需要 200 毫秒，在此期间它在多个文件系统 I/O 上总共等待 180 毫秒。应用程序因文件系统而阻塞的时间占总耗时的 90% (100 \* 180 ms/200 ms)。消除文件系统延迟可将性能提高多达 10 倍。

再举一个例子，如果一个应用程序事务需要 200 毫秒，其中在文件系统中只花费了 2 毫秒，则文件系统以及整个磁盘 I/O 栈只为事务运行时间贡献了 1%。这个结果非常有用，因为它可以引导性能调查找到延迟的真正来源。

如果应用程序以“非阻塞”方式发出 I/O，则应用程序可以在文件系统响应时继续在 CPU 上执行。在这种情况下，阻塞文件系统延迟仅测量应用程序因阻塞而未在 CPU 上运行的时间。

<!-- source-id: ch08#ch08lev5sec3 -->
### 8.5.3 工作负载特征

在进行容量规划、基准测试和模拟工作负载时，表征所应用的负载是一项重要的工作。通过识别可以消除的不必要的工作，它还可以带来一些最大的性能提升。

以下是表征文件系统工作负载的基本属性：

- 操作速率和操作类型
- 文件 I/O 吞吐量
- 文件 I/O 大小
- 读/写比率
- 同步写入比率
- 随机与顺序文件偏移访问

操作速率和吞吐量在[第 8.1 节](#ch08-ch08lev1)、[术语](#ch08-ch08lev1)中定义。[第 8.3 节](#ch08-ch08lev3)、[概念](#ch08-ch08lev3)中描述了同步写入以及随机 I/O 与顺序 I/O。

这些特征可能会随时变化，特别是对于间隔执行的定时应用程序任务。为了更好地描述工作负载的特征，请捕获最大值和平均值。更好的是，检查值随时间的完整分布。

下面是一个工作负载描述示例，展示了如何一起表达这些属性：

在金融交易数据库上，文件系统承担随机读取工作负载，平均读取速率为每秒 18,000 次，平均读取大小为 4 KB。总操作速率为每秒 21,000 次，其中包括读取、统计、打开、关闭以及大约每秒 200 次同步写入。写入速率稳定，而读取速率会变化，最高可达每秒 39,000 次读取。

这些特征可以用单个文件系统实例或同一系统上同种类型文件系统的所有实例来描述。

<!-- source-id: ch08#ch08lev3_23 -->
#### 高级工作负载特征／清单

可能会包含其他详细信息来描述工作负载的特征。这些已在此处列出作为需要考虑的问题，也可以作为彻底研究文件系统问题时的清单：

- 文件系统缓存命中率是多少？未命中率是多少？
- 文件系统缓存容量和当前使用情况是多少？
- 还存在哪些其他缓存（目录、索引节点、缓冲区），以及它们的统计数据是什么？
- 过去是否尝试过调整文件系统？是否有任何文件系统参数设置为默认值以外的值？
- 哪些应用程序或用户正在使用该文件系统？
- 正在访问哪些文件和目录？创建和删除？
- 是否遇到任何错误？这是由于无效请求还是文件系统问题？
- 为什么会发出文件系统 I/O（用户态调用路径）？
- 应用程序直接（同步）请求文件系统 I/O 的程度如何？
- I/O 到达时间的分布如何？

其中许多问题可以针对每个应用程序或每个文件提出，也可以随时间检查，以找出最大值、最小值和随时间的变化。另请参阅[第 2.5.10 节](#ch02-ch02lev5sec10)、工作负载特征（位于[第 2 章](#ch02-ch02)、[方法论](#ch02-ch02)），其中提供了待测特征的高层摘要（谁、为什么、什么、如何）。

<!-- source-id: ch08#ch08lev3_24 -->
#### 性能表征

前面的工作负载特征列表检查了所应用的工作负载。下面检查最终的性能：

- 文件系统操作的平均延迟是多少？
- 是否存在高延迟异常值？
- 操作延迟的完整分布是怎样的？
- 文件系统或磁盘 I/O 的系统资源控制是否存在且处于活动状态？

可以针对每种操作类型分别询问前三个问题。

<!-- source-id: ch08#ch08lev3_25 -->
#### 事件追踪

跟踪工具可将所有文件系统操作及其详细信息记录到日志中，供日后分析。这可以包括每个 I/O 的操作类型、操作参数、文件路径、开始和结束时间戳、完成状态以及进程 ID 和名称。虽然这可能是工作负载特征分析的终极工具，但实际上，文件系统操作速率很高，会产生大量开销；除非严格过滤（例如只记录慢速 I/O，请参阅[第 8.6.14 节](#ch08-ch08lev6sec14)中的 ext4slower(8)工具），否则通常不切实际。

<!-- source-id: ch08#ch08lev5sec4 -->
### 8.5.4 性能监控

性能监控可以随着时间的推移识别活动问题和行为模式。文件系统性能的关键指标包括：

- 操作速率
- 操作延迟

操作速率是应用程序工作负载最基本的特征，而延迟是由此产生的性能指标。正常或糟糕的延迟值取决于工作负载、环境和延迟要求。如果不确定，可以对已知良好和不良的工作负载执行微基准来调查延迟（例如，通常命中文件系统缓存的工作负载与通常未命中的工作负载）。请参见[第 8.7 节](#ch08-ch08lev7)、[实验](#ch08-ch08lev7)。

操作等待时间度量可以作为每秒平均值来监控，并且可以包括其他值，例如最大值和标准偏差。理想情况下，可以检查延迟的完整分布，例如通过使用直方图或热图来查找异常值和其他模式。

还可以记录每种操作类型（读、写、统计、打开、关闭等）的速率和延迟。通过识别特定操作类型的差异，这样做将极大地帮助调查工作负载和性能变化。

对于实施基于文件系统的资源控制的系统，可以包含统计信息以显示是否以及何时使用限制。

不幸的是，在 Linux 中，通常没有现成的文件系统操作统计信息（例外情况包括，对于 NFS，通过 nfsstat(8)）。

<!-- source-id: ch08#ch08lev5sec5 -->
### 8.5.5 静态性能调优

静态性能调优重点关注配置环境的问题。对于文件系统性能，请检查静态配置的以下方面：

- 有多少文件系统已挂载并正在使用？
- 文件系统记录大小是多少？
- 是否启用访问时间戳？
- 启用了哪些其他文件系统选项（压缩、加密...）？
- 文件系统缓存是如何配置的？最大尺寸？
- 其他缓存（目录、索引节点、缓冲区）是如何配置的？
- 二级缓存是否存在并正在使用？
- 有多少个存储设备存在并且正在使用？
- 存储设备如何配置？RAID 配置是什么？
- 使用哪些文件系统类型？
- 文件系统（或内核）的版本是什么？
- 是否存在需要考虑的文件系统错误/补丁？
- 文件系统 I/O 是否使用资源控制？

回答这些问题可以揭示被忽视的配置选择。有时，系统已针对一种工作负载进行配置，然后重新用于另一种工作负载。此方法会提醒您重新审视这些选择。

<!-- source-id: ch08#ch08lev5sec6 -->
### 8.5.6 缓存调整

内核和文件系统可以使用许多不同的缓存，包括缓冲区缓存、目录缓存、inode 缓存和文件系统（页面）缓存。[第 8.4 节](#ch08-ch08lev4)、[架构](#ch08-ch08lev4)中描述了各种缓存。根据可用的可调选项，可以检查并经常调优这些缓存。

<!-- source-id: ch08#ch08lev5sec7 -->
### 8.5.7 工作负载分离

某些类型的工作负载在配置为使用自己的专用文件系统和磁盘设备时性能会更好。这种方法被称为使用“独立主轴”，因为在两个不同工作负载的位置之间寻道会产生随机 I/O，对旋转磁盘尤其不利（请参阅[第 9 章](#ch09-ch09)、[磁盘](#ch09-ch09)）。

例如，数据库可以受益于为其日志文件和数据库文件拥有单独的文件系统和磁盘。数据库的安装指南经常包含有关其数据存储的放置的建议。

<!-- source-id: ch08#ch08lev5sec8 -->
### 8.5.8 微基准测试

文件系统和磁盘基准测试工具（有很多）可用于测试给定工作负载下不同文件系统类型或文件系统内部设置的性能。可以测试的典型因素包括：

- **操作类型**：读取、写入和其他文件系统操作的速率
- **I/O 大小**：1 字节至 1 MB 及以上
- **文件偏移模式**：随机或顺序
- **随机访问模式**：均匀、随机或帕累托分布
- **写入类型**：异步或同步（O\_SYNC）
- **工作集大小**：工作集在文件系统缓存中的容纳程度
- **并发**：并行 I/O 数量或执行 I/O 的线程数量
- **内存映射**：通过 mmap(2) 进行文件访问，而不是 read(2)/write(2)
- **缓存状态**：文件系统缓存是“冷”（未填充）还是“热”
- **文件系统可调参数**：可能包括压缩、重复数据删除等

常见的组合包括随机读取、顺序读取、随机写入和顺序写入。我没有在此列表中包含直接 I/O，因为直接 I/O 微基准测试的目的是绕过文件系统并测试磁盘设备性能（请参阅[第 9 章](#ch09-ch09)、[磁盘](#ch09-ch09)）。

对文件系统进行微基准测试时，一个关键因素是“工作集大小”（WSS），即访问的数据量。根据基准测试，这可能是正在使用的文件的总大小。除非使用直接 I/O 标志，否则较小的工作集可能完全从主存（DRAM）中的文件系统缓存返回。较大的工作集可能主要从存储设备（磁盘）返回。性能差异可能达到几个数量级。针对刚挂载的文件系统运行基准测试，然后在缓存填充后再次运行并比较结果，通常可以很好地说明 WSS。（另请参阅[第 8.7.3 节](#ch08-ch08lev7sec3)、[缓存刷新](#ch08-ch08lev7sec3)。）

考虑[表 8.5](#ch08-ch08tab05)中不同基准测试的一般预期，其中包括文件总大小（WSS）。

<!-- source-id: ch08#ch08tab05 -->
**表 8.5 文件系统基准测试期望**

| **系统内存** | **总文件大小（WSS）** | **[基准测试](#gloss-glo-019)** | **预期** |
| --- | --- | --- | --- |
| 128 GB | 10 GB | 随机读取 | 100% 缓存命中 |
| 128 GB | 10 GB | 随机读取，直接 I/O | 100% 磁盘读取（由于直接 I/O） |
| 128 GB | 1,000 GB | 随机读取 | 主要是磁盘读取，约 12% 缓存命中 |
| 128 GB | 10 GB | 顺序读取 | 100% 缓存命中 |
| 128 GB | 1,000 GB | 顺序读取 | 缓存命中（大部分是由于预取）和磁盘读取的混合 |
| 128 GB | 10 GB | 缓冲写入 | 主要是缓存命中（缓冲），根据文件系统行为，写入会受到一些阻塞 |
| 128 GB | 10 GB | 同步写入 | 100% 磁盘写入 |

某些文件系统基准测试工具没有明确说明测试对象，可能暗示它们在测试“磁盘”，但使用的总文件大小很小，文件完全从缓存返回，实际上并未测试磁盘。请参阅[第 8.3.12 节](#ch08-ch08lev3sec12)、[逻辑 I/O 与物理 I/O](#ch08-ch08lev3sec12)，了解测试文件系统（逻辑 I/O）与测试磁盘（物理 I/O）的区别。

一些“磁盘”基准测试工具通过使用直接 I/O 的文件系统来避免缓存和缓冲。文件系统仍扮演次要角色，增加代码路径开销，以及文件位置到磁盘位置的映射差异。

有关这一主题的更多信息，请参阅[第 12 章](#ch12-ch12)、[基准测试](#ch12-ch12)。

### 8.6.1 mount

Linux mount(1) 命令列出已挂载的文件系统及其挂载标志：

![点此查看代码图片](../images/pg392-1.jpg)

```text
$ mount
/dev/nvme0n1p1 on / type ext4 (rw,relatime,discard)
devtmpfs on /dev type devtmpfs (rw,relatime,size=986036k,nr_inodes=246509,mode=755)

```

第一行显示，存储在 /dev/nvme0n1p1 上的 ext4 文件系统挂载于 /，挂载标志为 rw、relatime 和 discard。relatime 是一个性能改进选项，可减少 inode 访问时间更新及其后续磁盘 I/O 成本：只有在修改时间或变更时间更新时，或者距上次更新已超过一天时，才更新访问时间。

### 8.6.2 free

Linux free(1) 命令显示内存和交换统计信息。以下两个命令分别显示普通输出和宽输出（`-w`），单位均为兆字节（`-m`）：

![点此查看代码图片](../images/pg392-2.jpg)

```text
$ free -m
            total      used      free    shared  buff/cache   available
Mem:         1950       568       163         0        1218        1187
Swap:           0         0         0
$ free -mw
            total      used      free    shared     buffers       cache   available
Mem:         1950       568       163         0          84        1133        1187
Swap:           0         0         0
```

宽输出显示缓冲区缓存大小的 `buffers` 列和页面缓存大小的 `cached` 列；普通输出将两者合并为 `buff/cache`。

一个重要的列是 `available`（free(1) 的新增内容），它显示了应用程序无需交换即可使用的内存量。它考虑到了无法立即回收的内存。

这些字段也可以从 /proc/meminfo 中读取，它以千字节为单位提供它们。

### 8.6.5 sar

系统活动报告器 sar(1) 提供各种文件系统统计信息，并可配置为定期记录这些统计信息。本书各章都提到了 sar(1)，因为它提供不同的统计数据；它在[第 4.4 节](#ch04-ch04lev4)、[sar](#ch04-ch04lev4)中介绍过。

以一秒的间隔执行 sar(1) 以报告当前活动：

![点击查看代码图片](../images/pg393-3.jpg)

```text
# sar -v 1
Linux 5.3.0-1009-aws (ip-10-1-239-218)     02/08/20       _x86_64_  (2 CPU)

21:20:24    dentunusd   file-nr  inode-nr    pty-nr
21:20:25        27027      1344     52945         2
21:20:26        27012      1312     52922         2
21:20:27        26997      1248     52899         2
```

`-v` 选项提供以下列：

- **`dentunusd`**：目录条目缓存未使用计数（可用条目）

### 8.6.7 strace

可以使用包括 Linux strace(1) 在内的跟踪工具，在系统调用接口处测量文件系统延迟。然而，当前基于 ptrace(2) 的 strace(1) 实现可能严重损害性能，只有在可以接受其开销且无法使用其他方法分析延迟时才适合使用。有关 strace(1) 的更多信息，请参阅[第 5 章](#ch05-ch05)、[第 5.5.4 节](#ch05-ch05lev5sec4)、[strace](#ch05-ch05lev5sec4)。

此示例显示 strace(1) 在 ext4 文件系统上的计时读取：

![点此查看代码图片](../images/pg395-1.jpg)

```text
$ strace -ttT -p 845
[...]
18:41:01.513110 read(9, "\334\260/\224\356k..."..., 65536) = 65536 <0.018225>
18:41:01.531646 read(9, "\371X\265|\244\317..."..., 65536) = 65536 <0.000056>
18:41:01.531984 read(9, "\357\311\347\1\241..."..., 65536) = 65536 <0.005760>
18:41:01.538151 read(9, "*\263\264\204|\370..."..., 65536) = 65536 <0.000033>
18:41:01.538549 read(9, "\205q\327\304f\370..."..., 65536) = 65536 <0.002033>
18:41:01.540923 read(9, "\6\2738>zw\321\353..."..., 65536) = 65536 <0.000032>
```

`-tt` 选项在左侧打印相对时间戳，`-T` 在右侧打印系统调用时间。每次 read(2) 的数据量为 64 KB，第一次需要 18 毫秒，接下来是 56 微秒（可能已缓存），然后是 5 毫秒。读取的对象是文件描述符 9。要检查这是否是文件系统（而不是套接字），可以使用 open(2) 系统调用在早期的 strace(1) 输出中可见，或者可以使用其他工具，例如 lsof(8)。您还可以在 /proc 文件系统中找到有关 FD 9 的信息：/proc/845/fd{,info}/9}。

考虑到 strace(1) 当前的开销，测量的延迟可能会因观察者效应而产生偏差。查看更新的跟踪工具，包括 ext4slower(8)，它使用每 CPU 缓冲跟踪和 BPF 来大大减少开销，提供更准确的延迟测量。

### 8.6.8 fatrace

fatrace(1) 是一种使用 Linux fanotify API（文件访问通知）的专用跟踪器。输出示例：

![点此查看代码图片](../images/pg395-2.jpg)

```text
# fatrace
sar(25294): O /etc/ld.so.cache
sar(25294): RO /lib/x86_64-linux-gnu/libc-2.27.so
sar(25294): C /etc/ld.so.cache
sar(25294): O /usr/lib/locale/locale-archive
sar(25294): O /usr/share/zoneinfo/America/Los_Angeles
sar(25294): RC /usr/share/zoneinfo/America/Los_Angeles
sar(25294): RO /var/log/sysstat/sa09
sar(25294): R /var/log/sysstat/sa09
[...]
```

每行显示进程名称、PID、事件类型、完整路径和可选状态。事件类型可以是打开（O）、读取（R）、写入（W）和关闭（C）。fatrace(1) 可用于工作负载特征分析：了解访问了哪些文件，并查找可以消除的不必要工作。

然而，对于繁忙的文件系统工作负载，fatrace(1) 每秒可以生成数万行输出，并可能消耗大量 CPU 资源。过滤为单一事件类型可以在一定程度上缓解这种情况。基于 BPF 的跟踪工具（包括 opensnoop(8)，见[第 8.6.10 节](#ch08-ch08lev6sec10)）也能大幅降低开销。

<!-- source-id: ch08#ch08lev6sec9 -->
### 8.6.9 LatencyTOP

LatencyTOP 是用于报告系统范围及每个进程的延迟来源聚合的工具。它也会报告文件系统延迟。例如：

![点此查看代码图片](../images/pg396.jpg)

```text
Cause                                                Maximum     Percentage
Reading from file                                 209.6 msec         61.9 %
synchronous write                                  82.6 msec         24.0 %
Marking inode dirty                                 7.9 msec          2.2 %
Waiting for a process to die                        4.6 msec          1.5 %
Waiting for event (select)                          3.6 msec         10.1 %
Page fault                                          0.2 msec          0.2 %

Process gzip (10969)                       Total: 442.4 msec
Reading from file                                 209.6 msec         70.2 %
synchronous write                                  82.6 msec         27.2 %
Marking inode dirty                                 7.9 msec          2.5 %
```

上半部分是系统范围摘要，下半部分是正在压缩文件的单个 gzip(1) 进程。gzip(1) 的大部分延迟来自 70.2% 的 `Reading from file`；写入新的压缩文件时，`synchronous write` 占 27.2%。

LatencyTOP 由 Intel 开发，但已经有一段时间没有更新，网站也已下线。它还需要通常未启用的内核选项。[^fn-ch08-ch08-footnote-7] 使用 BPF 跟踪工具可能更容易测量文件系统延迟：请参阅[第 8.6.13 节](#ch08-ch08lev6sec13)至[第 8.6.15 节](#ch08-ch08lev6sec15)。

### 8.6.10 opensnoop

opensnoop(8)[^fn-ch08-ch08-footnote-8] 是 BCC 和 bpftrace 工具，用于跟踪打开的文件。它有助于发现数据文件、日志文件和配置文件的位置，也能发现频繁打开导致的性能问题，或帮助排查文件缺失问题。以下是一些示例输出，其中 `-T` 包含时间戳：

![点此查看代码图片](../images/pg397.jpg)

```text
# opensnoop -T

0.000000000   26447  sshd                5   0 /var/log/btmp
[...]
1.961686000   25983  mysqld              4   0 /etc/mysql/my.cnf
1.961715000   25983  mysqld              5   0 /etc/mysql/conf.d/
1.961770000   25983  mysqld              5   0 /etc/mysql/conf.d/mysql.cnf
1.961799000   25983  mysqld              5   0 /etc/mysql/conf.d/mysqldump.cnf
1.961818000   25983  mysqld              5   0 /etc/mysql/mysql.conf.d/
1.961843000   25983  mysqld              5   0 /etc/mysql/mysql.conf.d/mysql.cnf
1.961862000   25983  mysqld              5   0 /etc/mysql/mysql.conf.d/mysqld.cnf
[...]
2.438417000   25983  mysqld              4   0 /var/log/mysql/error.log
[...]
2.816953000   25983  mysqld             30   0 ./binlog.000024
2.818827000   25983  mysqld             31   0 ./binlog.index_crash_safe
2.820621000   25983  mysqld              4   0 ./binlog.index

```

此输出展示了 MySQL 数据库的启动过程；opensnoop(8) 显示了配置文件、日志文件、数据文件（二进制日志）等。

opensnoop(8) 仅通过跟踪 open(2) 变体系统调用来工作：open(2) 和 openat(2)。由于打开通常很少见，因此预计开销可以忽略不计。

BCC 版本的选项包括：

- **`-T`**：包括时间戳列
- **`-x`**：仅显示打开失败
- **`-p PID`**：仅跟踪此进程
- **`-n NAME`**：仅当进程名称包含 NAME 时显示打开的文件

`-x` 选项可用于故障排除：重点关注应用程序无法打开文件的情况。

### 8.6.11 filetop

filetop(8)[^fn-ch08-ch08-footnote-9] 是一个 BCC 工具，类似于针对文件的 top(1)，显示最常读取或写入的文件名。输出示例：

![点此查看代码图片](../images/pg398-1.jpg)

```text
# filetop

TID    COMM             READS  WRITES R_Kb    W_Kb    T FILE
23033  mysqld           481    0      7681    0       R sb1.ibd
23033  mysqld           3      0      48      0       R mysql.ibd
23032  oltp_read_only.  3      0      20      0       R oltp_common.lua
23031  oltp_read_only.  3      0      20      0       R oltp_common.lua
23032  oltp_read_only.  1      0      19      0       R Index.xml

23035  systemd-udevd    4      0      16      0       R sys_vendor

```

默认情况下，显示前二十个文件，按读取字节列排序。第一行显示 mysqld 从 sb1.ibd 文件中读取了 481 次，总计 7,681 KB。

该工具用于工作负载特征分析和一般文件系统可观测性。正如可以使用 top(1) 发现意外消耗 CPU 的进程一样，它也能帮助发现意外繁忙的 I/O 文件。

filetop 默认情况下也只显示常规文件。 `-a` 选项显示所有文件，包括 TCP 套接字和设备节点：

```text
23335  sshd             1      0      8       0       S TCP
1      systemd          4      0      4       0       R comm
[...]
```

输出现在包含其他文件类型 (`O`) 和套接字 (`S`)。在本例中，类型其他文件 ptmx 是 /dev 中的字符特殊文件。

选项包括：

- **`-C`**：不清除屏幕：滚动输出
- **`-a`**：显示所有文件类型
- **`-r ROWS`**：打印这么多行（默认 20）
- **`-p PID`**：仅跟踪此进程

除非使用 `-C`，否则屏幕每秒刷新一次（如 top(1)）。我更喜欢使用 `-C`，以便输出位于终端回滚缓冲区中，以防我稍后需要引用它。

### 8.6.12 cachestat

cachestat(8)[^fn-ch08-ch08-footnote-10] 是一个 BCC 工具，显示页面缓存命中和未命中统计信息。它可用于检查页面缓存的命中率和效率，也可在调查系统和应用程序调优时运行，以获得缓存性能反馈。输出示例：

![点此查看代码图片](../images/pg399.jpg)

```text
$ cachestat -T 1
```

此输出显示完全缓存的读取工作负载（`HITS` 具有 100% `HITRATIO`）和更高的写入工作负载（`DIRTIES`）。理想情况下，命中率接近 100%，以便应用程序读取不会因等待磁盘 I/O 而阻塞。

虽然该工具为页面缓存命中率提供了重要的见解，但它也是一个使用 kprobes 跟踪某些内核函数的实验性工具，因此需要维护才能在不同的内核版本上工作。更好的是，如果添加跟踪点或 /proc 统计信息，可以重写该工具以使用它们并变得稳定。今天它的最佳用途可能只是表明这样的工具是可能的。

### 8.6.15 bpftrace

bpftrace 是一种基于 BPF 的跟踪器，它提供了一种高级编程语言，允许创建强大的单行代码和短脚本。它非常适合根据其他工具的线索进行自定义文件系统分析。

bpftrace 在[第 15 章](#ch15-ch15)、[BPF](#ch15-ch15)中进行了解释。本节展示文件系统分析的一些示例：单行程序、系统调用跟踪、VFS 跟踪和文件系统内部结构。

#### 系统调用跟踪

系统调用是很好的跟踪目标，也是许多跟踪工具的插桩来源。然而，一些系统调用缺乏文件系统上下文，使得跟踪结果难以解释。我将分别给出一个可行的示例（openat(2) 跟踪）和一个不可行的示例（read(2) 跟踪），并提出补救措施。

##### openat(2)

跟踪 open(2) 系列系统调用可以显示打开的文件。如今 openat(2) 变体更常用。下面跟踪它：

![点此查看代码图片](../images/pg404-1.jpg)

```text

    str(args->filename)); }'
```

此输出捕获了用于归档统计数据的 sar(1) 的执行，以及它正在打开的文件。bpftrace 使用跟踪点提供的文件名参数；可以使用 -lv 列出所有参数：

![点此查看代码图片](../images/pg404-2.jpg)


这些参数是系统调用号、文件描述符、文件名、打开标志和打开模式；信息足够单行程序和 opensnoop(8) 等工具使用。

##### read(2)

read(2) 看起来应该是了解文件系统读取延迟的有用跟踪目标。但是，先看看它的跟踪点参数，问题就会显现：

![点此查看代码图片](../images/pg404-3.jpg)

```text
# bpftrace -lv t:syscalls:sys_enter_read
tracepoint:syscalls:sys_enter_read
    int __syscall_nr;
    unsigned int fd;
    char * buf;
    size_t count;
```

read(2) 可以用于文件系统、套接字、/proc 和其他目标，而其参数无法区分这些目标。为展示这有多混乱，下面按进程名统计 read(2) 系统调用：

![点此查看代码图片](../images/pg405-1.jpg)

```text
# bpftrace -e 't:syscalls:sys_enter_read { @[comm] = count(); }'
Attaching 1 probe...
^C

@[systemd-journal]: 13
@[sshd]: 141
@[java]: 3472
```

跟踪期间，Java 执行了 3,472 个 read(2) 系统调用，但这些调用来自文件系统、套接字还是其他对象？（sshd 的读取可能是套接字 I/O。）

read(2) 确实提供一个整数形式的文件描述符（FD），但它只是一个数字，并不显示 FD 类型（而且 bpftrace 运行在受限内核模式下，无法在 /proc 中查找 FD 信息）。至少有四种解决方案：

- 从 bpftrace 打印 PID 和 FD，然后使用 lsof(8) 或 /proc 查找 FD 以了解它们是什么。
- 即将推出的 BPF 助手 get\_fd\_path() 可以返回 FD 的路径名。这将有助于区分文件系统读取（具有路径名）与其他类型。
- 相反，从 VFS 进行跟踪，其中有更多数据结构可用。
- 直接跟踪文件系统函数，排除其他 I/O 类型。 ext4dist(8) 和 ext4slower(8) 使用此方法。

以下有关 VFS 延迟跟踪的部分展示了基于 VFS 的解决方案。

```text
#!/usr/local/bin/bpftrace
#include <linux/fs.h>

BEGIN
{
        printf("Tracing vfs_read() by type... Hit Ctrl-C to end.\n");
}

kprobe:vfs_read
{
        @file[tid] = ((struct file *)arg0)->f_inode->i_sb->s_type->name;
        @ts[tid] = nsecs;
}

kretprobe:vfs_read
/@ts[tid]/
{
        @us[str(@file[tid])] = hist((nsecs - @ts[tid]) / 1000);
        delete(@file[tid]); delete(@ts[tid]);
}

END
{
        clear(@file); clear(@ts);
}
```

#### ZFS

ZFS 附带 zpool(1M)，它具有用于观察 ZFS 池统计信息的 `iostat` 子选项。它报告池操作速率（读取和写入）和吞吐量。

一个流行的附加组件是 arcstat.pl 工具，它报告 ARC 和 L2ARC 大小以及命中率和未命中率。例如：

![点此查看代码图片](../images/pg410.jpg)

```text
$ arcstat 1
    time  read  miss  miss%  dmis  dm%  pmis  pm%  mmis  mm%  arcsz     c
04:45:47     0     0      0     0    0     0    0     0    0    14G   14G
04:45:49   15K    10      0    10    0     0    0     1    0    14G   14G
04:45:50   23K    81      0    81    0     0    0     1    0    14G   14G
04:45:51   65K    25      0    25    0     0    0     4    0    14G   14G
[...]
```

统计数据是每个时间间隔的：

- **`read, miss`**：ARC 访问总数、未命中次数
- **`miss, dm%, pm%, mm%`**：ARC 总未命中率，以及需求、预取、元数据未命中率
- **`dmis, pmis, mmis`**：需求、预取、元数据未命中次数
- **`arcsz, c`**：ARC 大小、ARC 目标大小

arcstat.pl 是一个从 kstat 读取统计信息的 Perl 程序。

### 8.6.18 可视化

应用于文件系统的负载可以随着时间的推移绘制为折线图，以帮助识别基于时间的使用模式。为读取、写入和其他文件系统操作绘制单独的图表可能很有用。

文件系统延迟的分布预计是双峰的：一个峰是文件系统缓存命中的低延迟峰，另一个峰是缓存未命中的高延迟峰（存储设备 I/O）。因此，将分布表示为单个值（例如均值、众数或中位数）会产生误导。

解决此问题的一种方法是使用显示完整分布的可视化效果，例如热图。[第 2 章](#ch02-ch02)、[方法论](#ch02-ch02)、[第 2.10.3 节](#ch02-ch02lev10sec3)、[热图](#ch02-ch02lev10sec3)介绍了热图。[图 8.13](#ch08-ch08fig13)展示了文件系统延迟热图示例：x 轴显示时间，y 轴显示 I/O 延迟 [\[Gregg 09a\]](#ch08-ch08ref10)。

此热图显示启用 L2ARC 设备对 NFSv3 延迟的影响。L2ARC 是主存之后的辅助 ZFS 缓存，通常使用闪存（见[第 8.3.2 节](#ch08-ch08lev3sec2)、[缓存](#ch08-ch08lev3sec2)）。[图 8.13](#ch08-ch08fig13)中的系统具有 128 GB 主存（DRAM）和 600 GB L2ARC（读取优化 SSD）。热图左半部分显示没有 L2ARC 设备（L2ARC 已禁用）时的延迟，右半部分显示启用 L2ARC 后的延迟。

<!-- source-id: ch08#ch08fig13 -->
![图 8.13 文件系统延迟热图](../images/08fig13.jpg)

对于左半部分，文件系统延迟要么低要么高，中间有一个间隙。低延迟是底部的蓝线，大约 0 毫秒，这可能是主内存缓存命中。高延迟从大约 3 毫秒开始，一直延伸到顶部，显示为“云”，这可能是旋转磁盘延迟。当由旋转磁盘支持时，这种双峰延迟分布是文件系统延迟的典型特征。

对于右半部分，L2ARC 已启用，延迟现在通常低于 3 毫秒，并且较高的磁盘延迟较少。您可以看到 L2ARC 的延迟如何填补热图左侧空白的范围，从而总体上减少文件系统延迟。

## 8.7 实验

本节介绍用于主动测试文件系统性能的工具。请参阅[第 8.5.8 节](#ch08-ch08lev5sec8)、[微基准测试](#ch08-ch08lev5sec8)，了解建议采用的策略。

使用这些工具时，最好让 iostat(1) 持续运行，以确认工作负载是否按预期到达磁盘——也可能根本没有到达。例如，测试能够轻松放入文件系统缓存的工作集时，读取工作负载预期会 100% 命中缓存，因此 iostat(1) 不应显示大量磁盘 I/O。iostat(1)见[第 9 章](#ch09-ch09)、[磁盘](#ch09-ch09)。

### 8.7.1 临时测试

dd(1) 命令（设备到设备复制）可用于执行顺序文件系统性能的临时测试。以下命令写入并读取名为 `file1` 且 I/O 大小为 1 MB 的 1 GB 文件：

![点此查看代码图片](../images/pg411.jpg)

```text
write: dd if=/dev/zero of=file1 bs=1024k count=1k
read: dd if=file1 of=/dev/null bs=1024k
```

Linux 版本的 dd(1) 在完成时打印统计信息。例如：

![点此查看代码图片](../images/pg412-1.jpg)

```text
$ dd if=/dev/zero of=file1 bs=1024k count=1k
1024+0 records in
1024+0 records out
1073741824 bytes (1.1 GB, 1.0 GiB) copied, 0.76729 s, 1.4 GB/s
```

这显示文件系统写入吞吐量为 1.4 GB/s（正在使用回写缓存，因此此次写入仅使内存中的页面变为脏页，稍后才刷新到磁盘，具体取决于 vm.dirty\_\* 可调参数；请参阅[第 7 章](#ch07-ch07)、[内存](#ch07-ch07)、[第 7.6.1 节](#ch07-ch07lev6sec1)、[可调参数](#ch07-ch07lev6sec1)）。

### 8.7.2 微基准测试工具

有许多可用的文件系统基准测试工具，包括 Bonnie、Bonnie++、iozone、tiobench、SysBench、fio 和 FileBench。下面按复杂性递增的顺序讨论其中一些工具。另请参见[第 12 章](#ch12-ch12)、[基准测试](#ch12-ch12)。我个人建议使用 fio。

#### Bonnie、Bonnie++

Bonnie 是一个简单的 C 程序，用于由单个线程测试单个文件上的多个工作负载。它最初由 Tim Bray 于 1989 年编写 [\[Bray 90\]](#ch08-ch08ref5)。用法很简单，不需要参数（将使用默认值）：

![点此查看代码图片](../images/pg412-2.jpg)

```text

```

输出包括每次测试期间的 CPU 时间；100% 表明 Bonnie 从未因磁盘 I/O 阻塞，而是始终命中缓存并运行在 CPU 上。原因是目标文件大小为 100 MB，该文件完全缓存于此系统中。可以使用 `-s size` 更改文件大小。

有一个名为 Bonnie-64 的 64 位版本，它允许测试更大的文件。还有一个 C++ 重写版本，名为 Bonnie++，由 Russell Coker [\[Coker 01\]](#ch08-ch08ref8) 编写。

#### FileBench

FileBench 是一个可编程文件系统基准测试工具，可以使用其工作负载模型语言描述应用程序工作负载并对其进行模拟。这允许模拟具有不同行为的线程，并指定同步线程行为。它附带各种称为“个性”的配置，其中包括模拟 Oracle 数据库 I/O 模型的配置。不幸的是，FileBench 并不容易学习和使用，可能只有全职从事文件系统工作的人才会感兴趣。

### 8.7.3 缓存刷新

Linux 提供了一种刷新（删除条目）文件系统缓存的方法，这对于从一致且“冷”的缓存状态进行性能基准测试很有用，就像系统启动后那样。内核源代码文档（Documentation/sysctl/vm.txt）对这一机制的描述非常简单：

![点此查看代码图片](../images/pg414.jpg)

```text
To free pagecache:
        echo 1 > /proc/sys/vm/drop_caches
To free reclaimable slab objects (includes dentries and inodes):
        echo 2 > /proc/sys/vm/drop_caches
To free slab objects and pagecache:
        echo 3 > /proc/sys/vm/drop_caches
```

在其他基准测试运行之前释放全部内容（3）尤其有用，可以让系统从一致的状态（冷缓存）开始，从而有助于获得一致的基准测试结果。

## 8.8 调优

许多调优方法（包括缓存调优和工作负载特征分析）已在[第 8.5 节](#ch08-ch08lev5)、[方法论](#ch08-ch08lev5)中介绍。后者通过识别和消除不必要的工作，往往能带来最大的性能收益。本节介绍特定的调优参数（可调参数）。

### 8.8.1 应用程序调用

[第 8.3.7 节](#ch08-ch08lev3sec7)、[同步写入](#ch08-ch08lev3sec7)提到，可以使用 fsync(2) 刷新逻辑写入组，从而改善同步写入工作负载的性能，而不必在使用 O\_DSYNC/O\_RSYNC open(2) 标志时逐个刷新。

其他可以提高性能的调用包括 posix_fadvise() 和 madvise(2)，它们提供有关缓存资格的提示。

<!-- source-id: ch08#ch08lev3_34 -->
#### posix\_fadvise()

该库调用是 fadvise64(2) 系统调用的包装器，作用于文件的某个区域，函数原型为：

![点此查看代码图片](../images/pg415-1.jpg)

```text
int posix_fadvise(int fd, off_t offset, off_t len, int advice);
```

这些建议如[表 8.8](#ch08-ch08tab08)所示。

<!-- source-id: ch08#ch08tab08 -->
**表 8.8 Linux posix\_fadvise() 建议标志**

| 建议 | 描述 |
| --- | --- |
| POSIX\_FADV\_SEQUENTIAL | 将顺序访问指定的数据范围。 |
| POSIX\_FADV\_RANDOM | 将随机访问指定的数据范围。 |
| POSIX\_FADV\_NOREUSE | 数据将不会被重用。 |
| POSIX\_FADV\_WILLNEED | 该数据将在不久的将来再次使用。 |
| POSIX\_FADV\_DONTNEED | 该数据近期不会再次使用。 |

内核可以使用这些信息来提高性能，帮助决定何时预取数据以及何时缓存数据。根据应用程序的建议，这可以提高高优先级数据的缓存命中率。有关建议参数的完整列表，请参阅系统上的手册页。

该系统调用作用于内存映射，其原型如下：

![点击查看代码图片](../images/pg415-2.jpg)


<!-- source-id: ch08#ch08tab09 -->
**表 8.9 Linux madvise(2) 建议标志**

| **建议** | **说明** |
| --- | --- |
| MADV\_RANDOM | 偏移量将以随机顺序访问。 |

与 posix\_fadvise() 一样，内核可以使用此信息来提高性能，包括做出更好的缓存决策。

```text
              Access time is only updated if the previous access time was ear-

              noatime, but it doesn't break mutt or  other  applications  that
              need  to know if a file has been read since the last time it was
              modified.)

              Since Linux 2.6.30, the kernel defaults to the behavior provided
              by   this   option  (unless  noatime  was  specified),  and  the
              strictatime option is required to obtain traditional  semantics.
              In  addition, since Linux 2.6.30, the file's last access time is
              always updated if it is more than 1 day old.
[...]
```

noatime 选项历来用于通过避免访问时间戳更新及其相关磁盘 I/O 来提高性能。如输出所述，relatime 现在是默认值，也能减少这些更新。

mount(8) 手册页涵盖通用挂载选项和文件系统特定的挂载选项；但对 ext4 而言，文件系统特定的挂载选项有自己的手册页 ext4(5)：

### 8.8.3 ZFS

ZFS 为每个文件系统提供大量可调参数（称为“属性”），其中少量参数可以在系统范围内设置。可以使用 zfs(1) 命令列出这些参数。例如：

![点击查看代码图片](../images/pg418.jpg)

```text
# zfs get all zones/var
NAME       PROPERTY              VALUE                  SOURCE
[...]
zones/var  recordsize            128K                   default
zones/var  mountpoint            legacy                 local
zones/var  sharenfs              off                    default
zones/var  checksum              on                     default
zones/var  compression           off                    inherited from zones
zones/var  atime                 off                    inherited from zones
[...]
```

（截断的）输出包括属性名称、当前值和来源列。来源显示属性的设置方式：是从更高级别的 ZFS 数据集继承、使用默认值，还是在该文件系统中本地设置。

还可以使用 zfs(1M) 命令设置参数，具体说明见其手册页。[表 8.10](#ch08-ch08tab10)列出了与性能相关的关键参数。

<!-- source-id: ch08#ch08tab10 -->
**表 8.10 关键 ZFS 数据集可调参数**

| **参数** | **选项** | **描述** |
| --- | --- | --- |
| recordsize | 512 至 128 K | 建议的文件块大小 |
| compression | on \| off \| lzjb \| gzip \| gzip-\[1–9\] \| zle \| lz4 | 轻量级算法（例如 lzjb）可以通过缓解后端 I/O 拥塞来提高某些情况下的性能 |
| atime | on \| off | 访问时间戳更新（导致读取后进行一些写入） |
| primarycache | all \| none \| metadata | ARC 策略；可以通过使用“none”或“metadata”（仅）来减少低优先级文件系统（例如档案）造成的缓存污染 |
| secondarycache | all \| none \| metadata | L2ARC 策略 |
| logbias | latency \| throughput | 同步写入建议：“latency”使用日志设备，而“throughput”使用池设备 |
| sync | standard \| always \| disabled | 同步写入行为 |

通常最重要的调优参数是与应用程序 I/O 匹配的记录大小。它通常默认为 128 KB，对小型随机 I/O 效率较低。请注意，这不适用于小于记录大小的文件；这类文件会以等于文件长度的动态记录大小保存。如果不需要访问时间戳，禁用 atime 也可以提高性能。

ZFS 还提供系统范围的可调参数，包括用于调整事务组 (TXG) 同步时间（zfs\_txg\_synctime\_ms、zfs\_txg\_timeout），以及 Metaslab 切换到空间而不是时间优化分配的阈值 (metaslab\_df\_free\_pct)。将 TXG 调小可以通过减少与其他 I/O 的争用和排队来提高性能。

与其他内核可调参数一样，请检查其文档以获取完整列表、描述和警告。

## 8.9 练习

1. 回答以下有关文件系统术语的问题：
    - 逻辑 I/O 和物理 I/O 之间有什么区别？
    - 随机 I/O 和顺序 I/O 之间有什么区别？
    - 什么是直接 I/O？
    - 什么是非阻塞 I/O？
    - 什么是工作集大小？
2. 回答以下概念性问题：
    - VFS 的作用是什么？
    - 描述文件系统延迟，特别是可以从哪里测量延迟。
    - 预取（预读）的目的是什么？
    - 直接 I/O 的目的是什么？
3. 回答以下更深层次的问题：
    - 描述使用 fsync(2) 相对于 O\_SYNC 的优点。
    - 描述 mmap(2) 相对于 read(2)/write(2) 的优缺点。
    - 描述逻辑 I/O 在变为物理 I/O 时变得“膨胀”的原因。
    - 描述逻辑 I/O 转换为物理 I/O 时变得“缩减”的原因。
    - 解释文件系统写时复制如何提高性能。
4. 为您的操作系统制定以下过程：
    - 文件系统缓存调整清单。这应该列出存在的文件系统缓存、如何检查它们当前的大小和使用情况以及命中率。
    - 文件系统操作的工作负载特征检查表。包括如何获取每个细节，并首先尝试使用现有的操作系统可观测性工具。
5. 执行以下任务：
    - 选择一个应用程序，并测量文件系统操作和延迟。包括：
          - 文件系统操作延迟的完整分布，而不仅仅是平均值。
          - 每个应用程序线程每秒花费在文件系统操作上的部分。
    - 使用微基准测试工具，通过实验确定文件系统缓存的大小。解释您在使用该工具时的选择。当工作集无法再完全容纳于缓存时，还显示性能下降（使用任何指标）。
6. （可选，高级）开发一个可观测性工具，为同步与异步文件系统写入提供指标。这应该包括它们的速率和延迟，并能够识别发出它们的进程 ID，使其适合工作负载特征分析。
7. （可选，高级）开发一个工具，提供间接和膨胀的文件系统 I/O 的统计信息：额外字节数，以及不是由应用程序直接发出的 I/O。该工具应该将这些额外 I/O 分解为不同类型，以解释其原因。

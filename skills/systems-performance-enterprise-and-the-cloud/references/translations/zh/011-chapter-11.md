# 第 11 章 — 云计算

云计算的兴起解决了性能领域的一些老问题，同时也产生了新问题。可以立即创建云环境并按需扩展，而无需构建和管理本地数据中心的典型开销。云还可以实现更好的部署粒度——服务器的一部分可以根据需要由不同的客户使用。然而，这也带来了挑战：虚拟化技术的性能开销以及与相邻租户的资源争用。

本章的学习目标是：

- 了解云计算架构及其性能影响。
- 了解虚拟化的类型：硬件、操作系统和轻量级硬件。
- 熟悉虚拟化内部结构，包括 I/O 代理的使用和调优技术。
- 了解每种虚拟化类型下不同工作负载的预期开销。
- 诊断宿主机和客户实例的性能问题，了解工具的使用如何根据所使用的虚拟化而变化。

虽然整本书都适用于云性能分析，但本章重点讨论云特有的性能主题：虚拟机管理程序和虚拟化如何工作、如何将资源控制应用于客户实例以及宿主机和客户实例的可观测性如何工作。云供应商通常会提供自己的自定义服务和 API，此处不予介绍：请参阅每个云供应商为其自己的服务集提供的文档。

本章由四个主要部分组成：

- **背景**呈现通用云计算架构及其性能影响。
- **硬件虚拟化**，虚拟机管理程序将多个客户操作系统实例作为虚拟机进行管理，每个实例都使用虚拟化设备运行自己的内核。本节以 Xen、KVM 和 Amazon Nitro 虚拟机管理程序为例。
- **操作系统虚拟化**，其中单个内核管理系统，创建彼此隔离的虚拟操作系统实例。本节以 Linux 容器为例。
- **轻量级硬件虚拟化**提供了两全其美的解决方案，其中轻量级硬件虚拟化实例使用专用内核运行，具有与容器类似的启动时间和密度优势。本部分使用 AWS Firecracker 作为示例管理程序。

虚拟化部分按照它们在云中广泛可用的时间排序。例如，Amazon Elastic Compute Cloud (EC2) 在 2006 年提供了硬件虚拟化实例，在 2017 年提供了操作系统虚拟化容器 (Amazon Fargate)，在 2019 年提供了轻量级虚拟机 (Amazon Firecracker)。

## 11.1 背景

云计算允许将计算资源作为服务提供，从服务器的一小部分扩展到多服务器系统。云的构建块取决于安装和配置了多少层软件。本章重点介绍以下云产品，它们都提供*服务器实例*，可能是：

- **硬件实例**：也称为“基础设施即服务”(IaaS)，使用硬件虚拟化提供。每个服务器实例都是一个虚拟机。
- **操作系统实例**：用于提供轻量级实例，通常通过操作系统虚拟化。

这些可以一起称为*服务器实例*、*云实例*或简称为*实例*。支持这些的云提供商的示例包括 Amazon Web Services (AWS)、Microsoft Azure 和 Google Cloud Platform (GCP)。还有其他类型的云原语，包括功能即服务 (FaaS)（请参阅[第 11.5 节](#ch11-ch11lev5)、[其他类型](#ch11-ch11lev5)）。

概括云计算的关键术语：*云计算*是为实例动态配置资源的框架。一个或多个实例作为物理*宿主机*（Host）上的*客户实例*（Guest）运行。客户实例也称为*租户*；*多租户*表示这些实例在同一宿主机上运行。宿主机可以由运营*公有云*的云提供商管理，也可以由您的公司管理，仅供内部使用，作为*私有云*的一部分。有些公司构建跨越公有云和私有云的*混合云*。[^fn-ch11-ch11-footnote-1] 云中的客户实例（租户）由其最终用户管理。

对于硬件虚拟化，一种称为“虚拟机管理程序”（或“虚拟机监视器”，VMM）的技术创建和管理“虚拟机”实例，这些实例显示为专用计算机，并允许安装整个操作系统和内核。

实例通常可以在几分钟或几秒钟内创建（和销毁）并立即投入生产使用。通常会提供*云 API*，以便其他程序可以自动执行此配置。

可以通过讨论各种与性能相关的主题来进一步理解云计算：实例类型、架构、容量规划、存储和多租户。以下各节总结了这些内容。

### 11.1.1 实例类型

云提供商通常提供不同的实例类型和大小。

某些实例类型是通用的并且在资源之间保持平衡。其他类型可能针对特定资源进行优化：内存、CPU、磁盘等。例如，AWS 将类型分组为“家族”（缩写为字母）和世代（数字），目前提供：

- **m5**：通用（平衡）
- **c5**：计算优化
- **i3、d2**：存储优化
- **r4、x1**：内存优化
- **p1、g3、f1**：加速计算（GPU、FPGA 等）

每个系列都有不同的规模。例如，AWS m5 系列的范围从 m5.large（2 个 vCPU 和 8 GB 主内存）到 m5.24xlarge（96 个 vCPU 和 384 GB 主内存）。

各种尺寸通常具有相当一致的性价比，允许客户选择最适合其工作负载的尺寸。

一些提供商（例如 Google Cloud Platform）还提供可以选择资源量的自定义机器类型。

有了如此多的选项以及重新部署实例的便利性，实例类型就变得像一个可根据需要进行修改的可调参数。与公司多年来可能无法改变的选择和订购物理硬件的传统企业模式相比，这是一个巨大的进步。

<!-- source-id: ch11#ch11lev1sec2 -->
### 11.1.2 可扩展架构

企业环境历来使用“垂直可扩展性”方法来处理负载：构建更大的单一系统（大型机）。这种方法有其局限性。计算机的物理尺寸存在实际限制（可能受到电梯门或集装箱尺寸的限制），并且随着 CPU 数量增加，维持 CPU 缓存一致性也越来越困难，供电和散热同样面临挑战。解决这些限制的方法是在许多（可能是小型）系统中扩展负载；这称为“水平可扩展性”。在企业中，它已用于计算机群和集群，特别是高性能计算（HPC，其使用早于云）。

云计算也基于水平可扩展性。[图 11.1](#ch11-ch11fig01) 中显示了一个示例环境，其中包括负载均衡器、Web 服务器、应用程序服务器和数据库。

<!-- source-id: ch11#ch11fig01 -->
![图 11.1 云架构：水平扩展](../images/11fig01.jpg)

每个环境层都由一个或多个并行运行的服务器实例组成，并添加更多服务器实例来处理负载。可以单独添加实例，也可以将架构划分为垂直分区，其中将由数据库服务器、应用程序服务器和 Web 服务器组成的组作为单个单元添加。[^fn-ch11-ch11-footnote-2]

该模型的一个挑战是传统数据库的部署，其中一个数据库实例必须是主要的。这些数据库（例如 MySQL）的数据可以在逻辑上分为称为“分片”的组，每个组都由自己的数据库（或主/辅助对）管理。分布式数据库架构（例如 Riak）动态处理并行执行，将负载分散到可用实例上。现在有专为在云上使用而设计的“云原生数据库”，包括 Cassandra、CockroachDB、Amazon Aurora 和 Amazon DynamoDB。

由于每台服务器实例的大小通常较小，例如 8 GB（在具有 512 GB 或更多 DRAM 的物理宿主机上），因此可以使用细粒度扩展来实现最佳性价比，而不是预先投资于可能大部分闲置的大型系统。

### 11.1.3 容量规划

本地服务器可能是一笔巨大的基础设施成本，无论是硬件还是可能持续数年的服务合同费用。新服务器投入生产也可能需要几个月的时间：花费时间在批准、等待部件可用性、运输、上架、安装和测试上。容量规划至关重要，因此可以购买适当大小的系统：太小意味着失败，太大则成本高昂（并且，根据服务合同，未来几年的成本可能会很高）。还需要进行容量规划，以便提前预测需求的增长，以便及时完成冗长的采购程序。

本地服务器和数据中心是企业环境的常态。云计算则非常不同。服务器实例价格低廉，并且几乎可以立即创建和销毁。公司无需花时间规划可能需要的内容，而是可以“根据需要”增加他们使用的服务器实例的数量，以应对实际负载。这可以根据性能监控软件的指标，通过云 API 自动完成。小型企业或初创公司可以从一个小型实例发展到数千个实例，而无需像企业环境中那样进行详细的容量规划研究。[^fn-ch11-ch11-footnote-3]

对于成长中的初创公司来说，另一个需要考虑的因素是代码更改的速度。站点通常每周、每天甚至每天多次更新其生产代码。容量规划研究可能需要数周时间，并且由于它基于性能指标的快照，因此在完成时可能已经过时。这与运行商业软件的企业环境不同，商业软件每年的变化可能不会超过几次。

在云中执行的容量规划活动包括：

- **动态调整大小**：自动添加和删除服务器实例
- **可扩展性测试**：短期购买大型云环境，以测试可扩展性与合成负载（这是一个*基准测试*活动）

考虑到时间限制，还可以对可扩展性进行建模（类似于企业研究），以估计实际可扩展性如何低于理论上的水平。

#### 动态调整规模（自动扩缩容）

云供应商通常支持部署可以随着负载增加而自动扩展的服务器实例组（例如，AWS *自动扩展组* (ASG)）。它还支持“微服务”架构，其中应用程序被分成更小的网络部分，这些部分可以根据需要单独扩展。

自动扩缩容可以解决快速响应负载变化的需求，但也存在“过度配置”的风险，如[图 11.2](#ch11-ch11fig02)所示。例如，DoS 攻击可能表现为负载增加，从而触发服务器实例的昂贵增加。应用程序更改也存在类似的风险，这些更改会导致性能下降，需要更多实例来处理相同的负载。监控对于验证这些增加是否有意义非常重要。

云提供商按小时、分钟甚至秒计费，允许用户快速扩展*和缩减*。当他们缩小规模时，可以立即实现成本节约。这可以自动化，以便实例计数与每日模式相匹配，仅根据需要为一天中的每一分钟配置足够的容量。[^fn-ch11-ch11-footnote-4] Netflix 为其云执行此操作，每天添加和删除数以万计的实例，以匹配其每日每秒流数模式；[图 11.3](#ch11-ch11fig03) 展示了一个示例[\[Gregg 14b\]](#ch11-ch11ref16)。

作为其他示例，2012 年 12 月，Pinterest 报告称，通过在下班后根据流量负载自动关闭云系统，将成本从 $54/hour 降至 $20/hour [\[Hoff 12\]](#ch11-ch11ref15)；2018 年，Shopify 迁移到云后也节省了大量基础设施成本：从平均空闲时间为 61% 的服务器迁移到平均空闲时间为 19% 的云实例 [\[Kwiatkowski 19\]](#ch11-ch11ref32)。性能调优也可以立即节省成本，因为它能减少处理负载所需的实例数量。

某些云架构（请参阅[第 11.3 节](#ch11-ch11lev3)、[操作系统虚拟化](#ch11-ch11lev3)）可以使用称为“突发”的策略立即动态分配更多 CPU 资源（如果可用）。这无需额外成本即可提供，旨在通过提供缓冲区来帮助防止过度配置，在此期间可以检查增加的负载以确定其是否真实且可能继续。如果是这样，可以配置更多实例，从而保证资源的继续使用。

这些技术中的任何一种都应该比企业环境高效得多，尤其是那些选择固定大小来处理服务器生命周期内预期峰值负载的技术：此类服务器可能大部分时间都处于空闲状态。

### 11.1.4 存储

云实例需要存储操作系统、应用软件和临时文件。在 Linux 系统上，这是根卷和其他卷。这可以由本地物理存储或网络存储来提供。该实例存储是易失性的，并且会在实例被销毁时被销毁（称为“临时驱动器”）。对于持久存储，通常使用独立的服务，它为实例提供存储作为：

- **文件存储**：例如，NFS 上的文件
- **块存储**：例如 iSCSI 上的块
- **对象存储**：通过 API，通常基于 HTTP

它们通过网络运行，并且网络基础设施和存储设备都与其他租户共享。由于这些原因，尽管可以通过云提供商使用资源控制来提高性能一致性，但性能的可预测性可能比本地磁盘低得多。

云提供商通常为此提供自己的服务。例如，Amazon 提供 Amazon Elastic File System (EFS) 作为文件存储、Amazon Elastic Block Store (EBS) 作为块存储以及 Amazon Simple Storage Service (S3) 作为对象存储。

[图 11.4](#ch11-ch11fig04)中显示了本地和网络存储。

通常通过对频繁访问的数据使用内存缓存来缓解网络存储访问延迟的增加。

当需要可靠的性能时，某些存储服务允许购买 IOPS 速率（例如，Amazon EBS 预置 IOPS 卷）。

### 11.1.5 多租户

Unix 是一个多任务操作系统，旨在处理访问相同资源的多个用户和进程。Linux 后来添加的功能提供了资源限制和控制，以更公平地共享这些资源，并提供可观测性，以便在出现涉及资源争用的性能问题时识别和量化。

云计算的不同之处在于整个操作系统实例可以共存于同一物理系统上。每个客户实例都是其自己的隔离操作系统：客户实例（通常为 [^fn-ch11-ch11-footnote-5]）无法观察同一宿主机上其他客户实例的用户和进程（这将被视为信息泄漏），即使它们共享相同的物理资源。

由于资源在租户之间共享，因此性能问题可能是由“吵闹的邻居”引起的。例如，同一宿主机上的另一个客户实例可能会在峰值负载期间执行完整数据库转储，从而干扰您的磁盘和网络 I/O。更糟糕的是，邻居可能会通过执行微基准来评估云提供商，这些微基准故意使资源饱和以找到其极限。

这个问题有一些解决方案。多租户效应可以通过*资源管理*来控制：设置提供*性能隔离*（也称为*资源隔离*）的操作系统*资源控制*。这是对系统资源的使用施加每个租户限制或优先级的地方：CPU、内存、磁盘或文件系统 I/O 以及网络吞吐量。

除了限制资源使用之外，能够观察多租户争用还可以帮助云运营商调整限制并更好地平衡可用宿主机上的租户。可观测性的程度取决于虚拟化类型。

### 11.1.6 编排（Kubernetes）

许多公司使用在自己的裸机或云系统上运行的“编排软件”来运行自己的私有云。最流行的此类软件是 Kubernetes（缩写为 k8s），最初由 Google 创建。Kubernetes（希腊语中意为“舵手”）是一个开源系统，它使用容器（通常是 Docker 容器，但任何实现开放容器接口的运行时也可以工作，例如 containerd）管理应用程序部署 [\[Kubernetes 20b\]](#ch11-ch11ref44)。公共云提供商还创建了 Kubernetes 服务来简化在其平台上的部署，包括 Google Kubernetes Engine (GKE)、Amazon Elastic Kubernetes Service (Amazon EKS) 和 Microsoft Azure Kubernetes Service (AKS)。

Kubernetes 将容器部署为称为 *Pods* 的共置组，其中容器可以共享资源并在本地（localhost）相互通信。每个 Pod 都有自己的 IP 地址，可用于通过网络与其他 Pod 通信。Kubernetes *服务*是由一组 Pod 提供的端点抽象，其元数据包括 IP 地址；它是这些端点的持久且稳定的接口，而 Pod 本身可以添加和删除，因此可将其视为一次性的。Kubernetes 服务支持微服务架构。Kubernetes 包括自动扩缩容策略，例如“Horizontal Pod Autoscaler”，可以根据目标资源利用率或其他指标调整 Pod 副本数量。在 Kubernetes 中，物理机称为“节点”；如果一组节点连接到同一个 Kubernetes API 服务器，则它们属于一个 Kubernetes“集群”。

Kubernetes 中的性能挑战包括调度（在集群上的何处运行容器以最大限度地提高性能）和网络性能，因为需要使用额外的组件来实现容器网络和负载平衡。

对于调度，Kubernetes 会考虑 CPU 和内存请求和限制，以及*节点污点*（其中节点被标记为从调度中排除）和*标签选择器*（自定义元数据）等元数据。Kubernetes 目前不限制块 I/O（将来可能会使用 blkio cgroup 添加对此的支持 [\[Xu 20\]](#ch11-ch11ref47)），从而使磁盘争用成为性能问题的可能根源。

对于网络，Kubernetes 允许使用不同的网络组件，确定使用哪个组件是确保最大性能的重要活动。容器网络可以通过插件容器网络接口（CNI）软件实现；示例 CNI 软件包括基于 netfilter 或 iptables 的 Calico，以及基于 BPF 的 Cilium。两者都是开源的 [\[Calico 20\]](#ch11-ch11ref35)[\[Cilium 20b\]](#ch11-ch11ref37)。为了实现负载平衡，Cilium 还提供了 kube-proxy 的 BPF 替代品 [\[Borkmann 19\]](#ch11-ch11ref28)。

## 11.2 硬件虚拟化

硬件虚拟化创建了一个可以运行整个操作系统（包括其自己的内核）的虚拟机（VM）。VM 由虚拟机管理程序创建，也称为虚拟机监视器（VMM）。虚拟机管理程序的常见分类将其标识为类型 1 或类型 2 [\[Goldberg 73\]](#ch11-ch11ref1)，它们是：

- **类型 1** 直接在处理器上执行。虚拟机管理程序可由有权创建并启动新客户机的特权客户机进行管理。类型 1 也称为“原生虚拟机监控器”或“裸机虚拟机监控器”。该虚拟机管理程序包含自己的客户虚拟机 CPU 调度程序。一个流行的例子是 Xen 虚拟机管理程序。
- **类型 2** 在宿主机操作系统中执行，该宿主机操作系统具有管理虚拟机管理程序和启动新客户机的权限。对于这种类型，系统启动传统操作系统，然后运行虚拟机管理程序。该虚拟机管理程序由宿主机内核 CPU 调度程序进行调度，而客户机在宿主机上显示为进程。

尽管您可能仍然会遇到术语“类型 1”和“类型 2”，但随着虚拟机管理程序技术的发展，这种分类已不再严格适用 [\[Liguori, 07\]](#ch11-ch11ref10)——通过使用内核模块，类型 2 已变得类似类型 1，使虚拟机管理程序的某些部分可以直接访问硬件。[图 11.5](#ch11-ch11fig05) 展示了更实用的分类，即我称为配置 A 和 B 的两种常见配置 \[Gregg 19\]。

<!-- source-id: ch11#ch11fig05 -->
![图 11.5 常见虚拟机管理程序配置](../images/11fig05.jpg)

这些配置是：

- **配置 A**：也称为原生虚拟机监控器或裸机虚拟机监控器。虚拟机管理程序软件直接在处理器上运行，创建用于运行客户虚拟机 的域，并将虚拟客户机 CPU 调度到真实 CPU 上。特权域（[图 11.5](#ch11-ch11fig05) 中的数字 0）可以管理其他域。一个流行的例子是 Xen 虚拟机管理程序。
- **配置 B**：虚拟机管理程序软件由宿主机操作系统内核执行，并且可以由内核级模块和用户级进程组成。宿主机操作系统具有管理虚拟机管理程序的权限，其内核调度 VM CPU 以及宿主机上的其他进程。通过使用内核模块，此配置还提供对硬件的直接访问。一个流行的例子是 KVM 虚拟机管理程序。

两种配置都可能涉及在域 0 (Xen) 或宿主机操作系统 (KVM) 中运行 I/O 代理（例如，使用 QEMU 软件），以服务客户机 I/O。这增加了 I/O 的开销，多年来已经通过添加共享内存传输和其他技术进行了优化。

最初的硬件虚拟机管理程序由 VMware 于 1998 年首创，使用“二进制转换”来执行完整的硬件虚拟化 [\[VMware 07\]](#ch11-ch11ref11)。这涉及在执行之前重写特权指令，例如系统调用和页表操作。非特权指令可以直接在处理器上运行。这提供了一个由虚拟化硬件组件组成的完整虚拟系统，可以在其上安装未经修改的操作系统。对于服务器整合带来的节省来说，这种高性能开销通常是可以接受的。

此后，这一问题得到了改进：

- **处理器虚拟化支持**：AMD-V 和 Intel VT-x 扩展于 2005-2006 年推出，旨在为处理器的 VM 操作提供更快的硬件支持。这些扩展提高了虚拟化特权指令和 MMU 的速度。
- **半虚拟化**（paravirt 或 PV）：提供一个虚拟系统，其中包括一个供客户操作系统有效使用宿主机资源的接口（通过 *hypercall*），而不需要所有组件的完全虚拟化。例如，启用定时器通常涉及多个必须由管理程序模拟的特权指令。这可以简化为单个超级调用，供半虚拟化客户机使用，以便管理程序更有效地进行处理。为了进一步提高效率，Xen 虚拟机管理程序将这些超级调用批处理为*多重调用（multicall）*。半虚拟化可以包括客户机使用半虚拟网络设备驱动程序来更有效地将数据包传递到宿主机中的物理网络接口。虽然性能得到了提高，但这依赖于客户操作系统对半虚拟化的支持（Windows 历史上从未提供过）。
- **设备硬件支持**：为了进一步优化虚拟机性能，处理器以外的硬件设备已经添加了虚拟机支持。这包括网络和存储设备的单根 I/O 虚拟化 (SR-IOV)，它允许客户虚拟机直接访问硬件。这需要驱动程序支持（示例驱动程序包括 ixgbe、ena、hv\_netvsc 和 nvme）。

多年来，Xen 不断发展并提高了其性能。现代 Xen VM 通常以硬件 VM 模式 (HVM) 启动，然后使用支持 HVM 的 PV 驱动程序来提高性能：一种称为 PVHVM 的配置。通过完全依赖某些驱动程序的硬件虚拟化（例如网络和存储设备的 SR-IOV），可以进一步改进这一点。

### 11.2.1 实施

硬件虚拟化有许多不同的实现方式，其中一些已经提到过（Xen 和 KVM）。例子有：

- **VMware ESX**：VMware ESX 于 2001 年首次发布，是一款用于服务器整合的企业产品，是 VMware vSphere 云计算产品的关键组件。它的虚拟机管理程序是在裸机上运行的微内核，第一个虚拟机称为“服务控制台”，它可以管理虚拟机管理程序和新虚拟机。
- **Xen**：Xen 于 2003 年首次发布，最初是剑桥大学的一个研究项目，后来被 Citrix 收购。Xen 是一个类型 1 虚拟机管理程序，可运行半虚拟化客户机以获得高性能；后来添加了对硬件辅助客户机的支持，以支持未经修改的操作系统（Windows）。虚拟机称为 *domains*，其中权限最高的是 *dom0*，虚拟机管理程序通过该域进行管理并启动新域。Xen 是开源的，可以从 Linux 启动。Amazon Elastic Compute Cloud (EC2) 以前基于 Xen。
- **Hyper-V**：Hyper-V 随 Windows Server 2008 一起发布，是一种类型 1 虚拟机管理程序，可为运行客户操作系统创建*分区*。Microsoft Azure 公共云可能正在运行 Hyper-V 的定制版本（具体细节尚未公开）。
- **KVM**：这是由 Qumranet 开发的，该公司是一家初创公司，于 2008 年被 Red Hat 收购。KVM 是一个类型 2 虚拟机管理程序，作为内核模块执行。它支持硬件辅助扩展，并且为了获得高性能，在客户操作系统支持的某些设备上使用半虚拟化。为了创建完整的硬件辅助虚拟机实例，它与称为 QEMU（快速仿真器）的用户进程配对；QEMU 是一个可以创建和管理虚拟机的 VMM（虚拟机管理程序）。QEMU 最初是一个使用二进制翻译的高质量开源类型 2 虚拟机管理程序，由 Fabrice Bellard 编写。KVM 是开源的，由 Google 用于 Google Compute Engine [\[Google 20c\]](#ch11-ch11ref39)。
- **Nitro**：该虚拟机管理程序由 AWS 于 2017 年推出，使用基于 KVM 的部件，并为所有主要资源提供硬件支持：处理器、网络、存储、中断和计时器 [\[Gregg 17e\]](#ch11-ch11ref22)。不使用 QEMU 代理。Nitro 为客户虚拟机提供近乎裸机的性能。

以下部分描述与硬件虚拟化相关的性能主题：开销、资源控制和可观测性。这些因实现及其配置而异。

<!-- source-id: ch11#ch11lev2sec2 -->
### 11.2.2 开销

了解虚拟化何时会产生性能开销、何时不会，对于调查云性能问题非常重要。

硬件虚拟化可以通过多种方式实现。资源访问可能需要虚拟机管理程序进行代理和转换，从而增加开销，或者它可以使用基于硬件的技术来避免这些开销。以下部分总结了 CPU 执行、内存映射、内存大小、执行 I/O 以及来自其他租户的争用的性能开销。

<!-- source-id: ch11#ch11lev3_2 -->
#### CPU

一般来说，客户机应用程序直接在处理器上执行，而受 CPU 限制的应用程序可能会体验到与裸机系统几乎相同的性能。在进行特权处理器调用、访问硬件和映射主内存时可能会遇到 CPU 开销，具体取决于管理程序如何处理它们。下面描述了不同硬件虚拟化类型如何处理 CPU 指令：

- **二进制翻译**：识别并翻译对物理资源进行操作的客户机内核指令。在硬件辅助虚拟化可用之前，就使用了二进制翻译。在没有虚拟化硬件支持的情况下，VMware 采用的方案是在处理器环 0 中运行 VMM，并将客户机内核移至此前未使用的环 1（应用程序运行在环 3；大多数处理器提供四个环；保护环在[第 3 章](#ch03-ch03)、[操作系统](#ch03-ch03)、[第 3.2.2 节](#ch03-ch03lev2sec2)、[内核态和用户态](#ch03-ch03lev2sec2)中介绍）。由于某些客户机内核指令假设它们在环 0 中运行，因此为了从环 1 执行，它们需要进行转换，调用 VMM，以便可以应用虚拟化。此转换在运行时执行，会消耗大量 CPU 开销。
- **半虚拟化**：客户操作系统中必须虚拟化的指令被对虚拟机管理程序的超级调用所取代。如果修改客户操作系统以优化超级调用，使其知道自己正在虚拟化硬件上运行，则可以提高性能。
- **硬件辅助**：在硬件上操作的未修改客户机内核指令由虚拟机管理程序处理，该虚拟机管理程序在低于环 0 的特权级别运行 VMM。客户机内核特权指令不是通过二进制翻译执行，而是被强制捕获到更高特权级别的 VMM，然后由 VMM 模拟这些特权操作以支持虚拟化 [\[Adams 06\]](#ch11-ch11ref4)。

硬件辅助虚拟化通常是首选，具体取决于实施和工作负载，而半虚拟化则用于提高某些工作负载（尤其是 I/O）的性能（如果客户操作系统支持）。

作为实现差异的一个例子，VMware 的二进制转换模型多年来一直在大力优化，正如他们在 2007 年 \[VMware 07\] 中所写：

由于管理程序到客户机转换的开销较高以及严格的编程模型，VMware 的二进制转换方法目前在大多数情况下优于第一代硬件辅助实现。第一代实现中的严格编程模型在管理虚拟机管理程序到客户机转换的频率或成本方面几乎没有留下软件灵活性的空间。

客户机和虚拟机管理程序之间的转换速率以及虚拟机管理程序中花费的时间可以作为 CPU 开销的指标进行研究。这些事件通常称为“客户机退出”，因为发生这种情况时虚拟 CPU 必须停止在客户机内部执行。[图 11.6](#ch11-ch11fig06) 显示了 KVM 内部与客户机退出相关的 CPU 开销。

![图 11.6 硬件虚拟化 CPU 开销](../images/11fig06.jpg)

该图显示了用户进程、宿主机内核和客户机之间的客户机退出流程。离开客户机、处理退出事件所花费的时间是硬件虚拟化的 CPU 开销；处理退出所花费的时间越多，开销就越大。当客户机退出时，部分事件可以直接在内核中处理。无法在内核中处理的事件必须离开内核并返回到用户进程；与内核可以处理的退出相比，这会导致更大的开销。

一种常见的客户机退出是 `halt` 指令，通常在内核找不到更多工作要执行时由空闲线程调用（这允许处理器在低功耗模式下运行，直到被中断）。它由 handle\_halt() 函数处理（见前面的 EXIT\_REASON\_HLT 列表），该函数最终调用 kvm\_vcpu\_halt()（arch/x86/kvm/x86.c）：

```text
int kvm_vcpu_halt(struct kvm_vcpu *vcpu)
{
        ++vcpu->stat.halt_exits;
        if (lapic_in_kernel(vcpu)) {
                vcpu->arch.mp_state = KVM_MP_STATE_HALTED;
                return 1;
        } else {
                vcpu->run->exit_reason = KVM_EXIT_HLT;
                return 0;
        }

```

与许多客户机退出类型一样，代码保持较小，以最大限度地减少 CPU 开销。此示例从 vcpu 统计增量开始，该增量跟踪发生了多少次暂停。其余代码执行该特权指令所需的硬件模拟。这些函数可以在 Linux 上使用虚拟机管理程序宿主机上的 kprobes 进行插桩，以跟踪它们的类型和退出持续时间。还可以使用 kvm:kvm\_exit 跟踪点全局跟踪退出，该跟踪点在[第 11.2.4 节](#ch11-ch11lev2sec4)、[可观测性](#ch11-ch11lev2sec4)中使用。

虚拟化中断控制器和高分辨率定时器等硬件设备也会产生一些 CPU（和少量内存）开销。

#### 内存映射

如[第 7 章](#ch07-ch07)、[内存](#ch07-ch07)中所述，操作系统与 MMU 一起创建从虚拟内存到物理内存的页面映射，并将它们缓存在 TLB 中以提高性能。对于虚拟化，将新的内存页面（缺页异常）从客户机映射到硬件涉及两个步骤：

1. 虚拟地址到客户机物理地址的转换，由客户机内核执行
2. 客户机物理到宿主机物理（实际）转换，由虚拟机管理程序 VMM 执行

然后，从客户机虚拟地址到宿主机物理地址的映射可以缓存在 TLB 中，以便后续访问可以正常速度运行，而不需要额外的转换。现代处理器支持 MMU 虚拟化，因此可以仅在硬件中更快地恢复已离开 TLB 的映射（页表遍历），而无需调用虚拟机管理程序。支持此功能的机制在 Intel 上称为“扩展页表”（EPT），在 AMD 上称为“嵌套页表”（NPT） [\[Milewski 11\]](#ch11-ch11ref13)。

如果没有 EPT/NPT，提高性能的另一种方法是维护客户虚拟机到宿主机物理映射的“影子页表”，这些映射由虚拟机管理程序管理，然后在客户机执行期间通过覆盖客户机的 CR3 寄存器进行访问。通过这种策略，客户机内核可以维护自己的页表，正常情况下，该页表从客户机虚拟地址映射到客户机物理地址。虚拟机管理程序拦截对这些页表的更改，并在影子页中创建到宿主机物理页的等效映射。然后，在客户机执行期间，管理程序会覆盖 CR3 寄存器以指向影子页面。

<!-- source-id: ch11#ch11lev3_4 -->
#### 内存大小

与操作系统虚拟化不同，使用硬件虚拟化时会有一些额外的内存消耗。每个客户机运行自己的内核，该内核消耗少量内存。存储架构还可能导致双重缓存，即客户机和宿主机都缓存相同的数据。 KVM 风格的虚拟机管理程序还为每个 VM 运行一个 VMM 进程，例如 QEMU，它本身会消耗一些主内存。

<!-- source-id: ch11#ch11lev3_5 -->
#### I/O

从历史上看，I/O 是硬件虚拟化的最大开销来源。这是因为每个设备 I/O 都必须由虚拟机管理程序进行转换。对于高频 I/O，例如 10 Gbit/s 网络，每个 I/O（数据包）的少量开销可能会导致整体性能显著下降。人们已经创建了一些技术来减轻这些 I/O 开销，最终通过硬件支持完全消除这些开销。此类硬件支持包括 I/O MMU 虚拟化（AMD-Vi 和 Intel VT-d）。

提高 I/O 性能的一种方法是使用半虚拟化驱动程序，它可以合并 I/O 并执行更少的设备中断，从而减少管理程序开销。

另一种技术是“PCI 直通”，它将 PCI 设备直接分配给客户机，因此可以像在裸机系统上一样使用它。 PCI 直通可以提供可用选项的最佳性能，但它会降低配置具有多个租户的系统时的灵活性，因为某些设备现在由客户机拥有并且无法共享。这也可能使实时迁移变得复杂 [\[Xen 19\]](#ch11-ch11ref33)。

有一些技术可以通过虚拟化来提高使用 PCI 设备的灵活性，包括单根 I/O 虚拟化（SR-IOV，前面提到过）和多根 I/O 虚拟化（MR-IOV）。这些术语指的是公开的根复合体 PCI 拓扑的数量，以不同的方式提供硬件虚拟化。 Amazon EC2 云一直采用这些技术来先加速网络，随后再加速存储 I/O，这些技术默认与 Nitro 虚拟机管理程序 \[Gregg 17e\] 一起使用。

GK 是“客户机内核”，BE 是“后端”。虚线箭头表示“控制路径”，其中组件以同步或异步方式相互通知更多数据已准备好传输。在某些情况下，*数据路径*（实线箭头）可以通过共享内存和环形缓冲区来实现。 Nitro 未显示控制路径，因为它使用相同的数据路径直接访问硬件。

配置 Xen 和 KVM 有不同的方法，此处未显示。该图显示了它们使用 I/O 代理进程（通常是 QEMU 软件），这些进程是为每个客户虚拟机 创建的。但它们也可以配置为使用 SR-IOV，允许客户虚拟机 直接访问硬件（[图 11.7](#ch11-ch11fig07) 中未显示 Xen 或 KVM 的这种配置）。Nitro 需要此类硬件支持，从而无需 I/O 代理。

Xen 使用*设备通道*（dom0 和客户机域（domU）之间的异步共享内存传输）提高了其 I/O 性能。这避免了在域之间传递 I/O 数据时创建额外的 I/O 数据副本所带来的 CPU 和总线开销。它还可以使用单独的域来执行 I/O，如[第 11.2.3 节](#ch11-ch11lev2sec3)、[资源控制](#ch11-ch11lev2sec3)中所述。

I/O 路径（控制和数据）中的步骤数量对于性能至关重要：越少越好。2006 年，KVM 开发人员将 Xen 等特权客户机系统与 KVM 进行了比较，发现 KVM 可以使用一半的步骤执行 I/O（五比十，尽管测试是在没有半虚拟化的情况下执行的，因此不能反映大多数现代配置）[\[Qumranet 06\]](#ch11-ch11ref6)。

由于 Nitro 虚拟机管理程序消除了额外的 I/O 步骤，我希望所有寻求最高性能的大型云提供商都会效仿，使用硬件支持来消除 I/O 代理。

<!-- source-id: ch11#ch11lev3_6 -->
#### 多租户争用

根据虚拟机管理程序配置以及租户之间共享的 CPU 和 CPU 缓存数量，可能会出现其他租户造成的 CPU 窃取时间和 CPU 缓存污染，从而降低性能。这对于容器来说通常是一个比虚拟机更大的问题，因为容器促进这种共享以支持 CPU 爆发。

执行 I/O 的其他租户可能会导致执行中断，具体取决于虚拟机管理程序配置。

资源争用可以通过资源控制来管理。

<!-- source-id: ch11#ch11lev2sec3 -->
### 11.2.3 资源控制

作为客户机配置的一部分，CPU 和主内存通常配置有资源限制。虚拟机管理程序软件还可以提供对网络和磁盘 I/O 的资源控制。

对于类似 KVM 的虚拟机管理程序，宿主机操作系统最终控制物理资源；除了虚拟机管理程序提供的控制之外，操作系统提供的资源控制也可以应用于客户机。对于 Linux，这意味着 cgroup、任务集和其他资源控制。有关宿主机操作系统可用的资源控制的更多信息，请参阅[第 11.3 节](#ch11-ch11lev3)、[操作系统虚拟化](#ch11-ch11lev3)。以下部分作为示例描述了 Xen 和 KVM 虚拟机管理程序的资源控制。

<!-- source-id: ch11#ch11lev3_7 -->
#### CPU

CPU 资源通常作为虚拟 CPU (vCPU) 分配给客户机。然后，这些由虚拟机管理程序进行调度。分配的 vCPU 数量粗略地限制了 CPU 资源的使用。

对于 Xen，可以通过管理程序 CPU 调度程序为客户机应用细粒度的 CPU 配额。调度程序包括 [\[Cherkasova 07\]](#ch11-ch11ref7)[\[Matthews 08\]](#ch11-ch11ref12)：

- **借用虚拟时间（BVT）**：基于虚拟时间分配的公平共享调度器，可以提前借用，为实时和交互式应用程序提供低延迟执行
- **简单最早截止日期优先（SEDF）**：允许配置运行时保证的实时调度程序，调度程序优先考虑最早截止日期
- **基于信用**：支持 CPU 使用的优先级（*权重*）和上限，以及跨多个 CPU 的负载平衡

对于 KVM，宿主机操作系统可以应用细粒度的 CPU 配额，例如在使用前面描述的宿主机内核*公平共享调度程序*时。在 Linux 上，可以使用 cgroup CPU 带宽控制来应用此功能。

这两种技术如何尊重客户机的“优先级”都存在限制。客户机的 CPU 使用率通常对虚拟机管理程序来说是不透明的，并且客户机内核线程的优先级通常无法被看到或尊重。例如，一个客户机中的低优先级日志轮换守护进程可能与另一客户机中的关键应用程序服务器具有相同的虚拟机管理程序优先级。

对于 Xen，高 I/O 工作负载会消耗 dom0 中的额外 CPU 资源，从而使 CPU 资源使用变得更加复杂。仅客户机域中的后端驱动程序和 I/O 代理可能会消耗超过其 CPU 分配的资源，但不计入 [\[Cherkasova 05\]](#ch11-ch11ref3)。解决方案是创建隔离的驱动程序域（IDD），将 I/O 服务分开以实现安全性、性能隔离和用量核算。这如[图 11.8](#ch11-ch11fig08)所示。

<!-- source-id: ch11#ch11fig08 -->
![图 11.8 具有隔离驱动程序域的 Xen](../images/11fig08.jpg)

可以监控 IDD 的 CPU 使用情况，并可将这部分使用量计入相应客户机的资源用量。摘自[\[Gupta 06\]](#ch11-ch11ref5)：

我们修改后的调度程序 SEDF-DC for SEDF-Debt Collector 会定期从 XenMon 接收有关 IDD 代表客户机域进行 I/O 处理所消耗的 CPU 的反馈。使用此信息，SEDF-DC 限制客户机域的 CPU 分配，以满足指定的组合 CPU 使用限制。

Xen 中使用的最新技术是“存根域”，它运行迷你操作系统。

<!-- source-id: ch11#ch11lev3_8 -->
#### CPU 缓存

除了 vCPU 的分配之外，还可以使用 Intel 缓存分配技术 (CAT) 来控制 CPU 缓存的使用。它允许 LLC 在客户机之间进行分区，并共享分区。虽然这可以防止某个客户机污染另一个客户机的缓存，但它也会通过限制缓存使用来损害性能。

<!-- source-id: ch11#ch11lev3_9 -->
#### 内存容量

内存限制是作为客户机配置的一部分施加的，客户机只能看到设置的内存量。然后，客户机内核执行其自己的操作（分页、交换）以保持在其限制内。

为了提高静态配置的灵活性，VMware 开发了一个 *balloon 驱动程序* [\[Waldspurger 02\]](#ch11-ch11ref2)，它能够通过“膨胀”其中的气球模块来减少正在运行的客户机消耗的内存；该模块会占用客户机内存。然后，虚拟机管理程序会回收这部分内存以供其他客户机使用。气球也可以放气，将内存返回给客户机内核使用。在此过程中，客户机内核执行其正常的内存管理例程以释放内存（例如，分页）。VMware、Xen 和 KVM 都支持气球驱动程序。

当使用气球驱动程序时（要从客户机处检查，请在 dmesg(1) 的输出中搜索“balloon”），我会留意它们可能导致的性能问题。

<!-- source-id: ch11#ch11lev3_10 -->
#### 文件系统容量

宿主机为客户机提供虚拟磁盘卷。对于类似 KVM 的虚拟机管理程序，这些可能是由操作系统创建并相应调整大小的软件卷。例如，ZFS 文件系统可以创建所需大小的虚拟卷。

<!-- source-id: ch11#ch11lev3_11 -->
#### 设备 I/O

硬件虚拟化软件的资源控制历来侧重于控制 CPU 使用率，这可以间接控制 I/O 使用率。

网络吞吐量可能会受到外部专用设备的限制，或者在类似 KVM 的虚拟机管理程序的情况下，会受到宿主机内核功能的限制。例如，Linux 具有来自 cgroup 以及不同 qdisc 的网络带宽控制，可应用于客户机网络接口。

对 Xen 的网络性能隔离进行了研究，得出以下结论 [\[Adamczyk 12\]](#ch11-ch11ref14)：

...当考虑网络虚拟化时，Xen 的弱点是缺乏适当的性能隔离。

\[Adamczyk 12\] 的作者还提出了 Xen 网络 I/O 调度的解决方案，该解决方案添加了网络 I/O 优先级和速率的可调参数。如果您使用的是 Xen，请检查是否已提供该技术或类似技术。

对于具有完整硬件支持的虚拟机管理程序（例如 Nitro），I/O 限制可能由硬件或外部设备支持。在 Amazon EC2 云中，网络连接设备的网络 I/O 和磁盘 I/O 使用外部系统限制在配额内。

### 11.2.4 可观测性

虚拟化系统上可观测的内容取决于虚拟机管理程序以及可观测性工具的启动位置。一般来说：

- **从特权客户机 (Xen) 或宿主机 (KVM)**：所有物理资源都应该可以使用前面章节中介绍的标准操作系统工具进行观察。可以通过分析 I/O 代理（如果正在使用）来观察客户机 I/O。虚拟机管理程序应提供每个客户机的资源使用统计信息。客户机内部结构（包括其进程）无法直接观察。如果设备使用直通或 SR-IOV，某些 I/O 可能无法观察到。
- **从硬件支持的宿主机 (Nitro)**：使用 SR-IOV 可能会使从虚拟机管理程序观察设备 I/O 变得更加困难，因为客户机直接访问硬件，而不是通过代理或宿主机内核。 （亚马逊实际上如何在 Nitro 上实现虚拟机管理程序可观测性并不是公开知识。）
- **从客户机视角**：可以看到虚拟化资源及其在客户机内的使用情况，并推断物理问题。由于 VM 有自己的专用内核，因此可以分析内核内部结构，并且内核跟踪工具（包括基于 BPF 的工具）都可以工作。

从特权客户机或宿主机（Xen 或 KVM 虚拟机管理程序），通常可以在较高级别观察物理资源使用情况：利用率、饱和度、错误、IOPS、吞吐量和 I/O 类型。这些因素通常可以按每个客户机来表示，以便可以快速识别大量用户。无法直接观察哪些客户机进程正在执行 I/O 及其应用程序调用堆栈的详细信息。可以通过登录客户操作系统（前提是已授权和配置这样做的方法，例如 SSH）并使用客户操作系统提供的可观测性工具来观察它们。

当使用直通或 SR-IOV 时，客户机可能会直接向硬件执行 I/O。这可能会绕过虚拟机管理程序中的 I/O 路径以及它们通常收集的统计信息。结果是 I/O 对虚拟机管理程序来说变得不可见，并且不会出现在 iostat(1) 或其他工具中。一种可能的解决方法是使用 PMC 检查与 I/O 相关的计数器，并以此方式推断 I/O。

为了确定客户机性能问题的根本原因，云运营商可能需要登录虚拟机管理程序和客户机，并从两者执行可观测性工具。由于涉及的步骤，跟踪 I/O 路径变得复杂，并且还可能包括对虚拟机管理程序内部结构和 I/O 代理（如果使用）的分析。

从客户机来看，可能根本无法观察到物理资源的使用情况。这可能会诱使客户机用户将神秘的性能问题归咎于吵闹的邻居造成的资源争用。为了让云用户安心（并减少支持请求），有关物理资源使用情况（经过删节、隐去敏感信息）的信息可以通过其他方式提供，包括 SNMP 或云 API。

为了使容器性能更易于观察和理解，有各种监控解决方案可以呈现图形、仪表板和有向图来显示您的容器环境。此类软件包括 Google cAdvisor [\[Google 20d\]](#ch11-ch11ref40) 和 Cilium Hubble [\[Cilium 19\]](#ch11-ch11ref29)（两者都是开源的）。

以下部分演示了可以在不同位置使用的原始可观测性工具，并描述了分析性能的策略。 Xen 和 KVM 用于演示虚拟化软件可能提供的信息类型（不包括 Nitro，因为它是 Amazon 专有的）。

- **`Time%`**：退出所花费的时间占总体百分比
- **`Min Time`**：最短退出时间
- **`Max Time`**：最大退出时间
- **`Avg time`**：平均退出时间

虽然操作员直接查看客户虚拟机内部可能并不容易，但检查退出事件可以让您了解硬件虚拟化的开销可能会或可能不会影响租户。如果您看到退出数量较少且其中 `HLT` 的比例较高，则表明客户机 CPU 相当空闲。另一方面，如果您有大量 I/O 操作，同时生成中断并将其注入到客户机中，那么客户机很可能正在通过其虚拟 NIC 和磁盘执行 I/O。

#### 11.2.4.3 策略

前面的章节介绍了物理系统资源的分析技术，物理系统的管理员可以遵循这些技术来查找瓶颈和错误。还可以检查对客户机施加的资源控制，以查看客户机是否始终处于限制状态，并应通知和鼓励客户机升级。在不登录客户机的情况下，管理员无法识别更多信息，而登录可能是进行认真性能调查所必需的。[^fn-ch11-ch11-footnote-6]

对于客户机来说，可以应用前面章节中介绍的用于分析资源的工具和策略，但请记住，本例中的资源通常是虚拟的。由于虚拟机管理程序隐藏的资源控制或来自其他租户的争用，某些资源可能不会达到物理极限。理想情况下，云软件或供应商会为用户提供一种检查经过删节、隐去敏感信息的物理资源使用情况的方法，以便用户可以自行进一步调查性能问题。如果不是，则可能会根据 I/O 和 CPU 调度延迟的增加推断出争用和限制。这种延迟可以在系统调用层或客户机内核中测量。

我用来识别来自客户机的磁盘和网络资源争用的策略是仔细分析 I/O 模式。这可能涉及记录 biosnoop(8) 的输出（请参阅前面的示例），然后检查 I/O 序列以查看是否存在任何延迟异常值，以及它们是否是由其大小（大 I/O 速度较慢）、访问模式（例如，在写入刷新后排队读取）引起的，或者两者都不是，在这种情况下，可能是物理争用或设备问题。

## 11.3 操作系统虚拟化

操作系统虚拟化将操作系统划分为 Linux 称为“容器”的实例，这些实例就像独立的容器服务器一样，可以独立于宿主机进行管理和重新启动。它们为云用户提供小型、高效、快速启动的实例，为云运营商提供高密度服务器。操作系统虚拟化容器如[图 11.9](#ch11-ch11fig09)所示。

<!-- source-id: ch11#ch11fig09 -->
![图 11.9 操作系统虚拟化](../images/11fig09.jpg)

这种方法起源于 Unix chroot(8) 命令，该命令将进程隔离到 Unix 全局文件系统的子树（它将进程所看到的顶级目录“/”更改为指向其他位置）。 1998 年，FreeBSD 将其进一步发展为*FreeBSD jails*，提供能够作为独立服务器运行的安全隔离环境。 2005 年，Solaris 10 包含一个名为“Solaris Zones”的版本，具有各种资源控制。与此同时，Linux 一直在部分地添加进程隔离功能，*命名空间* 于 2002 年首次为 Linux 2.4.19 添加，*控制组* (cgroups) 于 2008 年首次为 Linux 2.6.24 添加[\[Corbet 07a\]](#ch11-ch11ref8)[\[Corbet 07b\]](#ch11-ch11ref9)[\[Linux 20m\]](#ch11-ch11ref42)。命名空间和 cgroup 组合起来创建容器，通常也使用 seccomp-bpf 来控制系统调用访问。

与硬件虚拟化技术的一个主要区别是只有一个内核在运行。以下是容器相对于硬件虚拟机（[第 11.2 节](#ch11-ch11lev2)、[硬件虚拟化](#ch11-ch11lev2)）的性能优势：

- 快速初始化时间：通常以毫秒为单位测量。
- 容器可以将内存完全用于应用程序（无需额外的内核）。
- 有统一的文件系统缓存——这可以避免宿主机和容器之间的双重缓存情况。
- 对资源共享（cgroup）进行更细粒度的控制。
- 对于宿主机操作员：提高了性能可观测性，因为容器进程及其交互是直接可见的。
- 容器可以共享常见文件的内存页面，释放页面缓存中的空间并提高 CPU 缓存命中率。
- CPU 是真实的 CPU；自适应互斥锁的假设仍然有效。

并且也有缺点：

- 增加了对内核资源（锁、缓存、缓冲区、队列）的争用。
- 对于容器：性能可观测性降低，因为通常无法分析内核。
- 任何内核恐慌都会影响所有容器。
- 容器无法运行自定义内核模块。
- 容器无法运行长时间运行的 PGO 内核（请参阅[第 3.5.1 节](#ch03-ch03lev5sec1)、[PGO 内核](#ch03-ch03lev5sec1)）。
- 容器无法运行不同的内核版本或内核。[^fn-ch11-ch11-footnote-7]

同时考虑前两个缺点：从虚拟机迁移到容器的租户更有可能遇到内核争用问题，同时也失去分析这些问题的能力。他们将更加依赖宿主机运营商进行此类分析。

容器的一个非性能缺点是它们被认为不太安全，因为它们共享内核。

所有这些缺点都可以通过轻量级虚拟化来解决，[第 11.4 节](#ch11-ch11lev4)、[轻量级虚拟化](#ch11-ch11lev4)对此进行了介绍，但代价是牺牲了一些优点。

以下部分描述了 Linux 操作系统虚拟化的细节：实现、开销、资源控制和可观测性。

#### 控制组

控制组（cgroup）限制资源的使用。Linux 内核中有两个版本的 cgroup，v1 和 v2[^fn-ch11-ch11-footnote-9]；许多项目（例如 Kubernetes）仍在使用 v1（v2 正在开发中）。v1 cgroup 包括[表 11.2](#ch11-ch11tab02)中列出的 cgroup。

<!-- source-id: ch11#ch11tab02 -->
**表 11.2 选定的 Linux cgroup**

| **cgroup** | **描述** |
| --- | --- |
| blkio | 限制块 I/O（磁盘 I/O）：字节和 IOPS |
| cpu | 基于份额限制 CPU 使用 |
| cpuacct | 进程组的 CPU 使用情况统计 |
| cpuset | 将 CPU 和内存节点分配给容器 |

| net\_prio | 设置网络接口优先级 |
| perf\_event | 允许 perf 监视 cgroup 中的进程 |
| pids | 限制可以创建的进程数 |
| rdma | 限制 RDMA 和 InfiniBand 资源使用 |

这些 cgroup 可以配置为限制容器之间的资源争用，例如通过对 CPU 和内存使用设置硬限制，或对 CPU 和磁盘使用设置软限制（基于共享）。还可以存在 cgroup 层次结构，包括在容器之间共享的系统 cgroup，如[图 11.10](#ch11-ch11fig10)所示。

cgroups v2 是基于层次结构的，解决了 v1 的各种缺点。预计容器技术将在未来几年迁移到 v2，而 v1 最终将被弃用。 2019 年发布的 Fedora 31 操作系统已经切换到 cgroups v2。

Linux 源代码中的 Documentation/cgroup-v1 和 Documentation/admin-guide/cgroup-v2.rst 以及 cgroups(7) 手册页中有一些有关 cgroup 的文档。

以下各节介绍容器虚拟化主题：开销、资源控制和可观测性。这些根据特定容器实现及其配置而有所不同。

<!-- source-id: ch11#ch11lev3sec2 -->
### 11.3.2 开销

容器执行的开销应该很小：应用程序的 CPU 和内存使用应接近裸机性能，尽管由于文件系统和网络路径中的层，内核中可能会有一些额外的 I/O 调用。最大的性能问题是由多租户争用引起的，因为容器促进了内核和物理资源的大量共享。以下部分总结了 CPU 执行、内存使用、执行 I/O 以及其他租户争用的性能开销。

<!-- source-id: ch11#ch11lev3_17 -->
#### CPU

当容器线程在用户模式下运行时，没有直接的 CPU 开销：线程直接在 CPU 上运行，直到主动让出 CPU 或被抢占。在 Linux 上，在命名空间和 cgroup 中运行进程也不会产生额外的 CPU 开销：无论是否使用容器，所有进程都已在默认命名空间和 cgroup 集中运行。

CPU 性能很可能因与其他租户的争用而降低（请参阅后面的多租户争用部分）。

对于 Kubernetes 等编排器，额外的网络组件可能会增加处理网络数据包的 CPU 开销。例如，当 Kubernetes 服务很多（数千个）而必须处理大型 iptables 规则集时，kube-proxy 会产生首包开销。可以改用 BPF 替换 kube-proxy 来消除这一开销 \[Borkmann 20\]。

<!-- source-id: ch11#ch11lev3_18 -->
#### 内存映射

内存映射、加载和存储应该在没有开销的情况下执行。

<!-- source-id: ch11#ch11lev3_19 -->
#### 内存大小

应用程序可以使用为容器分配的全部内存。与此相比，硬件虚拟机为每个租户运行一个内核，每个内核占用少量主内存。

通用容器配置（使用 OverlayFS）允许在访问同一文件的容器之间共享页面缓存。与虚拟机相比，这可以释放一些内存，虚拟机在内存中复制公共文件（例如系统库）。

<!-- source-id: ch11#ch11lev3_20 -->
#### I/O

I/O 开销取决于容器配置，因为它可能包含用于隔离的额外层：

- **文件系统 I/O**：例如，overlayfs
- **网络 I/O**：例如桥接网络

<!-- source-id: ch11#ch11lev3_21 -->
#### 多租户争用

其他正在运行的租户的存在可能会导致资源争用和中断，从而损害性能，包括：

- CPU 缓存的命中率可能较低，因为其他租户正在消耗和驱逐条目。对于某些处理器和内核配置，上下文切换到其他容器线程甚至可能刷新 L1 缓存。[^fn-ch11-ch11-footnote-10]
- TLB 缓存也可能由于其他租户的使用而具有较低的命中率，并且上下文切换还可能刷新 TLB（如果使用 PCID，则可以避免）。
- 对于执行中断服务例程的其他租户设备（例如网络 I/O），CPU 执行可能会短暂中断。
- 内核执行可能会遇到缓冲区、缓存、队列和锁的额外争用，因为多租户容器系统可能会将其负载增加一个数量级或更多。这种争用可能会稍微降低应用程序性能，具体取决于内核资源及其可扩展性特征。
- 由于使用 iptables 实现容器网络，网络 I/O 可能会遇到 CPU 开销。
- 可能会与正在使用系统资源（CPU、磁盘、网络接口）的其他租户发生争用。

Gianluca Borello 的一篇文章描述了当系统上存在某些其他容器时，容器的性能如何随着时间的推移缓慢而稳定地恶化 [\[Borello 17\]](#ch11-ch11ref20)。他追踪发现 lstat(2) 延迟较高，这是由其他容器的工作负载及其对 dcache 的影响造成的。

Maxim Leonovich 报告的另一个问题表明，从单租户虚拟机迁移到多租户容器会增加内核 posix\_fadvise() 调用的速率，从而产生瓶颈 [\[Leonovich 18\]](#ch11-ch11ref27)。

列表中的最后一项由资源控制管理。虽然其中一些因素存在于传统的多用户环境中，但它们在多租户容器系统中更为普遍。

<!-- source-id: ch11#ch11lev3sec3 -->
### 11.3.3 资源控制

资源控制对资源的访问限制，以便更公平地共享资源。在 Linux 上，这些主要通过 cgroup 提供。

单独的资源控制可以分为*优先级*或*限制*。优先级控制资源消耗，以根据重要性值平衡邻居之间的使用。限制是资源消耗的上限。酌情使用其中之一——对于某些资源，这意味着两者兼而有之。[表 11.3](#ch11-ch11tab03)中列出了示例。

<!-- source-id: ch11#ch11tab03 -->
**表 11.3 Linux 容器资源控制**

| **资源** | **优先级** | **限制** |
| --- | --- | --- |
| CPU | CFS 共享 | cpusets（整个 CPU）、CFS 带宽（部分 CPU） |
| 内存容量 | 内存软限制 | 内存限制 |
| 交换容量 | - | 交换限制 |
| 文件系统容量 | - | 文件系统配额/限制 |
| 文件系统缓存 | - | 内核内存限制 |
| 磁盘 I/O | blkio 权重 | blkio IOPS 限制；blkio 吞吐量限制 |
| 网络 I/O | net\_prio 优先级；qdiscs（fq 等）；自定义 BPF | qdiscs（fq 等）；自定义 BPF |

以下各节基于 cgroup v1 对这些内容进行了一般性描述。配置这些的步骤取决于您正在使用的容器平台（Docker、Kubernetes 等）；请参阅其相关文档。

<!-- source-id: ch11#ch11lev3_22 -->
#### CPU

可以使用 cpusets cgroup 跨容器分配 CPU，并使用 CFS 调度程序的共享和带宽。

##### cpusets

cpusets cgroup 允许将整个 CPU 分配给特定容器。好处是这些容器可以在 CPU 上运行而不会被其他容器中断，并且它们可用的 CPU 容量是一致的。缺点是空闲的 CPU 容量无法供其他容器使用。

##### 共享和带宽

CPU *共享*由 CFS 调度程序提供，是一种不同的 CPU 分配方法，允许容器共享其空闲 CPU 容量。共享支持“突发”的概念，即容器可以通过使用其他容器的空闲 CPU 有效地运行得更快。当没有空闲容量时（包括宿主机过度配置时），共享可以在需要 CPU 的容器之间尽力分配 CPU 资源。

CPU 份额通过将称为份额的分配单元分配给容器来工作，这些分配单元用于计算繁忙容器在给定时间将获得的 CPU 量。该计算使用以下公式：

容器 CPU =（所有 CPU × 容器份额）/系统上总繁忙份额

考虑一个在多个容器之间分配 100 个份额的系统。某一时刻，只有容器 A 和 B 需要 CPU 资源。容器 A 有 10 个份额，容器 B 有 30 个份额。因此，容器 A 可以使用系统上总 CPU 资源的 25%：所有 CPU × 10/(10 + 30)。

现在考虑一个所有容器同时繁忙的系统。给定容器的 CPU 分配将是：

容器 CPU = 所有 CPU × 容器份额 / 系统上的总份额

对于所描述的场景，容器 A 将获得 10% 的 CPU 容量（CPU × 10/100）。共享分配提供了 CPU 使用率的最低保证。突发可能会让容器使用更多。容器 A 可以使用 10% 到 100% 的 CPU 容量，具体取决于有多少其他容器处于繁忙状态。

共享的一个问题是突发可能会混淆容量规划，特别是因为许多监控系统不显示突发统计数据（它们应该显示）。测试容器的最终用户可能对其性能感到满意，但没有意识到这种性能只有通过突发才能实现。稍后，当其他租户搬入时，他们的容器将不再能够突发，性能也会降低。想象一下，容器 A 最初在空闲系统上进行测试并获得 100% 的 CPU，但后来由于添加了其他容器，因此仅获得 10%。我在现实生活中见过很多次这样的场景，最终用户认为一定是系统性能问题，并要求我帮忙调试。然后，他们失望地发现系统正在按预期工作，而且由于其他容器已移入，速度慢十倍已成为新常态。对客户来说，这可能感觉像是诱骗式切换。

可以通过限制过度突发来减轻这个问题，使性能下降不那么严重（尽管这也会限制性能）。在 Linux 上，这是使用 CFS *带宽*控制来完成的，它可以设置 CPU 使用的上限。例如，容器 A 的带宽可以设置为系统范围 CPU 容量的 20%，这样，通过共享，它现在可以在 10% 到 20% 的范围内运行，具体取决于空闲可用性。从基于共享的最小 CPU 到最大带宽的范围如[图 11.12](#ch11-ch11fig12)所示。它假设每个容器中有足够的繁忙线程来使用可用的 CPU（否则在达到系统施加的限制之前，容器会因其自身的工作负载而受到 CPU 限制）。

<!-- source-id: ch11#ch11fig12 -->
![图 11.12 CPU 份额与带宽](../images/11fig12.jpg)

带宽控制通常以整个 CPU 的百分比来显示：2.5 意味着两个半 CPU。这映射到内核设置，实际上是“周期”和“配额”（以微秒为单位）：容器每个周期都会获得 CPU 微秒的配额。

管理突发的另一种方法是，容器运营商在容器发生突发一段时间（例如几天）时通知最终用户，以便他们不会对性能产生错误预期。然后可以鼓励最终用户升级其容器大小，以便获得更多份额以及更高的 CPU 分配最低保证。

<!-- source-id: ch11#ch11lev3_23 -->
#### CPU 缓存

可以使用 Intel 缓存分配技术（CAT）控制 CPU 缓存的使用，以避免容器污染 CPU 缓存。这在[第 11.2.3 节](#ch11-ch11lev2sec3)、[资源控制](#ch11-ch11lev2sec3)中进行了描述，并且具有相同的警告：限制缓存访问也会损害性能。

<!-- source-id: ch11#ch11lev3_24 -->
#### 内存容量

内存 cgroup 提供了四种机制来管理内存使用。[表 11.4](#ch11-ch11tab04)通过内存 cgroup 设置名称来描述它们。

<!-- source-id: ch11#ch11tab04 -->
**表 11.4 Linux 内存 cgroup 设置**

| **名称** | **描述** |
| --- | --- |
| memory.limit\_in\_bytes | 大小限制（以字节为单位）。如果容器尝试使用超过分配的大小，则会遇到交换（如果已配置）或 OOM 杀手。 |
| memory.soft\_limit\_in\_bytes | 大小限制（以字节为单位）。尽力而为的方法，涉及回收内存以引导容器达到其软限制。 |
| memory.kmem.limit\_in\_bytes | 内核内存的大小限制（以字节为单位）。 |
| memory.kmem.tcp.limit\_in\_bytes | TCP 缓冲区内存的大小限制（以字节为单位）。 |

请注意，容器未使用的内存可以被内核页面缓存中的其他容器使用，从而提高它们的性能（以内存突发的形式）。

<!-- source-id: ch11#ch11lev3_25 -->
#### 交换容量

内存 cgroup 还允许配置交换限制。实际设置是 memory.memsw.limit\_in\_bytes，即内存加上 swap。

<!-- source-id: ch11#ch11lev3_26 -->
#### 文件系统容量

文件系统容量通常会受到文件系统的限制。例如，XFS 文件系统支持用户、组和项目的软配额和硬配额，其中软限制允许在硬限制下暂时超额使用。 ZFS 和 btrfs 也有配额。

<!-- source-id: ch11#ch11lev3_27 -->
#### 文件系统缓存

在 Linux 中，容器的文件系统页面缓存所使用的内存会计入该容器的内存 cgroup：不需要额外设置。如果容器配置了 swap，则可以通过 memory.swappiness 设置控制交换与页面缓存驱逐之间的倾向，类似于系统范围的 vm.swappiness（[第 7 章](#ch07-ch07)、[内存](#ch07-ch07)、[第 7.6.1 节](#ch07-ch07lev6sec1)、[可调参数](#ch07-ch07lev6sec1)）。

<!-- source-id: ch11#ch11lev3_28 -->
#### 磁盘 I/O

blkio cgroup 提供了管理磁盘 I/O 的机制。[表 11.5](#ch11-ch11tab05)通过 blkio cgroup 设置名称来描述它们。

<!-- source-id: ch11#ch11tab05 -->
**表 11.5 Linux blkio cgroup 设置**

| **名称** | **描述** |
| --- | --- |
| blkio.weight | 控制负载期间磁盘资源份额的 cgroup 权重，类似于 CPU 份额。它与 BFQ I/O 调度程序一起使用。 |
| blkio.weight\_device | 特定设备的权重设置。 |
| blkio.throttle.read\_bps\_device | 读取字节/秒的限制。 |

<!-- source-id: ch11#ch11lev3_29 -->
#### 网络 I/O

net\_prio cgroup 允许为出站网络流量设置优先级。这些与 SO\_PRIORITY 套接字选项相同（请参阅 socket(7)），并控制网络协议栈中数据包处理的优先级。net\_cls cgroup 可以使用类 ID 标记数据包，以便以后通过 qdisc 进行管理。（这也适用于 Kubernetes Pod，每个 Pod 可以使用一个 net\_cls。）

排队规则（qdisc，请参阅[第 10 章](#ch10-ch10)、[网络](#ch10-ch10)、[第 10.4.3 节](#ch10-ch10lev4sec3)、[软件](#ch10-ch10lev4sec3)）可以对类 ID 进行操作或分配给容器虚拟网络接口，以确定网络流量的优先级和限制。有 50 多种不同的 qdisc 类型，每种类型都有自己的策略、功能和可调参数。例如，Kubernetes kubernetes.io/ingress-bandwidth 和 kubernetes.io/egress-bandwidth 设置是通过创建令牌桶过滤器（tbf）qdisc [\[CNI 18\]](#ch11-ch11ref25) 来实现的。[第 10.7.6 节](#ch10-ch10lev7sec6)、[tc](#ch10-ch10lev7sec6) 提供了向网络接口添加和删除 qdisc 的示例。

BPF 程序可以附加到 cgroup，以实现自定义编程资源控制和防火墙。一个例子是 Cilium 软件，它使用 XDP、cgroup 和 tc (qdiscs) 等各个层的 BPF 程序组合来支持容器之间的安全、负载平衡和防火墙功能 [\[Cilium 20a\]](#ch11-ch11ref36)。

<!-- source-id: ch11#ch11lev3sec4 -->
### 11.3.4 可观测性

可观测的内容取决于启动可观测性工具的位置以及宿主机的安全设置。由于容器可以通过多种不同的方式进行配置，因此我将描述典型案例。一般来说：

- **从宿主机**（最具特权的命名空间）：可以观察到一切，包括硬件资源、文件系统、容器进程、容器 TCP 会话等。无需登录容器即可查看和分析容器进程。还可以从宿主机（云提供商）轻松浏览容器文件系统。
- **来自容器**：容器通常只能看到自己的进程、文件系统、网络接口和 TCP 会话。一个主要的例外是系统范围的统计信息，例如 CPU 和磁盘：这些通常显示宿主机而不仅仅是容器。这些统计信息的状态通常没有记录（我在下面的部分中编写了自己的文档，[传统工具](#ch11-ch11lev3-30)）。通常无法检查内核内部结构，因此使用内核跟踪框架（[第 13 章](#ch13-ch13)至[第 15 章](#ch15-ch15)）的性能工具通常不起作用。

最后一点已在前面描述过：容器更有可能遇到内核争用问题，同时它们使最终用户无法诊断这些问题。

容器性能分析的一个常见问题是可能存在“吵闹的邻居”，即其他容器租户，它们会大量消耗资源并导致其他人的访问争用。由于这些容器进程都在一个内核下，并且可以从宿主机同时进行分析，这与传统的在一个分时系统上运行的多个进程的性能分析没有什么不同。主要区别在于 cgroup 可能会在硬件限制之前施加额外的软件限制（资源控制）。

许多为独立系统编写的监控工具尚未开发出对操作系统虚拟化（容器）的支持，并且对 cgroup 和其他软件限制视而不见。尝试在容器中使用这些工具的用户可能会发现它们似乎可以工作，但实际上仅显示物理系统资源。如果不支持观察云资源控制，这些工具可能会错误地报告系统仍有余量，而实际上容器已经达到软件限制。它们还可能显示出实际上由其他租户造成的高资源使用率。

在 Linux 上，由于内核中当前没有容器 ID，[^fn-ch11-ch11-footnote-11] 也没有传统性能工具提供的太多容器支持，因此宿主机和容器的容器可观测性变得更加复杂和耗时。

以下各节描述了这些挑战，总结了传统性能工具的状态，探索了宿主机和容器的可观测性，并描述了分析性能的策略。

| `top` | 摘要标题显示宿主机；进程表显示所有宿主机和容器进程 | **摘要标题显示混合统计信息；有些来自宿主机，有些来自容器。** 进程表显示容器进程 |
| `ps` | 显示所有进程 | 显示容器进程 |
| `uptime` | 显示宿主机（系统范围）平均负载 | **显示宿主机平均负载** |
| `mpstat` | 显示宿主机 CPU 和宿主机使用情况 | **显示宿主机 CPU 和宿主机 CPU 使用情况** |
| `vmstat` | 显示宿主机 CPU、内存和其他统计数据 | **显示宿主机 CPU、内存和其他统计数据** |
| `pidstat` | 显示所有进程 | 显示容器进程 |
| `free` | 显示宿主机内存 | **显示宿主机内存** |
| `iostat` | 显示宿主机磁盘 | **显示宿主机磁盘** |
| `pidstat -d` | 显示所有进程磁盘 I/O | 显示容器进程磁盘 I/O |
| `sar -n DEV, TCP 1` | 显示宿主机网络接口和 TCP 统计数据 | 显示容器网络接口和 TCP 统计数据 |
| `perf` | 可以分析所有内容 | **要么无法运行，要么可以启用，然后可以分析其他租户** |
| `tcpdump` | 可以嗅探所有接口 | 仅嗅探容器接口 |
| `dmesg` | 显示内核日志 | **运行失败** |

随着时间的推移，容器对工具的支持可能会得到改进，以便它们仅在从容器运行时显示特定于容器的统计信息，或者更好的是，显示容器与宿主机统计信息的细分。宿主机工具可以显示所有内容，也可以通过添加对容器或 cgroup 的感知和过滤支持来改进。以下有关宿主机和容器可观测性的部分将详细解释这些主题。

#### 11.3.4.2 宿主机

登录宿主机后，可以使用前面章节中介绍的工具检查所有系统资源（CPU、内存、文件系统、磁盘、网络）。使用容器时还有两个额外因素需要检查：

- 每个容器的统计数据
- 资源控制的效果

正如 [第 11.3.1 节](#ch11-ch11lev3sec1)、[实现](#ch11-ch11lev3sec1) 中所述，内核中没有容器的概念：容器只是命名空间和 cgroup 的集合。您看到的容器 ID 是由用户空间软件创建和管理的。以下是来自 Kubernetes（在本例中为具有单个容器的 Pod）和 Docker 的示例容器 ID：

![点此查看代码图片](../images/pg620-01.jpg)

```text
# kubectl get pod
NAME                         READY   STATUS              RESTARTS   AGE
kubernetes-b94cb9bff-kqvml   0/1     ContainerCreating   0          3m
[...]
# docker ps
CONTAINER ID  IMAGE   COMMAND   CREATED      STATUS      PORTS  NAMES
6280172ea7b9  ubuntu  "bash"    4 weeks ago  Up 4 weeks         eager_bhaskara
[...]
```

这给 ps(1)、top(1) 等传统性能工具带来了问题。为了显示容器 ID，它们需要支持 Kubernetes、Docker 和所有其他容器平台。相反，如果内核支持容器 ID，它将成为所有性能工具支持的标准。Solaris 内核就是这种情况，其中容器称为“区域”，并具有基于内核的“区域 ID”，可以使用 ps(1) 等进行观察。（以下 BPF 跟踪小节显示了使用 UTS 命名空间中的节点名作为容器 ID 的 Linux 解决方案。）

在实践中，可以使用以下方法检查 Linux 上容器 ID 的性能统计数据：

- 容器平台提供的**容器工具**；例如，Docker 有一个用于显示容器资源使用情况的工具。
- **性能监控**软件，通常具有适用于各种容器平台的插件。
- **cgroup 统计信息** 以及使用它们的工具。这需要额外的步骤来确定哪些 cgroup 映射到哪个容器。
- 来自宿主机的**命名空间映射**，例如通过使用 nsenter(1)，以允许宿主机性能工具在容器中运行。当与 `-p`（PID 命名空间）选项一起使用时，这可以将可见进程减少为仅来自容器的进程。尽管性能工具统计数据可能不仅仅针对容器：请参阅 [表 11.6](#ch11-ch11tab06)。`-n`（网络命名空间）选项对于在同一网络命名空间（ping(8)、tcpdump(8)）内运行网络工具也很有用。
- **BPF 跟踪**，可以从内核读取 cgroup 和命名空间信息。

以下部分提供了容器工具、cgroup 统计信息、命名空间映射、BPF 跟踪以及资源控制可观测性的示例。

##### 命名空间映射

容器通常对进程 ID 和挂载使用不同的命名空间。

对于进程命名空间，这意味着容器中的 PID 不太可能与宿主机中的 PID 匹配。

在诊断性能问题时，我首先登录到容器，以便可以从最终用户的角度看到问题。稍后我可能会登录宿主机使用系统范围的工具继续排查，但 PID 可能不同。该映射显示在 /proc/PID/status 文件中。例如，来自宿主机：

![点此查看代码图片](../images/pg623-01.jpg)

```text
host# grep NSpid /proc/4915/status
NSpid:   4915    753
```

这表明宿主机上的 PID 4915 是容器中的 PID 753。不幸的是，我通常需要进行反向映射：给定容器 PID，我需要找到宿主机 PID。一种（有点低效）的方法是扫描所有状态文件：

![点此查看代码图片](../images/pg623-02.jpg)

```text
host# awk '$1 == "NSpid:" && $3 == 753 { print $2 }' /proc/*/status
4915
```

在本例中，它显示容器 PID 753 是宿主机 PID 4915。请注意，输出可能显示多个宿主机 PID，因为“753”可能出现在多个进程命名空间中。在这种情况下，您需要找出哪个 753 来自匹配的命名空间。/proc/PID/ns 文件是包含命名空间 ID 的符号链接，可用于此目的。先从容器检查，然后从宿主机检查：

![点击查看代码图片](../images/pg623-03.jpg)

```text
guest# ls -lh /proc/753/ns/pid
lrwxrwxrwx 1 root root 0 Mar 15 20:47 /proc/753/ns/pid -> 'pid:[4026532216]'

host# ls -lh /proc/4915/ns/pid
lrwxrwxrwx 1 root root 0 Mar 15 20:46 /proc/4915/ns/pid -> 'pid:[4026532216]'
```

请注意匹配的命名空间 ID (4026532216)：这确认宿主机 PID 4915 与容器 PID 753 相同。

挂载命名空间可能会带来类似的挑战。例如，从宿主机运行 perf(1) 命令会在 /tmp/perf-PID.map 中搜索补充符号文件，但容器应用程序将它们发送到容器中的 /tmp，这与宿主机中的 /tmp 不同。此外，由于进程命名空间的原因，PID 可能会有所不同。 Alice Goldfuss 首先发布了一个解决方法，涉及移动和重命名这些符号文件，以便它们在宿主机 [\[Goldfuss 17\]](#ch11-ch11ref21) 中可用。 perf(1) 自此获得了命名空间支持以避免此问题，并且内核提供了 /proc/PID/root 挂载命名空间映射，用于直接访问容器的根目录（“/”）。例如：

![点此查看代码图片](../images/pg623-04.jpg)

```text
host# ls -lh /proc/4915/root/tmp
total 0
-rw-r--r-- 1 root root 0 Mar 15 20:54 I_am_in_the_container.txt
```

这列出了容器的 /tmp 中的一个文件。

除了 /proc 文件之外，nsenter(1) 命令还可以在选定的命名空间中执行其他命令。以下命令从宿主机在挂载 (`-m`) 和进程 (`-p`) 命名空间中运行 PID 4915 的 top(1) 命令 (`-t 4915`)：

![点此查看代码图片](../images/pg624-01.jpg)

这表明顶级进程是 PID 753 的 java。

##### BPF 跟踪

一些 BPF 跟踪工具已经支持容器，但许多工具还没有。幸运的是，在需要时添加对 bpftrace 工具的支持通常并不困难；下面是一个例子。有关 bpftrace 编程的说明，请参阅[第 15 章](#ch15-ch15)。

forks.bt 工具通过对 clone(2)、fork(2) 和 vfork(2) 系统调用进行插桩来计算跟踪时创建的新进程的数量。源代码如下：

![点此查看代码图片](../images/pg624-02.jpg)

```text
#!/usr/local/bin/bpftrace

tracepoint:syscalls:sys_enter_clone,
tracepoint:syscalls:sys_enter_fork,
tracepoint:syscalls:sys_enter_vfork
{
        @new_processes = count();
}
```

输出示例：

```text
# ./forks.bt
Attaching 3 probes...
^C

@new_processes: 590
```

这显示了跟踪时在系统范围内创建的 590 个新进程。

要按容器对此进行分解，一种方法是从 uts 命名空间打印节点名（主机名）。这依赖于配置此命名空间的容器软件，通常就是这种情况。代码变为，突出显示添加内容：

![点此查看代码图片](../images/pg625-01.jpg)

```text
#!/usr/local/bin/bpftrace

#include <linux/sched.h>
#include <linux/nsproxy.h>
#include <linux/utsname.h>

tracepoint:syscalls:sys_enter_clone,
tracepoint:syscalls:sys_enter_fork,
tracepoint:syscalls:sys_enter_vfork
{
        $task = (struct task_struct *)curtask;
        $nodename = $task->nsproxy->uts_ns->name.nodename;
        @new_processes[$nodename] = count();
}
```

这段额外的代码从当前内核 task\_struct 遍历到 UTS 命名空间节点名，并将其作为键包含在 @new\_processes 输出映射中。

输出示例：

![点此查看代码图片](../images/pg625-02.jpg)

```text
# ./forks.bt
Attaching 3 probes...
^C

@new_processes[ip-10-1-239-218]: 171
@new_processes[efe9f9be6185]: 743
```

输出现在按容器进行细分，显示节点名称 `6280172ea7b9`（容器）在跟踪时创建了 252 个进程。另一个节点名称 `ip-10-1-239-218` 是宿主机系统。

这种方法之所以有效，是因为系统调用在任务（进程）上下文中运行，因此 `curtask` 返回对应的 task\_struct，我们可以从中获取节点名。如果跟踪的是进程的异步事件，例如磁盘 I/O 完成中断，原始进程可能并未在 CPU 上运行，`curtask` 就无法确定正确的节点名。

由于获取 uts 节点名可能会在 bpftrace 中常用，我想我们将添加一个内置变量 nodename，因此唯一的添加是：

![点此查看代码图片](../images/pg625-03.jpg)

```text
@new_processes[nodename] = count();
```

检查 bpftrace 更新以查看是否已添加。

##### 资源控制

必须观察[第 11.3.3 节](#ch11-ch11lev3sec3)、[资源控制](#ch11-ch11lev3sec3)中列出的资源控制，以确定容器是否受其限制。传统的性能工具和文档侧重于物理资源，而忽视了这些软件施加的限制。

USE 方法（[第 2 章](#ch02-ch02)、[方法论](#ch02-ch02)、[第 2.5.9 节](#ch02-ch02lev5sec9)、[USE 方法](#ch02-ch02lev5sec9)）中描述了检查资源控制，该方法迭代资源并检查利用率、饱和度和错误。由于存在资源控制，因此也必须对每个资源进行检查。

前面的 cgroup 统计信息部分显示了 /sys/fs/cgroup/.../cpu.stat 文件，该文件提供了有关 CPU 限制 (nr\_throttled) 和以纳秒为单位的限制时间 (throttled\_time) 的统计信息。这种限制指的是 CPU 带宽限制，并且很容易识别容器是否受到带宽限制：throttled\_time 将会增加。如果改用 cpuset，则可以通过每个 CPU 的工具和指标（包括 mpstat(1)）检查其 CPU 利用率。

CPU 也可以通过共享进行管理，如前面的共享和带宽部分所述。受共享限制的容器更难以识别，因为没有对应的统计数据。我在 [图 11.13](#ch11-ch11fig13) 中开发了流程图，用于确定容器 CPU 是否以及如何受到限制 [\[Gregg 17g\]](#ch11-ch11ref24)：

<!-- source-id: ch11#ch11fig13 -->
![图 11.13 容器 CPU 节流分析](../images/11fig13.jpg)

[图 11.13](#ch11-ch11fig13) 中的流程使用五个统计信息确定容器 CPU 是否以及如何受到限制：

- **节流时间**：cpu cgroup 的 throttled\_time
- **非自愿上下文切换**：可从 /proc/PID/status 中读取，表现为 nonvoluntary\_ctxt\_switches（非自愿上下文切换）计数的增加
- **宿主机有空闲 CPU**：可以从 mpstat(1) `%idle`、/proc/stat 和其他工具读取
- **cpuset CPU 100% 忙**：如果 cpuset 正在使用，则可以从 mpstat(1)、/proc/stat 等读取其利用率。
- **所有其他租户空闲**：可以通过特定于容器的工具 (`docker stat`) 或显示缺乏 CPU 资源竞争的系统工具来确定（例如，如果 top(1) 仅显示消耗 `%CPU` 的一个容器）

可以为其他资源开发类似的流程，并且应在监控软件和工具中提供包括 cgroup 统计数据在内的支持统计数据。理想的监控产品或工具可以为您做出决定，并报告每个容器是否以及如何受到限制。

此输出显示了 CPU 和磁盘工作负载，但该容器完全空闲。对于刚刚接触操作系统虚拟化的人来说，这可能会让人感到困惑——为什么我的容器很忙？这是因为这些工具显示的宿主机统计信息包括其他租户的活动。

[第 11.3.4 节](#ch11-ch11lev3sec4)、[可观测性](#ch11-ch11lev3sec4) 的[传统工具](#ch11-ch11lev3-30)小节中总结了这些性能工具的状态。随着时间的推移，这些工具变得更加“容器感知”，支持 cgroup 统计并在容器中提供仅容器统计信息。


这些计数器按操作类型统计。我用 sleep 10 打印了两次来设置间隔：您可以看到计数在该间隔期间没有增加；因此，容器没有发出磁盘 I/O。还有另一个字节文件：blkio.throttle.io\_service\_bytes。

不幸的是，这些计数器不能提供 iostat(1) 所需的所有统计信息。cgroup 需要公开更多计数器，以便 iostat(1) 能够感知容器。

##### 容器感知

让工具具有容器感知能力并不一定意味着将其视图限制在自己的容器内：允许容器查看物理资源的状态也有好处。这取决于使用容器的目标，可能是：

1. **容器是一个隔离的服务器**：如果这是目标，就像云供应商的典型情况一样，那么使工具具有容器感知能力意味着它们只显示当前容器的活动。例如，iostat(1) 应该只显示容器调用的磁盘 I/O，而不显示其他调用的磁盘 I/O。这可以通过隔离所有统计源以仅显示当前容器（/proc、/sys、netlink 等）来实现。这种隔离既有助于也妨碍容器的分析：诊断其他租户的资源争用问题将更加耗时，并且将依赖于无法解释的设备延迟增加的推断。
2. **容器是一种打包解决方案**：对于运营自己的容器云的公司来说，可能不一定需要隔离容器的统计数据。允许容器查看宿主机统计信息（无论如何，目前经常出现这种情况，如前面使用 iostat(1) 看到的那样）意味着最终用户可以更好地了解硬件设备的状态以及由吵闹的邻居引起的问题。在这种情况下，要使 iostat(1) 更加了解容器，可能意味着提供显示当前容器与宿主机或其他容器使用情况的细分，而不是隐藏这些统计信息。

对于这两种情况，工具还应该支持在适当的情况下显示资源控制，作为容器感知的一部分。继续 iostat(1) 示例，除了设备 `%util`（在场景 A 中不可见）之外，它还可以根据 blkio 吞吐量和 IOPS 限制提供 `%cap`，以便容器知道磁盘 I/O 是否受到资源控制的限制。[^fn-ch11-ch11-footnote-12]

如果允许观察物理资源，容器将能够排除某些类型的问题，包括吵闹的邻居。这可以减轻容器运营商的支持负担：人们倾向于归咎于他们无法观察到的事情。这也是与硬件虚拟化的一个重要区别，硬件虚拟化对客户机隐藏了物理资源，并且无法共享这些统计数据（除非使用外部手段）。理想情况下，Linux 中未来会有一个设置来控制宿主机统计信息的共享，以便每个容器环境可以根据需要在 A 或 B 之间进行选择。

##### 追踪工具

基于内核的高级跟踪工具，例如 perf(1)、Ftrace 和 BPF，也有类似的问题，并且在它们之前就实现了容器感知。由于各种系统调用（perf\_event\_open(2)、bpf(2) 等）以及访问各种 /proc 和 /sys 文件所需的权限，它们目前无法在容器内工作。描述早期场景 A 和 B 的未来：

1. **需要隔离**：允许容器使用跟踪工具可以通过以下方式实现：
    - **内核过滤**：事件及其参数可以由内核过滤，因此，例如，跟踪 block:block\_rq\_issue 跟踪点仅显示当前容器的磁盘 I/O。
    - **宿主机 API**：宿主机通过安全 API 或 GUI 公开对某些跟踪工具的访问。例如，容器可以请求执行常见的 BCC 工具，例如 execsnoop(8) 和 biolatency(8)，宿主机将验证该请求，执行该工具的过滤版本，并返回输出。
2. **不需要隔离**：资源（系统调用、/proc 和 /sys）在容器中可用，以便跟踪工具可以工作。跟踪工具本身可以感知容器，以便于仅过滤当前容器的事件。

在 Linux 和其他内核中，使工具和统计数据能够感知容器是一个缓慢的过程，并且可能需要很多年才能全部完成。这对登录系统并在命令行使用性能工具的高级用户影响最大；许多用户使用具有容器感知（在某种程度上）的代理的监控产品。

<!-- source-id: ch11#ch11lev3_33 -->
#### 11.3.4.4 策略

前面的章节介绍了物理系统资源的分析技术并包括各种方法。宿主机运营商可以遵循这些方法，容器在牢记前述限制的情况下也可以在一定程度上遵循。对于容器来说，高级资源使用通常是可观测的，但通常不可能深入到内核。

除了物理资源之外，宿主机运营商和容器租户还应该检查资源控制所施加的云限制。由于这些限制（如果存在）是在物理限制之前很久就遇到的，因此它们更有可能生效，因此应首先检查。

由于许多传统的可观测性工具是在容器和资源控制存在之前创建的（例如 top(1)、iostat(1)），因此它们默认不包含资源控制信息，用户可能会忘记检查这些控制。

以下是检查每个资源控制的一些注释和策略：

- **CPU**：参见[图 11.13](#ch11-ch11fig13)流程图。cpusets、带宽和共享的使用情况都需要检查。
- **[内存](#gloss-glo-103)**：对于主内存，根据任何内存 cgroup 限制检查当前使用情况。
- **文件系统容量**：对于任何其他文件系统（包括使用 df(1)），这应该是可观测到的。
- **磁盘 I/O**：检查 blkio cgroup 节流限制 (/sys/fs/cgroup/blkio) 的配置以及 blkio.throttle.io\_serviced 和 blkio.throttle.io\_service\_bytes 文件的统计信息：如果它们以与节流限制相同的速率递增，则表明磁盘 I/O 受到节流限制。如果 BPF 跟踪可用，则还可以使用 blkthrot(8) 工具来确认 blkio 节流 \[Gregg 19\]。
- **网络 I/O**：根据任何已知的带宽限制检查当前网络吞吐量，该限制只能从宿主机观察到。遇到限制会导致网络 I/O 延迟增加，因为租户受到限制。

最后的评论：本节的大部分内容描述了 cgroup v1 和 Linux 容器的当前状态。内核功能正在迅速变化，使得供应商文档和工具的容器感知能力等其他领域也在迎头赶上。为了跟上 Linux 容器的最新动态，您需要检查新内核版本中的新增内容，并通读 Linux 源代码中的文档目录。我还建议阅读 cgroups v2 的首席开发人员 Tejun Heo 编写的所有文档，包括 Linux 源代码 [\[Heo 15\]](#ch11-ch11ref17) 中的 Documentation/admin-guide/cgroup-v2.rst。

## 11.4 轻量级虚拟化

轻量级硬件虚拟化被设计为两全其美：兼具硬件虚拟化的安全性与容器的效率和快速启动时间。基于 Firecracker 的这种配置如[图 11.14](#ch11-ch11fig14)所示，并与容器并列比较。

轻量级硬件虚拟化使用基于处理器虚拟化的轻量级虚拟机管理程序和最少数量的模拟设备。这与全机硬件虚拟机管理程序（[第 11.2 节](#ch11-ch11lev2)、[硬件虚拟化](#ch11-ch11lev2)）不同，后者起源于桌面虚拟机，包括对视频、音频、BIOS、PCI 总线和其他设备的支持，以及不同级别的处理器支持。仅用于服务器计算的虚拟机管理程序不需要支持这些设备，今天编写的虚拟机管理程序可以假设现代处理器虚拟化功能可用。

<!-- source-id: ch11#ch11fig14 -->
![图 11.14 轻量级虚拟化](../images/11fig14.jpg)

描述一下这种差异：快速仿真器 (QEMU) 是用于 KVM 的全机硬件虚拟机管理程序，拥有超过 140 万行代码（QEMU 版本 4.2）。 Amazon Firecracker 是一个轻量级虚拟机管理程序，只有 5 万行代码 [\[Agache 20\]](#ch11-ch11ref34)。

轻量级 VM 的行为与[第 11.2 节](#ch11-ch11lev2)中描述的配置 B 硬件 VM 类似。与硬件虚拟机相比，轻量级虚拟机具有更快的启动时间、更低的内存开销和更高的安全性。轻量级虚拟机管理程序可以通过将命名空间配置为另一层安全性来进一步提高安全性，如[图 11.14](#ch11-ch11fig14)所示。

一些实现将轻量级虚拟机描述为“容器”，而其他实现则使用术语“MicroVM”。我更喜欢 MicroVM 这个术语，因为容器这个术语通常与操作系统虚拟化相关。

<!-- source-id: ch11#ch11lev4sec1 -->
### 11.4.1 实施

有几个轻量级硬件虚拟化项目，包括：

- **Intel Clear Containers**：于 2015 年推出，它使用 Intel VT 功能来提供轻量级虚拟机。该项目证明了轻量级容器的潜力，实现了 45 毫秒以下的启动时间 [\[Kadera 16\]](#ch11-ch11ref19)。 2017 年，英特尔 Clear Containers 加入了 Kata Containers 项目并继续开发。
- **Kata Containers**：该项目于 2017 年启动，基于 Intel Clear Containers 和 Hyper.sh RunV，并接受 OpenStack 基金会的管理。其网站口号是：“容器的速度，虚拟机的安全”[\[Kata Containers 20\]](#ch11-ch11ref41)。
- **Google gVisor**：gVisor 于 2018 年以开源方式推出，它使用用 Go 编写的专门用于容器实例的用户空间内核，可提高容器安全性。
- **Amazon Firecracker**：于 2019 年作为开源 [\[Firecracker 20\]](#ch11-ch11ref38) 推出，它使用 KVM 和新的轻量级 VMM 而不是 QEMU，并实现约 100 毫秒的启动时间（系统启动）\[Agache 20\]。

以下部分描述了常用的实现：轻量级硬件虚拟机管理程序（Intel Clear Containers、Kata Containers 和 Firecracker）。gVisor 是一种不同的方法，它实现了自己的轻量级内核，并且具有更类似于容器的特性（[第 11.3 节](#ch11-ch11lev3)、[操作系统虚拟化](#ch11-ch11lev3)）。

<!-- source-id: ch11#ch11lev4sec2 -->
### 11.4.2 开销

开销与[第 11.2.2 节](#ch11-ch11lev2sec2)、[开销](#ch11-ch11lev2sec2)中描述的 KVM 虚拟化类似，但由于 VMM 更小，因此内存占用更低。Intel Clear Containers 2.0 报告每个容器的内存开销为 48–50 MB \[Kadera 16\]；Amazon Firecracker 报告 \[Agache 20\] 小于 5 MB。

<!-- source-id: ch11#ch11lev4sec3 -->
### 11.4.3 资源控制

由于 VMM 进程在宿主机上运行，因此可以通过操作系统级别的资源控制来管理它们：cgroup、qdisc 等，类似于[第 11.2.3 节](#ch11-ch11lev2sec3)、[资源控制](#ch11-ch11lev2sec3)中描述的 KVM 虚拟化。[第 11.3.3 节](#ch11-ch11lev3sec3)、[资源控制](#ch11-ch11lev3sec3)中还针对容器更详细地讨论了这些操作系统级资源控制。

<!-- source-id: ch11#ch11lev4sec4 -->
### 11.4.4 可观测性

可观测性与[第 11.2.4 节](#ch11-ch11lev2sec4)、[可观测性](#ch11-ch11lev2sec4)中描述的 KVM 虚拟化类似。总之：

- **从宿主机视角**：可以使用标准操作系统工具观察所有物理资源，如前面的章节所述。客户虚拟机作为进程可见。无法直接观察客户机内部结构，包括虚拟机内部的进程和文件系统。对于要分析客户机内部结构的虚拟机管理程序操作员，必须授予他们访问权限（例如 SSH）。

## 11.5 其他类型

其他云计算原语和技术包括：

- **函数即服务（FaaS）**：开发人员向云端提交应用程序函数，该函数按需运行。尽管这简化了软件开发体验，但由于无需管理服务器（“无服务器”），因此会产生性能影响。该功能的启动时间可能很长，并且如果没有服务器，最终用户就无法运行传统的命令行可观测性工具。性能分析通常仅限于应用程序提供的时间戳。
- **软件即服务（SaaS）**：这提供了高级软件，最终用户无需自行配置服务器或应用程序。性能分析仅限于运营商：如果无法访问服务器，最终用户除了基于客户端的计时之外几乎无能为力。
- **Unikernels**：该技术将应用程序与最少的内核部分一起编译成单个软件二进制文件，可以直接由硬件管理程序执行，无需操作系统。虽然可以带来性能提升，例如最大限度地减少指令文本，从而减少 CPU 缓存污染，以及由于删除未使用的代码而带来的安全性收益，但 Unikernels 也带来了可观测性挑战，因为没有操作系统可以运行可观测性工具。内核统计信息（例如 /proc 中的统计信息）也可能不存在。幸运的是，实现通常允许 Unikernel 作为正常进程运行，从而提供一种分析路径（尽管在与虚拟机管理程序不同的环境中）。虚拟机管理程序还可以开发检查它们的方法，例如堆栈分析：我开发了一个原型，可以生成正在运行的 MirageOS Unikernel [\[Gregg 16a\]](#ch11-ch11ref18) 的火焰图。

对于所有这些，没有操作系统可供最终用户登录（或进入容器）并进行传统的性能分析。FaaS 和 SaaS 必须由运营商分析。Unikernels 需要自定义工具和统计数据，以及理想的虚拟机管理程序分析支持。

| CPU 性能 | 高（CPU 支持） | 高 | 高（CPU 支持） |
| CPU 分配 | 固定至 vCPU | 灵活（份额 + 带宽） | 固定至 vCPU |
| I/O 吞吐量 | 高（带 SR-IOV） | 高（无固有开销） | 高（带 SR-IOV） |
| I/O 延迟 | 低（带 SR-IOV，无 QEMU） | 低（无固有开销） | 低（带 SR-IOV） |
| 内存访问开销 | 一些（EPT/NPT 或影子页表） | 无 | 一些（EPT/NPT 或影子页表） |
| 内存丢失 | 一些（额外内核、页表） | 无 | 一些（额外内核、页表） |
| 内存分配 | 固定（可能有双重缓存） | 灵活（未使用的容器内存用于文件系统缓存） | 固定（可能有双重缓存） |
| 资源控制 | 大多数（内核加虚拟机管理程序控制） | 许多（取决于内核） | 大多数（内核加虚拟机管理程序控制） |
| 可观测性：来自宿主机 | 中（资源使用情况、虚拟机管理程序统计信息、类似 KVM 的虚拟机管理程序的操作系统检查，但看不到客户实例内部结构） | 高（查看所有内容） | 中（资源使用情况、虚拟机管理程序统计信息、类似 KVM 的虚拟机管理程序的操作系统检查，但看不到客户实例内部结构） |
| 可观测性：来自客户实例 | 高（完整内核和虚拟设备检查） | 中（仅限用户态、内核计数器；完整内核可见性受限），另有额外的宿主机范围指标（例如 iostat(1)） | 高（完整内核和虚拟设备检查） |
| 可观测性有利于 | 最终用户 | 宿主机运营商 | 最终用户 |
| 虚拟机管理程序复杂性 | 最高（添加复杂的虚拟机管理程序） | 中（操作系统） | 高（添加轻量级虚拟机管理程序） |
| 不同类型的客户操作系统 | 是 | 通常否（有时可以使用系统调用转换，这会增加开销） | 是 |

虽然随着为这些虚拟化技术开发更多功能，该表将会过时，但它仍然可以显示需要寻找的内容，即使开发的全新虚拟化技术不适合这些类别。

通常使用微基准测试来比较虚拟化技术，看看哪种技术表现最好。不幸的是，这忽视了能够观察系统的重要性，而观察系统可以带来最大的性能提升。可观测性通常使得识别和消除不必要的工作成为可能，从而使可能的性能优势远远大于细微的虚拟机管理程序差异。

对于云运营商来说，最高可观测性的选择是容器，因为他们可以从宿主机看到所有进程及其交互。对于最终用户来说，它是虚拟机，因为虚拟机为用户提供了内核访问权限来运行所有基于内核的性能工具，包括[第 13 章](#ch13-ch13)、[第 14 章](#ch14-ch14)和[第 15 章](#ch15-ch15)中的工具。另一种选择是具有内核访问权限的容器，使操作员和用户能够全面了解所有内容；然而，这只是当用户也运行容器宿主机时的一个选择，因为它缺乏容器之间的安全隔离。

虚拟化仍然是一个不断发展的领域，轻量级硬件管理程序只是近年来才出现。鉴于它们的好处，特别是对于最终用户的可观测性，我预计它们的使用量会增长。

## 11.7 练习

1. 回答以下有关虚拟化术语的问题：
    - 宿主机与客户实例有什么区别？
    - 什么是租户？
    - 什么是虚拟机管理程序？
    - 什么是硬件虚拟化？
    - 什么是操作系统虚拟化？
2. 回答以下概念性问题：
    - 描述性能隔离的作用。
    - 描述现代硬件虚拟化（例如 Nitro）的性能开销。
    - 描述操作系统虚拟化（例如 Linux 容器）的性能开销。
    - 描述来自硬件虚拟化客户实例（Xen 或 KVM）的物理系统可观测性。
    - 描述在采用操作系统虚拟化的容器实例内，对物理系统的可观测性。
    - 解释硬件虚拟化（例如 Xen 或 KVM）和轻量级硬件虚拟化（例如 Firecracker）之间的区别。
3. 选择一种虚拟化技术，并为客户实例回答以下问题：
    - 描述如何应用内存限制，以及如何对客户实例可见。（当客户实例内存耗尽时，系统管理员会看到什么？）
    - 如果有强制的 CPU 限制，请描述如何应用它以及如何从客户实例中看到它。
    - 如果存在强制的磁盘 I/O 限制，请描述如何应用该限制以及如何从客户实例中看到该限制。
    - 如果存在强制网络 I/O 限制，请描述其应用方式以及客户实例如何看到该限制。
4. 制定资源控制的 USE 方法清单。包括如何获取每个指标（例如，要执行哪个命令）以及如何解释结果。在安装或使用其他软件产品之前，尝试使用现有的操作系统可观测性工具。

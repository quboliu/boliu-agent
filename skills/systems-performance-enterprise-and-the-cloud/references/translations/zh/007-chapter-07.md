# 第 7 章 — 内存

主内存存储应用程序和内核指令、它们的工作数据以及文件系统缓存。这些数据的辅助存储通常是存储设备（磁盘），其速度慢几个数量级。一旦主内存填满，系统就可能开始在主内存和存储设备之间换入换出数据。这一过程很慢，通常会成为系统瓶颈，显著降低性能。系统还可能终止消耗内存最多的进程，导致应用程序中断。

其他需要考虑的性能因素包括分配和释放内存、复制内存以及管理内存地址空间映射的 CPU 开销。在多插槽架构上，内存局部性可能成为一个因素，因为连接到本地插槽的内存访问延迟低于远程插槽。

本章的学习目标是：

- 了解内存概念。
- 熟悉内存硬件内部结构。
- 熟悉内核和用户态分配器的内部结构。
- 具备 MMU 和 TLB 的应用知识。
- 掌握不同的内存分析方法。
- 描述系统范围和每个进程的内存使用情况。
- 识别由可用内存不足引起的问题。
- 定位进程地址空间和内核 slab 中的内存使用情况。
- 使用剖析器、跟踪器和火焰图调查内存使用情况。
- 了解内存的可调参数。

本章分为五个部分，前三个部分提供内存分析的基础，后两个部分展示其在基于 Linux 的系统中的实际应用。各部分如下：

- **背景**介绍与内存相关的术语和关键内存性能概念。
- **架构**提供硬件和软件内存架构的通用描述。
- **方法**解释性能分析方法。
- **可观测性工具**描述了用于内存分析的性能工具。
- **调整**解释调优和示例可调参数。

[第 6 章](#ch06-ch06)、[CPU](#ch06-ch06) 中涵盖了 CPU 内存缓存（1/2/3 级、TLB）。

## 7.1 术语

作为参考，本章中使用的与内存相关的术语包括以下内容：

- **主内存**：也称为*物理内存*，它描述了计算机的快速数据存储区域，通常由 DRAM 提供。
- **虚拟内存**：主内存的抽象，（几乎）无限且不存在竞争。虚拟内存不是真实内存。
- **驻留内存**：当前驻留在主内存中的内存。
- **匿名内存**：没有文件系统位置或路径名的内存，包括进程地址空间的工作数据（称为*堆*）。
- **地址空间**：内存上下文。每个进程和内核都有自己的虚拟地址空间。
- **段**：标记为特定用途的虚拟内存区域，例如用于存储可执行或可写页面。
- **指令文本**：内存中的 CPU 指令，通常位于一个段中。
- **OOM**：内存不足（Out of Memory），指内核检测到可用内存不足的状态。
- **页**：操作系统和 CPU 使用的内存单位。历史上通常为 4 或 8 KB。现代处理器支持*多种页面大小*，以适应更大的尺寸。
- **缺页异常**：无效的内存访问。这些是使用按需虚拟内存时的正常现象。
- **分页**：主内存和存储设备之间的页面传输。
- **交换**：Linux 使用术语“交换”来指代到交换设备的“匿名分页”（“交换页”的传输）。在 Unix 和其他操作系统中，交换是主内存和交换设备之间整个进程的传输。本书使用该术语的 Linux 版本。
- **交换空间**：用于分页匿名数据的磁盘区域。它可能是存储设备上的一个区域，也称为“物理交换设备”，也可能是一个文件系统文件，称为“交换文件”。某些工具使用术语“交换”来指代虚拟内存（这是令人困惑且不正确的）。

本章将介绍其他术语。术语表包含基本术语供需要时参考，包括 *[地址](#gloss-glo-004)*、*buffer* 和 *[DRAM](#gloss-glo-050)*。另请参阅 [第 2 章](#ch02-ch02) 和 [第 3 章](#ch03-ch03) 中的术语部分。

## 7.2 概念

以下是有关内存和内存性能的一些重要概念。

<!-- source-id: ch07#ch07lev2sec1 -->
### 7.2.1 虚拟内存

虚拟内存是一种抽象，它为每个进程和内核提供自己的大型、线性和私有地址空间。它简化了软件开发，将物理内存放置留给操作系统来管理。它还支持多任务处理（虚拟地址空间通过设计分开）和过度使用（使用中的内存可以扩展到主内存之外）。[第 3 章](#ch03-ch03)、[操作系统](#ch03-ch03)、[第 3.2.8 节](#ch03-ch03lev2sec8)、[虚拟内存](#ch03-ch03lev2sec8) 中引入了虚拟内存。有关历史背景，请参阅 [\[Denning 70\]](#ch07-ch07ref2)。

[图 7.1](#ch07-ch07fig01) 显示了进程虚拟内存在具有交换设备（辅助存储）的系统上的作用。图中显示了内存页面，因为大多数虚拟内存实现都是基于页面的。

<!-- source-id: ch07#ch07fig01 -->
![图 7.1 进程虚拟内存](../images/07fig01.jpg)

进程地址空间由虚拟内存子系统映射到主内存和物理交换设备。内核可以根据需要在它们之间移动内存页面，Linux 将此称为*交换*（其他操作系统称为*匿名分页*）。这允许内核“超额分配”主内存。

内核可能会对超额分配施加限制。常用的限制是主内存加上物理交换设备的大小。内核可能拒绝尝试超出此限制的内存分配。这种“虚拟内存不足”错误乍一看可能会令人困惑，因为虚拟内存本身是一种抽象资源。

Linux 还允许其他行为，包括对内存分配设置“无”限制。这称为“内存超额分配”，并将在下面有关分页和按需分页的部分之后描述；内存超额分配依赖于这些机制。

<!-- source-id: ch07#ch07lev2sec2 -->
### 7.2.2 分页

分页是指将页面移入和移出主内存，分别称为“换入（page-in）”和“换出（page-out）”。它由 Atlas 计算机于 1962 年首次引入 [\[Corbató 68\]](#ch07-ch07ref1)，允许：

- 部分加载的程序执行
- 执行大于主内存的程序
- 程序在主内存和存储设备之间高效移动

这些能力在今天仍然有效。与早期交换整个程序的技术不同，分页是一种管理和释放主内存的细粒度方法，因为页面大小单位相对较小（例如 4 KB）。

虚拟内存分页（*分页虚拟内存*）由 BSD 引入 Unix，并成为标准 [\[Babaoglu 79\]](#ch07-ch07ref5)。

随着后来添加用于共享文件系统页面的页面缓存（请参阅[第 8 章](#ch08-ch08)、[文件系统](#ch08-ch08)），两种不同类型的分页变得可用：*文件系统分页*和*匿名分页*。

<!-- source-id: ch07#ch07lev3_1 -->
#### 文件系统分页

文件系统分页是由内存映射文件中页面的读写引起的。对于使用文件内存映射（mmap(2)）的应用程序和使用页面缓存的文件系统（大多数是这样；请参阅[第 8 章](#ch08-ch08)、[文件系统](#ch08-ch08)），这是正常行为。它被称为“良好”分页 [\[McDougall 06a\]](#ch07-ch07ref11)。

当需要时，内核可以通过换出一些内存来释放内存。这就是术语有点棘手的地方：如果主内存中的文件系统页面已被修改（称为“脏”），则页面换出将要求将其写入磁盘。相反，如果文件系统页面未被修改（称为“干净”），则页面换出仅释放内存以供立即重用，因为磁盘上已存在副本。因此，术语“换出”意味着页面被移出内存，这可能包括也可能不包括对存储设备的写入（您可能会在其他文本中看到术语“换出”的不同定义）。

<!-- source-id: ch07#ch07lev3_2 -->
#### 匿名分页（交换）

匿名分页涉及进程私有的数据：进程堆和堆栈。它被称为“匿名”，因为它在操作系统中没有命名位置（即没有文件系统路径名）。匿名页面换出需要将数据移动到物理交换设备或交换文件。Linux 使用术语“交换”来指代这种类型的分页。

匿名分页会损害性能，因此被称为“不良”分页 [\[McDougall 06a\]](#ch07-ch07ref11)。当应用程序访问已换出的内存页时，会阻塞，等待将其读回主内存所需的磁盘 I/O。[^fn-ch07-ch07-footnote-1] 这称为*匿名页换入*，会给应用程序带来同步延迟。匿名页面换出可能不会直接影响应用程序性能，因为它们可以由内核异步执行。

没有匿名分页（交换）时，性能最佳。这可以通过将应用程序配置为保留在可用主内存内，并监视页面扫描、内存利用率和匿名分页来实现，以确保没有内存短缺的迹象。

<!-- source-id: ch07#ch07lev2sec3 -->
### 7.2.3 按需分页

支持按需分页的操作系统（大多数都支持）按需将虚拟内存页映射到物理内存，如[图 7.2](#ch07-ch07fig02)中所示。这会将创建映射的 CPU 开销推迟到实际需要并访问页面时，而不是在首次分配内存范围时。

<!-- source-id: ch07#ch07fig02 -->
![图 7.2 缺页异常示例](../images/07fig02.jpg)

[图 7.2](#ch07-ch07fig02)中显示的序列以提供已分配内存的 malloc()（步骤 1）开始，然后是新分配内存的存储指令（步骤 2）。为了让 MMU 确定存储的主内存位置，它对内存页面执行虚拟到物理的查找（步骤 3），但由于尚未存在映射而失败。此故障称为“缺页异常”（步骤 4），它会触发内核创建按需映射（步骤 5）。一段时间后，内存页面可以被换出到交换设备以释放内存（步骤 6）。

对于映射文件，步骤 2 也可以是加载指令，该文件应包含数据但尚未映射到该进程地址空间。

如果可以从内存中的另一个页面满足映射，则称为*[次缺页异常](#gloss-glo-105)*。在进程的内存增长期间，从可用内存映射新页面时可能会发生这种情况（如图所示）。它也可能发生在映射到另一个现有页面时，例如从映射的共享库读取页面。

需要访问存储设备（图中未显示）的缺页异常（例如访问未缓存的内存映射文件）称为“主缺页异常”。

虚拟内存模型和需求分配的结果是虚拟内存的任意页都可能处于以下状态之一：

1. 未分配
2. 已分配，但未映射（未填充且尚未触发缺页异常）
3. 已分配并映射到主内存（RAM）
4. 已分配并映射到物理交换设备（磁盘）

如果页面由于系统内存压力而被换出，则达到状态 (D)。从 (B) 到 (C) 的转换是缺页异常。如果需要磁盘 I/O，则为主缺页异常；否则，会出现次缺页异常。

从这些状态中，还可以定义两个内存使用术语：

- **驻留集大小** (RSS)：分配的主内存页的大小 (C)
- **虚拟内存大小**：所有分配区域的大小（B + C + D）

按需分页与分页虚拟内存一起通过 BSD 添加到 Unix。它已成为标准并被 Linux 使用。

<!-- source-id: ch07#ch07lev2sec4 -->
### 7.2.4 内存超额分配

Linux 支持“内存超额分配”的概念，它允许分配比系统可能存储的内存更多的内存——比物理内存和交换设备的总和还要多。它依赖于按需分页以及应用程序不使用其分配的大量内存这一趋势。

通过内存超额分配，应用程序对内存的请求（例如 malloc(3)）将会成功，否则它们会失败。应用程序程序员可以慷慨地分配内存，然后根据需要稀疏地使用它，而不是保守地分配内存以保持在虚拟内存限制内。

在 Linux 上，可以使用可调参数配置内存超额分配的行为。详细信息请参见[第 7.6 节](#ch07-ch07lev6)、[调优](#ch07-ch07lev6)。内存超额分配的后果取决于内核如何管理内存压力；参见[第 7.3 节](#ch07-ch07lev3)、[架构](#ch07-ch07lev3)中关于 OOM 杀手的讨论。

<!-- source-id: ch07#ch07lev2sec5 -->
### 7.2.5 进程交换

进程交换是整个进程在主内存和物理交换设备或交换文件之间的移动。这是管理主内存的原始 Unix 技术，也是术语 *swap* [\[Thompson 78\]](#ch07-ch07ref4) 的起源。

要换出进程，必须将其所有私有数据写入交换设备，包括进程堆（匿名数据）、其打开的文件表以及仅在进程处于活动状态时才需要的其他元数据。源自文件系统且未经修改的数据可以丢弃，并在需要时从原始位置再次读取。

进程交换会严重损害性能，因为已换出的进程需要大量磁盘 I/O 才能再次运行。对于当时的机器来说，它在早期的 Unix 上更有意义，例如 PDP-11，其最大进程大小为 64 KB [\[Bach 86\]](#ch07-ch07ref6)。（现代系统允许以 GB 为单位测量进程大小。）

此描述是为了提供历史背景。 Linux 系统根本不交换进程，仅依赖分页。

<!-- source-id: ch07#ch07lev2sec6 -->
### 7.2.6 文件系统缓存使用

系统启动后内存使用量增加是正常现象，因为操作系统使用可用内存来缓存文件系统，从而提高性能。原则是：如果有空闲的主内存，就将其用于有用的事情。这可能会让天真的用户感到苦恼，因为他们会在启动后发现可用内存缩减到接近于零。但它不会给应用程序带来问题，因为当应用程序需要时，内核应该能够快速从文件系统缓存中释放内存。

有关可以消耗主内存的各种文件系统缓存的更多信息，请参阅[第 8 章](#ch08-ch08)、[文件系统](#ch08-ch08)。

<!-- source-id: ch07#ch07lev2sec7 -->
### 7.2.7 利用率和饱和度

主内存利用率可以计算为已用内存与总内存之比。文件系统缓存使用的内存可以视为未使用，因为它可供应用程序重用。

如果对内存的需求超过主内存的数量，主内存就会“饱和”。然后，操作系统可以通过使用分页、进程交换（如果支持）以及 Linux 上的 OOM 杀手（稍后描述）来释放内存。任何这些活动都是主内存饱和的指标。

如果系统对其愿意分配的虚拟内存量施加限制（Linux 内存超额分配则没有），则还可以根据容量利用率来研究虚拟内存。如果是这样，一旦虚拟内存耗尽，内核将无法分配；例如，malloc(3) 失败，errno 设置为 ENOMEM。

请注意，系统上当前可用的虚拟内存有时（令人困惑地）称为“可用交换空间”。

<!-- source-id: ch07#ch07lev2sec8 -->
### 7.2.8 分配器

虽然虚拟内存处理物理内存的多任务处理，但虚拟地址空间内的实际分配和放置通常由分配器处理。这些是用户态库或基于内核的例程，它们为软件程序员提供了一个简单的内存使用界面（例如，malloc(3)、free(3)）。

分配器可以对性能产生重大影响，并且系统可以提供多个用户级分配器库以供选择。它们可以通过使用包括每线程对象缓存在内的技术来提高性能，但如果分配变得碎片化和浪费，它们也会损害性能。[第 7.3 节](#ch07-ch07lev3)、[架构](#ch07-ch07lev3) 中介绍了具体示例。

<!-- source-id: ch07#ch07lev2sec9 -->
### 7.2.9 共享内存

内存可以在进程之间共享。这通常用于系统库，通过与使用它的所有进程共享一份只读指令文本副本来节省内存。

这给显示每个进程主内存使用情况的可观测性工具带来了困难。报告进程的总内存大小时是否应该包括共享内存？Linux 使用的一项技术是提供额外的衡量标准，即“比例集大小”（PSS），其中包括私有内存（非共享）加上共享内存除以使用者数量。请参阅[第 7.5.9 节](#ch07-ch07lev5sec9)、[pmap](#ch07-ch07lev5sec9)，了解可以显示 PSS 的工具。

<!-- source-id: ch07#ch07lev2sec10 -->
### 7.2.10 工作集大小

*工作集大小* (WSS) 是进程经常用于执行工作的主内存量。对于内存性能调整来说，这是一个有用的概念：如果 WSS 可以适应 CPU 缓存而不是主内存，性能应该会大大提高。此外，如果 WSS 超过主内存大小，性能将大大降低，并且应用程序必须交换才能执行工作。

虽然作为一个概念很有用，但在实践中很难测量：可观测性工具中没有 WSS 统计数据（它们通常报告 RSS，而不是 WSS）。[第 7.4.10 节](#ch07-ch07lev4sec10)、[内存收缩](#ch07-ch07lev4sec10) 描述了 WSS 估计的实验方法，[第 7.5.12 节](#ch07-ch07lev5sec12)、[wss](#ch07-ch07lev5sec12) 展示了实验性工作集大小估计工具 wss(8)。

<!-- source-id: ch07#ch07lev2sec11 -->
### 7.2.11 字长

正如[第 6 章](#ch06-ch06)、[CPU](#ch06-ch06)中所介绍的，处理器可以支持多种字大小，例如 32 位和 64 位，从而允许任一软件运行。由于地址空间大小受到字大小可寻址范围的限制，因此需要超过 4 GB 内存的应用程序对于 32 位地址空间来说太大，需要针对 64 位或更高位进行编译。[^fn-ch07-ch07-footnote-2]

根据内核和处理器的不同，某些地址空间可能会保留给内核地址，并且不能供应用程序使用。一个极端的情况是具有 32 位字大小的 Windows，默认情况下为内核保留 2 GB，只为应用程序保留 2 GB [\[Hall 09\]](#ch07-ch07ref14)。在 Linux（或启用了 /3GB 选项的 Windows）上，内核预留空间为 1 GB。对于 64 位字大小（如果处理器支持的话），地址空间要大得多，因此内核预留不应该成为问题。

根据 CPU 架构，使用更大的位宽也可以提高内存性能，因为指令可以在更大的字长上运行。如果数据类型具有较大位宽的未使用位，则可能会浪费少量内存。

<!-- source-id: ch07#ch07lev3sec1 -->
### 7.3.1 硬件

内存硬件包括主内存、总线、CPU 缓存和 MMU。

<!-- source-id: ch07#ch07lev3_3 -->
#### 主内存

当今使用的常见主内存类型是“动态随机存取存储器”（DRAM）。这是一种易失性存储器，断电时其内容就会丢失。DRAM 提供高密度存储，因为每个位仅使用两个逻辑组件来实现：电容器和晶体管。电容器需要定期刷新以保持电量。

企业服务器根据其用途配置不同数量的 DRAM，通常范围从 1 GB 到 1 TB 甚至更大。云计算实例通常较小，每个实例为 512 MB 至 256 GB。[^fn-ch07-ch07-footnote-3] 然而，云计算旨在将负载分散到实例池上，因此它们可以共同为分布式应用程序带来更多的在线 DRAM，尽管一致性成本要高得多。

##### 延迟

主内存的访问时间可以用*列地址选通*（CAS）延迟来衡量：向内存模块发送所需地址（列）与数据可供读取之间的时间。这取决于内存类型（对于 DDR4，约为 10 至 20 ns [\[Crucial 18\]](#ch07-ch07ref21)）。对于内存 I/O 传输，内存总线（例如 64 位宽）传输高速缓存行（例如 64 *字节*宽）时，此延迟可能会发生多次。CPU 和 MMU 读取新的可用数据时还存在其他延迟；从 CPU 缓存返回的读取指令可避免这些延迟。如果处理器支持回写缓存（例如英特尔处理器），写入指令也可以避免这些延迟。

#### 主内存架构

[图 7.3](#ch07-ch07fig03) 中显示了通用双处理器*统一内存访问*（UMA）系统的示例主内存架构。

![图 7.3 UMA 主内存架构示例，双处理器](../images/07fig03.jpg)

每个 CPU 通过共享系统总线对所有内存具有统一的访问延迟。当由跨所有处理器统一运行的单个操作系统内核实例管理时，这也是对称多处理（SMP）架构。

为了进行比较，[图 7.4](#ch07-ch07fig04) 中显示了一个示例双处理器*非一致内存访问*（NUMA）系统，该系统使用作为内存架构一部分的 CPU 互连。对于这种架构，主内存的访问时间根据其相对于 CPU 的位置而变化。

<!-- source-id: ch07#ch07fig04 -->
![图 7.4 NUMA 主内存架构示例，双处理器](../images/07fig04.jpg)

CPU 1 可以通过其内存总线直接对 DRAM A 执行 I/O。这称为*本地内存*。CPU 1 通过 CPU 2 和 CPU 互连（两跳）对 DRAM B 执行 I/O。这被称为“远程内存”，并且具有较高的访问延迟。

连接到每个 CPU 的内存组称为“内存节点”，或简称为“节点”。操作系统可以基于处理器提供的信息了解内存节点拓扑。然后，它可以根据“内存局部性”分配内存并调度线程，尽可能使用本地内存以提高性能。

#### 总线

主内存如何物理连接到系统取决于主内存架构，如前图所示。实际的实现可能涉及 CPU 和内存之间的附加控制器和总线。主内存可以通过以下方式之一访问：

- **共享系统总线**：单处理器或多处理器，通过共享系统总线、内存桥控制器，最后是内存总线。这在 UMA 示例[图 7.3](#ch07-ch07fig03)以及 Intel 前端总线示例[图 6.9](#ch06-ch06fig09)（见[第 6 章](#ch06-ch06)、[CPU](#ch06-ch06)）中有所描绘。该示例中的内存控制器是北桥。
- **直接**：通过内存总线直接连接内存的单处理器。
- **互连**：多处理器，每个处理器通过内存总线直接连接内存，并通过 CPU 互连连接处理器。这在之前的[图 7.4](#ch07-ch07fig04)中被描述为 NUMA 示例；CPU 互连在[第 6 章](#ch06-ch06)、[CPU](#ch06-ch06)中讨论。

如果您怀疑您的系统不属于上述任何一种情况，请找到系统功能图并沿着 CPU 和内存之间的数据路径进行跟踪，并记下沿途的所有组件。

##### DDR 内存

对于任何架构，内存总线的速度通常由处理器和系统板支持的内存接口标准决定。自 1996 年以来使用的通用标准是“双倍数据速率同步动态随机存取存储器”（DDR SDRAM）。术语“双倍数据速率”是指在时钟信号的上升和下降沿传输数据（也称为“双沿传输”）。术语“同步”是指内存与 CPU 同步计时。

#### CPU 缓存

处理器通常包括片上硬件缓存以提高内存访问性能。缓存可能包括以下级别，速度逐渐降低，大小逐渐增大：

- **1 级**：通常分为单独的指令缓存和数据缓存
- **2 级**：指令和数据的缓存
- **3 级**：另一个更大级别的缓存

根据处理器的不同，级别 1 通常由虚拟内存地址引用，级别 2 及以上由物理内存地址引用。

这些缓存在[第 6 章](#ch06-ch06)、[CPU](#ch06-ch06)中进行了更深入的讨论。本章讨论另一种类型的硬件高速缓存，即 TLB。

MMU（内存管理单元）负责虚拟地址到物理地址的转换。这些转换按页执行，并且直接映射页内的偏移量。MMU 是在[第 6 章](#ch06-ch06)、[CPU](#ch06-ch06)中 CPU 缓存的上下文附近引入的。

##### 多种页面大小

现代处理器支持多种页面大小，这允许操作系统和 MMU 使用不同的页面大小（例如 4 KB、2 MB、1 GB）。 Linux *大页面* 功能支持更大的页面大小，例如 2 MB 或 1 GB。

#### TLB

[图 7.5](#ch07-ch07fig05)中的 MMU 使用 TLB（转换后备缓冲区）作为第一级地址转换缓存，后面是主内存中的页表。TLB 可以分为指令页和数据页的单独高速缓存。

由于 TLB 的映射条目数量有限，因此使用较大的页面大小会增加可从其缓存转换的内存范围（其*覆盖范围*），从而减少 TLB 未命中并提高系统性能。TLB 可以针对每个页面大小进一步划分为单独的高速缓存，从而提高在高速缓存中保留较大映射的可能性。

### 7.3.2 软件

内存管理软件包括虚拟内存系统、地址转换、交换、分页和分配。本节包含与性能最相关的主题：释放内存、空闲列表、页面扫描、交换、进程地址空间和内存分配器。

<!-- source-id: ch07#ch07lev3_9 -->
#### 释放内存

当系统上的可用内存变低时，内核可以使用多种方法来释放内存，将其添加到页面的“空闲列表”中。这些方法如适用于 Linux 的[图 7.6](#ch07-ch07fig06)所示，按照可用内存减少时的“一般”顺序。

<!-- source-id: ch07#ch07fig06 -->
![图 7.6 Linux 内存可用性管理](../images/07fig06.jpg)

这些方法是：

- **空闲列表**：未使用且可立即分配的页面列表（也称为*空闲内存*）。这通常以多个“空闲页面列表”的形式实现，每个列表对应一个 NUMA 内存节点。
- **页面缓存**：文件系统缓存。名为 *swappiness* 的可调参数用于调节从页面缓存回收内存与进行交换之间的相对偏好。
- **交换**：这是由换出守护进程 kswapd 进行的分页，它会查找最近未使用的页面以添加到空闲列表中，包括应用程序内存。这些页面会被换出，可能涉及写入基于文件系统的交换文件或交换设备。当然，只有配置了交换文件或设备后，这才可用。
- **回收**：当超过低内存阈值时，可以指示内核模块和内核 slab 分配器立即释放任何可以轻易释放的内存。这也称为“收缩”。
- **OOM 杀手**：内存不足杀手通过查找并终止牺牲进程来释放内存：使用 select\_bad\_process() 找到进程，然后调用 oom\_kill\_process() 终止它。这可能会作为“内存不足：终止进程”消息记录在系统日志（/var/log/messages）中。

Linux swappiness 参数控制是通过分页应用程序，还是通过从页面缓存回收内存来释放内存。它是 0 到 100 之间的数字（默认值为 60），其中较高的值有利于通过分页释放内存。控制这些内存释放技术之间的平衡，可以在保留热文件系统缓存的同时换出冷应用程序内存，从而提高系统吞吐量 [\[Corbet 04\]](#ch07-ch07ref9)。

考虑没有配置交换设备或交换文件时会发生什么也很有意思。这限制了虚拟内存大小，因此如果禁用了内存超额分配，内存分配将很快失败。在 Linux 上，这也可能意味着 OOM 杀手会更快被使用。

考虑一个存在内存无限增长问题的应用程序。如果配置了交换，这可能首先因分页而成为性能问题，从而提供实时调试问题的机会。如果没有交换，就没有分页带来的缓冲时间，因此应用程序要么遇到“内存不足”错误，要么被 OOM 杀手终止。如果仅在使用数小时后才发现问题，这可能会延迟调试问题。

在 Netflix 的云环境中，实例通常不使用交换，因此应用程序如果耗尽内存就会被 OOM 终止。应用程序分布在大量实例中，某个实例中的应用程序被 OOM 终止会使流量立即重定向到其他运行状况良好的实例。这被认为比允许一个实例由于交换而缓慢运行更好。

当使用内存 cgroup 时，可以使用与[图 7.6](#ch07-ch07fig06)中所示类似的内存释放技术来管理 cgroup 内存。系统可能拥有大量可用内存，但仍在交换或遇到 OOM 杀手，因为容器已耗尽其 cgroup 控制的限制 [\[Evans 17\]](#ch07-ch07ref18)。有关 cgroup 和容器的更多信息，请参阅[第 11 章](#ch11-ch11)、[云计算](#ch11-ch11)。

以下部分描述了空闲列表、回收和换出守护进程。

#### 空闲列表

最初的 Unix 内存分配器使用内存映射和首次适应扫描。随着 BSD 中分页虚拟内存的引入，添加了“空闲列表”和“换出守护进程”[\[Babaoglu 79\]](#ch07-ch07ref5)。空闲列表（如[图 7.7](#ch07-ch07fig07)所示）允许立即找到可用内存。

<!-- source-id: ch07#ch07fig07 -->
![图 7.7 空闲列表操作](../images/07fig07.jpg)

释放的内存将添加到列表的头部以供将来分配。由页面换出守护进程释放的内存（并且可能仍然包含有用的缓存文件系统页面）被添加到尾部。如果在重用有用页面之前发生对这些页面之一的未来请求，则可以“回收”该页面并将其从空闲列表中删除。

基于 Linux 的系统仍在使用一种形式的空闲列表，如[图 7.6](#ch07-ch07fig06)所示。空闲列表通常通过分配器使用，例如内核的 slab 分配器和用户空间的 libc malloc()（有自己的空闲列表）。这些分配器依次消耗页面，然后通过其分配器 API 提供内存。

Linux 使用伙伴分配器来管理页面。这为不同大小的内存分配提供了多个空闲列表，遵循以 2 的整数次幂划分的方案。术语“buddy”指的是寻找空闲内存的相邻页面，以便可以将它们一起分配。有关历史背景，请参阅 [\[Peterson 77\]](#ch07-ch07ref3)。

伙伴空闲列表位于以下层次结构的底部，从每个内存节点 pg\_data\_t 开始：

- **节点**：内存组，NUMA 感知
- **区域**：用于某些目的的内存范围（直接内存访问 \[DMA\]、[^fn-ch07-ch07-footnote-4] normal、highmem）
- **迁移类型**：不可移动、可回收、可移动等。
- **阶**：页数为 2 的整数次幂

在节点空闲列表内进行分配可以提高内存局部性和性能。对于最常见的分配（单页），伙伴分配器为每个 CPU 保留单页列表，以减少 CPU 锁争用。

<!-- source-id: ch07#ch07lev3_11 -->
#### 回收

回收主要涉及从内核 slab 分配器缓存中释放内存。这些缓存包含 slab 大小块中未使用的内存，可供重用。回收将此内存返回给系统以进行页面分配。

在 Linux 上，内核模块还可以调用 register\_shrinker() 来注册特定函数以回收自己的内存。

<!-- source-id: ch07#ch07lev3_12 -->
#### 页面扫描

通过分页释放内存是由内核换出守护进程管理的。当空闲列表中的可用主内存低于阈值时，换出守护进程开始*页面扫描*。仅在需要时才进行页面扫描。正常平衡的系统可能不会经常进行页面扫描，并且可能只在短时间内进行页面扫描。

在 Linux 上，换出守护进程称为 kswapd，它扫描非活动和活动内存的 LRU 页面列表以释放页面。它根据可用内存和两个阈值来唤醒以提供迟滞，如[图 7.8](#ch07-ch07fig08)所示。

<!-- source-id: ch07#ch07fig08 -->
![图 7.8 kswapd 唤醒和模式](../images/07fig08.jpg)

一旦可用内存达到最低阈值，kswapd 将在前台运行，根据请求同步释放内存页，这种方法有时称为“直接回收”[\[Gorman 04\]](#ch07-ch07ref10)。这个最低阈值是可调的（vm.min\_free\_kbytes），其他阈值基于它进行缩放（低阈值缩放 2 倍，高阈值缩放 3 倍）。对于分配突发超过 kswapd 回收能力的工作负载，Linux 提供了额外的可调参数以进行更积极的扫描：vm.watermark\_scale\_factor 和 vm.watermark\_boost\_factor。请参阅[第 7.6.1 节](#ch07-ch07lev6sec1)、[可调参数](#ch07-ch07lev6sec1)。

页面缓存具有单独的“非活动页面”和“活动页面”列表。它们以 LRU 方式运行，允许 kswapd 快速找到空闲页面。它们显示在[图 7.9](#ch07-ch07fig09)中。

<!-- source-id: ch07#ch07fig09 -->
![图 7.9 kswapd 列表](../images/07fig09.jpg)

kswapd 首先扫描非活动列表，然后根据需要扫描活动列表。术语“扫描”是指在遍历列表时检查页面：如果页面被锁定或为脏页，则可能没有资格释放该页面。kswapd 使用的术语“扫描”与原始 UNIX 换出守护进程执行的扫描具有不同的含义，后者扫描所有内存。

### 7.3.3 进程虚拟地址空间

进程虚拟地址空间由硬件和软件管理，是根据需要映射到物理页的一系列虚拟页。这些地址被分为名为[段](#gloss-glo-147)的区域，用于存储线程堆栈、进程可执行文件、库和堆。[图 7.10](#ch07-ch07fig10)中显示了 Linux 上 32 位进程的示例，适用于 x86 和 SPARC 处理器。

<!-- source-id: ch07#ch07fig10 -->
![图 7.10 进程虚拟内存地址空间示例](../images/07fig10.jpg)

在 SPARC 上，内核驻留在单独的完整地址空间中（[图 7.10](#ch07-ch07fig10)中未显示）。请注意，在 SPARC 上，无法仅根据指针值来区分用户地址和内核地址；x86 采用不同的方案，其中用户和内核地址不重叠。[^fn-ch07-ch07-footnote-5]

程序可执行段包含单独的文本段和数据段。库还由单独的可执行文本和数据段组成。这些不同的段类型是：

- **可执行文本**：包含进程的可执行 CPU 指令。这是从文件系统上二进制程序的文本段映射的。它是只读的，具有执行权限。
- **可执行数据**：包含从二进制程序的数据段映射的初始化变量。它具有读/写权限，以便可以在程序运行时修改变量。它还有一个私有标志，以便修改不会刷新到磁盘。
- **堆**：这是程序的工作内存，并且是匿名内存（无文件系统位置）。它根据需要增长，并通过 malloc(3) 分配。
- **堆栈**：正在运行的线程的堆栈，映射读/写。

库文本段可以由使用同一库的其他进程共享，每个进程都有库数据段的私有副本。

##### 堆增长

造成混乱的一个常见原因是堆的无休止增长。是内存泄漏吗？对于简单的分配器，free(3) 不会将内存返回给操作系统；相反，内存会被保留以供将来分配。这意味着进程驻留内存只能增长，这是正常的。进程减少系统内存使用的方法包括：

- **重新执行**：调用 execve(2) 从空地址空间开始
- **内存映射**：使用 mmap(2) 和 munmap(2)，将内存返回给系统

内存映射文件在[第 8 章](#ch08-ch08)、[文件系统](#ch08-ch08)、[第 8.3.10 节](#ch08-ch08lev3sec10)、[内存映射文件](#ch08-ch08lev3sec10)中进行了描述。

glibc 通常在 Linux 上使用，是一种高级分配器，支持 mmap 操作模式，以及用于向系统释放可用内存的 malloc\_trim(3) 函数。当堆顶可用内存变大时，malloc\_trim(3) 由 free(3) 自动调用，[^fn-ch07-ch07-footnote-6]并使用 sbrk(2) 系统调用释放它。

#### 分配器

有多种用于内存分配的用户级和内核级分配器。[图 7.11](#ch07-ch07fig11)展示了分配器的作用，包括一些常见的类型。

<!-- source-id: ch07#ch07fig11 -->
![图 7.11 用户级和内核级内存分配器](../images/07fig11.jpg)

页面管理之前已在[第 7.3.2 节](#ch07-ch07lev3sec2)、[软件](#ch07-ch07lev3sec2)中的空闲列表下进行了描述。

内存分配器功能可包括：

- **简单 API**：例如，malloc(3)、free(3)。
- **高效的内存使用**：当为各种大小的内存分配提供服务时，内存使用可能会变得“碎片化”，其中有许多未使用的区域浪费了内存。分配器可以努力合并未使用的区域，以便更大的分配可以利用它们，从而提高效率。
- **性能**：内存分配可能很频繁，并且在多线程环境中，由于同步原语的争用，它们的性能可能会很差。分配器可以设计为谨慎使用锁，还可以利用每线程或每 CPU 缓存来提高内存局部性。
- **[可观测性](#gloss-glo-110)**：分配器可以提供统计和调试模式以显示它的使用方式以及哪些代码路径负责分配。

以下各节介绍了内核级分配器（slab 和 SLUB）以及用户级分配器（glibc、TCMalloc 和 jemalloc）。

##### slab

内核 slab 分配器管理特定大小对象的缓存，允许它们快速回收，而无需页面分配的开销。这对于内核分配尤其有效，内核分配通常用于固定大小的结构。

作为内核示例，以下两行来自 ZFS arc.c[^fn-ch07-ch07-footnote-7]：

![点此查看代码图片](../images/pg321.jpg)

```text
        df = kmem_alloc(sizeof (l2arc_data_free_t), KM_SLEEP);
        head = kmem_cache_alloc(hdr_cache, KM_PUSHPAGE);
```

第一个是 kmem\_alloc()，显示了传统风格的内核分配，其大小作为参数传递。内核根据该大小将其映射到一个 slab 缓存（非常大的大小由*oversize arena*以不同的方式处理）。第二个，kmem\_cache\_alloc()，直接在自定义的 slab 分配器缓存上运行，在本例中是（kmem\_cache\_t \*)hdr\_cache。

为 Solaris 2.4 [\[Bonwick 94\]](#ch07-ch07ref7) 开发，slab 分配器后来通过称为 *magazines* [\[Bonwick 01\]](#ch07-ch07ref8) 的每 CPU 缓存进行了增强：

我们的基本方法是为每个 CPU 提供一个称为 magazine 的 M 元素缓存，借用了自动武器弹匣的类比。在 CPU 需要重新装载之前，每个 CPU 的 magazine 可以满足 M 次分配，即用满 magazine 替换空 magazine。

除了高性能之外，原始的 slab 分配器还具有调试和分析功能，包括审计跟踪分配细节和堆栈跟踪。

slab 分配已被各种操作系统采用。BSD 有一个称为通用内存分配器（UMA）的内核 slab 分配器，它非常高效且支持 NUMA。在 Linux 2.2 版本中，slab 分配器也被引入，多年来它一直是默认选项。Linux 此后已将 SLUB 作为选项或默认选项。

##### SLUB

Linux 内核 SLUB 分配器基于 slab 分配器，旨在解决各种问题，特别是 slab 分配器的复杂性。改进包括删除对象队列和每 CPU 缓存，将 NUMA 优化留给页面分配器（请参阅前面的空闲列表部分）。

SLUB 分配器在 Linux 2.6.23 [\[Lameter 07\]](#ch07-ch07ref13) 中成为默认选项。

##### glibc

用户级 GNU libc 分配器基于 Doug Lea 的 dlmalloc。其行为取决于分配请求的大小。小分配由内存分箱（bin）提供，其中包含类似大小的单元，可以使用类似伙伴的算法来合并这些单元。较大的分配可以使用树查找来有效地查找空间。非常大的分配切换到使用 mmap(2)。最终结果是一个高性能的分配器，受益于多种分配策略。

##### TCMalloc

TCMalloc 是用户级线程缓存 malloc，它使用每线程缓存进行小型分配，减少锁争用并提高性能 [\[Ghemawat 07\]](#ch07-ch07ref12)。定期垃圾回收将内存迁移回中央堆进行分配。

##### jemalloc

libjemalloc 最初是 FreeBSD 用户级 libc 分配器，也可用于 Linux。它使用多 arena、每线程缓存和小对象 slab 等技术来提高可扩展性并减少内存碎片。它可以使用 mmap(2) 和 sbrk(2) 来获取系统内存，优先使用 mmap(2)。Facebook 使用 jemalloc 并添加了分析和其他优化 [\[Facebook 11\]](#ch07-ch07ref17)。

### 7.4.1 工具方法

工具方法是遍历可用工具、检查它们提供的关键指标的过程。这是一种简单的方法，但可能会忽略现有工具可见性较差或完全无法观测的问题，而且执行起来可能非常耗时。

对于内存，工具方法可能涉及针对 Linux 检查以下内容：

- **页面扫描**：查找连续页面扫描（超过 10 秒）作为内存压力的迹象。这可以使用 `sar -B` 并检查 `pgscan` 列来完成。
- **压力停滞信息（PSI）**：使用 `cat /proc/pressure/memory`（Linux 4.20+）检查内存压力（饱和度）统计信息及其随时间的变化情况。
- **交换**：如果配置了交换，则内存页面的交换（Linux 交换的定义）进一步表明系统内存不足。您可以使用 vmstat(8) 并检查 `si` 和 `so` 列。
- **`vmstat`**：运行 `vmstat 1` 并检查 `free` 列的可用内存。
- **OOM 杀手**：这些事件可以在系统日志（/var/log/messages）或 dmesg(1) 中看到。搜索“内存不足”。
- **`top`**：查看哪些进程和用户是最大的物理内存消耗者（常驻）和虚拟内存消耗者（请参阅手册页了解列名称，这些名称根据版本而有所不同）。 top(1) 还总结了可用内存。
- **perf(1)/BCC/bpftrace**：使用堆栈跟踪跟踪内存分配，以识别内存使用的原因。请注意，这可能会花费相当大的开销。一种更便宜但粗糙的解决方案是执行 CPU 分析（定时堆栈采样）并搜索分配代码路径。

有关每个工具的更多信息，请参阅[第 7.5 节](#ch07-ch07lev5)、[可观测性工具](#ch07-ch07lev5)。

<!-- source-id: ch07#ch07lev4sec2 -->
### 7.4.2 USE 方法

USE 方法用于在性能调查的早期识别所有组件的利用率、饱和度和错误，然后再采取更深入、更耗时的策略。

检查系统范围内的：

- **利用率**：正在使用多少内存，以及有多少内存可用。物理内存和虚拟内存都应该检查。
- **饱和**：作为缓解内存压力的措施，执行页面扫描、分页、交换和 Linux OOM 杀手终止进程的程度。
- **错误**：软件或硬件错误。

您可能需要首先检查饱和度，因为持续饱和是内存问题的迹象。这些指标通常可以从操作系统工具中轻松获得，包括用于交换统计信息的 vmstat(8) 和 sar(1)，以及用于 OOM 杀手终止进程的 dmesg(1)。对于配置有单独磁盘交换设备的系统，交换设备的任何活动都是内存压力的另一个迹象。Linux 还提供内存饱和统计信息，作为压力停滞信息（PSI）的一部分。

不同的工具可以以不同的方式报告物理内存利用率，具体取决于它们是否考虑了未引用的文件系统缓存页面或非活动页面。系统可能会报告它只有 10 MB 的可用内存，而实际上它有 10 GB 的文件系统缓存，可以在需要时立即被应用程序回收。检查工具文档以了解其中包含的内容。

可能还需要检查虚拟内存利用率，具体取决于系统是否执行内存超额分配。对于不这样做的系统，一旦虚拟内存耗尽，内存分配就会失败——这是一种内存错误。

内存错误可能是由软件引起的，例如失败的内存分配或 Linux OOM 杀手，也可能是由硬件引起的，例如 ECC 错误。从历史上看，内存分配错误一直由应用程序报告，尽管并非所有应用程序都这样做（并且，由于 Linux 内存超额分配，开发人员可能认为没有必要）。硬件错误也很难诊断。使用 ECC 内存时，某些工具可能会报告 ECC 可纠正错误，例如 Linux 上的 dmidecode(8)、edac-utils 和 `ipmitool sel`。这些可纠正的错误可以用作 USE 方法的错误指标，并且可能是不久后发生不可纠正错误的信号。对于实际的（不可纠正的）内存错误，您可能会遇到任意应用程序无法解释且不可重现的崩溃（包括段错误和总线错误信号）。

对于实施内存限制或配额（资源控制）的环境（如在某些云计算环境中），可能需要以不同的方式测量内存利用率和饱和度。即使主机上有足够的物理内存，您的操作系统实例也可能达到软件内存限制并开始交换。请参见[第 11 章](#ch11-ch11)、[云计算](#ch11-ch11)。

<!-- source-id: ch07#ch07lev4sec3 -->
### 7.4.3 使用特征

在进行容量规划、基准测试和模拟工作负载时，表征内存使用情况是一项重要的练习。它还可以通过查找和纠正错误配置来带来一些最大的性能提升。例如，数据库缓存可能配置得太小，命中率低，或者太大，导致系统分页。

对于内存，表征使用情况涉及识别内存的使用位置和数量：

- 系统范围的物理和虚拟内存利用率
- 饱和度：交换和 OOM 杀死
- 内核和文件系统缓存内存使用情况
- 每个进程的物理和虚拟内存使用情况
- 内存资源控制的使用（如果存在）

以下示例描述了如何一起表述这些属性：

系统有 256 GB 的主内存，其中 1% 被进程使用（已利用），30% 被文件系统缓存使用。最大的进程是数据库，消耗 2 GB 主内存（RSS），这一限制沿用了数据库迁移前所在旧系统的配置。

随着更多内存用于缓存工作数据，这些特征可能会随着时间的推移而变化。除了常规缓存增长之外，内核或应用程序内存也可能由于内存泄漏（软件错误）而随着时间的推移而不断增长。

<!-- source-id: ch07#ch07lev3_14 -->
#### 高级使用分析/清单

这里列出了其他特征作为需要考虑的问题，也可以作为彻底研究内存问题时的清单：

- 应用程序的工作集大小（WSS）是多少？
- 内核内存在哪里使用？各个 slab 中分别使用了多少？
- 文件系统缓存有多少是活动的，而不是非活动的？
- 进程内存在哪里使用（指令、缓存、缓冲区、对象等）？
- 为什么进程要分配内存（调用路径）？
- 为什么内核分配内存（调用路径）？
- 进程库映射有什么奇怪的地方（例如，随时间变化）？
- 哪些进程正在被主动换出？
- 哪些进程之前已被换出？
- 进程或内核是否存在内存泄漏？
- 在 NUMA 系统中，内存在内存节点之间的分布情况如何？
- IPC 和内存停顿周期率是多少？
- 内存总线的平衡程度如何？
- 与远程内存 I/O 相比，执行了多少本地内存 I/O？

以下部分可以帮助回答其中一些问题。请参阅[第 2 章](#ch02-ch02)、[方法论](#ch02-ch02)，了解此方法的更高级别摘要以及要衡量的特征（谁、为什么、什么、如何）。

<!-- source-id: ch07#ch07lev4sec4 -->
### 7.4.4 周期分析

内存总线负载可以通过检查 CPU 性能监控计数器（PMC）来确定，该计数器可以通过编程来计算内存停顿周期、内存总线使用情况等。首先的指标是每周期指令数（IPC），它反映了 CPU 负载对内存的依赖程度。请参见[第 6 章](#ch06-ch06)、[CPU](#ch06-ch06)。

<!-- source-id: ch07#ch07lev4sec5 -->
### 7.4.5 性能监控

性能监控可以随着时间的推移识别活动问题和行为模式。内存的关键指标是：

- **利用率**：使用百分比，可以从可用内存推断
- **饱和**：交换、OOM 杀死

对于实施内存限制或配额（资源控制）的环境，可能还需要收集与所施加的限制相关的统计信息。

还可以监视错误（如果可用），如[第 7.4.2 节](#ch07-ch07lev4sec2)、[USE 方法](#ch07-ch07lev4sec2)中的利用率和饱和度所述。

监控一段时间内的内存使用情况，尤其是按进程监控内存使用情况，可以帮助识别内存泄漏的存在和发生率。

<!-- source-id: ch07#ch07lev4sec6 -->
### 7.4.6 泄漏检测

当应用程序或内核模块无休止地增长，消耗来自空闲列表、文件系统缓存以及最终来自其他进程的内存时，就会出现此问题。这可能首先表现为系统开始交换，或应用程序因持续的内存压力而被 OOM 杀死。

此类问题由以下任一原因引起：

- **内存泄漏**：一种软件错误，内存不再使用但从未释放。这可以通过修改软件代码或应用补丁或升级（修改代码）来解决。
- **内存增长**：软件正常消耗内存，但消耗速度远高于系统可接受的速度。通过更改软件配置或软件开发人员更改应用程序消耗内存的方式可以解决此问题。

内存增长问题经常被误认为是内存泄漏。首先要问的问题是：它应该这样做吗？检查内存使用情况、应用程序的配置及其分配器的行为。应用程序可以被配置为填充存储器高速缓存，并且观察到的增长可以是高速缓存预热。

如何分析内存泄漏取决于软件和语言类型。一些分配器提供调试模式来记录分配详细信息，然后可以对这些详细信息进行事后分析以识别负责的调用路径。某些运行时具有用于进行堆转储分析的方法，以及用于进行内存泄漏调查的其他工具。

Linux BCC 跟踪工具包括用于增长和泄漏分析的 memleak(8)：它跟踪分配并记录一段时间内未释放的分配以及分配代码路径。它无法判断这些是泄漏还是正常增长，因此需要分析代码路径以确定是哪种情况。（请注意，此工具在高分配率的情况下也会产生高开销。）BCC 包含在[第 15 章](#ch15-ch15)、[BPF](#ch15-ch15)、[第 15.1 节](#ch15-ch15lev1)、[BCC](#ch15-ch15lev1)中。

<!-- source-id: ch07#ch07lev4sec7 -->
### 7.4.7 静态性能调优

静态性能调优重点关注配置环境的问题。对于内存性能，请检查静态配置的以下方面：

- 主内存总共有多少？
- 应用程序配置使用多少内存（它们自己的配置）？
- 应用程序使用哪些内存分配器？
- 主存储器的速度是多少？它是可用的最快类型 (DDR5)吗？
- 主内存是否经过全面测试（例如，使用 Linux memtester）？
- 系统架构是怎样的？NUMA，还是 UMA？
- 操作系统是否支持 NUMA？它提供 NUMA 可调参数吗？
- 内存是连接到同一个插槽，还是跨插槽分开？
- 有多少内存总线？
- CPU 缓存与 TLB 的数量及大小是多少？
- BIOS 设置是什么？
- 是否配置和使用了大页面？
- 内存超额分配是否可用并已配置？
- 正在使用哪些其他系统内存可调参数？
- 是否存在软件施加的内存限制（资源控制）？

回答这些问题可能会揭示被忽视的配置选择。

<!-- source-id: ch07#ch07lev4sec8 -->
### 7.4.8 资源控制

操作系统可以提供细粒度的控制以将内存分配给进程或进程组。这些控制可能包括主内存和虚拟内存使用的固定限制。它们的工作原理取决于具体实现，并在[第 7.6 节](#ch07-ch07lev6)、[调优](#ch07-ch07lev6)和[第 11 章](#ch11-ch11)、[云计算](#ch11-ch11)中进行讨论。

<!-- source-id: ch07#ch07lev4sec9 -->
### 7.4.9 微基准测试

微基准测试可用于确定主内存的速度和特征，例如 CPU 高速缓存和高速缓存行大小。这在分析系统之间的差异时可能会有所帮助，因为内存访问速度对性能的影响可能比 CPU 时钟速度更大，具体取决于应用程序和工作负载。

在[第 6 章](#ch06-ch06)、[CPU](#ch06-ch06)中，CPU 缓存下的延迟部分（在[第 6.4.1 节](#ch06-ch06lev4sec1)、[硬件](#ch06-ch06lev4sec1)中）显示了微基准测试内存访问延迟的结果，以确定 CPU 缓存的特性。

<!-- source-id: ch07#ch07lev4sec10 -->
### 7.4.10 内存收缩

这是一种通过*反向实验*估算工作集大小（WSS）的方法，实验需要配置交换设备。逐步减少应用程序可用的主存，同时测量性能和换页活动：当性能急剧下降、换页活动大幅增加时，就表明可用内存已无法容纳工作集。

虽然值得作为反向实验的例子一提，但不建议将其用于生产环境，因为它会故意损害性能。有关其他 WSS 估计技术，请参阅[第 7.5.12 节](#ch07-ch07lev5sec12)、[wss](#ch07-ch07lev5sec12)中的实验性 wss(8) 工具以及我的 WSS 估计网站 [\[Gregg 18c\]](#ch07-ch07ref22)。

### 7.5.1 vmstat

虚拟内存统计命令 vmstat(8) 提供系统内存运行状况的高级视图，包括当前可用内存和分页统计信息。还包括 CPU 统计信息，如[第 6 章](#ch06-ch06)、[CPU](#ch06-ch06)中所述。

当 Bill Joy 和 Ozalp Babaoglu 于 1979 年为 BSD 引入它时，原始手册页包括：

已知问题（BUGS）：打印出的数字太多，有时很难弄清楚该看什么。

以下是 Linux 版本的输出示例：

![点此查看代码图片](../images/pg329.jpg)

```text
$ vmstat 1
procs -----------memory---------- ---swap-- -----io---- -system-- ----cpu----
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa
 4  0      0 34454064 111516 13438596   0   0    0    5    2    0  0  0 100  0
 4  0      0 34455208 111516 13438596   0   0    0    0 2262 15303 16 12 73  0
 5  0      0 34455588 111516 13438596   0   0    0    0 1961 15221 15 11 74  0
 4  0      0 34456300 111516 13438596   0   0    0    0 2343 15294 15 11 73  0
[...]
```

此版本的 vmstat(8) 不会在输出的第一行打印 `procs` 或 `memory` 列的启动后摘要值，而是立即显示当前状态。默认情况下，列以千字节为单位：

- **`swpd`**：换出的内存量
- **`free`**：可用内存
- **`buff`**：缓冲区高速缓存中的内存
- **`cache`**：页面缓存中的内存
- **`si`**：内存换入（分页）
- **`so`**：内存换出（分页）

缓冲区和页缓存在[第 8 章](#ch08-ch08)、[文件系统](#ch08-ch08)中进行了描述。系统中的可用内存在启动后减少并被这些缓存使用以提高性能是正常的。需要时可以将其释放以供应用程序使用。

如果 `si` 和 `so` 列持续不为零，则系统面临内存压力并且正在交换到交换设备或文件（请参阅 swapon(8)）。其他工具，包括那些按进程显示内存的工具（例如 top(1)、ps(1)），可用于调查正在消耗内存的内容。

在具有大量内存的系统上，列可能会变得不对齐并且有点难以读取。您可以尝试使用 `-S` 选项将输出单位更改为兆字节（使用 `m` 表示 1,000,000，使用 `M` 表示 1,048,576）：

![点此查看代码图片](../images/pg330-1.jpg)

```text
$ vmstat -Sm 1
procs -----------memory---------- ---swap-- -----io---- -system-- ----cpu----
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa
 4  0      0  35280    114  13761    0    0     0     5    2    1  0  0 100  0
 4  0      0  35281    114  13761    0    0     0     0 2027 15146 16 13 70  0
[...]
```

还有一个 `-a` 选项可以打印页面缓存中*非活动*和*活动*内存的详细信息：

![点击查看代码图片](../images/pg330-2.jpg)

```text
$ vmstat -a 1
procs -----------memory---------- ---swap-- -----io---- -system-- ----cpu----
 r  b   swpd   free  inact active   si   so    bi    bo   in   cs us sy id wa
 5  0      0 34453536 10358040 3201540   0   0    0    5    2    0  0  0 100  0
 4  0      0 34453228 10358040 3200648   0   0    0    0 2464 15261 16 12 71  0
[...]
```

可以使用小写的 `-s` 选项将这些内存统计信息打印为列表。

### 7.5.2 PSI

Linux 4.20 中添加的 Linux 压力停滞信息（PSI）包括内存饱和度的统计信息。这些不仅显示是否存在内存压力，还显示过去五分钟内存压力的变化情况。输出示例：

![点此查看代码图片](../images/pg331-1.jpg)

```text
# cat /proc/pressure/memory
some avg10=2.84 avg60=1.23 avg300=0.32 total=1468344
full avg10=1.85 avg60=0.66 avg300=0.16 total=702578
```

此输出显示内存压力正在增加，10 秒平均值（2.84）高于 300 秒平均值（0.32）。这些平均值是任务因内存而停滞的时间百分比。`some` 行显示某些任务（线程）何时受到影响，`full` 行显示何时所有可运行任务受到影响。

还按 cgroup2 跟踪 PSI 统计信息（[第 11 章](#ch11-ch11)、[云计算](#ch11-ch11)中涵盖了 cgroup）[\[Facebook 19\]](#ch07-ch07ref23)。

<!-- source-id: ch07#ch07lev5sec3 -->
### 7.5.3 swapon

swapon(1) 可以显示交换设备是否已配置以及其卷的使用量。例如：

![点此查看代码图片](../images/pg331-2.jpg)

```text
$ swapon
NAME      TYPE      SIZE   USED PRIO
/dev/dm-2 partition 980M 611.6M   -2
/swap1    file       30G  10.9M   -3
```

此输出显示两个交换设备：一个 980 MB 的物理磁盘分区和一个名为 /swap1 的 30 GB 文件。输出还显示两者的使用量。现在很多系统都没有配置交换；在这种情况下，swapon(1) 将不会打印任何输出。

如果交换设备具有活动 I/O，则可以在 vmstat(1) 中的 `si` 和 `so` 列中看到，并在 iostat(1) 中看到设备 I/O（[第 9 章](#ch09-ch09)）。

### 7.5.4 sar

系统活动报告器 sar(1) 可用于观察当前活动，并可配置为存档和报告历史统计数据。本书的各个章节中都提到了它提供的不同统计数据，并在[第 4 章](#ch04-ch04)、[可观测性工具](#ch04-ch04)、[第 4.4 节](#ch04-ch04lev4)、[sar](#ch04-ch04lev4)中进行了介绍。

Linux 版本通过以下选项提供内存统计信息：

- **`-B`**：分页统计
- **`-H`**：大页统计
- **`-r`**：内存利用率
- **`-S`**：交换空间统计
- **`-W`**：交换统计数据

这些涵盖内存使用情况、换出守护进程的活动以及大页面使用情况。有关这些主题的背景信息，请参阅[第 7.3 节](#ch07-ch07lev3)、[架构](#ch07-ch07lev3)。

提供的统计数据包括[表 7.5](#ch07-ch07tab05)中的统计数据。

另一个有用的指标是 pgscand，它有效地显示应用程序因等待内存分配而阻塞、进入直接回收的速率（越高越糟）。要查看应用程序在直接回收事件期间花费的时间，您可以使用跟踪工具：请参阅[第 7.5.11 节](#ch07-ch07lev5sec11)、[drsnoop](#ch07-ch07lev5sec11)。

### 7.5.6 numastat

numastat(8)[^fn-ch07-ch07-footnote-8] 工具提供非一致内存访问（NUMA）系统（通常是具有多个 CPU 插槽的系统）的统计信息。以下是双插槽系统的一些输出示例：

![点此查看代码图片](../images/pg334.jpg)

```text
# numastat
                           node0           node1
numa_hit            210057224016    151287435161
numa_miss             9377491084       291611562
numa_foreign           291611562      9377491084
interleave_hit             36476           36665
local_node          210056887752    151286964112
other_node            9377827348       292082611
```

该系统有两个 NUMA 节点，每个插槽对应一个内存节点。Linux 尝试在最近的 NUMA 节点上分配内存，numastat(8) 显示了这一策略的效果。主要统计数据是：

- **`numa_hit`**：目标 NUMA 节点上的内存分配。
- **`numa_miss + numa_foreign`**：内存分配不在首选 NUMA 节点上。 （`numa_miss` 显示本应在其他地方的本地分配，`numa_foreign` 显示本应在本地的远程分配。）
- **`other_node`**：进程在其他地方运行时在此节点上的内存分配。

示例输出显示 NUMA 分配策略表现良好：与其他统计数据相比，命中率很高。如果命中率低得多，您可以考虑调整 sysctl(8) 中的 NUMA 可调参数，或使用其他方法来提高内存局部性（例如，对工作负载或系统进行分区，或选择具有较少 NUMA 节点的不同系统）。如果没有办法改进 NUMA，numastat(8) 至少可以帮助解释内存 I/O 性能不佳的原因。

numastat(8) 支持 `-n` 以 MB 为单位打印统计信息，并支持 `-m` 以 /proc/meminfo 的样式打印输出。根据您的 Linux 发行版，numastat(8) 可能在 numactl 软件包中提供。

### 7.5.7 ps

进程状态命令 ps(1) 列出所有进程的详细信息，包括内存使用统计信息。其用法已在[第 6 章](#ch06-ch06)、[CPU](#ch06-ch06)中介绍过。

例如，使用 BSD 风格的选项：

![点此查看代码图片](../images/pg335-1.jpg)

```text
$ ps aux
USER       PID %CPU %MEM    VSZ   RSS TTY  STAT START   TIME COMMAND
[...]
bind      1152  0.0  0.4 348916 39568 ?    Ssl  Mar27  20:17 /usr/sbin/named -u bind
root      1371  0.0  0.0  39004  2652 ?    Ss   Mar27  11:04 /usr/lib/postfix/master
root      1386  0.0  0.6 207564 50684 ?    Sl   Mar27   1:57 /usr/sbin/console-kit-daemon --no-daemon
rabbitmq  1469  0.0  0.0  10708   172 ?    S    Mar27   0:49 /usr/lib/erlang/erts-5.7.4/bin/epmd -daemon
rabbitmq  1486  0.1  0.0 150208  2884 ?    Ssl  Mar27 453:29 /usr/lib/erlang/erts-5.7.4/bin/beam.smp -W w -K true -A30 ...
```

此输出包括以下列：

- **`%MEM`**：主内存使用量（物理内存，RSS）占系统总量的百分比
- **`RSS`**：驻留集大小（千字节）
- **`VSZ`**：虚拟内存大小（千字节）

虽然 `RSS` 显示主内存使用情况，但它包括共享内存段，例如系统库，可能由数十个进程映射。如果您要对 `RSS` 列进行求和，您可能会发现它超出了系统中的可用内存，因为该共享内存被重复计算。有关共享内存的背景信息，请参见[第 7.2.9 节](#ch07-ch07lev2sec9)、[共享内存](#ch07-ch07lev2sec9)，以及稍后用于分析共享内存使用情况的 pmap(1) 命令。

可以使用 SVR4 样式的 `-o` 选项来选择这些列，例如：

![点击查看代码图片](../images/pg335-2.jpg)

```text
# ps -eo pid,pmem,vsz,rss,comm
  PID %MEM  VSZ  RSS COMMAND
[...]
13419  0.0 5176 1796 /opt/local/sbin/nginx
13879  0.1 31060 22880 /opt/local/bin/ruby19
13418  0.0 4984 1456 /opt/local/sbin/nginx
15101  0.0 4580   32 /opt/riak/lib/os_mon-2.2.6/priv/bin/memsup
10933  0.0 3124 2212 /usr/sbin/rsyslogd
[...]
```

Linux 版本还可以打印主缺页和次缺页的列（`maj_flt`、`min_flt`）。

ps(1) 的输出可以在内存列上进行后排序，以便可以快速识别最高消耗者。或者，尝试 top(1)，它提供交互式排序。

### 7.5.8 top

top(1) 命令监视当前运行的进程并包括内存使用统计信息。在[第 6 章](#ch06-ch06)、[CPU](#ch06-ch06)中引入。例如，在 Linux 上：

![点击查看代码图片](../images/pg336.jpg)

```text
$ top -o %MEM
top - 00:53:33 up 242 days,  2:38,  7 users,  load average: 1.48, 1.64, 2.10
```

### 7.5.11 drsnoop

drsnoop(8)[^fn-ch07-ch07-footnote-10] 是一种 BCC 工具，用于跟踪释放内存的直接回收方法，显示受影响的进程和延迟：回收所用的时间。它可用于量化内存受限系统对应用程序性能的影响。例如：

![点此查看代码图片](../images/pg342-1.jpg)

```text
# drsnoop -T
TIME(s)       COMM           PID     LAT(ms) PAGES
0.000000000   java           11266      1.72    57
0.004007000   java           11266      3.21    57
0.011856000   java           11266      2.02    43
0.018315000   java           11266      3.09    55
0.024647000   acpid          1209       6.46    73
[...]
```

此输出显示了 Java 的一些直接回收，需要 1 到 7 毫秒。在量化应用程序影响时可以考虑这些回收率及其持续时间（以毫秒为单位）(`LAT(ms)`)。

该工具通过跟踪 vmscan mm\_vmscan\_direct\_reclaim\_begin 和 mm\_vmscan\_direct\_reclaim\_end 跟踪点来工作。这些预计是低频事件（通常突发发生），因此开销应该可以忽略不计。

drsnoop(8) 支持 `-T` 选项来包含时间戳，并支持 `-p PID` 来匹配单个进程。

### 7.5.12 wss

wss(8) 是我开发的一个实验工具，用于展示如何使用页表条目（PTE）的“访问”位来测量进程工作集大小（WSS）。这是一项较长研究的一部分，旨在总结确定工作集大小的不同方法 \[Gregg 18c\]。我在这里包含了 wss(8)，因为工作集大小（频繁访问的内存量）是了解内存使用情况的重要指标，并且拥有带有警告的实验工具比没有工具好。

以下输出显示 wss(8) 测量 MySQL 数据库服务器 (mysqld) 的 WSS，并每秒打印累积的 WSS：

![点此查看代码图片](../images/pg342-2.jpg)

```text
# ./wss.pl $(pgrep -n mysqld) 1
Watching PID 423 page references grow, output every 1 seconds...
Est(s)     RSS(MB)    PSS(MB)    Ref(MB)
1.014       403.66     400.59      86.00
2.034       403.66     400.59      90.75
3.054       403.66     400.59      94.29
4.074       403.66     400.59      97.53
5.094       403.66     400.59     100.33
6.114       403.66     400.59     102.44
7.134       403.66     400.59     104.58
8.154       403.66     400.59     106.31
9.174       403.66     400.59     107.76
10.194      403.66     400.59     109.14
```

输出显示，到 5 秒时，mysqld 已触及大约 100 MB 的内存。mysqld 的 RSS 为 400 MB。输出还包括该间隔的估计时间，其中包括设置和读取访问位（`Est(s)`）所花费的时间，以及比例集大小（PSS），该指标说明与其他进程共享的页面。

该工具的工作原理是重置进程中每个页面的 PTE 访问位，暂停一段时间，然后检查这些位以查看哪些位已设置。由于这是基于页面的，因此分辨率就是页面大小，通常为 4 KB。应将它报告的数字视为已向上取整到页面大小。

警告：此工具使用 /proc/PID/clear\_refs 和 /proc/PID/smaps，这可能会导致内核遍历页面结构时应用程序延迟稍高（例如 10%）。对于大型进程（\> 100 GB），这种较高延迟的持续时间可能会持续一秒以上，在此期间该工具会消耗内核 CPU 时间。请记住这些开销。该工具还会重置 referenced 标志，这可能会使内核对要回收的页面感到困惑，特别是在交换处于活动状态时。此外，它还会激活一些以前可能未在您的环境中使用过的旧内核代码。首先在实验室环境中进行测试，以确保您了解开销。

## 7.6 调优

您可以做的最重要的内存调优是确保应用程序保留在主内存中，并且分页和交换不会频繁发生。[第 7.4 节](#ch07-ch07lev4)、[方法论](#ch07-ch07lev4)和[第 7.5 节](#ch07-ch07lev5)、[可观测性工具](#ch07-ch07lev5)中介绍了如何识别此问题。本节讨论其他内存调优：内核可调参数、配置大页面、分配器和资源控制。

调优的细节（可用选项以及将其设置为什么）取决于操作系统版本和预期工作负载。以下部分按调优类型组织，提供了可用的可调参数以及为什么需要调优它们的示例。

<!-- source-id: ch07#ch07lev6sec1 -->
### 7.6.1 可调参数

本节介绍近期 Linux 内核的可调参数示例。

内核源代码文档 Documentation/sysctl/vm.txt 描述了各种内存可调参数，并且可以使用 sysctl(8) 进行设置。[表 7.7](#ch07-ch07tab07)中的示例来自 5.3 内核，默认值来自 Ubuntu 19.10（本书第一版中列出的内容从那时起就没有改变）。

<!-- source-id: ch07#ch07tab07 -->
**表 7.7 Linux 内存可调参数示例**

| **选项** | **默认** | **说明** |
| --- | --- | --- |
| vm.dirty\_background\_bytes | 0 | 触发 pdflush 后台写回的脏内存量 |
| vm.dirty\_background\_ratio | 10 | 触发 pdflush 后台写回的脏系统内存百分比 |
| vm.dirty\_bytes | 0 | 导致写入进程开始回写的脏内存量 |
| vm.dirty\_ratio | 20 | 导致写入进程开始回写的脏系统内存比率 |
| vm.dirty\_expire\_centisecs | 3,000 | 脏内存符合 pdflush 条件的最短时间（促进*写回取消*） |
| vm.dirty\_writeback\_centisecs | 500 | pdflush 唤醒间隔（0 表示禁用） |
| vm.min\_free\_kbytes | 动态 | 设置所需的可用内存量（某些内核原子分配可能会消耗此内存） |
| vm.watermark\_scale\_factor | 10 | 控制 kswapd 唤醒和休眠的内存水位线（min、low、high）之间的距离（单位为万分比，10 表示系统内存的 0.1%） |
| vm.watermark\_boost\_factor | 5000 | 当内存出现碎片时（最近发生碎片事件），kswapd 的扫描回收目标会超过高水位线多少；单位是 10000 的分数，所以 5000 意味着 kswapd 可以提升至高水位线的 150%； 0 禁用 |
| vm.percpu\_pagelist\_fraction | 0 | 这可以覆盖可分配给每 CPU 页面列表的默认最大页面比例（值 10 将其限制为页面的 1/10） |
| vm.overcommit\_memory | 0 | 0 = 使用启发式方法允许合理的内存超额分配；1 = 总是内存超额分配；2 = 不要内存超额分配 |
| vm.swappiness | 60 | 释放内存时，偏向交换（分页）而非从页面缓存回收内存的程度 |
| vm.vfs\_cache\_pressure | 100 | 回收缓存目录和 inode 对象的程度；较低的值更能保留它们；0 表示从不回收——很容易导致内存不足的情况 |
| kernel.numa\_balancing | 1 | 启用自动 NUMA 页面平衡 |
| kernel.numa\_balancing\_scan\_size\_mb | 256 | 每次 NUMA 平衡扫描扫描多少 MB 的页面 |

可调参数使用包含单位的一致命名方案。请注意，dirty\_background\_bytes 和 dirty\_background\_ratio 是互斥的，dirty\_bytes 和 dirty\_ratio 也是互斥的（当设置其中一个时，它将覆盖另一个）。

vm.min\_free\_kbytes 的大小动态设置为主内存的一部分。选择此值的算法不是线性的，因为对可用内存的需求并不随主存容量线性增长。（作为参考，Linux 源代码中的 mm/page\_alloc.c 对此进行了记录。）可以减少 vm.min\_free\_kbytes 来为应用程序释放一些内存，但这也可能导致内核在内存压力期间不堪重负，并更快地诉诸 OOM。增加它可以帮助避免 OOM 终止。

避免 OOM 的另一个参数是 vm.overcommit\_memory，可以将其设置为 2 以禁用内存超额分配并避免由此导致 OOM 的情况。如果您想按进程控制 OOM 杀手，请根据内核版本检查 /proc 可调参数，例如 oom\_adj 或 oom\_score\_adj。这些在 Documentation/filesystems/proc.txt 中进行了描述。

如果 vm.swappiness 可调参数使应用程序内存比预期更早开始交换，则会显著影响性能。此可调参数的值可以在 0 到 100 之间，较高的值有利于交换应用程序，从而保留页面缓存。可能需要将其设置为零，以便尽可能长时间地保留应用程序内存，但会消耗页面缓存。当内存仍然不足时，内核仍然可以使用交换。

在 Netflix，早期内核（大约 Linux 3.13）的 kernel.numa\_balancing 设置为零，因为过度激进的 NUMA 扫描消耗了太多 CPU [\[Gregg 17d\]](#ch07-ch07ref19)。这个问题在后来的内核中得到了修复，并且还有其他可调参数，包括 kernel.numa\_balancing\_scan\_size\_mb，用于调整 NUMA 扫描的积极性。

### 7.6.2 多种页面大小

大页面大小可以通过提高 TLB 缓存的命中率（增加其覆盖范围）来提高内存 I/O 性能。大多数现代处理器支持多种页面大小，例如 4 KB 默认页面和 2 MB 大页面。

在 Linux 上，大页面（称为*huge pages*）可以通过多种方式进行配置。有关参考，请参阅 Documentation/vm/hugetlbpage.txt。

这些通常从创建大页面开始：

![点此查看代码图片](../images/pg352-1.jpg)

```text
# echo 50 > /proc/sys/vm/nr_hugepages
# grep Huge /proc/meminfo
AnonHugePages:         0 kB
HugePages_Total:      50
HugePages_Free:       50
HugePages_Rsvd:        0
HugePages_Surp:        0
Hugepagesize:       2048 kB
```

应用程序消耗大页面的一种方法是通过共享内存段以及 shmget(2) 的 SHM\_HUGETLBS 标志。另一种方法涉及创建一个基于大页面的文件系统，供应用程序映射内存：

![点此查看代码图片](../images/pg352-2.jpg)

```text
# mkdir /mnt/hugetlbfs
# mount -t hugetlbfs none /mnt/hugetlbfs -o pagesize=2048K
```

其他方法包括将 MAP\_ANONYMOUS|MAP\_HUGETLB 标志传给 mmap(2)，以及使用 libhugetlbfs API [\[Gorman 10\]](#ch07-ch07ref15)。

最后，*透明大页面*（THP）是另一种使用大页面的机制，通过自动将普通页面合并为大页面、将大页面拆回普通页面，而不需要应用程序指定大页面 [\[Corbet 11\]](#ch07-ch07ref16)。在 Linux 源代码中，请参阅 Documentation/vm/transhuge.txt 和 admin-guide/mm/transhuge.rst。[^fn-ch07-ch07-footnote-11]

### 7.6.3 分配器

可以使用不同的用户级分配器，从而为多线程应用程序提供更好的性能。这些分配器可以在编译时选择，或者在执行时通过设置 LD\_PRELOAD 环境变量来选择。

### 7.6.4 NUMA 绑定

在 NUMA 系统上，numactl(8) 命令可用于将进程绑定到 NUMA 节点。这可以提高不需要多个主内存 NUMA 节点的应用程序的性能。用法示例：

```text
# numactl --membind=0 3161
```

这会将 PID 3161 绑定到 NUMA 节点 0。如果此节点无法满足这些要求，则此进程的未来内存分配将失败。使用此选项时，您还应该研究使用 `--physcpubind` 选项来将 CPU 使用范围限制为连接到该 NUMA 节点的 CPU。我通常同时使用 NUMA 和 CPU 绑定来将进程限制到单个插槽，以避免 CPU 互连访问的性能损失。

使用 numastat(8)（[第 7.5.6 节](#ch07-ch07lev5sec6)）列出可用的 NUMA 节点。

### 7.6.5 资源控制

使用 ulimit(1) 可以实现基本资源控制，包括设置主内存限制和虚拟内存限制。

对于 Linux，容器组（cgroups）内存子系统提供各种附加控制。这些包括：

- **`memory.limit_in_bytes`**：允许的最大用户内存，包括文件缓存使用量，以字节为单位
- **`memory.memsw.limit_in_bytes`**：允许的最大内存和交换空间，以字节为单位（当使用交换时）
- **`memory.kmem.limit_in_bytes`**：允许的最大内核内存，以字节为单位
- **`memory.tcp.limit_in_bytes`**：最大 tcp 缓冲区内存，以字节为单位。
- **`memory.swappiness`**：与前面描述的 vm.swappiness 类似，但可以为 cgroup 设置
- **`memory.oom_control`**：可以设置为 0，以允许此 cgroup 使用 OOM 杀手，或设置为 1，以禁用它

Linux 还允许在 /etc/security/limits.conf 中进行系统范围的配置。

有关资源控制的更多信息，请参阅[第 11 章](#ch11-ch11)、[云计算](#ch11-ch11)。

    - 换出守护进程的作用是什么？
    - OOM 杀手的作用是什么？

# 第 9 章 — 磁盘

磁盘 I/O 可能会导致严重的应用程序延迟，因此是系统性能分析的重要目标。在高负载下，磁盘成为瓶颈，导致 CPU 在系统等待磁盘 I/O 完成时处于空闲状态。识别并消除这些瓶颈可以将性能和应用程序吞吐量提高几个数量级。

术语“磁盘”是指系统的主存储设备。它们包括基于闪存的固态磁盘 (SSD) 和磁性旋转磁盘。 SSD 的引入主要是为了提高磁盘 I/O 性能，而它们确实做到了这一点。然而，对容量、I/O 速率和吞吐量的需求也在不断增加，闪存设备也无法避免性能问题。

本章的学习目标是：

- 了解磁盘模型和概念。
- 了解磁盘访问模式如何影响性能。
- 了解解释磁盘利用率的危险。
- 熟悉磁盘设备的特性和内部结构。
- 熟悉从文件系统到设备的内核路径。
- 了解 RAID 级别及其性能。
- 遵循不同的磁盘性能分析方法。
- 表征系统范围和每个进程的磁盘 I/O。
- 测量磁盘 I/O 延迟分布并识别异常值。
- 识别请求磁盘 I/O 的应用程序和代码路径。
- 使用跟踪器详细调查磁盘 I/O。
- 了解磁盘可调参数。

本章由六部分组成，前三部分提供磁盘 I/O 分析的基础，后三部分展示其在基于 Linux 的系统中的实际应用。各部分如下：

- **背景**介绍存储相关术语、磁盘设备的基本模型以及关键的磁盘性能概念。
- **架构**提供存储硬件和软件架构的通用描述。
- **方法**描述了观测和实验的性能分析方法。
- **可观测性工具**：介绍基于 Linux 的系统上的磁盘性能可观测性工具，包括跟踪和可视化。
- **实验**总结了磁盘基准测试工具。
- **调优**：描述磁盘可调参数示例。

上一章介绍了构建在磁盘之上的文件系统性能，是研究应用程序性能的更好切入点。

## 9.1 术语

本章中使用的与磁盘相关的术语包括：

- **虚拟磁盘**：存储设备的模拟。它在系统中显示为单个物理磁盘，但它可以由多个磁盘或磁盘的一部分构建。
- **传输**：用于通信的物理总线，包括数据传输 (I/O) 和其他磁盘命令。
- **[扇区](#gloss-glo-146)**：磁盘上的存储块，传统上为 512 字节大小，但现在通常为 4 KB。
- **I/O**：严格来说，I/O 只包括磁盘读写，不包括其他磁盘命令。 I/O 至少可以通过方向（读或写）、磁盘地址（位置）和大小（字节）来描述。
- **磁盘命令**：可以命令磁盘执行其他非数据传输命令（例如，缓存刷新）。
- **吞吐量**：对于磁盘，吞吐量通常指当前数据传输速率，以每秒字节数为单位。
- **带宽**：这是存储传输或控制器的最大可能数据传输速率；它受到硬件的限制。
- **I/O 延迟**：I/O 操作从开始到结束的时间。 [第 9.3.1 节](#ch09-ch09lev3sec1)、[测量时间](#ch09-ch09lev3sec1)，定义了更精确的时间术语。请注意，网络使用术语“延迟”来指启动 I/O 所需的时间，然后是数据传输时间。
- **延迟异常值**：延迟异常高的磁盘 I/O。

本章将介绍其他术语。术语表包含供需要时参考的基本术语，包括*磁盘*、*[磁盘控制器](#gloss-glo-048)*、*[存储阵列](#gloss-glo-165)*、*[本地磁盘](#gloss-glo-094)*、*[远程磁盘](#gloss-glo-137)* 和*IOPS*。另请参阅 [第 2 章](#ch02-ch02) 和 [3](#ch03-ch03) 中的术语部分。

## 9.2 模型

以下简单模型说明了磁盘 I/O 性能的一些基本原理。

<!-- source-id: ch09#ch09lev2sec1 -->
### 9.2.1 简单磁盘

现代磁盘包含用于 I/O 请求的盘上队列，如 [图 9.1](#ch09-ch09fig01) 所示。

<!-- source-id: ch09#ch09fig01 -->
![图 9.1 带队列的简单磁盘](../images/09fig01.jpg)

磁盘接受的 I/O 可能正在队列中等待或正在接受服务。这个简单的模型类似于杂货店的收银台，顾客排队等待服务。它也非常适合使用排队论进行分析。

虽然这可能意味着先到先服务的队列，但磁盘控制器可以应用其他算法来优化性能。这些算法可能包括旋转磁盘的电梯寻道（请参阅 [第 9.4.1 节](#ch09-ch09lev4sec1)、[磁盘类型](#ch09-ch09lev4sec1) 中的讨论），或用于读取和写入 I/O 的单独队列（尤其是基于闪存的磁盘）。

<!-- source-id: ch09#ch09lev2sec2 -->
### 9.2.2 缓存磁盘

增加盘上缓存后，某些读取请求可以由更快的内存类型满足，如 [图 9.2](#ch09-ch09fig02) 所示。它可以实现为物理磁盘设备内部的一小块内存（DRAM）。

<!-- source-id: ch09#ch09fig02 -->
![图 9.2 带盘上缓存的简单磁盘](../images/09fig02.jpg)

虽然缓存命中返回的延迟非常低（良好），但缓存未命中仍然很频繁，并且磁盘设备延迟很高。

磁盘缓存还可以通过将其用作“回写”缓存来提高“写入”性能。这表示写入已在数据传输到缓存之后、较慢的传输到永久磁盘存储之前完成。相反的术语是“直写式”缓存，它仅在完全传输到下一级后才完成写入。

在实践中，存储回写式缓存通常与电池配合使用，以便在断电时仍然可以保存缓冲的数据。此类电池可以位于磁盘或磁盘控制器上。

## 9.3 概念

以下是磁盘性能中的重要概念。

<!-- source-id: ch09#ch09lev3sec1 -->
### 9.3.1 测量时间

I/O 时间可以通过以下方式测量：

- **I/O 请求时间（也称为 *I/O 响应时间*）**：从发出 I/O 到完成的整个时间
- **I/O 等待时间**：在队列中等待所花费的时间
- **I/O 服务时间**：I/O 得到处理的时间（不包括等待）

这些时间如 [图 9.4](#ch09-ch09fig04) 所示。

<!-- source-id: ch09#ch09fig04 -->
![图 9.4 I/O 时间术语（通用）](../images/09fig04.jpg)

术语“服务时间”源自磁盘是由操作系统直接管理的简单设备，因此操作系统知道磁盘何时主动提供 I/O 服务。磁盘现在进行自己的内部排队，操作系统服务时间包括等待内核队列所花费的时间。

在可能的情况下，我会使用更明确的术语说明测量的内容，即从哪个开始事件到哪个结束事件。开始和结束事件可以基于内核或磁盘；基于内核的时间从磁盘设备的块 I/O 接口测量（如 [图 9.7](#ch09-ch09fig07) 所示）。

从内核：

- ***块 I/O 等待时间***（也称为***操作系统等待时间***）是从创建新 I/O 并将其插入内核 I/O 队列，到它离开最后一个内核队列并发往磁盘设备所经过的时间。这可能跨越多个内核级队列，包括块 I/O 层队列和磁盘设备队列。
- ***块 I/O 服务时间*** 是从向设备发出请求，到设备发出完成中断所经过的时间。
- ***块 I/O 请求时间*** 同时包括块 I/O 等待时间和块 I/O 服务时间：从创建 I/O 到其完成的完整时间。

从磁盘：

- ***磁盘等待时间*** 是磁盘队列上花费的时间。
- ***磁盘服务时间*** 是I/O 离开盘上队列后，得到实际处理所需的时间。
- ***磁盘请求时间***（也称为***磁盘响应时间***和***磁盘 I/O 延迟***）同时包括磁盘等待时间和磁盘服务时间，并且等于块 I/O 服务时间。

这些时间如 [图 9.5](#ch09-ch09fig05) 所示，其中 DWT 是磁盘等待时间，DST 是磁盘服务时间。此图还显示了盘上缓存，以及缓存命中如何导致更短的磁盘服务时间（DST）。

<!-- source-id: ch09#ch09fig05 -->
![图 9.5 内核和磁盘时间术语](../images/09fig05.jpg)

I/O 延迟是另一个常用术语，在 [第 1 章](#ch01-ch01) 中引入。与其他术语一样，这意味着什么取决于测量的位置。仅 I/O 延迟可能指的是块 I/O 请求时间：整个 I/O 时间。应用程序和性能工具通常使用术语“磁盘 I/O 延迟”来指代磁盘请求时间：设备上的整个时间。如果您从设备的角度与硬件工程师交谈，他们可能会使用术语“磁盘 I/O 延迟”来指代磁盘等待时间。

块 I/O 服务时间通常被视为当前磁盘性能的衡量标准（这是旧版本的 iostat(1) 显示的）；但是，您应该意识到这是一种简化。在 [图 9.7](#ch09-ch09fig07) 中，描绘了一个通用 I/O 栈，其中显示了块设备接口下方的三个可能的驱动程序层。其中任何一个都可能实现自己的队列，或者可能因等待互斥锁而阻塞，从而增加 I/O 的延迟。该延迟包含在块 I/O 服务时间中。

<!-- source-id: ch09#ch09lev3_1 -->
#### 计算时间

磁盘服务时间通常无法直接从内核统计数据中观察到，但可以使用 IOPS 和利用率推断平均磁盘服务时间：

磁盘服务时间 = 利用率 / IOPS

例如，利用率为 60% 且 IOPS 为 300 时，平均服务时间为 2 毫秒 (600 毫秒/300 IOPS)。这假设利用率反映的是单个设备（或*服务中心*），该设备一次只能处理一个 I/O。磁盘通常可以并行处理多个 I/O，因此计算不准确。

事件跟踪可以通过测量磁盘 I/O 发出和完成时的高分辨率时间戳，提供准确的磁盘服务时间，而不依赖内核统计数据。这可以使用本章后面介绍的工具完成（例如 [第 9.6.6 节](#ch09-ch09lev6sec6)、[biolatency](#ch09-ch09lev6sec6) 中的 biolatency(8)）。

### 9.3.2 时间尺度

磁盘 I/O 的时间尺度可能有几个数量级的变化，从几十微秒到几千毫秒。在最慢的一端，单个缓慢的磁盘 I/O 可能会导致应用程序响应时间不佳；在最快的一端，只有大量磁盘 I/O 才可能成为问题（许多快速 I/O 的总和等于慢速 I/O）。

对于上下文，[表 9.1](#ch09-ch09tab01) 提供了磁盘 I/O 延迟可能范围的一般概念。有关精确的当前值，请查阅磁盘供应商文档，并执行您自己的微基准测试。另请参阅 [第 2 章](#ch02-ch02)、[方法论](#ch02-ch02)，了解磁盘 I/O 以外的时间尺度。

为了更好地说明所涉及的数量级，“缩放”列显示了假设盘上缓存命中延迟为一秒的比较。

<!-- source-id: ch09#ch09tab01 -->
**表 9.1 磁盘 I/O 延迟的时间尺度示例**

| **事件** | **延迟** | **缩放** |
| --- | --- | --- |
| 磁盘缓存命中 | \< 100 μs[^fn-ch09-ch09-footnote-1] | 1 s |
| 闪存读取 | ~100 至 1,000 μs（从小到大 I/O） | 1 至 10 s |
| 旋转磁盘顺序读取 | ~1 ms | 10 s |
| 旋转磁盘随机读取 (7,200 rpm) | ~8 ms | 1.3 分钟 |
| 旋转磁盘随机读取（慢速、排队） | \> 10 ms | 1.7 分钟 |
| 旋转磁盘随机读取（队列中数十个） | \> 100 毫秒 | 17 分钟 |
| 最坏情况虚拟磁盘 I/O（硬件控制器、RAID-5、队列、随机 I/O） | \> 1,000 毫秒 | 2.8 小时 |

根据环境要求，这些延迟可能会有不同的解释。在企业存储行业工作时，我认为任何耗时超过 10 毫秒的磁盘 I/O 都异常缓慢，并且是性能问题的潜在根源。在云计算行业中，对高延迟的容忍度更大，尤其是在网络和客户端浏览器之间已经期望高延迟的面向 Web 的应用程序中。在这些环境中，磁盘 I/O 可能仅在超过 50 毫秒（单独或在应用程序请求期间总共）时成为问题。

此表还说明磁盘可以返回两种类型的延迟：一种用于盘上缓存命中（小于 100 μs），另一种用于未命中（1–8 毫秒或更高，具体取决于访问模式和设备类型）。由于磁盘会返回这两种延迟的混合，将它们合并表示为“平均”延迟（如 iostat(1) 所做的那样）可能会产生误导，因为实际情况是一个双峰分布。有关磁盘 I/O 延迟分布直方图的示例，请参阅 [图 2.23](#ch02-ch02fig23) 中的 [第 2 章](#ch02-ch02)、[方法论](#ch02-ch02) 内容。

<!-- source-id: ch09#ch09lev3sec4 -->
### 9.3.4 随机与顺序 I/O

磁盘 I/O 工作负载可以根据磁盘上 I/O 的相对位置（*磁盘偏移*），使用术语“随机”和“顺序”来描述。这些术语在 [第 8 章](#ch08-ch08)、[文件系统](#ch08-ch08) 中针对文件访问模式进行了讨论。

顺序工作负载也称为“流式工作负载”。术语“流式传输”通常在应用程序级别使用，描述“磁盘”（文件系统）的流式读取和写入。

在旋转磁盘时代，研究随机磁盘 I/O 模式与顺序磁盘 I/O 模式非常重要。对于这类磁盘，当磁头在 I/O 之间寻道、盘片旋转时，随机 I/O 会产生额外延迟。 [图 9.6](#ch09-ch09fig06) 展示了这一点：磁头在扇区 1 和扇区 2 之间移动时，既需要寻道也需要等待旋转（实际路径会尽可能直接）。性能调优涉及识别随机 I/O 并尝试通过多种方式消除它，包括缓存、将随机 I/O 隔离到单独的磁盘，以及通过磁盘布局减少寻道距离。

<!-- source-id: ch09#ch09fig06 -->
![图 9.6 旋转盘](../images/09fig06.jpg)

其他磁盘类型（包括基于闪存的 SSD）在随机读取模式和顺序读取模式上的性能通常没有什么不同。根据驱动器的不同，可能会因其他因素而存在微小差异，例如，地址查找缓存可以跨越顺序访问，但不能跨越随机访问。由于读取-修改-写入周期，小于块大小的写入可能会遇到性能损失，特别是对于随机写入。

请注意，从操作系统看到的磁盘偏移量可能与物理磁盘上的偏移量不匹配。例如，硬件提供的虚拟磁盘可以跨多个磁盘映射连续的偏移范围。磁盘可以按照自己的方式重新映射偏移量（通过磁盘数据控制器）。有时随机 I/O 不是通过检查偏移量来识别的，但可以通过测量增加的磁盘服务时间来推断。

<!-- source-id: ch09#ch09lev3sec5 -->
### 9.3.5 读/写比率

除了识别随机工作负载与顺序工作负载之外，另一个特征指标是读取与写入的比率，指的是 IOPS 或吞吐量。这可以表示为随时间变化的比率（百分比），例如，“系统自启动以来，读取占 I/O 的 80%”。

了解此比率有助于设计和配置系统。具有高读取率的系统可能会从添加缓存中受益最多。添加更多磁盘以提高最大可用吞吐量和 IOPS 可能会给写入速率较高的系统带来最大好处。

读取和写入本身可能会显示不同的工作负载模式：读取可能是随机 I/O，而写入可能是顺序的（尤其是对于写入时复制文件系统）。它们还可能表现出不同的 I/O 大小。

<!-- source-id: ch09#ch09lev3sec6 -->
### 9.3.6 I/O 大小

平均 I/O 大小（字节）或 I/O 大小的分布是另一个工作负载特征。较大的 I/O 大小通常会提供较高的吞吐量，但每个 I/O 的延迟会较长。

I/O 大小可能由磁盘设备子系统改变（例如量化为 512 字节扇区）。I/O 从应用程序层发出后，文件系统、卷管理器和设备驱动程序等内核组件也可能将其放大或缩小。请参阅 [第 8 章](#ch08-ch08)、[文件系统](#ch08-ch08)、[第 8.3.12 节](#ch08-ch08lev3sec12)、[逻辑 I/O 与物理 I/O](#ch08-ch08lev3sec12) 中的“放大与缩小（Inflated and Deflated）”部分。

某些磁盘设备（尤其是基于闪存的磁盘设备）在读取和写入大小不同时，性能差异很大。例如，基于闪存的磁盘驱动器可以以 4 KB 读取和 1 MB 写入来实现最佳性能。理想的 I/O 大小可以由磁盘供应商记录或使用微基准测试来识别。当前使用的 I/O 大小可以使用可观测性工具找到（参见 [第 9.6 节](#ch09-ch09lev6)、[可观测性工具](#ch09-ch09lev6)）。

<!-- source-id: ch09#ch09lev3sec7 -->
### 9.3.7 IOPS 不可直接比较

由于最后三个特征，IOPS 并不相同，并且无法在不同设备和工作负载之间进行直接比较。 IOPS 值本身并没有多大意义。

例如，对于旋转磁盘，5,000 个顺序 IOPS 的工作负载可能比 1,000 个随机 IOPS 的工作负载快得多。基于闪存的 IOPS 也很难比较，因为它们的 I/O 性能通常与 I/O 大小和方向（读或写）相关。

IOPS 对于应用程序工作负载来说甚至可能没有那么重要。由随机请求组成的工作负载通常对延迟敏感，在这种情况下需要高 IOPS 速率。流式（顺序）工作负载对吞吐量敏感，这可能会使较大 I/O 的较低 IOPS 速率更理想。

要理解 IOPS，请包括其他详细信息：随机或顺序、I/O 大小、读/写、缓冲/直接以及并行 I/O 数量。还可以考虑使用基于时间的指标，例如利用率和服务时间，它们反映了最终的性能并且可以更容易地进行比较。

<!-- source-id: ch09#ch09lev3sec8 -->
### 9.3.8 非数据传输磁盘命令

除了 I/O 读取和写入之外，还可以向磁盘发送其他命令。例如，可以命令带有盘上缓存（RAM）的磁盘将缓存刷新到磁盘。这类命令本身不传输数据；数据此前已通过写入操作发送到磁盘。

另一个示例命令用于丢弃数据：ATA TRIM 命令或 SCSI UNMAP 命令。这告诉驱动器不再需要某个扇区范围，并且可以帮助 SSD 驱动器保持写入性能。

这些磁盘命令会影响性能，并可能在其他 I/O 等待时占用磁盘资源。

<!-- source-id: ch09#ch09lev3sec9 -->
### 9.3.9 利用率

利用率可以计算为磁盘在某个时间间隔内忙于主动执行工作的时间。

利用率为 0% 的磁盘处于“空闲”状态，利用率为 100% 的磁盘持续忙于执行 I/O（和其他磁盘命令）。利用率为 100% 的磁盘很可能是性能问题的根源，尤其是当它们在一段时间内保持 100% 的状态时。然而，任何磁盘利用率都可能导致性能不佳，因为磁盘 I/O 通常是一项缓慢的活动。

在 0% 到 100%（例如 60%）之间也可能存在某个点，此时磁盘的性能不再令人满意，因为排队的可能性增加（无论是在磁盘上队列还是在操作系统中）。成为问题的确切利用率值取决于磁盘、工作负载和延迟要求。请参阅 [第 2 章](#ch02-ch02)、[方法论](#ch02-ch02)、[第 2.6.5 节](#ch02-ch02lev6sec5)、[排队理论](#ch02-ch02lev6sec5) 中的 M/D/1 和 60% 利用率部分。

要确认高利用率是否导致应用程序问题，请研究磁盘响应时间以及应用程序是否在此 I/O 上阻塞。应用程序或操作系统可能正在异步执行 I/O，因此缓慢的 I/O 不会直接导致应用程序等待。

请注意，利用率是间隔汇总。磁盘 I/O 可能会突发发生，尤其是由于写入刷新，这在较长时间间隔内进行汇总时可能会被掩盖。有关利用率指标类型的进一步讨论，请参阅 [第 2 章](#ch02-ch02)、[方法论](#ch02-ch02)、[第 2.3.11 节](#ch02-ch02lev3sec11)、[利用率](#ch02-ch02lev3sec11)。

<!-- source-id: ch09#ch09lev3_2 -->
#### 虚拟磁盘利用率

对于由硬件（例如磁盘控制器或网络附加存储）提供的虚拟磁盘，操作系统可能知道虚拟磁盘何时繁忙，却完全不知道构成它的底层磁盘的性能。这会导致操作系统报告的虚拟磁盘利用率与实际磁盘上的情况显著不同，甚至违反直觉：

- 100% 繁忙且基于多个物理磁盘构建的虚拟磁盘可能仍能接受更多工作。在这种情况下，100% 可能意味着某些磁盘一直处于繁忙状态，但并非所有磁盘始终繁忙，因此有些磁盘仍处于空闲状态。
- 包含回写式缓存的虚拟磁盘在写入工作负载期间可能不会显得非常繁忙，因为磁盘控制器会立即返回写入完成，即使底层磁盘随后会繁忙一段时间。
- 由于硬件 RAID 重建，磁盘可能很忙，操作系统看不到相应的 I/O。

出于同样的原因，解释操作系统软件（软件 RAID）创建的虚拟磁盘的利用率可能很困难。但是，操作系统也应该公开物理磁盘的利用率，可以进行检查。

一旦物理磁盘达到 100% 利用率并请求更多 I/O，它就会饱和。

<!-- source-id: ch09#ch09lev3sec10 -->
### 9.3.10 饱和度

饱和度衡量排队工作超出资源交付能力的程度。对于磁盘设备，可以将其计算为操作系统中设备等待队列的平均长度（假设设备确实排队）。

这提供了超过 100% 利用率点的性能衡量标准。利用率为 100% 的磁盘可能没有饱和（没有排队），也可能高度饱和，并因 I/O 排队而显著影响性能。

您可能会假设利用率低于 100% 的磁盘没有饱和，但这实际上取决于利用率间隔：间隔期间的 50% 磁盘利用率可能意味着一半时间利用率为 100%，其余时间空闲。任何区间总结都可能遇到类似的问题。当准确了解发生的情况非常重要时，可以使用跟踪工具来检查 I/O 事件。

<!-- source-id: ch09#ch09lev3sec11 -->
### 9.3.11 I/O 等待

I/O 等待是每个 CPU 的性能指标，显示当 CPU 调度程序队列（处于睡眠状态）上有线程在磁盘 I/O 上被阻塞时，空闲时间。这将 CPU 空闲时间分为闲置时间和磁盘 I/O 阻塞时间。每个 CPU 的高 I/O 等待率表明磁盘可能是瓶颈，导致 CPU 在等待磁盘时处于空闲状态。

I/O 等待可能是一个非常令人困惑的指标。如果出现另一个需要大量 CPU 的进程，I/O 等待值可能会下降：CPU 现在有事情可做，而不是闲置。然而，尽管 I/O 等待指标有所下降，但相同的磁盘 I/O 仍然存在并阻塞线程。当系统管理员升级应用程序软件并且新版本效率更高并且使用更少的 CPU 周期时，有时会发生相反的情况，*显示*I/O 等待。这可能会让系统管理员认为升级导致了磁盘问题并使性能变差，而实际上磁盘性能相同，但 CPU 性能有所提高。

更可靠的指标是应用程序线程在磁盘 I/O 上被阻塞的时间。这捕获了由磁盘引起的应用程序线程所承受的痛苦，无论 CPU 可能正在执行什么其他工作。该指标可以使用静态或动态插桩来测量。

I/O 等待仍然是 Linux 系统上的一个流行指标，尽管其性质令人困惑，但它已成功用于识别一种磁盘瓶颈：磁盘繁忙，CPU 空闲。解释它的一种方法是将任何等待 I/O 视为系统瓶颈的标志，然后调整系统以将其最小化 — 即使 I/O 仍然与 CPU 使用率同时发生。并发 I/O 更有可能是非阻塞 I/O，并且不太可能导致直接问题。由 I/O 等待确定的非并发 I/O 更有可能是应用程序阻塞 I/O，并且是瓶颈。

<!-- source-id: ch09#ch09lev3sec12 -->
### 9.3.12 同步与异步

重要的是要了解，如果应用程序 I/O 和磁盘 I/O 异步操作，则磁盘 I/O 延迟可能不会直接影响应用程序性能。这种情况通常发生在回写式缓存中，其中应用程序 I/O 提前完成，磁盘 I/O 稍后发出。

应用程序可以使用预读来执行异步读取，这在磁盘完成 I/O 时可能不会阻塞应用程序。文件系统可以自行启动此操作以预热缓存（预取）。

即使应用程序同步等待 I/O，该应用程序代码路径也可能是非关键的并且与客户端应用程序请求异步。它可以是一个应用程序 I/O 工作线程，创建它是为了在其他线程继续处理工作时管理 I/O。

内核通常还支持“异步”或“非阻塞 I/O”，其中为应用程序提供 API 来请求 I/O 并在稍后收到其完成的通知。有关这些主题的更多信息，请参阅 [第 8 章](#ch08-ch08)、[文件系统](#ch08-ch08)、[第 8.3.9 节](#ch08-ch08lev3sec9)、[非阻塞 I/O](#ch08-ch08lev3sec9)； [8.3.5](#ch08-ch08lev3sec5)，[预读](#ch08-ch08lev3sec5)； [8.3.4](#ch08-ch08lev3sec4)、[预取](#ch08-ch08lev3sec4)；和 [8.3.7](#ch08-ch08lev3sec7)、[同步写入](#ch08-ch08lev3sec7)。

<!-- source-id: ch09#ch09lev3sec13 -->
### 9.3.13 磁盘与应用程序 I/O

磁盘 I/O 是各种内核组件（包括文件系统和设备驱动程序）的最终结果。有很多原因导致该磁盘 I/O 的速率和数量可能与应用程序发出的 I/O 不匹配。这些包括：

- 文件系统 I/O 的放大、缩小以及无关 I/O。请参见 [第 8 章](#ch08-ch08)、[文件系统](#ch08-ch08)、[第 8.3.12 节](#ch08-ch08lev3sec12)、[逻辑 I/O 与物理 I/O](#ch08-ch08lev3sec12)。
- 由于系统内存不足而进行分页。请参见 [第 7 章](#ch07-ch07)、[内存](#ch07-ch07)、[第 7.2.2 节](#ch07-ch07lev2sec2)、[分页](#ch07-ch07lev2sec2)。
- 设备驱动程序 I/O 大小：对 I/O 大小进行向上取整，或对 I/O 进行分段。
- RAID 写入镜像块或校验和块，或者验证读取的数据。

当意想不到的时候，这种不匹配可能会令人困惑。通过学习架构和进行分析就可以理解。

<!-- source-id: ch09#ch09lev4 -->
## 9.4 架构

本节介绍磁盘架构。通常会在容量规划期间研究它，以确定不同组件和配置选择的限制；在调查后续性能问题时也应检查它，以防问题源于架构选择，而不是当前负载和调优。

<!-- source-id: ch09#ch09lev4sec1 -->
### 9.4.1 磁盘类型

目前最常用的两种磁盘类型是磁性旋转磁盘和基于闪存的 SSD。二者都提供持久存储；与易失性内存不同，其中存储的内容在电源循环后仍然可用。

<!-- source-id: ch09#ch09lev3_3 -->
#### 9.4.1.1 磁性旋转磁盘

这种磁盘也称为硬盘驱动器（HDD），由一个或多个磁盘组成，这些磁盘称为盘片，表面浸渍有氧化铁颗粒。这些颗粒的一小片区域可以沿两个方向之一磁化；该方向用于存储一个比特。盘片旋转，同时带有读写数据电路的机械臂伸到盘片表面上方。该电路包括*磁头*；一个机械臂可以有多个磁头，从而同时读写多个比特。数据以圆形磁道存储在盘片上，每条磁道又分为多个扇区。

作为机械设备，它们的执行速度相对较慢，尤其是对于随机 I/O。随着基于闪存的技术的进步，SSD 正在取代旋转磁盘，可以想象有一天旋转磁盘将被淘汰（以及其他较旧的存储技术：鼓磁盘和磁芯存储器）。同时，旋转磁盘在某些场景下仍然具有竞争力，例如经济的高密度存储（每兆字节成本较低），尤其是数据仓库。[^fn-ch09-ch09-footnote-2]

以下主题总结了旋转磁盘性能的因素。

##### 寻道与旋转

磁性旋转磁盘的 I/O 缓慢通常由磁头寻道时间和盘片旋转等待时间造成，二者都可能需要几毫秒。最佳情况是下一个请求的 I/O 位于当前正在服务的 I/O 末尾，这样磁头无需寻道或等待额外旋转。如前所述，这称为“顺序 I/O”；需要磁头寻道或等待旋转的 I/O 则称为“随机 I/O”。

有许多策略可以减少寻道和旋转等待时间，包括：

- 缓存：完全消除 I/O。
- 文件系统布局和行为，包括写时复制（这会使写入变为顺序操作，但可能使后续读取变为随机操作）。
- 将不同的工作负载分离到不同的磁盘，以避免在不同工作负载的 I/O 之间寻道。
- 将不同的工作负载转移到不同的系统（某些云计算环境可以这样做，以减少多租户效应）。
- 由磁盘本身执行的电梯寻道。
- 使用更高密度的磁盘，使工作负载位置更集中。
- 分区（或“切片”）配置，例如短行程。

减少旋转等待时间的另一个策略是使用转速更快的磁盘。磁盘有不同的转速，包括 5400、7200、10 K 和 15 K 转/分钟（rpm）。请注意，转速提高会增加热量和磨损，可能缩短磁盘寿命。

##### 理论最大吞吐量

如果已知磁盘每磁道的最大扇区数，则可以使用以下公式计算磁盘吞吐量：

最大吞吐量 = 每磁道最大扇区 × 扇区大小 × rpm/60 s

此公式对于准确公开此信息的旧磁盘更有用。现代磁盘向操作系统提供磁盘的虚拟映像，并且仅公开这些属性的合成值。

##### 短行程

短行程是指仅将磁盘的外圈磁道用于工作负载；其余部分未使用，或用于低吞吐量工作负载（例如归档）。这会减少寻道时间，因为磁头移动被限制在更小的范围内；磁盘还可以让磁头停在外缘，从而减少空闲后的首次寻道。由于分区记录，外圈磁道通常也具有更高的吞吐量（请参阅下一节）。检查已发布的磁盘基准时要留意短行程，尤其是不包含价格的基准，因为其中可能使用了许多短行程磁盘。

##### 扇区分区

磁盘磁道的长度各不相同，靠近磁盘中心的最短，外缘的最长。分区记录（也称为“多区域记录”）不固定每条磁道的扇区数（和比特数），而是为较长的磁道增加扇区数，因为物理上可以写入更多扇区。由于转速恒定，较长的外缘磁道比内圈磁道提供更高的吞吐量（兆字节/秒）。

##### 扇区大小

存储行业为磁盘设备开发了一种称为“高级格式”的新标准，以支持更大的扇区大小，尤其是 4 KB。这会减少 I/O 计算开销、提高吞吐量，也会减少磁盘为每个扇区存储元数据的开销。磁盘固件仍可通过称为 Advanced Format 512e 的仿真标准提供 512 字节扇区。根据磁盘的不同，这可能增加写入开销：需要通过读取—修改—写入周期，将 512 字节映射到 4 KB 扇区。还应注意未对齐的 4 KB I/O；它会跨越两个扇区，导致为其服务的扇区 I/O 被放大。

##### 磁盘缓存

这类磁盘通常包含少量内存（RAM），用于缓存读取结果和缓冲写入。该内存还允许 I/O（命令）在设备上排队并更高效地重新排序。对于 SCSI，这称为标记命令队列（TCQ）；对于 SATA，则称为原生命令队列（NCQ）。

##### 电梯寻道

*电梯算法*（也称为“电梯寻道”）是命令队列提高效率的一种方法。它根据 I/O 在磁盘上的位置重新排序，以最大限度地减少磁头的移动。结果类似于建筑物电梯，它不会根据按下楼层按钮的顺序来服务楼层，而是在建筑物上上下扫动，并在当前请求的楼层停止。

当检查磁盘 I/O 跟踪并发现按完成时间排序 I/O 与按开始时间排序不匹配时，此行为会变得很明显：I/O 未按顺序完成。

虽然这看起来是明显的性能优势，但请考虑以下场景：已向磁盘发送一批位于偏移量 1,000 附近的 I/O，以及一个位于偏移量 2,000 的 I/O。磁头当前位于 1,000。偏移量 2,000 处的 I/O 何时会得到服务？再考虑一下：在为 1,000 附近的 I/O 提供服务时，越来越多的 I/O 又到达 1,000 附近，连续不断的 I/O 让磁盘在 1,000 附近持续忙碌 10 秒。偏移量 2,000 处的 I/O 何时会得到服务？它最终的 I/O 延迟是多少？

##### 数据完整性

磁盘在每个扇区的末尾存储一个纠错码 (ECC) 以保证数据完整性，以便驱动器可以验证数据是否正确读取，或纠正可能发生的任何错误。如果未正确读取扇区，磁头可能会在下一次旋转时重试读取（并且可能会重试几次，每次都会稍微改变磁头的位置）。这可能是 I/O 异常缓慢的原因。驱动器可能会向操作系统提供软错误以解释发生的情况。监视软错误率可能很有用，因为软错误率的增加可能表明驱动器可能很快就会出现故障。

行业从 512 字节扇区切换到 4 KB 扇区的好处之一是，对于相同的数据量，需要的 ECC 比特更少，因为扇区越大，ECC 越高效 [\[Smith 09\]](#ch09-ch09ref6)。

请注意，其他校验和也可能用于验证数据。例如，循环冗余校验（CRC）可以用于验证到主机的数据传输，并且文件系统可以使用其他校验和。

##### 振动

虽然磁盘设备供应商很清楚振动问题，但业界并未广泛了解这些问题，也没有认真对待它们。2008 年，在调查一个神秘的性能问题时，我在磁盘阵列执行写入基准测试时对它“喊叫”，进行了一次诱发振动的实验，结果出现了一阵极慢的 I/O。我的实验立即被录制成视频并发布到 YouTube，随后走红；它被称为首次展示振动对磁盘性能影响的实验 [\[Turner 10\]](#ch09-ch09ref9)。该视频的观看次数已超过 1,700,000 次，提高了人们对磁盘振动问题的认识 [\[Gregg 08\]](#ch09-ch09ref4)。根据我收到的电子邮件，我似乎还意外催生了数据中心隔音行业：现在可以聘请专业人员分析数据中心声级，并通过阻尼振动来提高磁盘性能。

##### 慢盘（Sloth Disks）

一些旋转磁盘存在一种被称为“慢盘”（sloth disks）的性能问题。这类磁盘有时会返回极慢的 I/O，耗时超过一秒，却不报告任何错误。这远远超过基于 ECC 的重试所需的时间。如果这类磁盘直接返回失败，而不是耗时如此之久，反而可能更好：操作系统或磁盘控制器就能采取纠正措施，例如在冗余环境中将磁盘下线并报告故障。慢盘很麻烦，尤其是当它们属于存储阵列提供的虚拟磁盘，而操作系统无法直接看到它们时，因此更难识别。[^fn-ch09-ch09-footnote-3]

##### SMR

叠瓦式磁记录（SMR）驱动器通过使用更窄的磁道提供更高密度。这些磁道窄到写入磁头无法单独记录，但较小的读取磁头仍能读取；因此，写入时会部分重叠其他磁道，形似屋顶瓦片（故名）。采用 SMR 的驱动器密度约提高 25%，但代价是写入性能下降，因为被重叠的数据会被破坏，也必须重新写入。这类驱动器适合一次写入、之后主要读取的归档工作负载，但不适合 RAID 配置中的写入密集型工作负载 [\[Mellor 20\]](#ch09-ch09ref25)。

##### 磁盘数据控制器

机械磁盘为系统提供了一个简单的接口，意味着固定的扇区/磁道比率和连续的可寻址偏移范围。磁盘上实际发生的情况取决于磁盘数据控制器——一个由固件编程的磁盘内部微处理器。磁盘可以实现包括扇区分区在内的算法，从而影响偏移量的布局方式。这是需要注意的事情，但很难分析——操作系统无法看到磁盘数据控制器。

<!-- source-id: ch09#ch09lev3_4 -->
#### 9.4.1.2 固态硬盘

这些也称为固态磁盘（SSD）。术语“固态”指的是使用固态电子器件；这类器件提供可编程的非易失性内存，性能通常远胜旋转磁盘。由于没有移动部件，这些磁盘在物理上也很耐用，不易受到振动引起的性能问题影响。

这种磁盘类型的性能通常在不同的偏移量上是一致的（无旋转或寻道延迟），并且对于给定的 I/O 大小是可预测的。工作负载的随机或顺序特征远不如旋转磁盘那么重要。所有这些都使它们更容易研究和进行容量规划。然而，如果它们确实遇到性能问题，由于它们内部的运行方式，理解它们可能与旋转磁盘一样复杂。

一些 SSD 使用非易失性 DRAM（NV-DRAM），大多数使用闪存。

##### 闪存

基于闪存的 SSD 提供很高的读取性能，尤其是随机读取性能，可以比旋转磁盘高出几个数量级。大多数 SSD 使用 NAND 闪存构建；NAND 使用基于电子俘获电荷的存储介质，即使在断电状态下也能持久保存电子 [^fn-ch09-ch09-footnote-4] \[Cornwell 12\]。“闪存”这一名称与数据写入方式有关：写入需要一次擦除整个内存块（包括多个页面，通常每页 8 或 64 KB），然后重写其内容。由于这些写入开销，闪存的读写性能不对称：读取快，写入慢。驱动器通常使用回写缓存提高写入性能，并以小型电容器作为电源故障时的备用电源来缓解这一问题。

闪存有不同类型：

- **单级单元 (SLC)**：将数据位存储在各个单元中。
- **多级单元 (MLC)**：每个单元存储多个位（通常为两个，这需要四个电压电平）。
- **企业多级单元 (eMLC)**：带有高级固件的 MLC，供企业使用。
- **三电平单元 (TLC)**：存储三位（八个电压电平）。
- **四级单元 (QLC)**：存储四位。
- **3D NAND / 垂直 NAND (V-NAND)**：堆叠闪存层（例如 TLC）以增加密度和存储容量。

此列表大致按时间顺序排列，最新技术列在最后：3D NAND 自 2013 年起已投入商用。

与其他类型相比，SLC 往往具有更高的性能和可靠性，虽然成本更高，但曾更适合企业使用。由于密度更高，MLC 现在也常用于企业场景，尽管可靠性较低。闪存可靠性通常用驱动器预期支持的块写入次数（编程/擦除周期）衡量。SLC 约为 50,000 至 100,000 个周期；MLC 约为 5,000 至 10,000 个周期；TLC 约为 3,000 个周期；QLC 约为 1,000 个周期 [\[Liu 20\]](#ch09-ch09ref24)。

##### 控制器

SSD 的控制器具有以下任务 [\[Leventhal 13\]](#ch09-ch09ref16)：

- **输入**：按页进行读取和写入（通常为 8 KB）；写入只能发生在已擦除的页上；页以 32 至 64 页为一组（256–512 KB）进行擦除。
- **输出**：仿真硬盘驱动器块接口：读取或写入任意扇区（512 字节或 4 KB）。

输入和输出之间的转换由控制器的闪存转换层（FTL）执行，该层还必须跟踪空闲块。它本质上使用自己的文件系统来完成这项工作，例如日志结构文件系统。

写入特性可能给写入工作负载带来问题，尤其是写入小于闪存块大小（可能大至 512 KB）的 I/O 时。这可能导致“写入放大”：擦除前需要将块的剩余部分复制到其他位置，同时至少引入一个擦除—写入周期的延迟。一些闪存驱动器提供由电池支持的盘上缓冲区（基于 RAM），以缓解延迟问题；这样即使发生电源故障，也可以先缓冲写入、稍后再写入。

由于闪存布局，我使用过的最常见企业级闪存驱动器在 4 KB 读取和 1 MB 写入时性能最佳。这些值因驱动器而异，可以通过针对不同 I/O 大小的微基准测试找到。

鉴于闪存的原生操作与其对外提供的块接口之间存在差异，操作系统及其文件系统仍有改进空间。TRIM 命令就是一个例子：它通知 SSD 某个区域不再使用，使 SSD 更容易组装空闲块池，从而减少写入放大。（对于 SCSI，可以使用 UNMAP 或 WRITE SAME 命令实现；对于 ATA，可以使用 DATA SET MANAGEMENT 命令。Linux 支持包括 discard 挂载选项和 fstrim(8) 命令。）

##### 寿命

NAND 闪存作为存储介质存在各种问题，包括擦写耗尽（磨损失效）、数据衰减和读取干扰 [\[Cornwell 12\]](#ch09-ch09ref12)。SSD 控制器可以通过移动数据来缓解这些问题。它通常采用*磨损均衡*，将写入分散到不同块上，以减少单个块的擦写次数；还会采用*闪存空间预留（overprovisioning）*，保留额外闪存容量，以便需要时映射投入使用。

虽然这些技术可以延长使用寿命，但 SSD 每个块的写入周期数仍然有限，具体取决于闪存类型和驱动器采用的缓解功能。企业级驱动器使用闪存空间预留和最可靠的闪存类型 SLC，以实现 100 万次或更高的写入周期。基于 MLC 的消费级驱动器可能只有 1,000 次写入周期。

##### 异常情况

以下是一些需要注意的闪存 SSD 问题：

- 因老化而出现延迟异常，SSD 需要更努力地提取正确数据（使用 ECC 检查）。
- 因碎片而出现更高延迟（重新格式化可能通过清理 FTL 块映射来解决问题）。
- 如果 SSD 实施内部压缩，吞吐量性能会下降。

还应关注 SSD 性能特性的其他进展，以及实际遇到的问题。

#### 9.4.1.3 持久内存

持久内存采用电池供电的[^fn-ch09-ch09-footnote-5] DRAM 形式，用于存储控制器回写缓存。这种类型的性能比闪存快几个数量级，但其成本和有限的电池寿命使其仅限于特殊用途。

由英特尔和美光开发的一种名为 3D XPoint 的新型持久内存将使持久内存能够以介于 DRAM 和闪存之间的极具吸引力的性价比用于更多应用。 3D XPoint 的工作原理是将位存储在可堆叠的交叉网格数据访问数组中，并且可按字节寻址。英特尔性能比较报告显示，3D XPoint 的访问延迟为 14 微秒，而 3D NAND SSD [\[Hady 18\]](#ch09-ch09ref19) 的访问延迟为 200 微秒。 3D XPoint 的测试还显示出一致的延迟，而 3D NAND 的延迟分布更广泛，高达 3 毫秒。

3D XPoint 自 2017 年开始商用。英特尔使用 Optane 品牌，并将其作为 DIMM 封装中的英特尔 Optane 持久内存和英特尔 Optane SSD 发布。

### 9.4.2 接口

接口是驱动器支持的、用于与系统通信的协议，通常通过磁盘控制器实现。下面简要介绍 SCSI、SAS、SATA、FC 和 NVMe 接口。需要查阅当前接口及其支持的带宽，因为随着新规范的开发和采用，这些内容会随时间变化。

<!-- source-id: ch09#ch09lev3_6 -->
#### SCSI

小型计算机系统接口最初是并行传输总线，使用多个电连接器并行传输位。第一个版本是 1986 年的 SCSI-1，数据总线宽度为 8 位，允许每个时钟传输一个字节，并提供 5 Mbytes/s 的带宽。这是使用 50 针 Centronics C50 连接的。后来的并行 SCSI 版本使用了更宽的数据总线和更多的连接器引脚（多达 80 个引脚），带宽达到数百兆字节。

由于并行 SCSI 是共享总线，因此它可能会因总线争用而遭受性能问题，例如，当计划的系统备份使低优先级 I/O 使总线饱和时。解决方法包括将低优先级设备放置在它们自己的 SCSI 总线或控制器上。

并行总线的时钟在更高速度下也会成为一个问题，这与其他问题（包括有限的设备和对 SCSI 终结器包的需求）一起导致转向串行版本：SAS。

<!-- source-id: ch09#ch09lev3_7 -->
#### SAS

串行连接 SCSI 接口被设计为高速点对点传输，避免了并行 SCSI 的总线争用问题。最初的 SAS-1 规范为 3 Gbit/s（2003 年发布），随后是支持 6 Gbit/s（2009 年）的 SAS-2、支持 12 Gbit/s（2012 年）的 SAS-3，以及支持 22.5 Gbit/s（2017 年）的 SAS-4。SAS 支持链路聚合，因此多个端口可以组合起来提供更高带宽。由于采用 8b/10b 编码，实际数据传输率为带宽的 80%。

其他 SAS 功能包括与冗余连接器和架构一起使用的驱动器双端口、I/O 多路径、SAS 域、热插拔以及 SATA 设备的兼容性支持。这些功能使得 SAS 在企业中广受欢迎，尤其是在冗余架构中。

<!-- source-id: ch09#ch09lev3_8 -->
#### SATA

由于与 SCSI 和 SAS 类似的原因，并行 ATA（又名 IDE）接口标准已发展成为串行 ATA 接口。 SATA 1.0 创建于 2003 年，支持 1.5 Gbits/s；后来的主要版本是支持 3.0 Gbits/s 的 SATA 2.0 (2004 年) 和支持 6.0 Gbits/s 的 SATA 3.0 (2008 年)。主要和次要版本中添加了其他功能，包括原生命令队列支持。 SATA采用8b/10b编码，因此数据传输率为带宽的80%。 SATA 已广泛用于消费类台式机和笔记本电脑。

<!-- source-id: ch09#ch09lev3_9 -->
#### FC

光纤通道（FC）是一种用于数据传输的高速接口标准，最初仅面向光纤电缆（因此得名），后来也支持铜缆。FC 通常在企业环境中用于创建存储区域网络（SAN），多个存储设备可以通过光纤通道结构连接到多个服务器。与其他接口相比，这提供了更强的可扩展性和可访问性，类似于通过网络连接多个主机。与网络一样，FC 也可以使用交换机连接多个本地端点（服务器和存储）。光纤通道标准的开发始于 1988 年，第一个版本于 1994 年获 ANSI 批准 \[FICA 20\]。此后出现了许多变体和速度改进；最近的 Gen 7 256GFC 标准达到 51,200 MB/s 全双工 [\[FICA 18\]](#ch09-ch09ref18)。

<!-- source-id: ch09#ch09lev3_10 -->
#### NVMe

非易失性内存快速（NVMe）是面向存储设备的 PCIe 总线规范。NVMe 设备不是将存储设备连接到存储控制器卡，而是自身作为直接连接 PCIe 总线的卡。该规范创建于 2011 年；首个 NVMe 规范为 1.0e（2013 年发布），最新版本为 1.4（2019 年）[\[NVMe 20\]](#ch09-ch09ref27)。较新的规范增加了各种功能，例如热管理，以及用于自测试、数据验证和数据清理（使恢复变得不可能）的命令。NVMe 卡的带宽受 PCIe 总线限制；目前常用的 PCIe 4.0 对于 x16 卡（链路宽度）具有 31.5 GB/s 的单向带宽。

与传统 SAS 和 SATA 相比，NVMe 的优势在于支持多个硬件队列。可以由同一个 CPU 使用这些队列来保持缓存热度（借助 Linux 的多队列支持，还可以避免共享内核锁）。这些队列还允许更大的缓冲：每个队列最多支持 64,000 个命令，而典型的 SAS 和 SATA 分别限制为 256 个和 32 个命令。

NVMe 还支持 SR-IOV 以提高虚拟机存储性能（请参阅 [第 11 章](#ch11-ch11)、[云计算](#ch11-ch11)、[第 11.2 节](#ch11-ch11lev2)、[硬件虚拟化](#ch11-ch11lev2)）。

NVMe 用于低延迟闪存设备，预计 I/O 延迟低于 20 微秒。

### 9.4.3 存储类型

可以通过多种方式向服务器提供存储；以下各节介绍四种通用架构：磁盘设备、RAID、存储阵列和网络附加存储（NAS）。

<!-- source-id: ch09#ch09lev3_11 -->
#### 磁盘设备

最简单的架构是带有内部磁盘的服务器，由操作系统单独控制。磁盘连接到磁盘控制器，磁盘控制器是主板或扩展卡上的电路，允许查看和访问磁盘设备。在这种架构中，磁盘控制器仅充当管道，以便系统可以与磁盘进行通信。典型的个人计算机或笔记本电脑具有以这种方式连接的磁盘作为主存储。

这种架构最容易使用性能工具进行分析，因为每个磁盘对于操作系统都是已知的，并且可以单独观察。

一些磁盘控制器支持这种架构，它被称为“只是一堆磁盘”（JBOD）。

<!-- source-id: ch09#ch09lev3_12 -->
#### RAID

高级磁盘控制器可以为磁盘设备提供独立磁盘冗余阵列（RAID）架构（最初称为“廉价”磁盘冗余阵列 [\[Patterson 88\]](#ch09-ch09ref1)）。RAID 可以将多个磁盘呈现为一个大容量、高速且可靠的虚拟磁盘。这些控制器通常包含板载缓存（RAM），以提高读写性能。

通过磁盘控制器卡提供的 RAID 称为“硬件”RAID。RAID 也可以通过操作系统软件实现，但硬件 RAID 一直很受青睐，因为 CPU 代价高昂的校验和、奇偶校验计算可以在专用硬件上更快完成，而且此类硬件还可以包括电池备份单元（BBU）以提高弹性。然而，处理器进步带来了拥有富余 CPU 周期和核心的 CPU，减少了卸载奇偶校验计算的必要性。许多存储解决方案已回归软件 RAID（例如使用 ZFS），这降低了复杂性和硬件成本，并提高了操作系统的可观测性。发生重大故障时，软件 RAID 也可能比硬件 RAID 更容易修复（想象一下 RAID 卡损坏的情况）。

以下部分描述 RAID 的性能特征。经常使用“条带”这一术语：它指的是将数据分组为跨多个驱动器写入的块（就像在所有驱动器上画出一条条带）。

| --- | --- | --- |
| 0（串接） | 驱动器一次填满一个。 | 当多个驱动器参与时，随机读取性能最终会提高。 |
| 0（条带） | 驱动器并行工作，将 I/O 拆分（条带化）到多个驱动器上。 | 预期具有最佳的随机和顺序 I/O 性能（取决于条带大小和工作负载模式）。 |
| 1（镜像） | 将多个驱动器（通常是两个）分组，存储相同内容以实现冗余。 | 随机和顺序读取性能良好（取决于实现，可以同时从所有驱动器读取）。写入受镜像中最慢磁盘的限制，吞吐量开销加倍（两个驱动器）。 |
| 10 | 在多个 RAID-1 驱动器组上进行 RAID-0 条带化组合，提供容量和冗余。 | 性能特征类似 RAID-1，但像 RAID-0 一样允许更多驱动器组参与，从而增加带宽。 |
| 5 | 数据以条带形式存储在多个磁盘上，并附带额外的奇偶校验信息以实现冗余。 | 由于读取—修改—写入周期和奇偶校验计算，写入性能较差。 |
| 6 | RAID-5 的扩展版本，每个条带有两个奇偶校验磁盘。 | 类似 RAID-5，但性能更差。 |

虽然 RAID-0 条带化性能最佳，但它没有冗余，因此对于大多数生产用途来说不切实际。可能的例外包括不存储关键数据、且故障实例会自动替换的容错云计算环境，以及仅用于缓存的存储服务器。

##### 可观测性

正如前面有关虚拟磁盘利用率的部分所述，使用硬件提供的虚拟磁盘设备可能会使操作系统中的可观测性变得更加困难，因为操作系统不知道物理磁盘正在做什么。如果 RAID 通过软件提供，通常可以观察到各个磁盘设备，因为操作系统直接管理它们。

##### 读取—修改—写入

当数据以包含奇偶校验的条带存储（如 RAID-5）时，写入 I/O 可能会产生额外的读取 I/O 和计算时间。这是因为小于条带大小的写入可能需要读取整个条带、修改字节、重新计算奇偶校验，然后重写条带。RAID-5 可以采用一种优化来避免这种情况：不读取整个条带，而只读取包含修改数据的条带片段（strip）以及奇偶校验。通过一系列 XOR 运算，可以计算更新后的奇偶校验，并与修改后的条带片段一起写入。

跨越整个条带的写入可以覆盖之前的内容，而无需先读取它们。通过平衡条带大小与写入的平均 I/O 大小，可以提高此环境中的性能，以减少额外的读取开销。

##### 缓存

实现 RAID-5 的磁盘控制器可以使用回写缓存来缓解读取—修改—写入带来的性能影响。这些缓存必须由电池供电，以便发生电源故障时仍能完成缓冲写入。

##### 附加功能

请注意，高级磁盘控制器卡可以提供可能影响性能的高级功能。浏览供应商文档是个好主意，这样您至少可以了解可能发生的情况。例如，以下是 Dell PERC 5 卡 [\[Dell 20\]](#ch09-ch09ref22) 的一些功能：

- **巡检读取**：每隔几天，读取所有磁盘块并验证其校验和。如果磁盘忙于处理请求，则分配给巡检读取功能的资源就会减少，以避免与系统工作负载竞争。
- **缓存刷新间隔**：将缓存中的脏数据刷新到磁盘之间的时间（以秒为单位）。由于写入取消和更好的聚合写入，更长的时间可能会减少磁盘 I/O；然而，它们也可能在较大的刷新期间导致更高的读取延迟。

这两者都会对性能产生重大影响。

<!-- source-id: ch09#ch09lev3_13 -->
#### 存储阵列

存储阵列允许将许多磁盘连接到系统。它们使用先进的磁盘控制器来配置 RAID，通常还提供大容量缓存（数 GB）以提高读写性能。这些缓存通常也由电池供电，因此可以在回写模式下运行。常见策略是在电池出现故障时切换到直写模式；此时可能会因为等待读取—修改—写入周期而出现写入性能突然下降。

另一个性能因素是存储阵列如何连接到系统——通常通过外部存储控制器卡。控制器卡以及卡与存储阵列之间的传输都受 IOPS 和吞吐量限制。为了提高性能和可靠性，存储阵列通常支持双连接，即可以用两根物理电缆连接到一个或两个不同的存储控制器卡。

<!-- source-id: ch09#ch09lev3_14 -->
#### 网络附加存储

NAS 通常由称为 NAS 设备的专用系统，通过现有网络和 NFS、SMB/CIFS 或 iSCSI 等网络协议提供给系统。这些是独立的系统，应单独分析。可以在客户端上进行部分性能分析，以检查施加的工作负载和 I/O 延迟。网络性能也会成为因素，网络拥塞和多跳延迟都可能引发问题。

#### 块设备接口

块设备接口创建于早期 Unix，用于以 512 字节的块为单位访问存储设备，并提供缓冲区缓存以提高性能。Linux 中仍存在该接口，不过随着其他文件系统缓存的引入，缓冲区缓存的作用已经减弱，如 [第 8 章](#ch08-ch08)、[文件系统](#ch08-ch08) 中所述。

Unix 提供了一条绕过缓冲区缓存的路径，称为“裸块设备 I/O”（或简称“裸 I/O”），可通过字符特殊设备文件使用（请参阅 [第 3 章](#ch03-ch03)、[操作系统](#ch03-ch03)）。默认情况下，这些文件在 Linux 中已不常见。裸块设备 I/O 与 [第 8 章](#ch08-ch08)、[文件系统](#ch08-ch08) 中描述的“直接 I/O”文件系统功能不同，但在某些方面相似。

通常可以通过操作系统性能工具（iostat(1)）观察块 I/O 接口。这也是静态插桩的常见位置，最近也可以使用动态插桩进行探索。Linux 还通过附加功能增强了内核的这一区域。

这会对 I/O 进行分组，减少内核存储栈中每个 I/O 的 CPU 开销和磁盘开销，从而提高吞吐量。前向合并和后向合并的统计信息可在 iostat(1) 中找到。

##### I/O 调度程序

I/O 在块层中由经典调度器（仅存在于 5.0 之前的 Linux 版本）或较新的多队列调度器排队和调度。这些调度器可以对 I/O 重新排序（或重新调度），以优化交付。这可以提升性能并实现更公平的平衡，尤其适用于 I/O 延迟较高的设备（旋转磁盘）。

**经典调度程序**包括：

- **Noop**：这不执行调度（noop 在 CPU 术语中指空操作），并且可以在调度开销被认为不必要时使用（例如，在 RAM 磁盘中）。
- **Deadline**：尝试强制执行延迟截止时间；例如，可以选择以毫秒为单位的读写到期时间。这对于需要确定性的实时系统很有用。它还可以解决“饥饿”问题：新发出的 I/O 插队，导致某个 I/O 请求长期得不到磁盘资源，从而产生延迟异常值。饥饿可能源于“写入饿死读取”，也可能因为电梯寻道以及磁盘某一区域的大量 I/O，导致另一区域的 I/O 饿死。Deadline 调度器通过使用三个独立的 I/O 队列部分解决这一问题：读 FIFO、写 FIFO 和排序队列 [\[Love 10\]](#ch09-ch09ref8)。
- **CFQ**：完全公平排队调度器为进程分配 I/O 时间片，类似于 CPU 调度，以公平使用磁盘资源。它还允许通过 ionice(1) 命令为用户进程设置优先级和类别。

经典调度器的问题之一是使用由单个锁保护的单个请求队列，这在高 I/O 速率下会成为性能瓶颈。多队列驱动程序（blk-mq，于 Linux 3.13 加入）通过为每个 CPU 使用独立的提交队列、为设备使用多个分发队列来解决这一问题。与经典调度器相比，这能为 I/O 提供更好的性能和更低的延迟，因为请求可以并行处理，并且在发起 I/O 的同一 CPU 上处理。这对于支持基于闪存的设备及其他能够处理数百万 IOPS 的设备类型是必要的 [\[Corbet 13b\]](#ch09-ch09ref15)。

**多队列调度程序**包括：

- **None**：不进行排队。
- **BFQ**：预算公平排队调度器，与 CFQ 类似，但同时分配带宽和 I/O 时间。它为每个执行磁盘 I/O 的进程创建一个队列，并为每个队列维护以扇区为单位的预算。还存在系统范围的预算超时，以防止某个进程长时间占用设备。BFQ 支持 cgroup。
- **mq-deadline**：Deadline 调度器的 blk-mq 版本（前面已描述）。
- **Kyber**：一种根据性能调整读写分发队列长度的调度器，以满足目标读写延迟。它是一个简单的调度器，只有两个可调参数：目标读取延迟（read\_lat\_nsec）和目标同步写入延迟（write\_lat\_nsec）。Kyber 在 Netflix 云中显示出更低的存储 I/O 延迟，因此被默认使用。

从 Linux 5.0 开始，多队列调度器成为默认选项（不再包含经典调度器）。

I/O 调度程序在 Linux 源文件的 Documentation/block 下有详细记录。

I/O 调度完成后，请求会放入块设备队列，以便发往设备。

### 9.5.1 工具方法

工具方法是遍历可用工具、检查它们提供的关键指标的过程。虽然方法简单，但可能忽略工具可见性较差或完全无法观测的问题，而且执行起来可能非常耗时。

对于磁盘，工具方法可能涉及检查以下内容（对于 Linux）：

- **`iostat`**：使用扩展模式查找繁忙的磁盘（利用率超过 60%）、平均服务时间较高的磁盘（例如超过 10 毫秒）以及 IOPS 较高的磁盘（取决于具体情况）
- **`iotop/biotop`**：识别哪个进程导致磁盘 I/O
- **`biolatency`**：以直方图检查 I/O 延迟分布，查找多峰分布和延迟异常值（例如超过 100 毫秒）
- **`biosnoop`**：检查单个 I/O
- **perf(1)/BCC/bpftrace**：用于自定义分析，包括查看发出 I/O 的用户和内核堆栈
- **磁盘控制器特定工具**（来自供应商）

如果发现问题，请检查可用工具中的所有字段以了解更多背景信息。有关每个工具的更多信息，请参阅 [第 9.6 节](#ch09-ch09lev6)、[可观测性工具](#ch09-ch09lev6)。还可以使用其他方法，这可以识别更多类型的问题。

<!-- source-id: ch09#ch09lev5sec2 -->
### 9.5.2 USE 方法

USE 方法用于在性能调查早期识别所有组件的瓶颈和错误。以下部分介绍如何将 USE 方法应用于磁盘设备和控制器；[第 9.6 节](#ch09-ch09lev6)、[可观测性工具](#ch09-ch09lev6) 则展示用于测量具体指标的工具。

<!-- source-id: ch09#ch09lev3_17 -->
#### 磁盘设备

对于每个磁盘设备，检查：

- **利用率**：设备繁忙的时间
- **饱和度**：I/O 在队列中等待的程度
- **错误**：设备错误

可以先检查错误。错误有时会被忽视，因为即使磁盘发生故障，系统仍能正常运行（只是速度更慢）：磁盘通常配置在能够容忍部分故障的冗余磁盘池中。除了操作系统提供的标准磁盘错误计数器外，磁盘设备还可能支持更多错误计数器，可通过专用工具（例如 SMART 数据[^fn-ch09-ch09-footnote-6]）检索。

如果磁盘设备是物理磁盘，利用率应该很容易找到。如果它们是虚拟磁盘，利用率可能无法反映底层物理磁盘正在执行的操作。有关此问题的更多讨论，请参阅 [第 9.3.9 节](#ch09-ch09lev3sec9)、[利用率](#ch09-ch09lev3sec9)。

<!-- source-id: ch09#ch09lev3_18 -->
#### 磁盘控制器

对于每个磁盘控制器，检查：

- **利用率**：当前吞吐量与最大吞吐量的比值，以及当前操作速率与最大操作速率的比值
- **饱和度**：I/O 因控制器饱和而等待的程度
- **错误**：控制器错误

这里的利用率指标不是按时间定义的，而是按磁盘控制器卡的限制定义的：吞吐量（每秒字节数）和操作速率（每秒操作数）。操作包括读写及其他磁盘命令。吞吐量或操作速率也可能受连接磁盘控制器与系统的传输限制，也可能受控制器到各个磁盘之间的传输限制。每条传输都应以相同方式检查：错误、利用率和饱和度。

您可能会发现可观测性工具（例如 Linux iostat(1)）不提供每个控制器的指标，而只提供每个磁盘的指标。对此有一些解决办法：如果系统只有一个控制器，可以将所有磁盘的这些指标相加，以确定控制器的 IOPS 和吞吐量。如果系统有多个控制器，则需要确定哪些磁盘属于哪个控制器，并相应地求和。

磁盘控制器和传输的性能经常被忽视。幸运的是，它们并不是系统瓶颈的常见来源，因为其容量通常超过所连接磁盘的容量。如果即使在不同工作负载下，总磁盘吞吐量或 IOPS 始终在某个速率上趋于稳定，这可能表明磁盘控制器或传输实际上导致了问题。

<!-- source-id: ch09#ch09lev5sec3 -->
### 9.5.3 性能监控

性能监控可以随着时间的推移识别活动问题和行为模式。磁盘 I/O 的关键指标包括：

- 磁盘利用率
- 响应时间

磁盘利用率持续多秒达到 100% 很可能是一个问题。根据您的环境，超过 60% 也可能因队列增加而导致性能不佳。 “正常”或“不良”的值取决于您的工作负载、环境和延迟要求。如果您不确定，可以执行已知良好与不良工作负载的微基准测试，以显示如何通过磁盘指标找到这些工作负载。请参见 [第 9.8 节](#ch09-ch09lev8)、[实验](#ch09-ch09lev8)。

应针对每个磁盘检查这些指标，以查找不平衡的工作负载和个别性能不佳的磁盘。响应时间度量可以作为每秒平均值进行监控，并且可以包括其他值，例如最大值和标准偏差。理想情况下，可以检查响应时间的完整分布，例如使用直方图或热图来查找延迟异常值和其他模式。

如果系统实施磁盘 I/O 资源控制，则还可以收集显示这些控制是否以及何时生效的统计信息。由于施加的限制，磁盘 I/O 可能成为瓶颈，而不是磁盘本身的活动。

利用率和响应时间显示了磁盘性能的结果。可以添加更多指标来表征工作负载，包括 IOPS 和吞吐量，从而提供用于容量规划的重要数据（请参阅下一节和 [第 9.5.10 节](#ch09-ch09lev5sec10)、[扩展](#ch09-ch09lev5sec10)）。

<!-- source-id: ch09#ch09lev5sec4 -->
### 9.5.4 工作负载特征

表征所应用的负载是容量规划、基准测试和模拟工作负载的重要练习。通过识别可以消除的不必要的工作，它还可以带来一些最大的性能提升。

以下是表征磁盘 I/O 工作负载的基本属性：

- I/O 速率
- I/O 吞吐量
- I/O 大小
- 读/写比率
- 随机与顺序

随机与顺序、读/写比率和 I/O 大小在 [第 9.3 节](#ch09-ch09lev3)、[概念](#ch09-ch09lev3) 中进行了描述。 I/O 速率 (IOPS) 和 I/O 吞吐量在 [第 9.1 节](#ch09-ch09lev1)、[术语](#ch09-ch09lev1) 中定义。

这些特征可能会随时变化，特别是对于定期缓冲和刷新写入的应用程序和文件系统。为了更好地描述工作负载的特征，请捕获最大值和平均值。更好的是，检查值随时间的完整分布。

#### 高级工作负载特征/清单

可能会包含其他详细信息来描述工作负载的特征。这些已在此处列出作为需要考虑的问题，也可以作为彻底研究磁盘问题时的清单：

- 系统范围内的 IOPS 速率是多少？每个磁盘？每个控制器？
- 系统范围内的吞吐量是多少？每个磁盘？每个控制器？
- 哪些应用程序或用户正在使用磁盘？
- 正在访问哪些文件系统或文件？
- 是否遇到任何错误？是由于无效请求还是磁盘问题造成的？
- 可用磁盘上的 I/O 平衡程度如何？
- 所涉及的每条传输总线的 IOPS 是多少？
- 所涉及的每条传输总线的吞吐量是多少？
- 正在发出哪些非数据传输磁盘命令？
- 为什么发出磁盘 I/O（内核调用路径）？
- 磁盘 I/O 应用程序同步的程度如何？
- I/O 到达时间的分布如何？

IOPS 和吞吐量问题可以分别针对读取和写入提出。还可以随着时间的推移检查其中任何一个，以查找最大值、最小值和基于时间的变化。另请参阅 [第 2 章](#ch02-ch02)、[方法论](#ch02-ch02)、[第 2.5.11 节](#ch02-ch02lev5sec11)、[工作负载特征分析](#ch02-ch02lev5sec11)，它们提供了要测量的特征的更高级别摘要（谁、为什么、什么、如何）。

#### 性能表征

前面的工作负载特征列表检查了所应用的工作负载。下面检查最终的性能：

- 每个磁盘的繁忙程度（利用率）？
- 每个磁盘的 I/O（等待队列）饱和程度如何？
- 平均 I/O 服务时间是多少？
- 平均 I/O 等待时间是多少？
- 是否存在高延迟的 I/O 异常值？
- I/O 延迟的完整分布是怎样的？
- 系统资源控制（例如 I/O 限制）是否存在且处于活动状态？
- 非数据传输磁盘命令的延迟是多少？

<!-- source-id: ch09#ch09lev3_21 -->
#### 事件追踪

跟踪工具可用于将所有文件系统操作和详细信息记录到日志中以供以后分析（例如，[第 9.6.7 节](#ch09-ch09lev6sec7)、[biosnoop](#ch09-ch09lev6sec7)）。这可以包括磁盘设备 ID、I/O 或命令类型、偏移量、大小、发出和完成时间戳、完成状态以及原始进程 ID 和名称（如果可能）。通过发出和完成时间戳，可以计算 I/O 延迟（或者可以直接包含在日志中）。通过研究请求和完成时间戳的顺序，还可以识别设备的 I/O 重新排序。虽然这可能是工作负载表征的终极工具，但实际上，根据磁盘操作的速率，捕获和保存可能会花费大量开销。如果事件跟踪的磁盘写入包含在跟踪中，则不仅可能污染跟踪，而且还会创建反馈循环和性能问题。

<!-- source-id: ch09#ch09lev5sec5 -->
### 9.5.5 延迟分析

延迟分析涉及更深入地研究系统以找到延迟的根源。对于磁盘，这通常会在磁盘接口处结束：I/O 请求和完成中断之间的时间。如果这与应用程序级别的 I/O 延迟相匹配，通常可以安全地假设 I/O 延迟源自磁盘，从而使您可以将调查重点放在磁盘上。如果延迟不同，在操作系统 I/O 栈的不同级别上测量延迟将确定其来源。

[图 9.10](#ch09-ch09fig10) 描绘了一个通用 I/O 栈，其中显示了两个 I/O 异常值 A 和 B 的不同级别的延迟。

<!-- source-id: ch09#ch09fig10 -->
![图 9.10 I/O 栈延迟分析](../images/09fig10.jpg)

从应用程序到磁盘驱动器的每个级别，I/O A 的延迟都是相似的。这种相关性表明磁盘（或磁盘驱动程序）是延迟的原因。如果根据层之间相似的延迟值独立测量各层，则可以推断出这一点。

B 的延迟似乎源自文件系统级别（锁定或排队？），较低级别的 I/O 延迟贡献的时间要少得多。请注意，I/O 栈的不同层可能会增加或减少 I/O，这意味着一层与下一层的大小、计数和延迟会有所不同。 B 示例可能是仅观察较低级别（10 毫秒）的一个 I/O，但未能考虑为同一文件系统 I/O（例如元数据）提供服务的其他相关 I/O 的情况。

每个级别的延迟可以表示为：

- **每时间间隔 I/O 平均值**：通常由操作系统工具报告。
- **完整 I/O 分布**：作为直方图或热图；参见 [第 9.7.3 节](#ch09-ch09lev7sec3)、[延迟热图](#ch09-ch09lev7sec3)。
- **每 I/O 延迟值**：请参阅前面的事件跟踪部分。

最后两个对于跟踪异常值的起源很有用，并且可以帮助识别 I/O 已拆分或合并的情况。

### 9.5.6 静态性能调优

静态性能调优重点关注配置环境的问题。对于磁盘性能，请检查静态配置的以下方面：

- 有多少个磁盘？属于哪些类型（例如 SMR、MLC）？尺寸？
- 磁盘固件是什么版本？
- 有多少个磁盘控制器？属于哪几种接口类型？
- 磁盘控制器卡是否连接到高速插槽？
- 每个 HBA 连接了多少个磁盘？
- 如果存在磁盘/控制器备用电池，它们的剩余电量是多少？
- 磁盘控制器固件是什么版本？
- 是否配置了 RAID？具体如何，包括条带宽度？
- 多路径是否可用并已配置？
- 磁盘设备驱动程序是什么版本？
- 服务器主内存大小是多少？正在被页面缓存和缓冲区缓存使用？
- 任何存储设备驱动程序是否存在操作系统错误/补丁？
- 是否有用于磁盘 I/O 的资源控制？

请注意，设备驱动程序和固件中可能存在性能错误，最好通过供应商的更新来修复这些错误。

回答这些问题可以揭示被忽视的配置选择。有时，系统已针对一种工作负载进行配置，然后重新用于另一种工作负载。该战略将重新审视这些选择。

在担任 Sun ZFS 存储产品的性能主管期间，我收到的最常见的性能投诉是由错误配置引起的：使用 RAID-Z2（宽条带）的半个 JBOD（12 个磁盘）。这种配置提供了良好的可靠性，但性能并不令人印象深刻，类似于单个磁盘的性能。我学会了先询问配置详细信息（通常通过电话），然后再花时间登录系统并检查 I/O 延迟。

<!-- source-id: ch09#ch09lev5sec7 -->
### 9.5.7 缓存调整

系统中可能存在许多不同的缓存，包括应用程序级、文件系统、磁盘控制器以及磁盘本身。 [第 9.3.3 节](#ch09-ch09lev3sec3)、[缓存](#ch09-ch09lev3sec3) 中包含了这些列表，可以按照 [第 2 章](#ch02-ch02)、[方法论](#ch02-ch02)、[第 2.5.18 节](#ch02-ch02lev5sec18)、[缓存调优](#ch02-ch02lev5sec18) 中所述进行调整。总之，检查存在哪些缓存，检查它们是否正在工作，检查它们的工作情况，然后调整缓存的工作负载并针对工作负载调整缓存。

<!-- source-id: ch09#ch09lev5sec8 -->
### 9.5.8 资源控制

操作系统可以提供用于将磁盘 I/O 资源分配给进程或进程组的控制。这些控制可能包括 IOPS 和吞吐量的固定限制，或者更灵活的份额机制。具体工作方式取决于实现，如 [第 9.9 节](#ch09-ch09lev9)、[调优](#ch09-ch09lev9) 中所述。

<!-- source-id: ch09#ch09lev5sec9 -->
### 9.5.9 微基准测试

在 [第 8 章](#ch08-ch08)、[文件系统](#ch08-ch08) 中介绍了磁盘 I/O 微基准测试，并解释了测试文件系统 I/O 与测试磁盘 I/O 的区别。这里要测试的是磁盘 I/O，通常意味着通过操作系统的设备路径进行测试，尤其是原始设备路径（如果可用），以避免所有文件系统行为（包括缓存、缓冲、I/O 拆分、I/O 合并、代码路径开销和偏移映射差异）。

微基准测试的因素包括：

- **方向**：读取或写入
- **磁盘偏移模式**：随机或顺序
- **偏移范围**：完整磁盘或狭小范围（例如，仅偏移 0）
- **I/O 大小**：512 字节（典型最小值）最多 1 MB
- **并发**：运行中的 I/O 数量，或执行 I/O 的线程数量
- **设备数量**：单个磁盘测试或多个磁盘（以探索控制器和总线限制）

接下来的两节将展示如何结合这些因素来测试磁盘和磁盘控制器的性能。有关可用于执行这些测试的特定工具的详细信息，请参阅 [第 9.8 节](#ch09-ch09lev8)、[实验](#ch09-ch09lev8)。

<!-- source-id: ch09#ch09lev3_22 -->
#### 磁盘

可以在每个磁盘的基础上执行微基准测试，以确定以下内容以及建议的工作负载：

- **最大磁盘吞吐量**（每秒兆字节）：128 KB 或 1 MB 读取，顺序
- **最大磁盘操作率** (IOPS)：512 字节读取，[^fn-ch09-ch09-footnote-7] 仅偏移 0
- **最大磁盘随机读取** (IOPS)：512 字节读取，随机偏移
- **读取延迟特征**（平均微秒）：顺序读取，重复 512 字节、1K、2K、4K 等
- **随机 I/O 延迟特征**（平均微秒）：512 字节读取，重复完整偏移量范围，仅开始偏移量，仅结束偏移量

可以针对写入重复这些测试。使用“仅偏移0”的目的是将数据缓存在磁盘缓存中，以便可以测量缓存访问时间。[^fn-ch09-ch09-footnote-8]

<!-- source-id: ch09#ch09lev3_23 -->
#### 磁盘控制器

磁盘控制器可以通过将工作负载应用于多个磁盘来进行微基准测试，旨在达到控制器中的限制。这些测试可以使用以下内容以及建议的磁盘工作负载来执行：

- **最大控制器吞吐量**（每秒兆字节）：128 KB，仅偏移 0
- **最大控制器操作率** (IOPS)：512 字节读取，仅偏移 0

将工作负载逐一应用到磁盘，并观察限制。可能需要十几块磁盘才能找到磁盘控制器中的限制。

<!-- source-id: ch09#ch09lev5sec10 -->
### 9.5.10 扩展

磁盘和磁盘控制器具有吞吐量和 IOPS 限制，这可以通过前面所述的微基准测试来证明。调整只能将性能提高到这些限制。如果需要更高的磁盘性能，并且缓存等其他策略不起作用，则需要扩展磁盘。

这是一个基于资源容量规划的简单方法：

1. 根据吞吐量和 IOPS 确定目标磁盘工作负载。如果这是新系统，请参阅 [第 2 章](#ch02-ch02)、[方法论](#ch02-ch02)、[第 2.7 节](#ch02-ch02lev7)、[容量规划](#ch02-ch02lev7)。如果系统已有工作负载，请用当前磁盘吞吐量和 IOPS 来表示用户数量，并将这些数字调整为目标用户数量。 （如果不同时扩展缓存，则磁盘工作负载可能会增加，因为每个用户的缓存比率会变小。）
2. 计算支持该工作负载所需的磁盘数量，并将 RAID 配置纳入考虑。不要直接使用单块磁盘的最大吞吐量和 IOPS 值，否则磁盘利用率会达到 100%，立即因饱和与排队而产生性能问题。选择目标利用率（例如 50%），并据此按比例调整这些数值。
3. 计算支持该工作负载所需的磁盘控制器数量。
4. 确认未超出传输限制，并在必要时扩展传输能力。
5. 计算每个磁盘 I/O 的 CPU 周期以及所需的 CPU 数量（这可能需要多个 CPU 和并行 I/O）。

使用的每个磁盘的最大吞吐量和 IOPS 数量取决于其类型和磁盘类型。请参见 [第 9.3.7 节](#ch09-ch09lev3sec7)、[IOPS 不可直接比较](#ch09-ch09lev3sec7)。微基准测试可用于查找给定 I/O 大小和 I/O 类型的具体限制，工作负载特征可用于现有工作负载，以了解哪些大小和类型重要。

为了满足磁盘工作负载要求，需要数十个磁盘并通过存储阵列连接的服务器并不罕见。我们过去常说，“添加更多主轴。”我们现在可能会说，“添加更多闪存。”

### 9.6.1 iostat

iostat(1) 总结每个磁盘的 I/O 统计信息，提供工作负载特征、利用率和饱和度的指标。它可以由任何用户执行，并且通常是在命令行中用于调查磁盘 I/O 问题的第一个命令。它提供的统计信息通常也由监控软件显示，因此值得详细学习 iostat(1) 以加深您对监控统计信息的理解。这些统计信息默认由内核 [^fn-ch09-ch09-footnote-9] 启用，因此该工具的开销可以忽略不计。

“iostat”这个名称是“I/O stats”的缩写，尽管最好将其称为“diskiostat”以反映它报告的 I/O 类型。当用户知道应用程序正在执行 I/O（对文件系统）但想知道为什么无法通过 iostat(1)（磁盘）看到它时，这偶尔会导致混乱。

iostat(1) 是在 20 世纪 80 年代初为 Unix 编写的，不同的操作系统有不同的版本。可以通过 sysstat 包将其添加到基于 Linux 的系统。下面介绍Linux版本。

<!-- source-id: ch09#ch09lev3_24 -->
#### iostat 默认输出

如果没有任何参数或选项，则会打印 CPU 和磁盘统计信息的启动后摘要。此处介绍该工具；但是，您不应该使用此模式，因为稍后介绍的扩展模式更有用。

![点此查看代码图片](../images/pg459.jpg)

```text
$ iostat
Linux 5.3.0-1010-aws (ip-10-1-239-218)    02/12/20        _x86_64_  (2 CPU)

avg-cpu:  %user   %nice %system %iowait  %steal   %idle
           0.29    0.01    0.18    0.03    0.21   99.28

Device             tps    kB_read/s    kB_wrtn/s    kB_read    kB_wrtn
loop0             0.00         0.05         0.00       1232          0
[...]
nvme0n1           3.40        17.11        36.03     409902     863344
```

第一个输出行是系统的摘要，包括内核版本、主机名、日期、体系结构和 CPU 数量。后续行显示 CPU（`avg-cpu`；这些统计信息包含在 [第 6 章](#ch06-ch06)、[CPU](#ch06-ch06)）和磁盘设备（在 `Device:` 下）的自引导以来的摘要统计信息。每个磁盘设备显示为一行，基本详细信息显示在列中。我用粗体突出显示了列标题；他们是：

- **`tps`**：每秒事务数 (IOPS)
- **`kB_read/s, kB_wrtn/s`**：每秒读取的千字节数和每秒写入的千字节数
- **`kB_read, kB_wrtn`**：读取和写入的总千字节数

iostat(1) 可能不会显示某些 SCSI 设备，包括 CD-ROM。可以使用 tapestat(1) 来检查 SCSI 磁带驱动器，该命令也在 sysstat 包中。另请注意，虽然 iostat(1) 报告块设备读取和写入，但它可能会排除某些其他类型的磁盘设备命令，具体取决于内核（请参阅内核函数 blk\_do\_io\_stat() 中的逻辑）。 iostat(1) 扩展模式包括这些设备命令的额外字段。

<!-- source-id: ch09#ch09lev3_25 -->
#### iostat 选项

iostat(1) 可以使用各种选项来执行，后跟可选的间隔和计数。例如：

```text
# iostat 1 10
```

将打印一秒钟的摘要十次。并且：

```text
# iostat 1
```

将无休止地打印一秒摘要（直到键入 Ctrl-C）。

常用的选项有：

- **`-c`**：显示CPU报告
- **`-d`**：显示磁盘报告
- **`-k`**：使用千字节而不是（512 字节）块
- **`-m`**：使用兆字节而不是（512 字节）块
- **`-p`**：包括每个分区的统计信息
- **`-t`**：时间戳输出
- **`-x`**：扩展统计
- **`-s`**：短（窄）输出
- **`-z`**：跳过显示零活动摘要

还有一个环境变量 POSIXLY\_CORRECT=1，用于输出块（每个块 512 字节）而不是千字节。某些旧版本包含 NFS 统计信息 `-n` 的选项。从 sysstat 版本 9.1.3 开始，它已移至单独的 nfsiostat 命令。

<!-- source-id: ch09#ch09lev3_26 -->
#### iostat 扩展短输出

扩展输出 (`-x`) 提供了对前面介绍的方法有用的额外列。这些额外的列包括用于工作负载特征的 IOPS 和吞吐量指标、USE 方法的利用率和队列长度，以及用于性能特征和延迟分析的磁盘响应时间。

多年来，扩展输出获得了越来越多的字段，最新版本（12.3.1，2019 年 12 月）产生了 197 个字符宽的输出。这不仅不适合本书，也不适合许多宽终端，导致输出由于换行而难以阅读。 2017 年添加了一个解决方案，即 `-s` 选项，以提供“短”或窄的输出，旨在适应 80 个字符的宽度。

以下是短 (`-s`) 扩展 (`-x`) 统计信息和跳过零活动设备 (`-z`) 的示例：

![点此查看代码图片](../images/pg461.jpg)

```text
$ iostat -sxz 1
[...]
avg-cpu:  %user   %nice %system %iowait  %steal   %idle
          15.82    0.00   10.71   31.63    1.53   40.31

Device             tps      kB/s    rqm/s   await aqu-sz  areq-sz  %util
nvme0n1        1642.00   9064.00   664.00    0.44   0.00     5.52 100.00
[...]
```

磁盘列是：

- **`tps`**：每秒发出的事务数 (IOPS)
- **`kB/s`**：每秒千字节数
- **`rqm/s`**：每秒排队和合并的请求
- **`await`**：平均 I/O 响应时间，包括在操作系统中排队的时间和设备的 I/O 响应时间（毫秒）
- **`aqu-sz`**：在驱动程序请求队列中等待的请求与设备上正在处理的请求的平均总数
- **`areq-sz`**：平均请求大小（以千字节为单位）
- **`%util`**：设备忙于处理 I/O 请求的时间百分比（利用率）

实际性能最重要的指标是 `await`，它显示 I/O 的平均总等待时间。什么构成“好”或“坏”取决于需求。在示例输出中，`await` 为 0.44 毫秒，对于该数据库服务器来说令人满意。它可能因多种原因增加：排队（负载）、I/O 大小较大、旋转设备上的随机 I/O，以及设备错误。

对于资源使用和容量规划，`%util` 很重要，但请记住，它只是繁忙度（非空闲时间）的衡量标准，对于多个磁盘支持的虚拟设备可能意义不大。通过施加的负载可以更好地理解这些设备：`tps`（IOPS）和`kB/s`（吞吐量）。

`rqm/s` 列中的非零计数表明连续请求在传送到设备之前已合并，以提高性能。该指标也是顺序工作负载的标志。

由于 `areq-sz` 是合并后的，因此较小的大小（8 KB 或更少）表明存在无法合并的随机 I/O 工作负载。大尺寸可能是大 I/O 或合并的顺序工作负载（如前面的列所示）。

这些将许多 `-sx` 指标分解为读取和写入组件，还包括丢弃和刷新。

额外的列是：

- **`r/s`**、**`w/s`**、**`d/s`**、**`f/s`**：每秒从磁盘设备完成的读取、写入、丢弃和刷新请求（合并后）
- **`rkB/s`**、**`wkB/s`**、**`dkB/s`**：每秒从磁盘设备读取、写入和丢弃 Kbytes
- **`%rrqm/s`**、**`%wrqm/s`**、**`%drqm/s`**：排队和合并的读取、写入和丢弃请求占该类型总请求的百分比
- **`r_await`**、**`w_await`**、**`d_await`**、**`f_await`**：读、写、丢弃和刷新平均响应时间，包括在操作系统中排队的时间和设备的响应时间（毫秒）
- **`rareq-sz`**、**`wareq-sz`**、**`dareq-sz`**：读取、写入和丢弃平均大小（KB）

单独检查读取和写入很重要。应用程序和文件系统通常使用技术来减轻写入延迟（例如回写缓存），因此应用程序不太可能在磁盘写入时阻塞。这意味着对读取和写入进行分组的任何指标都会受到可能不直接重要的组件（写入）的影响。通过拆分它们，您可以开始检查 `r_wait`，它显示平均读取延迟，并且可能是应用程序性能的最重要指标。

读写 IOPS（`r/s`、`w/s`）和吞吐量（`rkB/s`、`wkB/s`）对于工作负载表征非常重要。

丢弃和刷新统计信息是 iostat(1) 的新增内容。丢弃操作释放驱动器上的块（ATA TRIM 命令），并且它们的统计信息已添加到 Linux 4.19 内核中。 Linux 5.5 中添加了 Flush 统计功能。这些可以帮助缩小磁盘延迟的原因。

### 9.6.2 sar

系统活动报告器 sar(1) 可用于观察当前活动，并可配置为存档和报告历史统计数据。它在 [第 4.4 节](#ch04-ch04lev4)、[sar](#ch04-ch04lev4) 中进行了介绍，并在本书的其他各个章节中提到了它提供的不同统计数据。

### 9.6.3 PSI

Linux 4.20 中添加的 Linux 压力停滞信息 (PSI) 包括 I/O 饱和度的统计信息。这些不仅显示是否存在 I/O 压力，还显示它在过去五分钟内的变化情况。输出示例：

![点此查看代码图片](../images/pg464-1.jpg)

```text
# cat /proc/pressure/io
some avg10=63.11 avg60=32.18 avg300=8.62 total=667212021
full avg10=60.76 avg60=31.13 avg300=8.35 total=622722632
```

此输出显示 I/O 压力正在增加，10 秒平均值 (63.11) 高于 300 秒平均值 (8.62)。这些平均值是任务 I/O 停滞的时间百分比。 `some` 行显示某些任务（线程）何时受到影响，`full` 行显示何时所有可运行任务受到影响。

与平均负载一样，这可以是用于警报的高级指标。一旦您意识到存在磁盘性能问题，您可以使用其他工具来查找根本原因，包括按进程进行磁盘统计的 pidstat(8)。

### 9.6.4 pidstat

Linux pidstat(1) 工具默认打印 CPU 使用情况，并包含用于磁盘 I/O 统计信息的 `-d` 选项。这在内核 2.6.20 及更高版本上可用。例如：

![点此查看代码图片](../images/pg464-2.jpg)

```text
$ pidstat -d 1
Linux 5.3.0-1010-aws (ip-10-0-239-218)    02/13/20        _x86_64_  (2 CPU)

09:47:41      UID       PID   kB_rd/s   kB_wr/s kB_ccwr/s iodelay  Command
09:47:42        0      2705  32468.00      0.00      0.00       5  tar
09:47:42        0      2706      0.00   8192.00      0.00       0  gzip

[...]
09:47:56      UID       PID   kB_rd/s   kB_wr/s kB_ccwr/s iodelay  Command
09:47:57        0       229      0.00     72.00      0.00       0  systemd-journal
09:47:57        0       380      0.00      4.00      0.00       0  auditd
09:47:57        0      2699      4.00      0.00      0.00      10  kworker/
u4:1-flush-259:0
09:47:57        0      2705  15104.00      0.00      0.00       0  tar
09:47:57        0      2706      0.00   6912.00      0.00       0  gzip
```

栏目包括：

- **`kB_rd/s`**：每秒读取的千字节数
- **`kB_wd/s`**：每秒写入的千字节数
- **`kB_ccwr/s`**：每秒写入取消的千字节数（例如，刷新前覆盖或删除）
- **`iodelay`**：进程在磁盘 I/O 上阻塞的时间（时钟滴答数），包括交换

输出中看到的工作负载是 `tar` 命令将文件系统读取到管道，`gzip` 读取管道并写入压缩存档文件。 `tar` 读取会导致 iodelay（5 个时钟滴答），而 `gzip` 写入则不会，因为页面缓存中存在回写缓存。一段时间后，页面缓存被刷新，从 `kworker/u4:1-flush-259:0` 进程输出的第二个间隔中可以看出，该进程经历了 iodelay。

iodelay 是最近添加的，它显示了性能问题的严重程度：应用程序等待了多长时间。其他列显示所应用的工作负载。

请注意，只有超级用户 (root) 才能访问不属于他们的进程的磁盘统计信息。这些是通过 /proc/PID/io 读取的。

堆栈跟踪可以帮助解释磁盘 I/O 的性质。在本例中，它来自调用 fsync(2) 的 mysqld log\_flusher() 例程。内核代码路径显示它是由 ext4 文件系统处理的，并通过 blk\_mq\_try\_issue\_list\_directly() 发出磁盘 I/O 请求。

通常，I/O 将排队，然后由内核线程稍后发出，并且跟踪 block:block\_rq\_issue 跟踪点不会显示原始进程或用户级堆栈跟踪。在这些情况下，您可以尝试跟踪 block:block\_rq\_insert ，这用于队列插入。请注意，它会错过未排队的 I/O。

#### 磁盘 I/O 延迟

磁盘 I/O 延迟（前面描述为“磁盘请求时间”）也可以通过记录磁盘请求发出和完成事件以供以后分析来确定。以下命令将事件记录 60 秒，然后将事件写入 out.disk01.txt 文件：

此输出显示磁盘 nvme0n1 的写入工作负载，主要来自 mysqld，PID 174，具有不同的 I/O 大小。这些列是：

- **`TIME(s)`**：I/O 完成时间（以秒为单位）
- **`COMM`**：进程名称（如果此工具已知）
- **`PID`**：进程 ID（如果此工具已知）
- **`DISK`**：存储设备名称
- **`T`**：类型：R == 读取，W == 写入
- **`SECTOR`**：磁盘上的地址，以 512 字节扇区为单位
- **`BYTES`**：I/O 请求的大小

示例输出的中间是一系列 262,144 字节的写入，延迟从 1.82 毫秒开始，随后每个 I/O 的延迟不断增加，最终达到 4.03 毫秒。这是我经常看到的模式，其可能原因可以根据另一列 `TIME(s)` 计算出来：将 `LAT(ms)` 从 `TIME(s)` 中减去，即可得到 I/O 的开始时间；这些 I/O 大约同时开始。这似乎是一组同时发送、在设备上排队、随后依次完成的写入，因此每个写入的延迟逐渐增加。

通过仔细检查开始和结束时间，还可以识别设备上的重新排序。由于输出可以有数千行，因此我经常使用 R 统计软件将输出绘制为散点图，以帮助识别这些模式（请参阅 [第 9.7 节](#ch09-ch09lev7)、[可视化](#ch09-ch09lev7)）。

我在 2005 年为基于 Solaris 的系统编写了第一个 iotop [\[McDougall 06a\]](#ch09-ch09ref2)。现在有很多版本，包括基于内核记账统计的Linux iotop(1)工具[^fn-ch09-ch09-footnote-13] [\[Chazarain 13\]](#ch09-ch09ref14)，以及我自己的基于BPF的biotop(8)。

- **`PID`**：缓存的进程ID（尽力而为）

- **`Kbytes`**：间隔期间的总磁盘吞吐量（千字节）
- **`AVGms`**：I/O（延迟）从发出到设备到完成的平均时间（毫秒）

当向设备发出磁盘 I/O 时，请求进程可能不再位于 CPU 上，并且识别它可能会很困难。 biotop(8) 使用尽力而为的方法：`PID` 和 `COMM` 列通常会匹配正确的进程，但这不能保证。

### 9.6.10 blktrace

blktrace(8) 是 Linux 上使用内核 blktrace 跟踪器的块设备 I/O 事件的自定义跟踪工具。这是一个通过 BLKTRACE ioctl(2) 系统调用对磁盘设备文件进行控制的专用跟踪器。前端工具包括 blktrace(8)、blkparse(1) 和 btrace(8)。

blktrace(8) 启用内核块驱动程序跟踪并检索原始跟踪数据，这些数据可以使用 blkparse(1) 进行处理。为了方便起见，btrace(8) 工具同时运行 blktrace(8) 和 blkparse(1)，因此以下内容是等效的：

![点此查看代码图片](../images/pg476-1.jpg)

```text
# blktrace -d /dev/sda -o - | blkparse -i -
# btrace /dev/sda
```

blktrace(8) 是一个低级工具，可显示每个 I/O 的多个事件。

#### 默认输出

下面显示了 btrace(8) 的默认输出，并通过 cksum(1) 命令捕获单个磁盘读取事件：

对于此单个磁盘 I/O，报告了八行输出，显示涉及块设备队列和设备的每个操作（事件）。

默认情况下，有七列：

1. 设备主、次设备号
2. CPU ID
3. 序号

#### RWBS 描述

为了跟踪可观测性，内核提供了一种使用名为 *rwbs* 的字符串来描述每个 I/O 类型的方法。 rwbs 由 blktrace(8) 和其他磁盘跟踪工具使用。它在内核 blk\_fill\_rwbs() 函数中定义并使用以下字符：

- R：读取
- W：写入
- M：元数据
- S：同步
- A：预读
- F：刷新或强制单元访问
- D：丢弃
- E：擦除
- N：无

这些字符可以组合。例如，“WM”表示元数据写入。

### 9.6.11 bpftrace

bpftrace 是一种基于 BPF 的跟踪器，它提供了一种高级编程语言，允许创建强大的单行代码和短脚本。它非常适合根据其他工具的线索进行自定义磁盘分析。

bpftrace 在 [第 15 章](#ch15-ch15) 中进行了解释。本节显示一些磁盘分析示例：单行、磁盘 I/O 大小和磁盘 I/O 延迟。

#### 磁盘 I/O 延迟

磁盘响应时间（通常称为磁盘 I/O 延迟）可以通过对设备发出到完成事件进行插桩来测量。 biolatency.bt 工具执行此操作，将磁盘 I/O 延迟显示为直方图。例如：

![点此查看代码图片](../images/pg482-1.jpg)

```text
# biolatency.bt
Attaching 4 probes...
Tracing block device I/O... Hit Ctrl-C to end.
^C

@usecs:
[32, 64)               2 |@                                                   |
[64, 128)              1 |                                                    |
[128, 256)             1 |                                                    |
[256, 512)            27 |@@@@@@@@@@@@@@@@@@@@@@@@@@                          |
[512, 1K)             43 |@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@           |
[1K, 2K)              54 |@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@|
[2K, 4K)              41 |@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@             |
[4K, 8K)              47 |@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@       |
[8K, 16K)             16 |@@@@@@@@@@@@@@@                                     |
[16K, 32K)             4 |@@@                                                 |
```

此输出显示 I/O 通常在 256 微秒到 16 毫秒（`16K` 微秒）之间完成。

源代码是：

![点击查看代码图片](../images/pg482-2.jpg)

```text
#!/usr/local/bin/bpftrace
BEGIN
{
        printf("Tracing block device I/O... Hit Ctrl-C to end.\n");
}

tracepoint:block:block_rq_issue
{
        @start[args->dev, args->sector] = nsecs;
}

tracepoint:block:block_rq_complete
/@start[args->dev, args->sector]/
{
        @usecs = hist((nsecs - @start[args->dev, args->sector]) / 1000);
        delete(@start[args->dev, args->sector]);
}
END
{
        clear(@start);
}
```

测量 I/O 延迟需要存储每个 I/O 开始的自定义时间戳，然后在 I/O 完成时引用它来计算经过的时间。当在 [第 8 章](#ch08-ch08)、[文件系统](#ch08-ch08)、[第 8.6.15 节](#ch08-ch08lev6sec15)、[BPF](#ch15-ch15)trace 中测量 VFS 延迟时，开始时间戳存储在以线程 ID 为键的 BPF 映射中：这有效，因为相同的线程 ID 将在 CPU 上用于启动和完成事件。磁盘 I/O 的情况并非如此，因为完成事件将中断 CPU 上的任何其他操作。 biolatency.bt 中的唯一 ID 是根据设备和扇区号构建的：它假设一次只有一个 I/O 会传输到给定扇区。

与 I/O 大小单行一样，您可以将 `args->rwbs` 添加到映射键以按 I/O 类型进行细分。

#### 磁盘 I/O 错误

I/O 错误状态是 block:block\_rq\_complete 跟踪点的一个参数，以下 bioerr(8) 工具[^fn-ch09-ch09-footnote-15] 使用它来打印发生错误的 I/O 操作的详细信息（之前已包含此单行版本）：

![点击查看代码图片](../images/pg483.jpg)

```text
#!/usr/local/bin/bpftrace

BEGIN
{
        printf("Tracing block I/O errors. Hit Ctrl-C to end.\n");
}

tracepoint:block:block_rq_complete
/args->error != 0/
{
        time("%H:%M:%S ");
        printf("device: %d,%d, sector: %d, bytes: %d, flags: %s, error: %d\n",
            args->dev >> 20, args->dev & ((1 << 20) - 1), args->sector,
            args->nr_sector * 512, args->rwbs, args->error);
}
```

查找有关磁盘错误的更多信息可能需要较低级别的磁盘工具，例如接下来的三个（MegaCli、smartctl、SCSI 日志记录）。

### 9.6.14 SCSI 日志记录

Linux 有一个内置的 SCSI 事件日志记录工具。它可以通过 sysctl(8) 或 /proc 启用。例如，这两个命令将所有事件类型的日志记录设置为最大值（警告：根据您的磁盘工作负载，这可能会淹没您的系统日志）：

![点击查看代码图片](../images/pg486-1.jpg)

```text
# sysctl -w dev.scsi.logging_level=03333333333
# echo 03333333333 > /proc/sys/dev/scsi/logging_level
```

数字的格式是一个位字段，它为 10 种不同的事件类型设置从 1 到 7 的日志记录级别（此处以八进制编写；十六进制为 0x1b6db6db）。该位字段在 drivers/scsi/scsi\_logging.h 中定义。 sg3-utils 软件包提供了一个 scsi\_logging\_level(8) 工具来设置这些。例如：

![点此查看代码图片](../images/pg486-2.jpg)

```text
# scsi_logging_level -s --all 3
```

事件示例：

## 9.7 可视化

有许多类型的可视化可以帮助分析磁盘 I/O 性能。本节通过各种工具的屏幕截图来演示这些内容。有关可视化的一般讨论，请参阅 [第 2 章](#ch02-ch02)、[方法论](#ch02-ch02)、[第 2.10 节](#ch02-ch02lev10)、[可视化](#ch02-ch02lev10)。

<!-- source-id: ch09#ch09lev7sec1 -->
### 9.7.1 折线图

性能监控解决方案通常将磁盘 IOPS、吞吐量和利用率测量值随时间的变化绘制为折线图。这有助于说明基于时间的模式，例如一天中负载的变化，或重复发生的事件（例如文件系统刷新间隔）。

请注意绘制图表的指标。平均延迟可以隐藏多峰分布和异常值。所有磁盘设备的平均值可以隐藏不平衡的行为，包括单个设备的异常值。长期平均值也可以隐藏短期波动。

<!-- source-id: ch09#ch09lev7sec2 -->
### 9.7.2 延迟散点图

散点图对于可视化每个事件的 I/O 延迟非常有用，其中可能包括数千个事件。 x 轴可以显示完成时间，y 轴可以显示 I/O 响应时间（延迟）。 [图 9.11](#ch09-ch09fig11) 中的示例绘制了来自生产 MySQL 数据库服务器的 1,400 个 I/O 事件，使用 iosnoop(8) 捕获并使用 R 绘制。

<!-- source-id: ch09#ch09fig11 -->
![图 9.11 磁盘读写延迟散点图](../images/09fig11.jpg)

散点图以不同方式显示读取 (+) 和写入 (°)。可以绘制其他维度，例如 y 轴上的磁盘块地址而不是延迟。

此处可以看到几个读取异常值，延迟超过 150 毫秒。这些异常值的原因此前尚不清楚。该散点图以及其他包含类似异常值的散点图表明它们发生在大量写入之后。由于写入是从 RAID 控制器回写缓存返回的，因此写入延迟较低，在返回完成后会将它们写入设备。我怀疑读取在设备写入后面排队。

该散点图显示了单个服务器几秒钟的情况。多个服务器或更长的时间间隔可以捕获更多的事件，这些事件在绘制时合并在一起并变得难以阅读。此时，请考虑使用延迟热图。

<!-- source-id: ch09#ch09lev7sec3 -->
### 9.7.3 延迟热图

*热图*可用于可视化延迟，将时间的流逝放在 x 轴上，将 I/O 延迟放在 y 轴上，将特定时间和延迟范围内的 I/O 数量放在 z 轴上，以颜色显示（颜色越深意味着越多）。 [第 2 章](#ch02-ch02)、[方法论](#ch02-ch02)、[第 2.10.3 节](#ch02-ch02lev10sec3)、[热图](#ch02-ch02lev10sec3) 中引入了热图。 [图 9.12](#ch09-ch09fig12) 中显示了一个有趣的磁盘示例。

可视化的工作负载是实验性的：我对多个磁盘逐一应用顺序读取，以探索总线和控制器的限制。由此产生的热图是出乎意料的（它被描述为翼手龙），并显示了仅考虑平均值时会错过的信息。看到的每个细节都有技术原因：例如，“喙”以八个磁盘结束，等于连接的 SAS 端口数量（两个 x4 端口），一旦这些端口开始出现争用，“头”就从九个磁盘开始。

受 taztool 的启发，我发明了延迟热图来可视化延迟随时间的变化，如下一节所述。 [图 9.12](#ch09-ch09fig12) 来自 Sun Microsystems ZFS 存储设备中的分析 [\[Gregg 10a\]](#ch09-ch09ref7)：我收集了此图和其他有趣的延迟热图，以公开共享并推广其使用。

<!-- source-id: ch09#ch09fig12 -->
![图 9.12 磁盘延迟翼手龙](../images/09fig12.jpg)

x 轴和 y 轴与延迟散点图相同。热图的主要优点是它们可以扩展到数百万个事件，而散点图则成为“油漆”。此问题已在 [第 2.10.2 节](#ch02-ch02lev10sec2)、[散点图](#ch02-ch02lev10sec2) 和 [2.10.3](#ch02-ch02lev10sec3)、[热图](#ch02-ch02lev10sec3) 中讨论。

### 9.7.4 偏移热图

I/O 位置或偏移量也可以可视化为热图（早于计算中的延迟热图）。 [图 9.13](#ch09-ch09fig13) 显示了一个示例。

<!-- source-id: ch09#ch09fig13 -->
![图 9.13 DTraceTazTool](../images/09fig13.jpg)

y 轴显示磁盘偏移（块地址），x 轴显示时间。每个像素都根据该时间和延迟范围内的 I/O 数量进行着色，数字越大颜色越深。可视化的工作负载是一个文件系统存档，它从块 0 开始在磁盘上爬行。深色线表示顺序 I/O，浅色云表示随机 I/O。

### 9.7.5 利用热图

每个设备的利用率也可以显示为热图，以便可以识别设备利用率平衡和各个异常值 [\[Gregg 11b\]](#ch09-ch09ref10)。在这种情况下，利用率百分比位于 y 轴上，颜色越深意味着处于该利用率水平的磁盘越多。此热图类型可用于将单个热磁盘（包括慢盘）识别为热图顶部的线条 (100%)。有关利用率热图示例，请参阅 [第 6 章](#ch06-ch06)、[CPU](#ch06-ch06)、[第 6.7.1 节](#ch06-ch06lev7sec1)、[利用率热图](#ch06-ch06lev7sec1)。

## 9.8 实验

本节介绍用于主动测试磁盘 I/O 性能的工具。请参阅 [第 9.5.9 节](#ch09-ch09lev5sec9)、[微基准测试](#ch09-ch09lev5sec9)，了解要遵循的建议方法。

使用这些工具时，最好让 iostat(1) 持续运行，以便可以立即双重检查任何结果。一些微基准测试工具可能需要“直接”操作模式来绕过文件系统缓存，并专注于磁盘设备性能。

<!-- source-id: ch09#ch09lev8sec1 -->
### 9.8.1 临时测试

dd(1) 命令（设备到设备复制）可用于执行顺序磁盘性能的临时测试。例如，测试使用 1 MB I/O 大小的顺序读取：

![点击查看代码图片](../images/pg490.jpg)

```text
# dd if=/dev/sda1 of=/dev/null bs=1024k count=1k
1024+0 records in
1024+0 records out
1073741824 bytes (1.1 GB) copied, 7.44024 s, 144 MB/s
```

由于内核可以缓存和缓冲数据，因此 dd(1) 测量的吞吐量可以是缓存和磁盘的吞吐量，而不仅仅是磁盘的吞吐量。要仅测试磁盘的性能，您可以为磁盘使用字符特殊设备：在 Linux 上，raw(8) 命令（如果可用）可以在 /dev/raw 下创建这些设备。顺序写入可以类似地测试；但是，请注意不要破坏磁盘上的所有数据，包括主引导记录和分区表！

更安全的方法是将直接 I/O 标志与 dd(1) 和文件系统文件一起使用，而不是磁盘设备。请记住，测试现在包括一些文件系统开销。例如，对名为 out1 的文件进行写入测试：

![点击查看代码图片](../images/pg491-1.jpg)

```text
# dd if=/dev/zero of=out1 bs=1024k count=1000 oflag=direct
1000+0 records in
1000+0 records out
1048576000 bytes (1.0 GB, 1000 MiB) copied, 1.79189 s, 585 MB/s
```

另一个终端会话中的 iostat(1) 确认磁盘 I/O 写入吞吐量约为 585 MB/秒。

使用 `iflag=direct` 与输入文件进行直接 I/O。

<!-- source-id: ch09#ch09lev8sec2 -->
### 9.8.2 自定义负载生成器

要测试自定义工作负载，您可以编写自己的负载生成器并使用 iostat(1) 测量结果性能。自定义负载生成器可以是一个简短的 C 程序，用于打开设备路径并应用预期的工作负载。在 Linux 上，块特殊设备文件可以使用 O\_DIRECT 打开，以避免缓冲。如果您使用高级语言，请尝试使用至少避免库缓冲的系统级接口（例如，Perl 中的 sysread()），并且最好也避免内核缓冲（例如，O\_DIRECT）。

<!-- source-id: ch09#ch09lev8sec3 -->
### 9.8.3 微基准测试工具

例如，可用的磁盘基准测试工具包括 Linux 上的 hdparm(8)：

![点此查看代码图片](../images/pg491-2.jpg)

```text

/dev/sdb:
```

`-T` 选项测试缓存读取，`-t` 测试磁盘设备读取。结果显示磁盘缓存命中和未命中之间存在显著差异。

研究工具文档以了解任何注意事项，并参阅 [第 12 章](#ch12-ch12)、[基准测试](#ch12-ch12)，了解有关微基准测试的更多背景信息。另请参阅 [第 8 章](#ch08-ch08)、[文件系统](#ch08-ch08)，了解通过文件系统测试磁盘性能的工具（还有更多可用工具）。

### 9.8.5 ioping

ioping(1) 是一个有趣的磁盘微基准测试工具，类似于 ICMP ping(8) 实用程序。在 nvme0n1 磁盘设备上运行 ioping(1)：

![点击查看代码图片](../images/pg492-1.jpg)

```text
# ioping /dev/nvme0n1
4 KiB <<< /dev/nvme0n1 (block device 8 GiB): request=1 time=438.7 us (warmup)
4 KiB <<< /dev/nvme0n1 (block device 8 GiB): request=2 time=421.0 us
4 KiB <<< /dev/nvme0n1 (block device 8 GiB): request=3 time=449.4 us
4 KiB <<< /dev/nvme0n1 (block device 8 GiB): request=4 time=412.6 us
4 KiB <<< /dev/nvme0n1 (block device 8 GiB): request=5 time=468.8 us
^C

--- /dev/nvme0n1 (block device 8 GiB) ioping statistics ---
4 requests completed in 1.75 ms, 16 KiB read, 2.28 k iops, 8.92 MiB/s
generated 5 requests in 4.37 s, 20 KiB, 1 iops, 4.58 KiB/s
min/avg/max/mdev = 412.6 us / 437.9 us / 468.8 us / 22.4 us
```

默认情况下，ioping(1) 每秒发出一次 4 KB 读取，并以微秒为单位打印其 I/O 延迟。终止时，它会打印各种统计数据。

ioping(1) 与其他基准测试工具的不同之处在于它的工作负载很轻。以下是 ioping(1) 运行时的一些 iostat(1) 输出：

![点击查看代码图片](../images/pg492-2.jpg)

```text
$ iostat -xsz 1
[...]
Device             tps      kB/s    rqm/s   await aqu-sz  areq-sz  %util
nvme0n1           1.00      4.00     0.00    0.00   0.00     4.00   0.40
```

磁盘利用率仅为 0.4%。 ioping(1) 可用于调试生产环境中的问题，而其他微基准测试不适合这些环境，因为它们通常会将目标磁盘驱动到 100% 利用率。

## 9.9 调优

[第 9.5 节](#ch09-ch09lev5)、[方法论](#ch09-ch09lev5) 中涵盖了许多调优方法，包括缓存调优、扩展和工作负载表征，这可以帮助您识别和消除不必要的工作。调优的另一个重要领域是存储配置，可以将其作为静态性能调优方法的一部分进行研究。

以下部分显示了可以调整的区域：操作系统、磁盘设备和磁盘控制器。可用的可调参数因操作系统版本、磁盘型号、磁盘控制器及其固件而异；请参阅各自的文档。虽然更改可调参数很容易，但默认设置通常是合理的，很少需要进行太多调整。

### 9.9.1 操作系统可调参数

其中包括 ionice(1)、资源控制和内核可调参数。

<!-- source-id: ch09#ch09lev3_45 -->
#### ionice

在 Linux 上， ionice(1) 命令可用于设置进程的 I/O 调度类和优先级。调度类别以数字方式标识：

- **0，none**：未指定类，因此内核将选择默认值（尽力而为），其优先级基于进程的nice值。
- **1、实时**：对磁盘的最高优先级访问。如果误用，这可能会导致其他进程挨饿（就像 RT CPU 调度类一样）。
- **2，尽力而为**：默认调度类，支持优先级0-7，其中0为最高。
- **3、空闲**：仅在磁盘空闲一段宽限期后才允许磁盘 I/O。

用法示例：

```text
# ionice -c 3 -p 1623
```

这会将进程 ID 1623 置于空闲 I/O 调度类中。这对于长时间运行的备份作业来说可能是理想的，这样它们就不太可能干扰生产工作负载。

<!-- source-id: ch09#ch09lev3_46 -->
#### 资源控制

现代操作系统提供资源控制，以自定义方式管理磁盘或文件系统 I/O 使用情况。

对于 Linux，容器组 (cgroups) 块 I/O (blkio) 子系统为进程或进程组提供存储设备资源控制。这可以是比例权重（如份额）或固定限制。可以独立设置读取和写入以及 IOPS 或吞吐量（每秒字节数）的限制。有关更多详细信息，请参见 [第 11 章](#ch11-ch11)、[云计算](#ch11-ch11)。

<!-- source-id: ch09#ch09lev3_47 -->
#### 可调参数

Linux 可调参数示例包括：

- **/sys/block/\*/queue/scheduler**：选择 I/O 调度策略：可能包括 noop、deadline、cfq 等。请参阅 [第 9.4 节](#ch09-ch09lev4)、[架构](#ch09-ch09lev4) 中的前文介绍。
- **/sys/block/\*/queue/nr\_requests**：块层可以分配的读或写请求的数量。
- **/sys/block/\*/queue/read\_ahead\_kb**：文件系统请求的最大预读千字节数。

与其他内核可调参数一样，请查看文档以获取完整列表、描述和警告。在 Linux 源代码中，请参阅 Documentation/block/queue-sysfs.txt。

### 9.9.2 磁盘设备可调参数

## 9.10 练习

1. 回答以下有关磁盘术语的问题：
    - 什么是 IOPS？
    - 服务时间和等待时间有什么区别？
    - 什么是磁盘 I/O 等待时间？
    - 什么是延迟异常值？
    - 什么是非数据传输磁盘命令？
2. 回答以下概念性问题：
    - 描述磁盘利用率和饱和度。
    - 描述随机磁盘 I/O 和顺序磁盘 I/O 之间的性能差异。
    - 描述磁盘缓存对于读取和写入 I/O 的作用。
3. 回答以下更深层次的问题：
    - 解释为什么虚拟磁盘的利用率（繁忙百分比）可能会产生误导。
    - 解释为什么“I/O 等待”指标可能会产生误导。
    - 描述 RAID-0（条带化）和 RAID-1（镜像）的性能特征。
    - 描述当磁盘工作超载时会发生什么，包括对应用程序性能的影响。
    - 描述当存储控制器工作负载（吞吐量或 IOPS）过载时会发生什么情况，包括对应用程序性能的影响。

# 第 5 章 — 应用

性能最好在最接近执行工作的位置进行调整：在应用程序中。其中包括数据库、Web 服务器、应用程序服务器、负载平衡器、文件服务器等。后面的章节从应用程序消耗的资源的角度来介绍应用程序：CPU、内存、文件系统、磁盘和网络。本章讨论应用程序级别。

应用程序本身可能变得极其复杂，尤其是在涉及许多组件的分布式环境中。应用程序内部结构的研究通常是应用程序开发人员的领域，可以包括使用第三方工具进行内省。对于那些研究系统性能的人来说，应用程序性能分析包括配置应用程序以充分利用系统资源、描述应用程序如何使用系统以及分析常见问题。

本章的学习目标是：

- 描述性能调整目标。
- 熟悉性能改进技术，包括多线程编程、哈希表和非阻塞 I/O。
- 了解常见的锁定和同步原语。
- 了解不同编程语言带来的挑战。
- 遵循线程状态分析方法。
- 执行 CPU 分析和 Off-CPU 分析。
- 执行系统调用分析，包括跟踪进程执行。
- 了解堆栈跟踪陷阱：缺少符号和堆栈。

本章讨论应用程序基础知识、应用程序性能基础知识、编程语言和编译器、通用应用程序性能分析策略以及基于系统的应用程序可观测性工具。

## 5.1 应用基础知识

在深入了解应用程序性能之前，您应该熟悉应用程序的角色、基本特征及其在行业中的生态系统。这构成了您可以了解应用程序活动的上下文。它还为您提供了了解常见性能问题和调优的机会，并提供了进一步研究的途径。要了解此背景，请尝试回答以下问题：

- **功能**：应用程序的作用是什么？它是数据库服务器、Web 服务器、负载均衡器、文件服务器、对象存储吗？
- **操作**：应用程序服务什么请求，或者执行什么操作？数据库服务*查询*（和*命令*），Web 服务器服务*HTTP 请求*，等等。这可以作为速率来测量，以衡量负载和容量规划。
- **性能要求**：运行应用程序的公司是否有服务级别目标（SLO）（例如，99.9% 的请求延迟低于 100 毫秒）？
- **CPU 模式**：应用程序是作为用户级软件还是内核级软件实现的？大多数应用程序都是用户级的，作为一个或多个进程执行，但有些应用程序是作为内核服务（例如 NFS）实现的，BPF 程序也是内核级的。
- **配置**：应用程序是如何配置的，为什么？该信息可以在配置文件中或通过管理工具找到。检查与性能相关的任何可调参数是否已更改，包括缓冲区大小、缓存大小、并行性（进程或线程）和其他选项。
- **主机**：应用程序的主机是什么？服务器还是云实例？ CPU、内存拓扑、存储设备等是什么？他们的极限是什么？
- **指标**：是否提供应用程序指标，例如操作率？它们可能由捆绑工具或第三方工具、通过 API 请求或通过处理操作日志来提供。
- **日志**：应用程序创建哪些操作日志？可以启用哪些日志？从日志中可以获得哪些性能指标（包括延迟）？例如，MySQL 支持“慢速查询日志”，为每个慢于特定阈值的查询提供有价值的性能详细信息。
- **版本**：应用程序是最新版本吗？最新版本的发行说明中是否注意到了性能修复或改进？
- **错误**：应用程序是否有缺陷数据库？您的应用程序版本有哪些“性能”缺陷？如果您当前遇到性能问题，请搜索缺陷数据库，查看以前是否发生过类似情况、如何调查该问题，以及还涉及哪些内容。
- **源代码**：应用程序是开源的吗？如果是这样，则可以研究分析器和跟踪器识别的代码路径，这可能会带来性能提升。您可以自行修改应用程序代码以提高性能，并向上游提交改进以包含在官方应用程序中。
- **社区**：该应用程序是否有一个可以共享性能发现的社区？社区可能包括论坛、博客、互联网中继聊天 (IRC) 频道、其他聊天频道（例如 Slack）、聚会和会议。聚会和会议经常在网上发布幻灯片和视频，这些都是多年后有用的资源。他们可能还有一位社区经理来分享社区更新和新闻。
- **书籍**：有关于应用程序和/或其性能的书籍吗？它们是好书吗（例如，由专家撰写、实用/可操作、充分利用读者的时间、最新的等等）？
- **专家**：谁是该应用程序公认的性能专家？了解他们的名字可以帮助您找到他们创作的材料。

无论来源如何，您的目标是从较高的层面了解应用程序 — 它的用途、运行方式以及性能表现。如果您能找到的话，一个非常有用的资源是说明应用程序内部结构的“功能图”。

接下来的部分将介绍其他应用程序基础知识：设定目标、优化常见情况、可观测性和大 O 表示法。

### 5.1.1 目标

性能目标为您的性能分析工作提供方向，并帮助您选择要执行的活动。如果没有明确的目标，性能分析就有可能变成随机的“钓鱼探险”。

对于应用程序性能，您可以从应用程序执行哪些操作（如前所述）以及性能目标是什么开始。目标可能是：

- **延迟**：应用程序响应时间短或一致
- **吞吐量**：较高的应用程序操作速率或数据传输率
- **资源利用率**：给定应用程序工作负载的效率
- **价格**：提高性价比，降低计算成本

如果可以使用源自业务或服务质量要求的指标来量化这些，那就更好了。例子有：

- 平均应用程序请求延迟为 5 毫秒
- 95% 的请求在 100 毫秒或更短的延迟内完成
- 消除延迟异常值：超过 1,000 毫秒的零请求
- 每台给定大小的服务器每秒至少处理 10,000 个应用程序请求的最大吞吐量[^fn-ch05-ch05-footnote-1]
- 每秒 10,000 个应用程序请求的平均磁盘利用率低于 50%

一旦选择了目标，您就可以研究该目标的限制因素。对于延迟，限制因素可能是磁盘或网络 I/O；对于吞吐量，可能是 CPU 使用率。本章和其他章节中的策略将帮助您识别它们。

对于基于吞吐量的目标，请注意并非所有操作在性能或成本方面都是相同的。如果目标是一定的操作率，那么指定操作的类型可能也很重要。这可以是基于预期或测量的工作负载的分布。

[第 5.2 节](#ch05-ch05lev2)、[应用程序性能技术](#ch05-ch05lev2)描述了提高应用程序性能的常用方法。其中一些可能对一个目标有意义，但对另一个目标则不然；例如，选择较大的 I/O 大小可能会以延迟为代价提高吞吐量。在确定哪些主题最适用时，请记住您所追求的目标。

<!-- source-id: ch05#ch05lev3_1 -->
#### Apdex

一些公司使用目标应用程序性能指数（ApDex 或 Apdex）作为目标和监控指标。它可以更好地传达客户体验，并首先对客户事件进行分类，以确定它们是“令人满意”、“可以忍受”还是“令人沮丧”。然后使用 [\[Apdex 20\]](#ch05-ch05ref11) 计算 Apdex：

Apdex =（满意 + 0.5 × 可容忍 + 0 × 令人沮丧）/总事件

生成的 Apdex 范围从 0（没有满意的客户）到 1（所有满意的客户）。

### 5.1.2 优化常见情况

软件内部结构可能很复杂，具有许多不同的代码路径和行为。如果您浏览源代码，这一点可能尤其明显：应用程序通常有数万行代码，而操作系统内核则有数十万行以上。随机选择要优化的区域可能会涉及大量工作而收效甚微。

有效提高应用程序性能的一种方法是找到生产工作负载中最常见的代码路径，并首先改进这些路径。如果应用程序受 CPU 限制，则可能意味着这些代码路径经常在 CPU 上运行。如果应用程序受 I/O 限制，则应查看经常导致 I/O 的代码路径。这些路径可以通过应用程序分析和性能剖析来确定，包括研究堆栈跟踪和火焰图，后续章节将对此进行介绍。应用程序可观测性工具还可以提供理解常见情况所需的更高层次上下文。

<!-- source-id: ch05#ch05lev1sec3 -->
### 5.1.3 可观测性

正如我在本书的许多章节中重申的那样，最大的性能提升可以来自“消除不必要的工作”。

当根据性能选择应用程序时，这一事实有时会被忽视。如果基准测试显示应用程序 A 比应用程序 B 快 10%，选择应用程序 A 可能很诱人。但是，如果应用程序 A 不透明，而应用程序 B 提供一套丰富的可观测性工具，那么从长远来看，应用程序 B 很可能是更好的选择。这些工具可以帮助发现并消除不必要的工作，更好地理解和调优正在执行的工作。通过增强可观测性获得的性能收益可能远大于最初的 10% 性能差异。语言和运行时的选择也是如此：例如，与选择一种新语言相比，选择成熟且拥有丰富可观测性工具的 Java 或 C 可能更好。

### 5.1.4 大 O 表示法

大 O 表示法通常作为计算机科学的一部分教授，用于分析算法的复杂度，并描述其性能如何随输入数据集规模扩展。O 指的是函数的“阶”，描述其增长率。此表示法可帮助程序员在开发应用程序时选择更高效、性能更佳的算法 [\[Knuth 76\]](#ch05-ch05ref1)[\[Knuth 97\]](#ch05-ch05ref2)。

[表 5.1](#ch05-ch05tab01)中列出了常见的大 O 表示法和算法示例。

<!-- source-id: ch05#ch05tab01 -->
**表 5.1 大 O 符号示例**

| **符号** | **示例** |
| --- | --- |
| O(1) | 布尔测试 |
| O(log n) | 排序数组的二分查找 |
| O(n) | 链表的线性搜索 |
| O(n log n) | 快速排序（平均情况） |
| O(n^2) | 冒泡排序（平均情况） |
| O(2^n) | 因式分解；指数增长 |
| O(n!) | 旅行商问题的暴力求解 |

该符号允许程序员估计不同算法的加速，确定哪些代码区域将带来最大的改进。例如，对于搜索包含 100 个项目的排序数组，线性搜索和二分搜索之间的差异是 21 倍 (100/log(100))。

[图 5.1](#ch05-ch05fig01) 中描绘了这些算法的性能，显示了它们随扩展的趋势。

<!-- source-id: ch05#ch05fig01 -->
![图 5.1 不同算法的运行时间与输入大小](../images/05fig01.jpg)

这种分类有助于系统性能分析师了解某些算法在规模扩大后性能会很差。当应用程序被迫为比以前更多的用户或数据对象提供服务时，性能问题可能会出现，此时 O(n^2) 等算法可能开始表现出病态性能。解决方案可能是开发人员使用更有效的算法，或以不同的方式划分数据集。

大 O 表示法确实忽略了每种算法产生的一些恒定计算成本。对于 *n*（输入数据大小）较小的情况，这些成本可能占主导地位。

## 5.2 应用程序性能技术

本节介绍一些可提高应用程序性能的常用技术：选择 I/O 大小、缓存、缓冲、轮询、并发性和并行性、非阻塞 I/O 以及处理器绑定。请参阅应用程序文档以了解使用了哪些功能，以及任何其他特定于应用程序的功能。

<!-- source-id: ch05#ch05lev2sec1 -->
### 5.2.1 选择 I/O 大小

与执行 I/O 相关的成本包括初始化缓冲区、进行系统调用、模式或上下文切换、分配内核元数据、检查进程权限和限制、将地址映射到设备、执行内核和驱动程序代码以交付 I/O，以及最后释放元数据和缓冲区。小型和大型 I/O 都需要支付“初始化税”。为了提高效率，每个 I/O 传输的数据越多越好。

增加 I/O 大小是应用程序用来提高吞吐量的常见策略。考虑到任何固定的每 I/O 成本，将 128 KB 作为单个 I/O 传输通常比 128 × 1 KB I/O 更高效。尤其是旋转磁盘 I/O，由于寻道时间，历史上每 I/O 成本较高。

当应用程序不需要更大的 I/O 大小时，就会有一个缺点。执行 8 KB 随机读取的数据库在使用 128 KB 磁盘 I/O 大小时可能会运行得更慢，因为浪费了 120 KB 的数据传输。这会引入 I/O 延迟，可以通过选择更接近应用程序请求的较小 I/O 大小来降低 I/O 延迟。不必要的较大 I/O 大小也会浪费缓存空间。

<!-- source-id: ch05#ch05lev2sec2 -->
### 5.2.2 缓存

操作系统使用缓存来提高文件系统读取性能和内存分配性能；应用程序出于类似的原因也经常使用缓存。与其每次都执行昂贵的操作，不如将常用操作的结果存储在本地缓存中供将来使用。一个例子是数据库缓冲缓存，它存储常用数据库查询的数据。

部署应用程序时的一项常见任务是确定提供或可以启用哪些缓存，然后配置其大小以适合系统。

虽然缓存可以提高读取性能，但它们的存储通常用作缓冲区来提高写入性能。

<!-- source-id: ch05#ch05lev2sec3 -->
### 5.2.3 缓冲

为了提高写入性能，数据可以在发送到下一级之前合并在缓冲区中。这增加了 I/O 大小和操作效率。根据写入的类型，它还可能会增加写入延迟，因为对缓冲区的第一次写入会在发送之前等待后续写入。

环形缓冲区（或*循环缓冲区*）是一种固定缓冲区，可用于异步作用于缓冲区的组件之间的连续传输。它可以使用开始和结束指针来实现，每个组件可以在添加或删除数据时移动开始指针和结束指针。

<!-- source-id: ch05#ch05lev2sec4 -->
### 5.2.4 轮询

轮询是一种技术，系统通过循环检查事件的状态来等待事件发生，检查之间有暂停。当几乎没有什么工作要做时，轮询存在一些潜在的性能问题：

- 重复检查带来的高昂 CPU 开销
- 事件发生和下一次轮询检查之间的高延迟

如果这是一个性能问题，应用程序可能能够更改其行为以侦听事件的发生，这会立即通知应用程序并执行所需的例程。

<!-- source-id: ch05#ch05lev3_2 -->
#### poll() 系统调用

有一个 poll(2) 系统调用来检查文件描述符的状态，它提供与轮询类似的功能，尽管它是基于事件的，因此不会遭受轮询的性能成本。

poll(2)接口支持多个文件描述符作为数组，这需要应用程序在事件发生时扫描数组以查找相关的文件描述符。此扫描的时间复杂度为 O(n)（请参阅 [第 5.1.4 节](#ch05-ch05lev1sec4)、[大 O 表示法](#ch05-ch05lev1sec4)），其开销可能会成为大规模的性能问题。 Linux 上的替代方案是 epoll(2)，它可以避免扫描，因此时间复杂度为 O(1)。在 BSD 上，等效项是 kqueue(2)。

<!-- source-id: ch05#ch05lev2sec5 -->
### 5.2.5 并发和并行

分时系统（包括所有源自 Unix 的系统）提供程序*[并发性](#gloss-glo-033)*：加载并开始执行多个可运行程序的能力。虽然它们的运行时间可能重叠，但它们不一定同时在 CPU 上执行。这些程序中的每一个都可以是一个应用程序进程。

要利用多处理器系统，应用程序必须同时在多个 CPU 上执行。这就是“并行性”，应用程序可以通过使用多个进程（*多进程*）或多线程（*多线程*）来实现，每个进程或线程执行自己的任务。由于[第 6 章](#ch06-ch06)、[CPU](#ch06-ch06)、[第 6.3.13 节](#ch06-ch06lev3sec13)、[多进程与多线程](#ch06-ch06lev3sec13)中解释的原因，多线程（或等效任务）效率更高，因此是首选方法。

除了增加 CPU 工作的吞吐量之外，多线程（或进程）是允许并发执行 I/O 的一种方法，因为当 I/O 阻塞的线程等待时，其他线程可以执行。 （另一种方式是异步 I/O。）

使用多进程或多线程架构意味着允许内核通过 CPU 调度程序来决定运行谁，并以上下文切换开销为代价。另一种方法是用户模式应用程序实现自己的调度机制和程序模型，以便它可以在同一操作系统线程中服务不同的应用程序请求（或程序）。机制包括：

- **纤程**：也称为*轻量级线程*，它们是线程的用户模式版本，其中每个纤程代表一个可调度的程序。应用程序可以使用自己的调度逻辑来选择运行哪个纤程。例如，可以为每个应用程序请求分配一个纤程，其开销低于使用操作系统线程执行相同操作。例如，Microsoft Windows 支持纤程。[^fn-ch05-ch05-footnote-2]
- **协同例程**：协同例程比纤程更轻量，是可以由用户模式应用程序调度的子例程，提供并发机制。
- **基于事件的并发**：程序被分解为一系列事件处理程序，可运行事件可以排入队列并执行。例如，可以为每个应用程序请求分配元数据，由事件处理程序引用。Node.js 运行时使用单个*事件工作线程*实现基于事件的并发（这可能成为瓶颈，因为它只能在一个 CPU 上执行）。

使用所有这些机制，I/O 仍然必须由内核处理，因此操作系统线程切换通常是不可避免的。[^fn-ch05-ch05-footnote-3] 此外，为了并行性，必须使用多个操作系统线程，以便可以跨多个 CPU 调度它们。

一些运行时使用协同例程来实现轻量级并发，并使用多个操作系统线程来实现并行性。一个例子是 Golang 运行时，它在操作系统线程池上使用*goroutines*（协同例程）。为了提高性能，当 goroutine 进行阻塞调用时，Golang 的调度程序会自动将阻塞线程上的其他 goroutine 移动到其他线程来运行 [\[Golang 20\]](#ch05-ch05ref12)。

多线程编程的三种常见模型是：

- **服务线程池**：服务网络请求的线程池，其中每个线程一次服务一个客户端连接。
- **CPU 线程池**：每个 CPU 创建一个线程。这通常用于长时间的批处理，例如视频编码。
- **分阶段事件驱动架构 (SEDA)**：应用程序请求被分解为可由包含一个或多个线程的线程池处理的阶段。

由于多线程编程与进程共享相同的地址空间，因此线程可以直接读写相同的内存，而不需要更昂贵的接口（例如多进程编程的进程间通信\[IPC\]）。为了完整性，使用同步原语，以便数据不会因多个线程同时读写而损坏。

<!-- source-id: ch05#ch05lev3_3 -->
#### 同步原语

同步原语管理对内存的访问以确保完整性，并且可以类似于交通灯调节对交叉路口的访问进行操作。而且，就像交通信号灯一样，它们可以阻止交通流动，从而导致等待时间（延迟）。应用程序常用的三种类型是：

- **互斥锁（mutex，MUTual EXclusion）**：只有锁的持有者可以进行操作；其他线程会阻塞，在脱离 CPU 的状态下等待。
- **自旋锁**：自旋锁允许持有者进行操作，而其他线程则在 CPU 上的紧凑循环中*自旋*，等待锁释放。它们可以提供低延迟访问——被阻塞的线程始终留在 CPU 上，锁一旦可用，经过几个周期即可运行——但线程自旋等待时也会浪费 CPU 资源。
- **读写锁（RW 锁）**：读写锁通过允许多个读者同时访问，或只允许一个写者且不允许读者访问，来保证数据完整性。
- **信号量**：这是一种变量类型，可以是计数信号量，允许给定数量的并行操作；也可以是二进制信号量，只允许一个操作（实际效果类似互斥锁）。

互斥锁可以由库或内核实现为自旋锁和互斥锁的混合体，如果持有者当前正在另一个 CPU 上运行，则等待线程会自旋；否则，或达到自旋阈值时，就会阻塞。它们最初于 2009 年针对 Linux 实现 [\[Zijlstra 09\]](#ch05-ch05ref3)，现在根据锁的状态具有三个路径（如 Documentation/locking/mutex-design.rst [\[Molnar 20\]](#ch05-ch05ref17) 中所述）：

1. **fastpath**：尝试使用 cmpxchg 指令获取锁以设置所有者。仅当未持有锁时此操作才会成功。
2. **midpath**：也称为*乐观自旋*；当锁持有者也在运行时，当前线程在 CPU 上自旋，希望锁很快释放，从而无需阻塞即可获取。
3. **slowpath**：这会阻塞并取消调度线程，以便稍后在锁可用时唤醒。

Linux 读取-复制-更新 (RCU) 机制是另一种在内核代码中大量使用的同步机制。它允许读取操作而无需获取锁，从而比其他锁类型提高了性能。使用 RCU，写入操作会创建受保护数据的副本并更新该副本，而进行中的读取操作仍可以访问原始数据。它可以检测何时不再有任何读取器（基于每个 CPU 的各种条件），然后用更新的副本替换原始副本 [\[Linux 20e\]](#ch05-ch05ref15)。

研究涉及锁的性能问题可能非常耗时，并且通常需要熟悉应用程序源代码。这通常是开发人员的一项活动。

<!-- source-id: ch05#ch05lev3_4 -->
#### 哈希表

锁的哈希表可用于为大量数据结构使用数量合适的锁。虽然这里只做概要介绍，但这是一个需要编程背景的高级主题。

想象一下以下两种方法：

- 所有数据结构的单个全局互斥锁。虽然这种解决方案很简单，但是并发访问会遇到锁争用和等待时的延迟。需要锁的多个线程将“串行化”——按顺序执行，而不是同时执行。
- 每个数据结构的互斥锁。虽然这将争用减少到仅真正需要的次数（对同一数据结构的并发访问），但存在锁的存储开销以及为每个数据结构创建和销毁锁的 CPU 开销。

锁哈希表是一种中间解决方案，适用于预期锁争用较少的情况。创建固定数量的锁，并使用哈希算法来选择哪个锁用于哪个数据结构。这避免了随着数据结构创建和销毁而反复创建、销毁锁的开销，也避免了只有单个锁的问题。

[图 5.2](#ch05-ch05fig02) 中显示的示例哈希表有四个条目，称为*桶（buckets）*，每个桶都包含自己的锁。

<!-- source-id: ch05#ch05fig02 -->
![图 5.2 哈希表示例](../images/05fig02.jpg)

此示例还展示了一种解决“哈希冲突”的方法，其中两个或多个输入数据结构哈希到同一存储桶。在这里，创建了一个数据结构链，将它们全部存储在同一个存储桶中，哈希函数将在其中再次找到它们。如果这些哈希链变得太长并且串行行走，则可能会出现性能问题，因为它们仅受一个锁的保护，而该锁的保持时间可能会很长。可以选择哈希函数和表大小，以将数据结构均匀分布在多个存储桶上，以使哈希链长度保持最小。应检查生产工作负载的哈希链长度，以防哈希算法未按预期工作，而是创建性能不佳的长哈希链。

理想情况下，哈希表桶的数量应等于或大于 CPU 数量，以获得最大并行性。哈希算法可以很简单：取数据结构地址的低位[^fn-ch05-ch05-footnote-4]，将其作为大小为 2 的幂的锁数组的索引。这种简单的算法也很快，可以快速定位数据结构。

对于内存中的一系列相邻锁，当锁落入同一高速缓存行时，可能会出现性能问题。两个 CPU 更新同一缓存行中的不同锁将遇到缓存一致性开销，每个 CPU 都会使对方缓存中的缓存行无效。这种情况称为“伪共享”，通常通过使用未使用的字节“填充”锁来解决，以便内存中的每个缓存行中仅存在一个锁。

<!-- source-id: ch05#ch05lev2sec6 -->
### 5.2.6 非阻塞 I/O

Unix 进程生命周期（如[第 3 章](#ch03-ch03)、[操作系统](#ch03-ch03)所示）显示进程在 I/O 期间阻塞并进入睡眠状态。该模型存在一些性能问题：

- 每个 I/O 操作在被阻塞时都会消耗一个线程（或进程）。为了支持许多并发 I/O，应用程序必须创建许多线程（通常每个客户端一个），这会产生与线程创建和销毁相关的成本，以及保留它们所需的堆栈空间。
- 对于频繁的短期 I/O，频繁上下文切换的开销会消耗 CPU 资源并增加应用程序延迟。

*非阻塞 I/O* 模型异步发出 I/O，不会阻塞当前线程，然后当前线程可以执行其他工作。这是 Node.js [\[Node.js 20\]](#ch05-ch05ref18) 的一个关键功能，Node.js 是一个服务器端 JavaScript 应用程序环境，指导代码以非阻塞方式开发。

有多种机制可以执行非阻塞或异步 I/O，包括：

- **open(2)**：通过 O\_ASYNC 标志。当文件描述符上的 I/O 变为可能时，会使用信号通知进程。
- **io\_submit(2)**：Linux 异步 I/O (AIO)。
- **sendfile(2)**：这会将数据从一个文件描述符复制到另一个文件描述符，将 I/O 交由内核执行，而不是通过用户态 I/O 执行。[^fn-ch05-ch05-footnote-5]
- **io\_uring\_enter(2)**：Linux io\_uring 允许使用用户和内核空间之间共享的环形缓冲区提交异步 I/O [\[Axboe 19\]](#ch05-ch05ref9)。

检查操作系统文档以了解其他方法。

<!-- source-id: ch05#ch05lev2sec7 -->
### 5.2.7 处理器绑定

对于 NUMA 环境，进程或线程在单个 CPU 上保持运行，并在执行 I/O 后继续运行在之前相同的 CPU 上，可能是有利的。这可以提高应用程序的内存局部性，减少内存 I/O 周期并提高整体应用程序性能。操作系统充分考虑了这一点，并设计为让应用程序线程保持在相同的 CPU 上（*CPU 亲和性*）。这些主题在[第 7 章](#ch07-ch07)、[内存](#ch07-ch07)中介绍。

某些应用程序通过将自身“绑定”到 CPU 来强制执行此行为。这可以显著提高某些系统的性能。当绑定与其他 CPU 绑定（例如设备中断映射到 CPU）冲突时，它还会降低性能。

当同一系统上运行其他租户或应用程序时，请特别注意 CPU 绑定的风险。这是我在操作系统虚拟化（容器）环境中遇到的一个问题，其中应用程序可以看到所有 CPU，然后绑定到某些 CPU，假设它是服务器上唯一的应用程序。当服务器被其他也绑定的租户应用程序共享时，多个租户可能会在不知不觉中绑定到相同的 CPU，从而导致 CPU 争用和调度程序延迟，即使其他 CPU 处于空闲状态。

在应用程序的生命周期中，主机系统也可能会发生变化，未更新的绑定可能会损害而不是帮助性能，例如，当它们不必要地跨多个处理器插槽绑定到 CPU 时。

<!-- source-id: ch05#ch05lev2sec8 -->
### 5.2.8 性能准则

有关提高应用程序性能的更多技术，请参阅[第 2 章](#ch02-ch02)中的性能箴言方法。总之：

1. 不要这样做。
2. 做一次，但不要再做一次。
3. 少做。
4. 稍后再做。
5. 在他们不注意的时候做。
6. 同时进行。
7. 做得更便宜。

第一项“不要这样做”就是消除不必要的工作。有关此方法的更多详细信息，请参阅[第 2 章](#ch02-ch02)、[方法论](#ch02-ch02)、[第 2.5.20 节](#ch02-ch02lev5sec20)、[性能箴言](#ch02-ch02lev5sec20)。

## 5.3 编程语言

编程语言可以被编译或解释，也可以通过虚拟机执行。许多语言将“性能优化”列为功能，但严格来说，这些通常是“执行”该语言的软件的功能，而不是语言本身。例如，Java HotSpot 虚拟机软件包含一个即时 (JIT) 编译器，可动态提高性能。

解释器和语言虚拟机还通过各自的专用工具提供不同程度的性能可观测性支持。对于系统性能分析师来说，使用这些工具进行基本分析可以快速取得成果。例如，高 CPU 使用率可能是垃圾回收（GC）造成的，然后可以通过一些常用可调参数修复；也可能由某条代码路径造成，而该路径可以在缺陷数据库中作为已知缺陷找到，并通过升级软件版本修复（这种情况很常见）。

以下部分描述了每种编程语言类型的基本性能特征。有关某种编程语言性能的更多信息，请查阅该语言的相关资料。

<!-- source-id: ch05#ch05lev3sec1 -->
### 5.3.1 编译语言

编译器接收程序并在运行时之前生成机器指令，这些指令存储在称为 *binaries* 的二进制可执行文件中；在 Linux 和其他 Unix 衍生系统上通常使用可执行与可链接格式（ELF），在 Windows 上使用可移植可执行格式（PE）。这些文件可以随时运行，无需再次编译。编译型语言包括 C、C++ 和汇编语言。有些语言可能同时具有解释器和编译器。

编译后的代码通常具有高性能，因为在 CPU 执行之前不需要进一步翻译。编译代码的一个常见示例是 Linux 内核，它主要是用 C 语言编写的，其中一些关键路径是用汇编语言编写的。

编译型语言的性能分析通常比较直接，因为执行的机器代码通常与原始程序紧密对应（尽管这取决于编译优化）。在编译期间，可以生成将地址映射到程序函数和对象名称的符号表。之后，对 CPU 执行情况的剖析和跟踪就可以直接映射到这些程序名称，使分析人员能够研究程序执行过程。堆栈跟踪及其中的数字地址也可以映射并转换为函数名称，以提供代码路径的调用祖先。

编译器可以通过使用*编译器优化*（优化 CPU 指令的选择和放置的例程）来提高性能。

<!-- source-id: ch05#ch05lev3_5 -->

对于不需要帧指针的函数，不要将帧指针保留在寄存器中。这样可以省去保存、设置和恢复帧指针的指令；在许多函数中还可以多出一个可用寄存器。**这也使得在某些机器上无法进行调试。**

这是一个权衡的例子：省略帧指针通常会破坏使用堆栈跟踪进行分析的分析器。

考虑到堆栈分析器的价值，此选项可能牺牲原本可以在后续发现的性能收益，而且这种损失可能远远超过该选项最初带来的性能增益。在这种情况下，可以使用 `-f`**no-**`omit-frame-pointer` 编译，以避免此优化。[^fn-ch05-ch05-footnote-6] 另一个推荐选项是 `-g`，用于包含调试信息，以便日后调试；如果需要，之后可以删除或剥离调试信息。[^fn-ch05-ch05-footnote-7]

如果出现性能问题，可能会倾向于简单地以降低的优化级别（例如从 `–O3` 到 `–O2`）重新编译应用程序，以期能够满足任何调试需求。事实证明这并不简单：对编译器输出的更改可能是巨大且重要的，并且可能会影响您最初尝试分析的问题的行为。

<!-- source-id: ch05#ch05lev3sec2 -->
### 5.3.2 解释语言

解释型语言在运行时将程序翻译为操作并执行，这一过程会增加执行开销。解释型语言通常不会追求高性能，而是用于编程和调试容易等其他因素更重要的场景。*Shell 脚本*就是解释型语言的一个例子。

除非提供可观测性工具，否则解释型语言的性能分析可能很困难。CPU 分析可以显示解释器的活动（包括解析、翻译和执行操作），但可能无法显示原始程序的函数名，从而使重要的程序上下文难以判断。这种解释器分析也并非完全没有价值，因为解释器本身可能存在性能问题，即使它正在执行的代码看起来设计良好。

根据解释器的不同，程序上下文可能作为解释器函数的参数提供，可以通过动态插桩观察。另一种方法是在了解程序布局的情况下检查进程内存（例如，使用 Linux process\_vm\_readv(2) 系统调用）。

通常，这些程序只是通过添加打印语句和时间戳来研究。更严格的性能分析并不常见，因为解释型语言通常不会被优先选用于高性能应用程序。

<!-- source-id: ch05#ch05lev3sec3 -->
### 5.3.3 虚拟机

“语言虚拟机”（也称为“进程虚拟机”）是模拟计算机的软件。一些编程语言（包括 Java 和 Erlang）通常使用虚拟机（VM）执行，虚拟机为它们提供了独立于平台的编程环境。应用程序被编译为虚拟机指令集（*字节码*），然后由虚拟机执行。这使编译后的对象具备可移植性，前提是目标平台上有可运行它们的虚拟机。

字节码可以由语言虚拟机以不同的方式执行。Java HotSpot 虚拟机既支持解释执行，也支持 JIT 编译；后者将字节码编译为机器代码，供处理器直接执行。这同时提供了编译代码的性能优势和虚拟机的可移植性。

虚拟机通常是最难观察的语言类型。当程序在 CPU 上执行时，编译或解释的多个阶段可能已经过去，并且有关原始程序的信息可能不容易获得。性能分析通常侧重于语言虚拟机提供的工具集（其中许多提供 USDT 探针）和第三方工具。

<!-- source-id: ch05#ch05lev3sec4 -->
### 5.3.4 垃圾回收

某些语言使用自动内存管理，分配的内存不需要显式释放，而是交给异步垃圾回收过程处理。虽然这使程序更容易编写，但也存在缺点：

- **内存增长**：对应用程序内存使用的控制较少，当对象未自动识别为有资格释放时，内存使用可能会增长。如果应用程序变得太大，它可能会达到自身的限制或遇到系统分页（Linux 交换），从而严重损害性能。
- **CPU 成本**：GC 通常会间歇性运行，并涉及搜索或扫描内存中的对象。这会消耗 CPU 资源，从而减少应用程序短期内可用的资源。随着应用程序内存的增长，GC 的 CPU 消耗也可能会增长。在某些情况下，这可能会达到 GC 持续消耗整个 CPU 的程度。
- **延迟异常值**：GC 执行时应用程序可能暂停，导致偶尔出现被 GC 打断的高延迟响应。[^fn-ch05-ch05-footnote-8] 这取决于 GC 类型：全停顿（stop-the-world）、增量式或并发式。

GC 是性能调整的常见目标，以降低 CPU 成本和延迟异常值的出现。例如，Java VM 提供了许多可调参数来设置 GC 类型、GC 线程数、最大堆大小、目标堆空闲比率等。

如果调整无效，问题可能是应用程序创建了太多垃圾或泄漏引用。这些都是应用程序开发人员需要解决的问题。一种方法是尽可能分配更少的对象，以减少 GC 负载。显示对象分配及其代码路径的可观测性工具可用于查找潜在的消除目标。

### 5.4.1 CPU 分析

CPU 分析是应用程序性能分析的一项重要活动，在[第 6 章](#ch06-ch06)、[CPU](#ch06-ch06)中有详细解释，从[第 6.5.4 节](#ch06-ch06lev5sec4)、[性能剖析](#ch06-ch06lev5sec4)开始。本节总结 CPU 分析和 CPU 火焰图，并说明如何将 CPU 分析用于某些脱离 CPU 的分析。

Linux 有许多 CPU 分析器，包括 perf(1) 和 profile(8)，它们都使用定时采样，相关内容总结在[第 5.5 节](#ch05-ch05lev5)、[可观测性工具](#ch05-ch05lev5)中。这些分析器在内核模式下运行，可以捕获内核堆栈和用户堆栈，生成*混合模式*性能剖析结果，从而（几乎）完整地呈现 CPU 使用情况。

应用程序和运行时有时会提供在用户模式下运行的自有分析器，但它们无法显示内核 CPU 使用情况。这些基于用户态的分析器对 CPU 时间的认识可能有偏差，因为它们可能不知道内核何时将应用程序移出 CPU，也不会对这段脱离 CPU 的时间作相应校正。我总是从基于内核的分析器（perf(1) 和 profile(8)）开始，只有在最后才使用基于用户态的分析器。

基于样本的分析器会生成许多样本：Netflix 的典型 CPU 性能剖析会以 49 Hz 的频率在（约）32 个 CPU 上收集堆栈跟踪，持续 30 秒，共生成 47,040 个样本。为了理解这些样本，分析器通常提供不同的汇总或可视化方式。采样堆栈跟踪的一种常用可视化方式称为“火焰图”，由我发明。

#### CPU 火焰图

[第 1 章](#ch01-ch01)中展示了一个 CPU 火焰图，[图 2.15](#ch02-ch02fig15)中展示了另一个示例摘录。[图 5.3](#ch05-ch05fig03)的示例包含 ext4 标注，供后文参考。这些都是*混合模式*火焰图，同时显示用户堆栈和内核堆栈。

在火焰图中，每个矩形都是堆栈跟踪中的一个帧，y 轴显示代码流：从上到下依次显示当前函数及其调用祖先。帧宽度与该帧在性能剖析结果中的出现比例成正比，而 x 轴的排序没有意义（它只是按字母顺序排列）。应寻找宽大的“平台”或“塔”，因为大部分 CPU 时间都花在那里。有关火焰图的更多详细信息，请参阅[第 6 章](#ch06-ch06)、[CPU](#ch06-ch06)、[第 6.7.3 节](#ch06-ch06lev7sec3)、[火焰图](#ch06-ch06lev7sec3)。

在[图 5.3](#ch05-ch05fig03)中，crc32\_z() 是占用 CPU 时间最多的函数，约占该摘录的 40%（中央平台）。左侧的塔显示了进入内核的 write(2) 系统调用路径，总计约占 CPU 时间的 30%。快速浏览即可确定这两个可能是底层优化目标。沿代码路径向调用祖先方向查看，还可以发现高层目标：在此例中，所有 CPU 使用都来自 MYSQL\_BIN\_LOG::commit() 函数。

![图 5.3 CPU 火焰图摘录](../images/05fig03.jpg)

我不知道 crc32\_z() 或 MYSQL\_BIN\_LOG::commit() 的作用（尽管大概可以猜到）。CPU 性能剖析会暴露应用程序的内部工作方式；除非你是应用程序开发者，否则不必预先知道这些函数的含义。要提出可执行的性能改进方案，就需要研究它们。

例如，我在互联网上搜索 MYSQL\_BIN\_LOG::commit()，很快找到了介绍 MySQL 二进制日志（用于数据库恢复和复制）以及如何调优或完全禁用它的文章。快速搜索 crc32\_z() 可知它是 zlib 中的校验和函数。也许有更新、更快的 zlib 版本？处理器是否支持优化的 CRC 指令，zlib 是否在使用它？MySQL 是否确实需要计算 CRC，还是可以关闭它？有关这种思路的更多信息，请参阅[第 2 章](#ch02-ch02)、[方法论](#ch02-ch02)、[第 2.5.20 节](#ch02-ch02lev5sec20)、[性能箴言](#ch02-ch02lev5sec20)。

[第 5.5.1 节](#ch05-ch05lev5sec1)、[perf](#ch05-ch05lev5sec1)总结了使用 perf(1) 生成 CPU 火焰图的命令。

#### 脱离 CPU 活动的线索

CPU 性能剖析不仅能显示 CPU 使用情况，还可以寻找其他脱离 CPU 问题类型的证据。例如，可以从文件系统访问和块 I/O 初始化所消耗的 CPU 时间，在一定程度上看出磁盘 I/O。这就像寻找熊的脚印：你没有看到熊，却发现了熊确实存在。

通过浏览 CPU 火焰图，您可能会发现文件系统 I/O、磁盘 I/O、网络 I/O、锁争用等的证据。 [图 5.3](#ch05-ch05fig03) 突出显示 ext4 文件系统 I/O 作为示例。如果您浏览了足够多的火焰图，您将熟悉要查找的函数名称：“tcp\_\*”表示内核 TCP 函数，“blk\_\*”表示内核块 I/O 函数等。以下是一些针对 Linux 系统的建议搜索术语：

- **“ext4”**（或**“btrfs”**、**“xfs”**、**“zfs”**）：查找文件系统操作。
- **“blk”**：查找块 I/O。
- **“tcp”**：查找网络 I/O。
- **“utex”**：显示锁争用（“mutex”或“futex”）。
- **“alloc”** 或“**object”**：显示执行内存分配的代码路径。

此方法只能识别这些活动是否存在，不能衡量其规模。CPU 火焰图显示 CPU 使用量，而不是线程阻塞在脱离 CPU 状态所花费的时间。要直接测量脱离 CPU 的时间，可以使用下面介绍的 Off-CPU 分析，不过这种测量通常开销更大。

### 5.4.2 Off-CPU 分析

Off-CPU 分析研究当前不在 CPU 上运行的线程：这种状态称为*[脱离 CPU](#gloss-glo-111)*。它包括线程阻塞的所有原因：磁盘 I/O、网络 I/O、锁争用、显式睡眠、调度器抢占等。对这些原因及其引起的性能问题的分析通常涉及多种工具。Off-CPU 分析是一种可以统一分析这些原因的方法，也可以由单个 Off-CPU 分析工具支持。

Off-CPU 分析可以通过不同的方式执行，包括：

- **采样**：收集脱离 CPU 线程的基于计时器的样本，或者收集所有线程（称为*墙上时钟采样（wall-clock sampling）*）。
- **调度器跟踪**：对内核 CPU 调度器进行插桩，测量线程脱离 CPU 的持续时间，并将这些时间与脱离 CPU 堆栈跟踪一起记录。线程脱离 CPU 时堆栈跟踪不会改变（因为线程没有运行来改变它），因此每个阻塞事件只需读取一次堆栈跟踪。
- **应用程序插桩**：某些应用程序对常见的阻塞代码路径（例如磁盘 I/O）内置了插桩。这类插桩可能包含应用程序专用上下文。虽然方便且有用，但这种方法通常看不到脱离 CPU 的事件（调度器抢占、缺页异常等）。

前两种方法更可取，因为它们适用于所有应用程序并且可以查看所有脱离 CPU 的事件；然而，它们会带来很大的开销。在 8-CPU 系统上，以 49 赫兹进行采样的开销可以忽略不计，但脱离 CPU 采样必须对线程池而不是 CPU 池进行采样。同一系统可能有 10,000 个线程，其中大部分是空闲的，因此对它们进行采样会增加 1,000x[^fn-ch05-ch05-footnote-9] 的开销（想象一下对 10,000 个 CPU 的系统进行 CPU 分析）。调度程序跟踪也会消耗大量开销，因为同一系统每秒可能有 100,000 个或更多调度程序事件。

调度器跟踪是目前常用的技术，我自己的 offcputime(8) 等工具就采用了这一方法（[第 5.5.3 节](#ch05-ch05lev5sec3)、[offcputime](#ch05-ch05lev5sec3)）。我采用的一项优化是只记录持续时间超过极小阈值的 Off-CPU 事件，以减少样本数量。[^fn-ch05-ch05-footnote-10]我还使用 BPF 在内核上下文中聚合调用栈，而不是将所有样本发送到用户空间，从而进一步降低开销。尽管这些技术很有帮助，仍应谨慎地在生产环境中进行 Off-CPU 性能剖析，并在使用前于测试环境中评估开销。

大部分脱离 CPU 时间都在 fsync() 代码路径和 ext4 文件系统中。鼠标指针停在函数 Prepared\_statement::execute() 上，可以看到底部的信息栏显示该函数的脱离 CPU 时间：总计 3.97 秒。解释方式与 CPU 火焰图类似：寻找最宽的塔并首先调查它们。

同时使用 CPU 上和脱离 CPU 火焰图，可以按代码路径完整了解两类时间，这是一个强大的工具。我通常将它们显示为两个独立的火焰图。也可以将它们合并为一个火焰图，我称之为*热/冷火焰图*。但效果并不好：由于热/冷火焰图的大部分内容是等待时间，CPU 时间会被压缩成一座细塔。这是因为脱离 CPU 的线程数可能比正在 CPU 上运行的线程数高出两个数量级，导致热/冷火焰图中 99% 都是脱离 CPU 时间，其中大部分（除非经过过滤）是等待时间。

#### 等待时间

除了收集脱离 CPU 性能剖析结果的开销之外，解释结果也是一个问题：结果可能被等待时间主导，也就是线程等待工作的时间。[图 5.5](#ch05-ch05fig05)展示了同一个脱离 CPU 时间火焰图，但没有放大到某个感兴趣的线程。

<!-- source-id: ch05#ch05fig05 -->
![图 5.5 脱离 CPU 时间火焰图（完整）](../images/05fig05.jpg)

此火焰图中的大部分时间现在都在类似的 pthread\_cond\_wait() 和 futex() 代码路径中：这些是等待工作的线程。火焰图中可以看到线程函数：从右到左依次是 srv\_worker\_thread()、srv\_purge\_coordinator\_thread()、srv\_monitor\_thread() 等。

有几种方法可以找到值得关注的脱离 CPU 时间：

- 放大（或按条件过滤）应用程序请求处理函数，因为我们最关心处理应用程序请求期间的脱离 CPU 时间。对 MySQL 服务器来说，这个函数是 do\_command()。搜索 do\_command() 并放大后，会得到类似[图 5.4](#ch05-ch05fig04)的火焰图。虽然这种方法很有效，但需要知道特定应用程序中应搜索的函数。
- 在收集期间使用内核过滤器排除不感兴趣的线程状态。效果取决于内核；在 Linux 上，匹配 TASK\_UNINTERRUPTIBLE 可以聚焦于许多有趣的脱离 CPU 事件，但也会排除一些事件。

有时会发现阻塞应用程序的代码路径正在等待其他东西，例如锁。要进一步深入，就需要知道锁持有者为何花了这么长时间才释放锁。除[第 5.4.7 节](#ch05-ch05lev4sec7)、[静态性能调优](#ch05-ch05lev4sec7)中描述的锁分析之外，一种通用技术是插桩唤醒事件。这是一项高级活动：请参阅*BPF 性能工具* [\[Gregg 19\]](#ch05-ch05ref10)的[第 14 章](#ch14-ch14)，以及 BCC 中的 wakeuptime(8) 和 offwaketime(8) 工具。

[第 5.5.3 节](#ch05-ch05lev5sec3)、[offcputime](#ch05-ch05lev5sec3)展示了如何使用 BCC 中的 offcputime(8) 生成脱离 CPU 火焰图。除了调度程序事件，系统调用事件也是研究应用程序的另一个有用目标。

### 5.4.3 系统调用分析

可以对系统调用（syscalls）进行插桩，以研究基于资源的性能问题。目的是找出系统调用时间花在哪里，包括系统调用的类型及其调用原因。

系统调用分析的目标包括：

- **新进程跟踪**：通过跟踪 execve(2) 系统调用，可以记录新进程的执行情况并分析短命进程的问题。请参阅[第 5.5.5 节](#ch05-ch05lev5sec5)、[execsnoop](#ch05-ch05lev5sec5)中的 execsnoop(8) 工具。
- **I/O 分析**：跟踪 read(2)/write(2)/send(2)/recv(2) 及其变体，并研究其 I/O 大小、标志和代码路径，有助于识别次优 I/O 问题，例如大量小型 I/O。参见[第 5.5.7 节](#ch05-ch05lev5sec7)、[bpftrace](#ch05-ch05lev5sec7)中的 bpftrace 工具。
- **内核时间分析**：当系统显示大量内核 CPU 时间（通常报告为“%sys”）时，对系统调用进行插桩可以找到原因。请参阅[第 5.5.6 节](#ch05-ch05lev5sec6)、[syscount](#ch05-ch05lev5sec6)中的 syscount(8) 工具。系统调用可以解释大部分但不是全部内核 CPU 时间；例外包括缺页异常、异步内核线程和中断。

系统调用是一个记录良好的 API（手册页），使它们成为易于研究的事件源。它们还与应用程序同步调用，这意味着从系统调用收集堆栈跟踪将显示负责的应用程序代码路径。此类堆栈跟踪可以可视化为火焰图。

### 5.4.4 USE 方法

正如[第 2 章](#ch02-ch02)、[方法论](#ch02-ch02)中介绍并在后续章节中应用的那样，USE 方法检查所有硬件资源的利用率、饱和度和错误。通过证明某项资源已成为瓶颈，可以解决许多应用程序性能问题。

USE 方法也可以应用于软件资源。如果能找到展示应用程序内部组件的功能图，就可以为每个软件资源考虑利用率、饱和度和错误指标，判断哪些指标有意义。

例如，应用程序可以使用工作线程池处理请求，并为等待轮到自己的请求维护一个队列。将其视为一种资源后，三个指标可以定义如下：

- **利用率**：一个时间间隔内忙于处理请求的线程平均数量，以总线程数的百分比表示。例如，50% 意味着平均有一半线程忙于处理请求。
- **饱和度**：一个时间间隔内请求队列的平均长度。这表示有多少请求排队等待工作线程。
- **错误**：因任何原因被拒绝或失败的请求。

接下来要做的是找到测量这些指标的方法。应用程序可能已经在某处提供了这些指标，也可能需要使用其他工具（例如动态跟踪）添加或测量它们。

像这个例子一样，排队系统也可以使用排队论来研究（参见[第 2 章](#ch02-ch02)、[方法论](#ch02-ch02)）。

再以文件描述符为例。系统可能会施加限制，使文件描述符成为一种有限资源。这三个指标可能如下：

- **利用率**：正在使用的文件描述符数量，以占限制值的百分比表示。
- **饱和度**：取决于操作系统的行为：如果线程因等待文件描述符而阻塞，则可以用等待该资源的阻塞线程数表示。
- **错误**：分配错误，例如 EFILE、“打开文件过多”。

对应用程序的组件重复此练习，并跳过任何没有意义的指标。此过程可以帮助您制定一个简短的清单，用于在继续使用其他方法之前检查应用程序的运行状况。

<!-- source-id: ch05#ch05lev4sec5 -->
### 5.4.5 线程状态分析

这是我处理每个性能问题时采用的第一种方法，但在 Linux 上它也是一项高级活动。目标是在较高层次上识别应用程序线程把时间花在哪里，从而立即解决一些问题，并指导对其他问题的调查。可以将每个应用程序的线程时间划分为若干有意义的状态来实现这一点。

至少有两种线程状态：在 CPU 上（on-CPU）和脱离 CPU（off-CPU）。可以使用标准指标和工具（例如 top(1)）识别线程是否处于在 CPU 上的状态，然后视情况进行 CPU 分析或 Off-CPU 分析（参见[第 5.4.1 节](#ch05-ch05lev4sec1)、[CPU 分析](#ch13-ch13lev9sec2)以及[第 5.4.2 节](#ch05-ch05lev4sec2)、[Off-CPU 分析](#ch05-ch05lev4sec2)）。状态划分越细，这种方法越有效。

<!-- source-id: ch05#ch05lev3_10 -->
#### 九种状态

下面是我选择的九种线程状态，相比之前的两种状态（在 CPU 上和脱离 CPU），它们能为分析提供更好的起点：

- **用户态**：在用户模式下运行于 CPU 上
- **内核态**：在内核模式下运行于 CPU 上
- **可运行**：脱离 CPU，等待轮到自己在 CPU 上运行
- **交换**（匿名分页）：可运行，但因匿名页换入而阻塞
- **磁盘 I/O**：等待块设备 I/O：读/写、数据页/代码页换入
- **网络 I/O**：等待网络设备 I/O：套接字读/写
- **睡眠**：主动进入睡眠
- **锁**：等待获取同步锁（等待其他线程）
- **空闲**：等待工作

该九态模型如[图 5.6](#ch05-ch05fig06)所示。

![图 5.6 九态线程模型](../images/05fig06.jpg)

通过减少除空闲之外的每个状态的时间，可以提高应用程序请求的性能。在其他条件相同的情况下，这意味着应用程序请求具有较低的延迟，并且应用程序可以处理更多的负载。

一旦确定了线程花费时间的状态，就可以进一步调查：

- **用户态或内核态**：分析可以确定哪些代码路径正在消耗 CPU，包括在锁上自旋所花费的时间。请参见[第 5.4.1 节](#ch05-ch05lev4sec1)、[CPU 分析](#ch05-ch05lev4sec1)。
- **可运行**：处于此状态的时间意味着应用程序需要更多 CPU 资源。检查整个系统的 CPU 负载以及应用程序存在的任何 CPU 限制（例如资源控制）。
- **交换**（匿名分页）：应用程序缺乏可用主内存可能会导致交换延迟。检查整个系统的内存使用情况以及存在的任何内存限制。详情请参见[第 7 章](#ch07-ch07)、[内存](#ch07-ch07)。
- **磁盘**：此状态包括直接磁盘 I/O 和缺页异常。要进行分析，请参见[第 5.4.3 节](#ch05-ch05lev4sec3)、[系统调用分析](#ch05-ch05lev4sec3)、[第 8 章](#ch08-ch08)、[文件系统](#ch08-ch08)以及[第 9 章](#ch09-ch09)、[磁盘](#ch09-ch09)。工作负载特征分析可以帮助解决许多磁盘 I/O 问题；请检查文件名、I/O 大小和 I/O 类型。
- **网络**：此状态表示网络 I/O（发送/接收）期间阻塞的时间，但不包括监听新连接的时间（那是空闲时间）。分析请参见[第 5.4.3 节](#ch05-ch05lev4sec3)、[系统调用分析](#ch05-ch05lev4sec3)；[第 5.5.7 节](#ch05-ch05lev5sec7)、[bpftrace](#ch05-ch05lev5sec7)中的 I/O 分析部分；以及[第 10 章](#ch10-ch10)、[网络](#ch10-ch10)。工作负载特征分析对网络 I/O 问题也很有用；请检查主机名、协议和吞吐量。
- **睡眠**：分析睡眠的原因（代码路径）和持续时间。
- **锁**：识别锁、持有锁的线程，以及持有者为何持锁如此之久。原因可能是持有者被另一把锁阻塞，需要进一步追查锁的依赖链。这是一项高级活动，通常由深入了解应用程序及其锁层次结构的软件开发人员执行。我开发了一个 BCC 工具来辅助此类分析：offwaketime(8)（包含在 BCC 中），它显示阻塞堆栈跟踪以及唤醒者。

由于应用程序通常等待工作的方式，您经常会发现处于网络 I/O 和锁定状态的时间实际上是空闲时间。应用程序工作线程可以通过等待网络 I/O 下一个请求（例如，HTTP 持久连接（Keep-Alive））或通过等待条件变量（锁定状态）被唤醒来处理工作来实现空闲。

下面总结如何在 Linux 上测量这些线程状态。

#### Linux

[图 5.7](#ch05-ch05fig07)展示了一个基于内核线程状态的 Linux 线程状态模型。

<!-- source-id: ch05#ch05fig07 -->
![图 5.7 Linux 线程状态](../images/05fig07.jpg)

内核线程状态基于内核 task\_struct 的 state 成员：Runnable 对应 TASK\_RUNNING，Disk 对应 TASK\_UNINTERRUPTIBLE，Sleep 对应 TASK\_INTERRUPTIBLE。ps(1) 和 top(1) 等工具分别用单字母代码 R、D 和 S 显示这些状态。（还有更多状态，例如被调试器停止的状态，此处未列出。）

虽然这为进一步分析提供了一些线索，但还远不能将时间划分为前面描述的九种状态。需要更多信息：例如，可以使用 /proc 或 getrusage(2) 统计信息，将 Runnable 拆分为用户态时间和内核态时间。

其他内核通常提供更多状态，使这种方法更容易应用。我最初在 Solaris 内核上开发并使用这种方法，受到其微状态记账功能的启发；该功能记录八种不同状态下的线程时间：用户、系统、陷阱、代码页缺页、数据页缺页、锁、睡眠和运行队列（调度器延迟）。这些状态与我理想的状态并不完全对应，但仍是更好的起点。

下面讨论我在 Linux 上使用的三种方法：基于线索、Off-CPU 分析和直接测量。

##### 基于线索的方法

您可以首先使用常见的操作系统工具（例如 pidstat(1) 和 vmstat(8)）来建议线程状态时间可能花费在何处。感兴趣的工具和列是：

- **用户态**：pidstat(1) “%usr”（直接测量此状态）
- **内核态**：pidstat(1) “%system”（直接测量此状态）
- **可运行**：vmstat(8) “r”（系统范围）
- **交换**：vmstat(8) “si” 和 “so”（系统范围）
- **磁盘 I/O**：pidstat(1) `-d` 的 “iodelay”（包括交换状态）
- **网络 I/O**：sar(1) `-n DEV` 的 “rxkB/s” 和 “txkB/s”（系统范围）
- **睡眠**：不容易获得
- **锁**：perf(1) `top`（可能直接识别自旋锁时间）
- **空闲**：不容易获得

其中一些统计数据是全系统范围的。如果通过 vmstat(8) 发现存在系统范围的交换率，可以使用更深入的工具调查该状态，以确认应用程序是否受到影响。以下各节和章节将介绍这些工具。

##### Off-CPU 分析

由于许多状态都处于脱离 CPU 状态（除用户态和内核态外的所有状态），因此可以应用 Off-CPU 分析来确定线程状态。请参见[第 5.4.2 节](#ch05-ch05lev4sec2)、[Off-CPU 分析](#ch05-ch05lev4sec2)。

##### 直接测量

可以按以下方式依据线程状态精确测量线程时间：

**用户态**：用户模式 CPU 时间可通过许多工具以及 /proc/PID/stat 和 getrusage(2) 获得。pidstat(1) 将其报告为 `%usr`。

**内核态**：内核模式 CPU 时间也可从 /proc/PID/stat 和 getrusage(2) 获得。pidstat(1) 将其报告为 `%system`。

**可运行**：由内核 *schedstats* 功能以纳秒为单位进行跟踪，并通过 /proc/PID/schedstat 暴露。它还可以使用跟踪工具（包括 perf(1) 的 `sched` 子命令和 BCC runqlat(8)）进行测量，但需要付出一些开销；这两个工具都在[第 6 章](#ch06-ch06)、[CPU](#ch06-ch06)中介绍。

**交换**：匿名分页产生的交换时间（纳秒）可以通过[第 4 章](#ch04-ch04)、[可观测性工具](#ch04-ch04)中介绍的*延迟记账*来测量，详见[第 4.3.3 节](#ch04-ch04lev3sec3)、[延迟记账](#ch04-ch04lev3sec3)，其中包含示例工具 getdelays.c。跟踪工具也可以用来插桩交换延迟。

**磁盘**：pidstat(1) `-d` 将 “iodelay”显示为进程因块 I/O 和交换而延迟期间的时钟滴答数；如果没有系统范围的交换（如 vmstat(8) 所报告），就可以推断任何 iodelay 都来自 I/O 状态。启用延迟记账及其他记账功能后，还可以提供块 I/O 时间，iotop(8) 就使用了这类信息。也可以使用 BCC 的 biotop(8) 等跟踪工具。

**网络**：可以使用 BCC 和 bpftrace 等跟踪工具调查网络 I/O，其中包括用于 TCP 网络 I/O 的 tcptop(8)。应用程序也可能提供用于跟踪 I/O（网络和磁盘）耗时的插桩。

**睡眠**：可以使用跟踪器和事件（包括 syscalls:sys\_enter\_nanosleep 跟踪点）检查进入主动睡眠的时间。我的 naptime.bt 工具跟踪这些睡眠，并打印 PID 和持续时间\[Gregg 19\][\[Gregg 20b\]](#ch05-ch05ref13)。

**锁**：可以使用跟踪工具调查锁相关的耗时，包括 BCC 中的 klockstat(8)，以及 bpf-perf-tools-book 仓库中的 pmlock.bt 和 pmheld.bt（用于 pthread 互斥锁）和 mlock.bt、mheld.bt（用于内核互斥锁）。

**空闲**：跟踪工具可用于对处理等待工作的应用程序代码路径进行插桩。

有时，应用程序可能看起来完全处于睡眠状态：它们在 CPU 之外保持阻塞状态，没有 I/O 或其他事件的速率。要确定应用程序线程处于什么状态，可能需要使用调试器（例如 pstack(1) 或 gdb(1)）来检查线程堆栈跟踪，或从 /proc/PID/stack 文件中读取它们。请注意，此类调试器可能会暂停目标应用程序并导致其自身的性能问题：在生产中尝试它们之前，请了解如何使用它们及其风险。

<!-- source-id: ch05#ch05lev4sec6 -->
### 5.4.6 锁分析

对于多线程应用程序，锁可能成为瓶颈，限制并行性和可扩展性。单线程应用程序也可能受内核锁（例如文件系统锁）限制。可以通过以下方式分析锁：

- 检查争用
- 检查保持时间是否过长

第一项用于确定*当前*是否存在问题。持锁时间过长不一定是眼前的问题，但随着未来并行负载增加，可能会变成问题。对于每一项，都应尝试识别锁的名称（如果有）以及导致使用该锁的代码路径。

虽然有用于锁分析的专用工具，但有时仅凭 CPU 分析就能解决问题。对于*自旋锁*，争用会表现为 CPU 使用，可通过对堆栈跟踪进行 CPU 分析轻松识别。对于*自适应互斥锁*，争用通常包含一段自旋，同样可以通过堆栈跟踪的 CPU 分析识别。此时要注意，CPU 性能剖析只能呈现部分情况，因为线程在等待锁时可能已经阻塞并进入睡眠。请参见[第 5.4.1 节](#ch05-ch05lev4sec1)、[CPU 分析](#ch05-ch05lev4sec1)。

Linux 上的具体锁分析工具，请参见[第 5.5.7 节](#ch05-ch05lev5sec7)、[bpftrace](#ch05-ch05lev5sec7)。

<!-- source-id: ch05#ch05lev4sec7 -->
### 5.4.7 静态性能调优

静态性能调优关注已配置环境中的问题。对于应用程序性能，请检查静态配置的以下方面：

- 应用程序正在运行什么版本，其依赖项是什么？是否有更新版本？更新版本的发行说明是否提到了性能改进？
- 是否存在已知的性能问题？是否有列出这些问题的缺陷数据库？
- 应用程序是如何配置的？
- 如果配置或调优与默认值不同，原因是什么？（是基于测量和分析，还是基于猜测？）
- 应用程序是否使用对象缓存？它的大小如何？
- 应用程序是否并发运行？如何配置（例如线程池大小）？
- 应用程序是否在特殊模式下运行？（例如，可能启用了会降低性能的调试模式，或者应用程序可能是调试版本而不是发布版本。）
- 应用程序使用哪些系统库？它们是什么版本？
- 应用程序使用什么内存分配器？
- 应用程序是否配置为在其堆中使用大页面？
- 应用程序是否已编译？什么版本的编译器？有哪些编译器选项和优化？ 64 位？
- 原生代码（机器码）是否包含高级指令？（应该包含吗？）（例如 SIMD/向量指令，包括 Intel SSE。）
- 应用程序是否遇到错误，现在是否处于降级模式？或者它是否配置错误并且始终以降级模式运行？
- 是否存在系统对 CPU、内存、文件系统、磁盘或网络使用施加的限制或资源控制？（这些在云计算中很常见。）

回答这些问题可能会揭示被忽视的配置选择。

<!-- source-id: ch05#ch05lev4sec8 -->
### 5.4.8 分布式追踪

在分布式环境中，应用程序可能由运行在不同系统上的服务组成。虽然可以把每个服务当作一个小型应用程序来研究，但也有必要把分布式应用程序作为一个整体来研究。这需要新的方法和工具，通常通过分布式追踪完成。

分布式追踪涉及记录每个服务请求的信息，然后将这些信息组合起来分析。跨越多个服务的每个应用程序请求都可以分解为其依赖请求，从而识别导致应用程序高延迟或错误的服务。

收集的信息可包括：

- 应用程序请求的唯一标识符（外部请求 ID）
- 请求在依赖关系层次结构中的位置
- 开始和结束时间
- 错误状态

分布式追踪的一个挑战是生成的日志数据量：每个应用程序请求都会产生多个条目。一种解决方案是执行“基于头部的采样”：在请求开始（“头部”）时决定是否对其进行采样（“追踪”），例如每一万个请求追踪一个。这足以分析大多数请求的性能，但由于数据有限，可能难以分析间歇性错误或异常值。一些分布式追踪器采用“基于尾部的采样”：先捕获所有事件，再根据延迟和错误等条件决定保留哪些事件。

一旦发现有问题的服务，就可以使用其他方法和工具对其进行更详细的分析。

### 5.5.4 strace

strace(1) 命令是 Linux 系统调用跟踪器。[^fn-ch05-ch05-footnote-13] 它可以跟踪系统调用，为每个系统调用打印一行摘要，也可以对系统调用计数并打印报告。

例如，通过 PID 1884 跟踪系统调用：

![点击查看代码图片](../images/pg206-1.jpg)

```text
$ strace -ttt -T -p 1884
1356982510.395542 close(3)              = 0 <0.000267>
1356982510.396064 close(4)              = 0 <0.000293>
1356982510.396617 ioctl(255, TIOCGPGRP, [1975]) = 0 <0.000019>
1356982510.396980 rt_sigprocmask(SIG_SETMASK, [], NULL, 8) = 0 <0.000024>
1356982510.397288 rt_sigprocmask(SIG_BLOCK, [CHLD], [], 8) = 0 <0.000014>
1356982510.397365 wait4(-1, [{WIFEXITED(s) && WEXITSTATUS(s) == 0}], WSTOPPED|
WCONTINUED, NULL) = 1975 <0.018187>
[...]
```

此命令中的选项如下（完整选项请参见 strace(1) 手册页）：

- **`-ttt`**：打印自纪元以来的时间的第一列，以秒为单位，具有微秒分辨率。
- **`-T`**：打印最后一个字段（`<`*time*`>`），这是系统调用的持续时间，以秒为单位，精度为微秒。
- **`-p PID`**：跟踪此进程 ID。还可以指定命令，以便 strace(1) 启动并跟踪它。

这里没有使用的其他选项包括用于跟踪子线程的 `-f`，以及用于将 strace(1) 输出写入指定文件名的 `-o` *filename*。

strace(1) 的一个功能可以在输出中看到——将系统调用参数转换为人类可读的形式。这对于理解 ioctl(2) 调用特别有用。

`-c` 选项可用于汇总系统调用活动。下面的示例直接调用并跟踪命令 dd(1)，而不是附加到 PID：

![点击查看代码图片](../images/pg206-2.jpg)

```text
$ strace -c dd if=/dev/zero of=/dev/null bs=1k count=5000k
5120000+0 records in
5120000+0 records out
5242880000 bytes (5.2 GB) copied, 140.722 s, 37.3 MB/s
% time     seconds  usecs/call     calls    errors syscall
------ ----------- ----------- --------- --------- ----------------
 51.46    0.008030           0   5120005           read
 48.54    0.007574           0   5120003           write
  0.00    0.000000           0        20        13 open
[...]
------ ----------- ----------- --------- --------- ----------------
100.00    0.015604              10240092        19 total
```

输出以 dd(1) 中的三行开始，后跟 strace(1) 摘要。这些列是：

- **`time`**：显示内核 CPU 时间花费在何处的百分比
- **`seconds`**：总内核 CPU 时间，以秒为单位
- **`usecs/call`**：每次调用的平均内核 CPU 时间，以微秒为单位
- **`calls`**：系统调用次数
- **`syscall`**：系统调用名称

##### strace 开销

警告：当前版本的 strace(1) 通过 Linux ptrace(2) 接口采用基于断点的跟踪。这会为所有系统调用的进入和返回设置断点（即使 `-e` 选项只选择某些系统调用）。这种方式具有侵入性，系统调用率较高的应用程序可能会出现一个数量级的性能下降。为说明这一点，下面是不使用 strace(1) 时相同的 dd(1) 命令：

![点击查看代码图片](../images/pg207.jpg)

```text
$ dd if=/dev/zero of=/dev/null bs=1k count=5000k
5120000+0 records in
5120000+0 records out
5242880000 bytes (5.2 GB) copied, 1.91247 s, 2.7 GB/s
```

dd(1) 在最后一行给出吞吐量统计信息：比较两次运行可以得出结论，strace(1) 使 dd(1) 慢了 73 倍。这是一个特别严重的例子，因为 dd(1) 产生的系统调用率非常高。

根据应用程序的需求，这种跟踪方式可以短时间使用，以确定正在调用的系统调用类型。如果开销不是问题，strace(1) 会更有用。其他跟踪器（包括 perf(1)、Ftrace、BCC 和 bpftrace）使用缓冲跟踪，大幅降低跟踪开销：事件写入共享的内核环形缓冲区，用户态跟踪器定期读取该缓冲区。这减少了用户态和内核态之间的上下文切换，从而降低开销。

strace(1) 的未来版本或许可以通过成为 perf(1) 的 `trace` 子命令（前面在[第 5.5.1 节](#ch05-ch05lev5sec1)、[perf](#ch05-ch05lev5sec1)中介绍）的别名来解决开销问题。其他基于 BPF 的高性能 Linux 系统调用跟踪器包括 Intel 的 vltrace [\[Intel 18\]](#ch05-ch05ref5)，以及 Microsoft Windows ProcMon 工具的 Linux 版本 [\[Microsoft 20\]](#ch05-ch05ref16)。

### 5.5.7 bpftrace

bpftrace 是一种基于 BPF 的跟踪器，提供一种高级编程语言，可以创建功能强大的单行程序和短脚本。它非常适合根据其他工具提供的线索进行定制化应用程序分析。

bpftrace 在[第 15 章](#ch15-ch15)中介绍。本节展示一些应用程序分析示例。

<!-- source-id: ch05#ch05lev3_15 -->
#### 信号追踪

下面的 bpftrace 单行程序跟踪进程信号（通过 kill(2) 系统调用），显示源 PID 和进程名、目标 PID 及信号编号：

![点击查看代码图片](../images/pg209-2.jpg)

```text
# bpftrace -e 't:syscalls:sys_enter_kill { time("%H:%M:%S ");
    printf("%s (PID %d) send a SIG %d to PID %d\n",
    comm, pid, args->sig, args->pid); }'
Attaching 1 probe...

09:08:00 systemd-journal (PID 214) send a SIG 0 to PID 501
09:08:00 systemd-journal (PID 214) send a SIG 0 to PID 550
09:08:00 systemd-journal (PID 214) send a SIG 0 to PID 392

```

输出显示 bash shell 向自身发送信号 2（Ctrl-C），然后 systemd-journal 向其他 PID 发送信号 0。信号 0 不执行任何操作；它通常用于根据系统调用返回值检查另一个进程是否仍然存在。

这行程序对于调试奇怪的应用程序问题（例如提前终止）很有用。时间戳可用于与监控软件中的性能问题进行交叉核对。也可以使用 BCC 和 bpftrace 中独立的 killsnoop(8) 工具跟踪信号。

#### 应用程序内部结构

如有需要，可以开发定制工具来汇总应用程序内部信息。首先检查是否有可用的 USDT 探针，或能否通过带相应选项重新编译来提供它们。如果无法提供或现有探针不足，可以考虑使用 uprobes。有关 bpftrace、uprobes 和 USDT 的示例，请参阅[第 4 章](#ch04-ch04)、[可观测性工具](#ch04-ch04)、[第 4.3.7 节](#ch04-ch04lev3sec7)、[uprobes](#ch04-ch04lev3sec7)以及[第 4.3.8 节](#ch04-ch04lev3sec8)、[USDT](#ch04-ch04lev3sec8)。[第 4.3.8 节](#ch04-ch04lev3sec8)还介绍了动态 USDT；对于深入了解 JIT 编译的软件，这可能是必要的，因为 uprobes 可能无法对其进行插桩。

一个复杂的例子是 Java：uprobes 可以对 JVM 运行时（C++ 代码）和操作系统库进行插桩，USDT 可以跟踪高级 JVM 事件，动态 USDT 则可以放置在 Java 代码中，以便了解方法执行情况。

## 5.6 陷阱

以下部分描述应用程序性能分析中的常见陷阱，尤其是缺少符号和堆栈跟踪。检查 CPU 性能剖析结果（例如火焰图）时，可能会首先遇到这些问题，并发现其中缺少函数名和堆栈跟踪。

这些问题属于高级主题；我在*BPF 性能工具*的[第 2 章](#ch02-ch02)、[第 12 章](#ch12-ch12)和第 18 章中更详细地介绍过，本节只做总结。

<!-- source-id: ch05#ch05lev6sec1 -->
### 5.6.1 缺失符号

当分析器或跟踪器无法将应用程序指令地址解析为函数名（符号）时，可能会将其打印为十六进制数字或字符串“\[unknown\]”。问题的修复方式取决于应用程序的编译器、运行时、构建配置以及分析器本身。

<!-- source-id: ch05#ch05lev3_19 -->
#### ELF 二进制文件（C、C++、...）

已编译的二进制文件中可能缺少符号，尤其是那些经过打包和分发的二进制文件，因为它们可能已使用 strip(1) 处理以减小文件大小。一种修复方法是调整构建流程，避免剥离符号；另一种是使用不同的符号信息源，例如 debuginfo 或 BPF 类型格式（BTF）。通过 perf(1)、BCC 和 bpftrace 进行的 Linux 分析支持 debuginfo 符号。

<!-- source-id: ch05#ch05lev3_20 -->
#### JIT 运行时（Java、Node.js...）

Java 和 Node.js 等即时（JIT）编译运行时通常会出现符号缺失。在这些情况下，JIT 编译器拥有自己的符号表，该表会在运行时变化，也不属于二进制文件中的预编译符号表。常见的修复方法是使用运行时生成的补充符号表，将其放入 perf(1) 和 BCC 读取的 /tmp/perf-\<PID\>.map 文件中。

例如，Netflix 使用 perf-map-agent [\[Rudolph 18\]](#ch05-ch05ref7)，它可以附加到正在运行的 Java 进程并转储补充符号文件。我使用另一个名为 jmaps [\[Gregg 20c\]](#ch05-ch05ref14) 的工具自动完成这项工作；该工具应在性能剖析之后、符号转换之前立即运行。例如，使用 perf(1)（[第 13 章](#ch13-ch13)）：

![点击查看代码图片](../images/pg214-1.jpg)

```text
# perf record -F 49 -a -g -- sleep 10; jmaps
# perf script --header > out.stacks
# [...]
```

并使用 bpftrace（[第 15 章](#ch15-ch15)）：

![点击查看代码图片](../images/pg214-2.jpg)

```text
# bpftrace --unsafe -e 'profile:hz:49 { @[ustack] = count(); }
    interval:s:10 { exit(); } END { system("jmaps"); }'
```

性能剖析与符号表转储之间的符号映射可能发生变化，从而在性能剖析结果中产生无效的函数名。这称为*符号抖动*；在 `perf record` 之后立即运行 jmaps 可以减少符号抖动。目前这还不是严重问题；如果问题变得严重，可以在性能剖析前后分别转储符号，以查找发生的变化。

还有其他方法可以解析 JIT 符号。一种是使用符号时间戳日志记录，perf(1) 支持这种方式，它可以解决符号抖动问题，但启用时开销较高。另一种是让 perf(1) 调用运行时自带的堆栈遍历器（通常用于异常堆栈）。这种方法有时称为使用 *stack helpers*；对于 Java，它由async-profiler [\[Pangin 20\]](#ch05-ch05ref19)实现。

请注意，JIT 运行时也包含预编译组件：JVM 还使用 libjvm 和 libc。请参阅前面的 ELF 二进制文件部分，了解如何处理这些组件的符号问题。

<!-- source-id: ch05#ch05lev6sec2 -->
### 5.6.2 丢失堆栈

另一个常见问题是堆栈跟踪丢失或不完整，可能短至一两帧。例如，下面是来自 MySQL 服务器的脱离 CPU 性能剖析结果：

![点击查看代码图片](../images/pg215.jpg)

```text
    finish_task_switch
    schedule
    futex_wait_queue_me
    futex_wait
    do_futex
    __x64_sys_futex
    do_syscall_64
    entry_SYSCALL_64_after_hwframe
    pthread_cond_timedwait@@GLIBC_2.3.2
    [unknown]
```

该堆栈不完整：pthread\_cond\_timedwait() 之后只有一个“\[unknown\]”帧。下面缺少 MySQL 函数，而这些函数正是我们真正需要了解应用程序上下文的部分。

有时堆栈是单个栈帧：

```text
    send
```

在火焰图中，这可能呈现为“草”状：图的底部有许多细窄的单个栈帧。

遗憾的是，不完整的堆栈跟踪很常见，通常由两个因素共同造成：1）可观测性工具使用基于帧指针的方法读取堆栈跟踪；2）目标二进制文件没有为帧指针保留寄存器（x86\_64 上的 RBP），而是将其重新用作通用寄存器，以便编译器优化性能。可观测性工具读取这个寄存器时，以为它是帧指针，但它实际上可能包含任何内容：数字、对象地址、指向字符串的指针等。工具会尝试在符号表中解析这个数字；幸运时找不到对应符号，可以打印“\[unknown\]”。不幸时，随机数可能解析为无关符号，导致打印出的堆栈跟踪包含错误的函数名，令最终用户困惑。

由于 libc 通常是在不保留帧指针的情况下编译的，因此经过 libc 的路径中很容易出现损坏的堆栈，包括前面两个示例中的 pthread\_cond\_timedwait() 和 send()。[^fn-ch05-ch05-footnote-17]

最简单的解决方案通常是修复帧指针寄存器：

- **对于 C/C++** 软件以及使用 gcc(1) 或 LLVM 编译的其他软件：使用 `-fno-omit-frame-pointer` 重新编译软件。
- **对于 Java**：使用 `-XX:+PreserveFramePointer` 运行 java(1)。

这可能带来性能成本，但通常测得不到 1%；能够借助堆栈跟踪发现性能收益，其价值通常远远超过这一成本。

另一种方法是改用不依赖帧指针的堆栈遍历技术。perf(1) 支持基于 DWARF 的堆栈遍历、ORC 以及最后分支记录（LBR）。其他堆栈遍历方法在[第 13 章](#ch13-ch13)、[perf](#ch13-ch13)、[第 13.9 节](#ch13-ch13lev9)、[perf record](#ch13-ch13lev9)中介绍。

截至撰写本文时，BPF 尚不支持基于 DWARF 和 LBR 的堆栈遍历，ORC 也尚不可用于用户态软件。

    - 应用程序是否存在已知的性能错误？
    - 该应用程序是否有社区（例如 IRC、聚会）？是否有专门讨论其性能的社区？

    - 描述应用于应用程序的工作负载（尤其是人员和内容）。

    - 应用程序是否同时运行？研究其同步原语的使用。

# 第 10 章 — 网络

随着系统变得更加分布式，特别是在云计算环境中，网络在性能方面发挥着越来越大的作用。网络性能的常见任务包括改善网络延迟和吞吐量，以及消除可能由数据包丢失或延迟引起的延迟异常值。

网络分析涵盖硬件和软件。硬件是物理网络，包括网络接口卡、交换机、路由器和网关（这些通常也有软件）。该软件是内核网络协议栈，包括网络设备驱动程序、数据包队列和数据包调度程序以及网络协议的实现。较低层协议通常是内核软件（IP、TCP、UDP 等），高层协议通常是库或应用程序软件（例如 HTTP）。

考虑到潜在的拥塞及其固有的复杂性（归咎于未知因素），网络经常被指责性能不佳。本章将展示如何弄清楚到底发生了什么，这可能会证明网络无罪，以便继续进行分析。

本章的学习目标是：

- 了解网络模型和概念。
- 了解网络延迟的不同衡量标准。
- 具备常用网络协议的应用知识。
- 熟悉网络硬件内部结构。
- 熟悉从套接字到设备的内核路径。
- 遵循不同的网络分析方法。
- 表征系统范围和每个进程的网络 I/O。
- 识别由 TCP 重传引起的问题。
- 使用跟踪工具调查网络内部结构。
- 了解网络可调参数。

本章由六个部分组成，前三部分提供网络分析的基础，后三部分展示其在基于 Linux 的系统中的实际应用。各部分如下：

- **背景**介绍与网络相关的术语、模型和关键网络性能概念。
- **架构**提供物理网络组件和网络协议栈的通用描述。
- **方法**描述了观测和实验的性能分析方法。
- **可观测性工具**：显示基于 Linux 的系统网络性能可观测性工具。
- **实验**总结了网络基准测试和实验工具。
- **调整**：描述示例可调参数。

网络基础知识（例如 TCP 和 IP 的作用）是本章假定的知识。

## 10.1 术语

作为参考，本章中使用的网络相关术语包括：

- **接口**：术语*接口端口*是指物理网络连接器。术语“接口”或“链路”是指操作系统看到并配置的网络接口端口的逻辑实例。（并非所有操作系统接口都由硬件支持：有些是虚拟的。）
- **[数据包](#gloss-glo-115)**：术语“数据包”是指数据包交换网络中的消息，例如 IP 数据包。
- **[帧](#gloss-glo-064)**：物理网络级消息，例如以太网帧。
- **[套接字](#gloss-glo-154)**：源自 BSD、用于表示网络端点的 API。
- **带宽**：网络类型的最大数据传输速率，通常以每秒位数为单位。 “100 GbE”是带宽为 100 Gbits/s 的以太网。每个方向可能存在带宽限制，因此 100 GbE 可能能够并行执行 100 Gbit/s 传输和 100 Gbit/s 接收（总吞吐量为 200 Gbit/s）。
- **吞吐量**：网络端点之间的当前数据传输速率，以每秒位数或每秒字节数为单位。
- **延迟**：网络*延迟*可以指消息在端点之间往返所需的时间，或建立连接（例如 TCP 握手）所需的时间，不包括随后的数据传输时间。

本章将介绍其他术语。术语表包含供参考的基本术语，包括*[客户端](#gloss-glo-031)*、*[以太网](#gloss-glo-058)*、*[主机](#gloss-glo-074)*、*[IP](#gloss-glo-083)*、*[RFC](#gloss-glo-138)*、*[服务器](#gloss-glo-148)*、*[SYN](#gloss-glo-170)*和*[ACK](#gloss-glo-002)*。另请参阅[第 2 章](#ch02-ch02)和[第 3 章](#ch03-ch03)中的术语部分。

## 10.3 概念

以下是网络和网络性能方面的一些重要概念的精选。

### 10.3.1 网络和路由

网络是一组连接的主机，通过网络协议地址关联。出于多种原因，特别是可扩展性，拥有多个网络（而不是一个庞大的全球网络）是可取的。一些网络消息将“广播”到所有相邻主机。通过创建更小的子网，可以在本地隔离此类广播消息，这样它们就不会造成大规模的洪泛问题。这也是隔离常规消息仅传输到源和目的地之间的网络的基础，从而更有效地利用网络基础设施。

路由管理跨这些网络的消息传递，这些消息称为“数据包”。路由的作用如[图 10.4](#ch10-ch10fig04)所示。

<!-- source-id: ch10#ch10fig04 -->
![图 10.4 通过路由器连接的网络](../images/10fig04.jpg)

从主机 A 的角度来看，*localhost* 就是主机 A 本身。图中的所有其他主机都是*远程主机*。

主机 A 可以通过本地网络连接到主机 B，通常由网络交换机驱动（参见[第 10.4 节](#ch10-ch10lev4)、[架构](#ch10-ch10lev4)）。主机 A 可以通过路由器 1 连接到主机 C，并通过路由器 1、2 和 3 连接到主机 D。由于路由器等网络组件是共享的，来自其他流量（例如主机 C 到主机 E）的争用可能会损害性能。

主机对之间的连接涉及*单播*传输。*多播*传输允许发送者同时传输到多个目的地，这可能跨越多个网络。这必须得到路由器配置的支持才能允许传送。在公共云环境中，它可能会被阻止。

除了路由器之外，典型的网络还将使用“防火墙”来提高安全性，阻止主机之间不需要的连接。

路由数据包所需的地址信息包含在 IP 标头中。

<!-- source-id: ch10#ch10lev3sec2 -->
### 10.3.2 协议

IP、TCP 和 UDP 等网络协议标准是系统和设备之间通信的必要要求。通信是通过传输称为“数据包”的可路由消息来执行的，通常通过有效负载数据的封装来实现。

网络协议具有不同的性能特征，这些特征源于原始协议设计、扩展或软件或硬件的特殊处理。例如，不同版本的 IP 协议 IPv4 和 IPv6 可以由不同的内核代码路径处理，并且可以表现出不同的性能特征。其他协议的设计性能不同，可以在适合工作负载时进行选择：示例包括流控制传输协议 (SCTP)、多路径 TCP (MPTCP) 和 QUIC。

通常，还有一些系统可调参数可以通过更改缓冲区大小、算法和各种计时器等设置来影响协议性能。特定协议的这些差异将在后面的部分中描述。

协议通常通过使用封装来传输数据。

<!-- source-id: ch10#ch10lev3sec3 -->

封装将元数据添加到有效负载的开头（*标头*）、结尾（*尾部*）或两者。这不会改变有效负载数据，尽管它确实稍微增加了消息的总大小，这会增加一些传输开销。

### 10.3.4 数据包大小

数据包的大小及其有效负载会影响性能，较大的数据包可提高吞吐量并减少数据包开销。对于 TCP/IP 和以太网，数据包可以在 54 到 9,054 字节之间，包括 54 字节（或更多，取决于选项或版本）的协议标头。

数据包大小通常受到网络接口*最大传输单元*（MTU）大小的限制，对于许多以太网来说，该大小配置为 1,500 字节。1,500 MTU 大小的起源来自以太网的早期版本，需要平衡 NIC 缓冲内存成本和传输延迟等因素[\[Nosachev 20\]](#ch10-ch10ref63)。主机竞相使用共享介质（同轴电缆或以太网集线器），并且较大的尺寸会增加主机等待轮到的延迟。

以太网现在支持高达约 9,000 字节的较大数据包（帧），称为“巨型帧”。这些帧可以通过减少所需的数据包数量来提高网络吞吐量性能，并降低数据传输的延迟。

两个因素阻碍了巨型帧的采用：较旧的网络硬件和配置错误的防火墙。不支持巨型帧的旧硬件可以使用 IP 协议对数据包进行分片（导致数据包重组的性能成本），或者以 ICMP“无法分片”错误进行响应，让发送方知道减小数据包大小。错误配置的防火墙也会造成问题：过去曾发生过基于 ICMP 的攻击（包括“死亡之 ping”），一些防火墙管理员通过阻止所有 ICMP 来应对这些攻击。这可以防止有用的“无法分片”消息到达发送者，并导致数据包大小超过 1,500 时网络数据包被静默丢弃。如果收到 ICMP 消息并发生分片，则还存在分片数据包被不支持它们的设备丢弃的风险。为了避免这些问题，许多系统坚持使用 1,500 MTU 默认值。

1,500 MTU 帧的性能已通过网络接口卡功能得到改进，包括*TCP 卸载*和*大段卸载*。这些功能将更大的缓冲区发送到网卡，然后网卡可以使用专用和优化的硬件将它们分成更小的帧。这在一定程度上缩小了 1,500 和 9,000 MTU 网络性能之间的差距。

<!-- source-id: ch10#ch10lev3sec5 -->
### 10.3.5 延迟

延迟是网络性能的一个重要指标，可以通过不同的方式进行测量，包括名称解析延迟、ping 延迟、连接延迟、首字节延迟、往返时间和连接寿命。这些被描述为由连接到服务器的客户端测量的。

<!-- source-id: ch10#ch10lev3_1 -->
#### 名称解析延迟

与远程主机建立连接时，主机名通常会解析为 IP 地址，例如通过 DNS 解析。所花费的时间可以单独测量为名称解析延迟。这种延迟的最坏情况是名称解析超时，这可能需要数十秒。

操作系统通常提供带缓存的名称解析服务，以便后续的 DNS 查找可以从缓存中快速解析。有时应用程序仅使用 IP 地址而不使用名称，因此完全避免了 DNS 延迟。

<!-- source-id: ch10#ch10lev3_2 -->
#### Ping 延迟

这是 ICMP 回显请求到回显响应的时间，由 ping(1) 命令测量。该时间用于测量主机之间的网络延迟，包括主机之间各跃点的延迟；也就是网络请求完成一次往返所需的时间。它之所以被广泛使用，是因为它简单且通常易于使用：许多操作系统默认都会响应 ping。它可能无法准确反映应用程序请求的往返时间，因为路由器可能以不同的优先级处理 ICMP。

[表 10.1](#ch10-ch10tab01)中显示了 ping 延迟示例。

<!-- source-id: ch10#ch10tab01 -->

<!-- source-id: ch10#ch10lev3_3 -->
#### 连接延迟

连接延迟是指在传输任何数据之前建立网络连接的时间。对于*TCP 连接延迟*，这是 TCP 握手时间。从客户端测量，是从发送 SYN 到收到相应 SYN-ACK 的时间。连接延迟可能更好地称为“连接建立延迟”，以明确区分它与连接生命周期。

连接延迟与 ping 延迟类似，尽管它使用更多的内核代码来建立连接，并且包括重新传输任何丢弃的数据包的时间。特别是，如果服务器的连接队列已满，服务器可能会丢弃该数据包，从而导致客户端发送基于计时器的 SYN 重传。这发生在 TCP 握手期间，因此连接延迟可能包括重新传输延迟，增加一秒或多秒。

连接延迟之后是第一个字节延迟。

<!-- source-id: ch10#ch10lev3_4 -->
#### 第一个字节延迟

也称为“第一个字节的时间”(TTFB)，第一个字节延迟是指从建立连接到接收到第一个数据字节的时间。这包括远程主机接受连接、调度为其提供服务的线程以及该线程执行和发送第一个字节的时间。

虽然 ping 和连接延迟衡量的是网络产生的延迟，但首字节延迟包括目标服务器的思考时间。如果服务器过载并且需要时间来处理请求（例如 TCP 连接队列）和调度服务器（CPU 调度程序延迟），这可能包括延迟。

<!-- source-id: ch10#ch10lev3_5 -->
#### 往返时间

往返时间 (RTT) 描述网络请求在端点之间进行往返所需的时间。这包括信号传播时间和每个网络跃点的处理时间。预期用途是确定网络的延迟，因此理想情况下，RTT 由请求和回复数据包在网络上花费的时间（而不是远程主机服务请求的时间）决定。人们经常研究 ICMP 回显请求的 RTT，因为远程主机处理时间很短。

<!-- source-id: ch10#ch10lev3_6 -->
#### 连接寿命

连接生命周期是指从网络连接建立到关闭的时间。某些协议采用持久连接（keep-alive）策略，延长连接的持续时间，使后续操作能够复用已有连接，避免重新建立连接（以及 TLS 连接）的开销和延迟。

有关更多网络延迟测量，请参阅[第 10.5.4 节](#ch10-ch10lev5sec4)、[延迟分析](#ch10-ch10lev5sec4)，其中介绍了如何使用这些指标诊断网络性能。

<!-- source-id: ch10#ch10lev3sec6 -->
### 10.3.6 缓冲

尽管可能会遇到各种网络延迟，但通过在发送器和接收器上使用缓冲，可以以高速率维持网络吞吐量。较大的缓冲区可以通过在阻塞和等待确认之前继续发送数据来减轻较长往返时间的影响。

TCP 采用缓冲以及滑动发送窗口来提高吞吐量。网络套接字也有缓冲区，应用程序也可以使用自己的缓冲区，在发送之前聚合数据。

缓冲也可以由外部网络组件（例如交换机和路由器）执行，以提高其自身的吞吐量。不幸的是，在这些组件上使用大缓冲区可能会导致“缓冲区膨胀”，即数据包排队时间较长。这会导致主机上的 TCP 拥塞避免，从而限制性能。 Linux 3.x 内核中添加了一些功能来解决此问题（包括字节队列限制、CoDel 排队规则 [\[Nichols 12\]](#ch10-ch10ref23) 和 TCP 小队列）。还有一个讨论该问题的网站[\[Bufferbloat 20\]](#ch10-ch10ref50)。

缓冲（或大缓冲）功能可能最好由端点（主机）而不是中间网络节点提供，遵循称为“端到端论证”[\[Saltzer 84\]](#ch10-ch10ref4)的原则。

<!-- source-id: ch10#ch10lev3sec7 -->
### 10.3.7 连接队列

另一种类型的缓冲用于初始连接请求。TCP 实现了连接队列，SYN 请求可以在被用户进程接受之前在内核中排队。当 TCP 连接请求过多、进程无法及时接受时，连接队列达到限制，SYN 数据包将被丢弃，稍后由客户端重传。这些数据包的重传会导致客户端连接延迟。该限制是可调的：它是 listen(2) 系统调用的一个参数，并且内核还可以提供系统范围的限制。

队列溢出丢弃和 SYN 重传是主机过载的指标。

<!-- source-id: ch10#ch10lev3sec8 -->
### 10.3.8 接口协商

网络接口可以以不同的模式运行，在连接的收发器之间自动协商。一些例子是：

- **带宽**：例如，10、100、1,000、10,000、40,000、100,000 Mbits/s
- **[双工](#gloss-glo-051)**：半双工或全双工

这些示例来自以太网，以太网倾向于使用以 10 为基数的整数来限制带宽。其他物理层协议（例如 SONET）具有不同的可能带宽集。

网络接口通常根据其最高带宽和协议进行描述，例如 1 Gbit/s 以太网 (1 GbE)。然而，如果需要，该接口可以自动协商到较低的速度。如果另一个端点无法更快地运行，或为了适应连接介质的物理问题（接线不良），则可能会发生这种情况。

全双工模式允许双向同时传输，具有单独的发送和接收路径，每个路径都可以在全带宽下运行。半双工模式一次只允许一个方向。

<!-- source-id: ch10#ch10lev3sec9 -->
### 10.3.9 拥塞避免

网络是共享资源，当流量负载较高时，网络可能会变得拥塞。这可能会导致性能问题：例如，路由器或交换机可能会丢弃数据包，从而导致 TCP 重传并增加延迟。当接收高数据包速率时，主机也会变得不堪重负，并且可能会自行丢弃数据包。

有很多机制可以避免这些问题；应研究这些机制，并在必要时进行调整，以提高负载下的可扩展性。不同协议的示例包括：

- **以太网**：不堪重负的主机可能会向发射器发送*暂停帧*，请求它们暂停传输（IEEE 802.3x）。每个类别还有优先级和*优先级暂停帧*。
- **IP**：包括显式拥塞通知 (ECN) 字段。
- **[TCP](#gloss-glo-174)**：包括拥塞窗口，并且可以使用各种*拥塞控制算法*。

后面的部分将更详细地描述 IP ECN 和 TCP 拥塞控制算法。

<!-- source-id: ch10#ch10lev3sec10 -->
### 10.3.10 利用率

网络接口利用率可以计算为当前吞吐量除以最大带宽。考虑到自动协商导致的可变带宽和双工，计算起来并不像听起来那么简单。

对于全双工，利用率适用于每个方向，并以当前协商带宽上该方向的当前吞吐量来衡量。通常，最重要的只是一个方向，因为主机通常是不对称的：服务器传输量大，客户端接收量大。

一旦网络接口方向达到 100% 利用率，它就会成为瓶颈，限制性能。

某些性能工具仅以数据包而非字节的形式报告活动。由于数据包大小可能变化很大（如前所述），因此不可能将数据包计数与字节计数关联起来以计算吞吐量或（基于吞吐量的）利用率。

<!-- source-id: ch10#ch10lev3sec11 -->
### 10.3.11 本地连接

网络连接可以发生在同一系统上的两个应用程序之间。这些是 *localhost* 连接并使用虚拟网络接口：*loopback*。

分布式应用程序环境通常分为通过网络进行通信的逻辑部分。这些可以包括 Web 服务器、数据库服务器、缓存服务器、代理服务器和应用程序服务器。如果它们在同一主机上运行，则它们的连接将连接到本地主机。

通过 IP 连接到本地主机是进程间通信 (IPC) 的“IP 套接字”技术。另一种技术是 Unix 域套接字 (UDS)，它在文件系统上创建文件以进行通信。使用 UDS 的性能可能会更好，因为可以绕过内核 TCP/IP 协议栈，跳过内核代码和协议数据包封装的开销。

对于 TCP/IP 套接字，内核可能会在握手后检测本地主机连接，然后快速绕过 TCP/IP 协议栈进行数据传输，从而提高性能。这是作为 Linux 内核功能开发的，称为“TCP friends”，但未合并[\[Corbet 12\]](#ch10-ch10ref20)。BPF 现在可以在 Linux 上用于此目的，正如用于容器网络性能和安全性的 Cilium 软件所做的那样 \[Cilium 20a\]。

## 10.4 架构

本节介绍网络架构：协议、硬件和软件。这些已被总结为性能分析和调优的背景，重点是性能特征。有关更多详细信息，包括一般网络主题，请参阅网络文本 [\[Stevens 93\]](#ch10-ch10ref7)[\[Hassan 03\]](#ch10-ch10ref14)、RFC 和网络硬件供应商手册。其中一些列在本章末尾。

<!-- source-id: ch10#ch10lev4sec1 -->
### 10.4.1 协议

本节总结了 IP、TCP、UDP 和 QUIC 的性能特征。这些协议如何在硬件和软件中实现（包括分段卸载、连接队列和缓冲等功能）将在后面的硬件和软件部分中介绍。

<!-- source-id: ch10#ch10lev3_7 -->
#### IP

互联网协议 (IP) 版本 4 和 6 包括一个用于设置所需连接性能的字段：IPv4 中的服务类型字段和 IPv6 中的流量类别字段。这些字段已被重新定义为包含区分服务代码点 (DSCP) (RFC 2474) [\[Nichols 98\]](#ch10-ch10ref10) 和显式拥塞通知 (ECN) 字段 (RFC 3168) [\[Ramakrishnan 01\]](#ch10-ch10ref12)。

DSCP 旨在支持不同的“服务类别”，每个服务类别都有不同的特征，包括丢包概率。示例服务类别包括：电话、广播视频、低延迟数据、高吞吐量数据和低优先级数据。

ECN 是一种机制，允许路径上的服务器、路由器或交换机通过在 IP 标头中设置一个位来明确表示存在拥塞，而不是丢弃数据包。接收器会将这个信号回传给发送器，然后发送器可以限制传输。这提供了避免拥塞的好处，而不会造成丢包的损失（前提是 ECN 位在网络中正确使用）。

<!-- source-id: ch10#ch10lev3_8 -->
#### TCP

传输控制协议（TCP）是一种常用的 Internet 标准，用于创建可靠的网络连接。TCP 由 RFC 793 [\[Postel 81\]](#ch10-ch10ref2)及后续补充内容指定。

在性能方面，通过使用缓冲和*滑动窗口*，即使在高延迟网络上，TCP 也可以提供高吞吐量。TCP 还采用拥塞控制和由发送方设置的“拥塞窗口”，以便它可以在不同且不断变化的网络上保持高而可靠的传输速率。拥塞控制可避免发送过多的数据包，否则会导致拥塞和性能下降。

以下是 TCP 性能特性的摘要，包括自原始规范以来的新增内容：

- **滑动窗口**：这允许在收到确认之前在网络上发送最多达到窗口大小的多个数据包，即使在高延迟网络上也能提供高吞吐量。窗口的大小由接收方通告，以指示当时愿意接收多少个数据包。
- **拥塞避免**：防止发送过多数据并导致饱和，这可能导致数据包丢弃和性能下降。
- **慢启动**：TCP 拥塞控制的一部分，从一个小的拥塞窗口开始，然后随着在一定时间内收到确认 (ACK) 而增加拥塞窗口。当未在该时间内收到确认时，拥塞窗口就会减小。
- **选择性确认** (SACK)：允许 TCP 确认不连续的数据包，减少所需的重传次数。
- **快速重传**：TCP 可以根据重复 ACK 的到达来重传丢弃的数据包，而不是等待计时器。这些是往返时间的函数，而不是通常慢得多的计时器。
- **快速恢复**：在检测到重复 ACK 后，通过调整拥塞窗口恢复 TCP 性能，而不必重新执行慢启动。
- **TCP 快速打开**：允许客户端在 SYN 数据包中包含数据，以便服务器请求处理可以更早开始，而无需等待 SYN 握手 (RFC7413)。这可以使用加密 cookie 来验证客户端。
- **TCP 时间戳**：包括在 ACK 中返回的已发送数据包的时间戳，以便可以测量往返时间 (RFC 1323) [\[Jacobson 92\]](#ch10-ch10ref6)。
- **TCP SYN cookie**：在可能的 SYN 洪水攻击（连接队列已满）期间向客户端提供加密 cookie，以便合法客户端可以继续连接，并且服务器不需要为这些连接尝试存储额外的数据。

在某些情况下，这些功能是通过使用添加到协议标头的扩展 TCP 选项来实现的。

TCP 性能的重要主题包括三次握手、重复 ACK 检测、拥塞控制算法、Nagle、延迟 ACK、SACK 和 FACK。

##### 三次握手

连接是通过主机之间的三次握手建立的。一台主机被动地监听连接；另一个主动发起连接。澄清术语：*被动*和*主动*来自 RFC 793 \[Postel 81\]；然而，它们通常按套接字 API 的名称分别称为 *listen* 和 *connect*。对于客户端/服务器模型，服务器执行listen，客户端执行connect。

##### 状态和计时器

TCP 会话根据数据包和套接字事件在 TCP 状态之间切换。状态包括 LISTEN、SYN-SENT、SYN-RECEIVED、ESTABLISHED、FIN-WAIT-1、FIN-WAIT-2、CLOSE-WAIT、CLOSING、LAST-ACK、TIME-WAIT 和 CLOSED [Postel 80]。性能分析通常关注处于 ESTABLISHED 状态的连接，即活动连接。此类连接可能正在传输数据，或者空闲等待下一个事件：数据传输或关闭事件。

完全关闭的会话进入 TIME\_WAIT[^fn-ch10-ch10-footnote-2] 状态，以便迟到的数据包不会与同一端口上的新连接错误关联。这可能会导致端口耗尽的性能问题，如[第 10.5.7 节](#ch10-ch10lev5sec7)、[TCP 分析](#ch10-ch10lev5sec7)中所述。

有些状态有与其关联的计时器。TIME\_WAIT 通常为两分钟（某些内核，例如 Windows 内核，允许对其进行调整）。ESTABLISHED 状态下还可能设置 TCP 保活定时器，设置为较长的持续时间（例如，两个小时），以触发探测数据包来检查远程主机是否仍然活动。

##### 重复 ACK 检测

快速重传和快速恢复算法使用重复 ACK 检测来快速检测发送的数据包（或其 ACK）何时丢失。其工作原理如下：

1. 发送方发送序列号为 10 的数据包。
2. 接收方回复序列号 11 的 ACK。
3. 发送方发送 11、12、13。
4. 数据包 11 被丢弃。
5. 接收方通过发送其仍在等待的 11 的 ACK 来回复 12 和 13。
6. 发送方收到 11 的重复 ACK。

各种拥塞避免算法也使用重复 ACK 检测。

##### 重传

TCP 检测和重传丢失数据包的两种常用机制是：

- **基于定时器的重传**：当一段时间过去并且尚未收到数据包确认时，就会发生这种情况。该时间是 TCP 重传超时，根据连接往返时间 (RTT) 动态计算。在 Linux 上，第一次重传至少需要 200 毫秒 (TCP\_RTO\_MIN)，[^fn-ch10-ch10-footnote-3] 和后续重传将慢得多，遵循指数退避算法，使超时加倍。
- **快速重传**：当重复的 ACK 到达时，TCP 可以假设数据包已丢失并立即重传。

为了进一步提高性能，开发了额外的机制来避免基于定时器的重传。出现的一个问题是当最后传输的数据包丢失，并且没有后续数据包触发重复 ACK 检测时。 （考虑前面的示例，数据包 13 丢失。）这是通过尾部丢失探测 (TLP) 解决的，它会在上次传输短暂超时后发送一个附加数据包（探测），以帮助检测数据包丢失 [\[Dukkipati 13\]](#ch10-ch10ref25)。

拥塞控制算法还可能在存在重传的情况下限制吞吐量。

##### 拥塞控制

拥塞控制算法的开发是为了维持拥塞网络的性能。某些操作系统（包括基于 Linux 的操作系统）允许选择算法作为系统调整的一部分。这些算法包括：

- **Reno**：收到 3 个重复 ACK 触发拥塞窗口减半、慢启动阈值减半、快速重传和快速恢复。
- **Tahoe**：收到 3 个重复 ACK 触发：快速重传、将慢启动阈值减半、拥塞窗口设置为一个最大分段大小 (MSS) 以及慢启动状态。 （Tahoe 与 Reno 一起最初是为 4.3BSD 开发的。）
- **CUBIC**：使用三次函数（因此得名）来缩放窗口，并使用“混合启动”函数来退出慢启动。 CUBIC 往往比 Reno 更激进，并且是 Linux 中的默认设置。
- **BBR**：BBR 不是基于窗口，而是使用探测阶段构建网络路径特征（RTT 和带宽）的显式模型。BBR 可以在某些网络路径上提供显著更好的性能，同时会损害其他网络路径的性能。BBRv2 目前正在开发中，有望修复 v1 的一些缺陷。
- **DCTCP**：数据中心 TCP 依赖于配置为在非常浅的队列占用情况下发出显式拥塞通知（ECN）标记的交换机，以快速增加到可用带宽（RFC 8257）[\[Bensley 17\]](#ch10-ch10ref30)。这使得 DCTCP 不适合跨 Internet 部署，但在适当配置的受控环境中，它可以显著提高性能。

之前未列出的其他算法包括 Vegas、New Reno 和 Hybla。

拥塞控制算法可以对网络性能产生很大的影响。例如，Netflix 云服务使用 BBR，发现它可以在严重丢包期间将吞吐量提高到原来的三倍 [\[Ather 17\]](#ch10-ch10ref29)。在分析 TCP 性能时，了解这些算法在不同网络条件下的反应是一项重要活动。

2020 年发布的 Linux 5.6 添加了对在 BPF 中开发新拥塞控制算法的支持 [\[Corbet 20\]](#ch10-ch10ref53)。这使得它们可以由最终用户定义并按需加载。

##### Nagle

此算法 (RFC 896) [\[Nagle 84\]](#ch10-ch10ref3) 通过延迟传输来减少网络上小数据包的数量，以允许更多数据到达并合并。仅当管道中有数据并且已经遇到延迟时，才会延迟数据包。

系统可能提供可调参数或套接字选项来禁用 Nagle；如果其操作与延迟 ACK 冲突，这可能是必要的（请参阅[第 10.8.2 节](#ch10-ch10lev8sec2)、[套接字选项](#ch10-ch10lev8sec2)）。

##### 延迟 ACK

该算法 (RFC 1122) [\[Braden 89\]](#ch10-ch10ref5) 将 ACK 的发送延迟最多 500 ms，以便可以组合多个 ACK。还可以组合其他 TCP 控制消息，从而减少网络上的数据包数量。

与 Nagle 一样，系统可以提供可调参数来禁用此行为。

##### SACK、FACK 和 RACK

TCP 选择性确认 (SACK) 算法允许接收方通知发送方它收到了不连续的数据块。如果不使用 SACK，单个数据包被丢弃最终将导致整个发送窗口被重新传输，以保留顺序确认方案。这会损害 TCP 性能，大多数支持 SACK 的现代操作系统都可以避免这种情况。

SACK 已通过前向确认 (FACK) 进行了扩展，Linux 默认支持 FACK。 FACK 跟踪附加状态并更好地调节网络中未完成的数据量，从而提高整体性能 [\[Mathis 96\]](#ch10-ch10ref8)。

SACK 和 FACK 都用于改善丢包恢复。较新的算法 Recent ACKnowledgment（RACK；现在称为 RACK-TLP，并结合了 TLP）使用 ACK 中的时间信息来实现更好的丢失检测和恢复，而不是单独使用 ACK 序列[\[Cheng 20\]](#ch10-ch10ref51)。对于 FreeBSD，Netflix 基于 RACK、TLP 和其他功能开发了一种新的重构 TCP 协议栈，称为 RACK[\[Stewart 18\]](#ch10-ch10ref42)。

##### 初始窗口

初始窗口 (IW) 是 TCP 发送方在连接开始时在等待发送方确认之前传输的数据包数量。对于短流，例如典型的 HTTP 连接，足够大的 IW 来跨越传输的数据可以大大减少完成时间，从而提高性能。然而，较大的 IW 可能会带来拥塞和数据包丢弃的风险。当多个流同时启动时，这种情况尤其复杂。

Linux 默认值（10 个数据包，又名 IW10）在慢速链接或启动许多连接时可能过高；其他操作系统默认为 2 或 4 个数据包（IW2 或 IW4）。

<!-- source-id: ch10#ch10lev3_9 -->
#### UDP

用户数据报协议（UDP）是一种常用的 Internet 标准，用于通过网络发送称为“数据报”的消息（RFC 768）[\[Postel 80\]](#ch10-ch10ref1)。在性能方面，UDP 提供：

- **简单性**：简单且小的协议头减少了计算和大小的开销。
- **无状态**：降低连接和传输的开销。
- **无重传**：重传会给 TCP 连接增加显著延迟。

虽然 UDP 简单且性能通常很高，但它并不可靠，并且数据可能会丢失或乱序接收。这使得它不适合许多类型的连接。UDP 也没有拥塞避免功能，因此可能会导致网络拥塞。

某些服务（包括 NFS 版本）可以根据需要配置为通过 TCP 或 UDP 运行。其他执行广播或多播数据的程序可能只能使用 UDP。

UDP 的一个主要用途是 DNS。由于 UDP 的简单性、缺乏拥塞控制和 Internet 支持（通常不会被防火墙阻断），现在有基于 UDP 构建的新协议来实现自己的拥塞控制和其他功能。一个例子是 QUIC。

<!-- source-id: ch10#ch10lev3_10 -->
#### QUIC 和 HTTP/3

QUIC 是由 Google 的 Jim Roskind 设计的网络协议，作为 TCP 的高性能、低延迟替代品，针对 HTTP 和 TLS 进行了优化 [\[Roskind 12\]](#ch10-ch10ref24)。 QUIC 基于 UDP 构建，并在其之上提供了多种功能，包括：

- 在同一“连接”之上多路复用多个应用程序定义的流的能力。
- 类似 TCP 的可靠有序流传输，可按需对个别子流关闭这一传输特性。
- 当客户端更改其网络地址时，基于连接 ID 的加密身份验证恢复连接。
- 有效负载数据的完全加密，包括 QUIC 标头。
- 0-RTT 连接握手，包括加密（对于之前已通信的对等点）。

Chrome 网络浏览器大量使用 QUIC。

虽然 QUIC 最初由 Google 开发，但互联网工程任务组 (IETF) 正在标准化 QUIC 传输本身以及使用 HTTP over QUIC 的具体配置（后一种组合称为 HTTP/3）。

<!-- source-id: ch10#ch10lev4sec2 -->
### 10.4.2 硬件

网络硬件包括接口、控制器、交换机、路由器和防火墙。即使这些设备由其他员工（网络管理员）管理，了解它们的工作方式也很有用。

<!-- source-id: ch10#ch10lev3_11 -->
#### 接口

物理网络接口在连接的网络上发送和接收消息，称为“帧”。它们管理所涉及的电、光或无线信号，包括传输错误的处理。

接口类型基于第 2 层标准，每种类型都提供最大带宽。更高带宽的接口提供更低的数据传输延迟，但成本更高。设计新服务器时，一个关键决策通常是如何平衡服务器的价格与所需的网络性能。

对于以太网，选择包括铜缆或光纤，最大速度为 1 Gbit/s（1 GbE）、10 GbE、40 GbE、100 GbE、200 GbE 和 400 GbE。许多供应商都生产以太网接口控制器，尽管您的操作系统可能不支持其中某些控制器的驱动程序。

接口利用率可以通过当前吞吐量除以当前协商带宽来检查。大多数接口都有单独的发送和接收通道，当在全双工模式下运行时，必须单独研究每个通道的利用率。

由于信号强度差和干扰，无线接口可能会出现性能问题。[^fn-ch10-ch10-footnote-4]

<!-- source-id: ch10#ch10lev3_12 -->
#### 控制器

物理网络接口通过控制器提供给系统，控制器可以内置于系统板中或通过扩展卡提供。

控制器由微处理器驱动，并通过 I/O 传输（例如 PCI）连接到系统。其中任何一个都可能成为网络吞吐量或 IOPS 的限制因素。

例如，双 10 GbE 网络接口卡连接到四通道 PCI Express (PCIe) Gen 2 插槽。该卡的最大发送或接收带宽为 2 × 10 GbE = 20 Gbits/s，双向带宽为 40 Gbit/s。该插槽的最大带宽为 4 × 4 Gbits/s = 16 Gbits/s。因此，两个端口上的网络吞吐量将受到 PCIe Gen 2 带宽的限制，并且不可能同时以线速驱动它们（我从实践中知道这一点！）。

<!-- source-id: ch10#ch10lev3_13 -->
#### 交换机和路由器

交换机在任意两个连接的主机之间提供专用通信路径，允许主机对之间进行多次传输而不会产生干扰。这项技术取代了集线器（以及更早的共享物理总线：常用的粗以太网同轴电缆）；集线器会与所有主机共享所有数据包。当主机同时传输时，这种共享会导致争用，接口使用“带冲突检测的载波侦听多路访问”（CSMA/CD）算法将其识别为“冲突”。该算法将呈指数级退避并重新传输，直到成功为止，从而在负载下产生性能问题。通过使用交换机，这种情况已经成为过去，但一些可观测性工具仍然具有碰撞计数器——尽管这些碰撞通常仅因错误（协商或接线不良）而发生。

路由器在网络之间传递数据包，并使用网络协议和路由表来确定有效的传递路径。在两个城市之间传递数据包可能涉及十几个或更多路由器，以及其他网络硬件。路由器和路由通常配置为动态更新，以便网络能够自动响应网络和路由器中断，并平衡负载。这意味着在给定的时间点，没有人可以确定数据包实际采用的路径。由于可能有多个路径，因此数据包也可能会无序传送，从而导致 TCP 性能问题。

网络上的这种神秘元素常常被归咎于性能不佳：也许来自其他不相关主机的大量网络流量正在使源和目标之间的路由器饱和？因此，网络管理团队经常被要求免除其基础设施的责任。他们可以使用先进的实时监控工具来检查所有路由器和其他涉及的网络组件。

路由器和交换机都包含缓冲区和微处理器，它们本身可能成为负载下的性能瓶颈。作为一个极端的例子，我曾经发现早期的 10 GbE 交换机由于其 CPU 容量有限，所有端口的总传输速度不能超过 11 Gb/s。

请注意，交换机和路由器也经常是发生“速率转换”的地方（从一种带宽切换到另一种带宽，例如从 10 Gbps 链路转换到 1 Gbps 链路）。发生这种情况时，需要进行一些缓冲以避免过度丢弃，但许多交换机和路由器会过度缓冲（请参阅[第 10.3.6 节](#ch10-ch10lev3sec6)、[缓冲](#ch10-ch10lev3sec6)中的缓冲区膨胀问题），从而导致高延迟。更好的队列管理算法可以帮助消除这个问题，但并非所有网络设备供应商都支持它们。在源处进行调速也可以通过减少流量的突发性来缓解速率转换问题。

<!-- source-id: ch10#ch10lev3_14 -->
#### 防火墙

防火墙通常用于仅允许基于配置的规则集的授权通信，从而提高网络的安全性。它们可能以物理网络设备和内核软件的形式出现。

防火墙可能成为性能瓶颈，尤其是在配置为有状态时。有状态规则存储每个可见连接的元数据，防火墙在处理许多连接时可能会遇到过多的内存负载。发生这种情况的原因可能是拒绝服务 (DoS) 攻击试图用连接淹没目标。当出站连接频率很高时，也可能会发生这种情况，因为它们可能需要类似的连接跟踪。

由于防火墙是定制硬件或软件，因此可用于分析它们的工具取决于每个防火墙产品。请参阅各自的文档。

由于其性能、可编程性、易用性和最终成本，使用扩展 BPF 在商用硬件上实现防火墙的情况正在不断增长。采用 BPF 防火墙和 DDoS 解决方案的公司包括 Facebook [\[Deepak 18\]](#ch10-ch10ref37)、Cloudflare [\[Majkowski 18\]](#ch10-ch10ref41) 和 Cilium [\[Cilium 20a\]](#ch10-ch10ref52)。

防火墙在性能测试期间也可能是一个麻烦：在调试问题时执行带宽实验可能涉及修改防火墙规则以允许连接（并与安全团队协调）。

<!-- source-id: ch10#ch10lev3_15 -->
#### 其他

您的环境可能包括其他物理网络设备，例如集线器、网桥、中继器和调制解调器。其中任何一个都可能成为性能瓶颈和丢包的根源。

#### TCP 连接队列

通过使用连接队列来处理突发的入站连接。有两种这样的队列，一种用于 TCP 握手完成前的未完成连接（也称为 *SYN 队列*），另一种用于等待应用程序接受的已建立会话（也称为 *监听队列*）。这些队列显示在[图 10.9](#ch10-ch10fig09)中。

<!-- source-id: ch10#ch10fig09 -->
![图 10.9 TCP 连接队列](../images/10fig09.jpg)

早期内核中只使用了一个队列，并且很容易受到 SYN 洪水攻击。SYN 洪水是一种 DoS 攻击，涉及从虚假 IP 地址向监听 TCP 端口发送大量 SYN。当 TCP 等待完成握手时，这会填满连接队列，从而阻止真正的客户端连接。

对于两个队列，第一个队列可以充当潜在虚假连接的暂存区域，仅在建立连接后才会将其提升到第二个队列。可将第一个队列设置得较长，以应对 SYN 洪水攻击，并加以优化，使其只存储必要的最少元数据。

SYN cookies 的使用绕过了第一个队列，因为它们显示客户端已经被授权。

这些队列的长度可以独立调整（请参阅[第 10.8 节](#ch10-ch10lev8)、[调优](#ch10-ch10lev8)）。第二个队列的容量上限还可以由应用程序通过 listen(2) 的 backlog 参数设置。

<!-- source-id: ch10#ch10lev3_18 -->
#### TCP 缓冲

通过使用与套接字关联的发送和接收缓冲区可以提高数据吞吐量。这些缓冲区显示在[图 10.10](#ch10-ch10fig10)中。

<!-- source-id: ch10#ch10fig10 -->
![图 10.10 TCP 发送和接收缓冲区](../images/10fig10.jpg)

发送和接收缓冲区的大小都是可调的。较大的大小可以提高吞吐量性能，但代价是每个连接花费更多的主内存。如果服务器期望执行更多的发送或接收，则可以将一个缓冲区设置为大于另一个缓冲区。 Linux 内核还将根据连接活动动态增加这些缓冲区的大小，并允许调整其最小、默认和最大大小。

<!-- source-id: ch10#ch10lev3_19 -->
#### 分段卸载：GSO 和 TSO

网络设备和网络一次最多接受最大段大小（MSS）的数据包，该大小可能小至 1,500 字节。为了避免发送许多小数据包的网络协议栈开销，Linux 使用通用分段卸载（GSO）发送最大 64 KB 的数据包（“超级数据包”），这些数据包在传送到网络设备之前被分割成 MSS 大小的分段。如果 NIC 和驱动程序支持 TCP 分段卸载（TSO），则 GSO 将拆分留给设备，从而提高网络协议栈吞吐量。[^fn-ch10-ch10-footnote-5]还有一个对 GSO 的通用接收卸载（GRO）补充[\[Linux 20i\]](#ch10-ch10ref58)。[^fn-ch10-ch10-footnote-6]GRO 和 GSO 在内核软件中实现，TSO 由 NIC 硬件实现。

<!-- source-id: ch10#ch10lev3_21 -->
#### 网络设备驱动程序

网络设备驱动程序通常有一个额外的缓冲区（环形缓冲区），用于在内核内存和 NIC 之间发送和接收数据包。这在[图 10.8](#ch10-ch10fig08)中被描绘为驱动程序队列。

高速网络中越来越常见的一个性能特征是使用“中断合并模式”。仅当达到计时器（轮询）或达到一定数量的数据包时才会发送中断，而不是为每个到达的数据包中断内核。这降低了内核与 NIC 通信的速率，允许缓冲更大的传输，从而提高吞吐量，但会付出一定的延迟代价。

Linux 内核采用 NAPI（New API）框架来减少中断开销：数据包速率较低时使用中断（通过软中断调度处理）；速率较高时暂停相关设备的中断，改用轮询以便批量处理数据包[\[Corbet 03\]](#ch10-ch10ref13)[\[Corbet 06b\]](#ch10-ch10ref16)。这样可根据工作负载提供较低延迟或较高吞吐量。NAPI 的其他功能包括：

- 数据包限制，允许网络适配器中尽早丢弃数据包，以防止系统被数据包风暴淹没。
- 接口调度，其中配额用于限制轮询周期内处理的缓冲区，以确保繁忙网络接口之间的公平性。
- 支持 SO\_BUSY\_POLL 套接字选项，其中用户级应用程序可以通过请求套接字 [\[Dumazet 17a\]](#ch10-ch10ref31) 上的*忙等待*（在 CPU 上自旋，直到事件发生）来减少网络接收延迟。

中断合并对于改进虚拟机网络尤其重要，AWS EC2 使用的 ena 网络驱动程序也采用了它。

<!-- source-id: ch10#ch10lev3_22 -->
#### 网卡发送和接收

对于发送的数据包，NIC 会收到通知，并且通常使用直接内存访问（DMA）从内核内存读取数据包（帧）以提高效率。NIC 提供用于管理 DMA 数据包的传输描述符；如果 NIC 没有空闲描述符，网络协议栈将暂停传输以允许 NIC 赶上。[^fn-ch10-ch10-footnote-7]

对于接收到的数据包，NIC 可以使用 DMA 将数据包放入内核环形缓冲区内存中，然后使用中断通知内核（可以忽略该中断以允许合并）。中断触发软中断，将数据包传送到网络协议栈进行进一步处理。

<!-- source-id: ch10#ch10lev3_23 -->
#### CPU 处理能力扩展

通过使用多个 CPU 来处理数据包和 TCP/IP 协议栈，可以实现高数据包速率。Linux 支持多种多 CPU 数据包处理方法（请参阅 Documentation/networking/scaling.txt）：

- **RSS：接收端扩展**：对于支持多个队列并可以将数据包散列到不同队列的现代 NIC，这些队列分别由不同的 CPU 处理，直接中断它们。此哈希可能基于 IP 地址和 TCP 端口号，因此来自同一连接的数据包最终由同一 CPU 处理。[^fn-ch10-ch10-footnote-8]
- **RPS：接收数据包引导**：RSS 的软件实现，适用于不支持多个队列的 NIC。这涉及一个短中断服务例程，将入站数据包映射到 CPU 进行处理。类似的散列可用于根据数据包标头中的字段将数据包映射到 CPU。
- **RFS：接收流引导**：这与 RPS 类似，但与套接字上次在 CPU 上处理的位置具有关联性，以提高 CPU 缓存命中率和内存局部性。
- **加速接收流引导**：对于支持此功能的 NIC，这可以在硬件中实现 RFS。它涉及使用流信息更新 NIC，以便它可以确定要中断哪个 CPU。
- **XPS：发送数据包引导**：对于具有多个发送队列的 NIC，该机制支持多个 CPU 通过这些队列发送数据包。

如果没有针对网络数据包的 CPU 负载均衡策略，一块网卡可能只中断一个 CPU，而该 CPU 的利用率可能达到 100%，成为瓶颈。这可能会显示为单个 CPU 上的高软中断 CPU 时间（例如使用 Linux mpstat(1)；请参阅[第 6 章](#ch06-ch06)、[CPU](#ch06-ch06)、[第 6.6.3 节](#ch06-ch06lev6sec3)、[mpstat](#ch06-ch06lev6sec3)）。这种情况尤其可能发生在负载均衡器或代理服务器（例如 nginx）上，因为它们的预期工作负载是高速率的入站数据包。

根据缓存一致性等因素将中断映射到 CPU（如 RFS 所做的那样）可以显著提高网络性能。这也可以通过 irqbalance 进程来完成，该进程将中断请求（IRQ）线分配给 CPU。

<!-- source-id: ch10#ch10lev3_24 -->
#### 内核绕过

[图 10.8](#ch10-ch10fig08)显示 TCP/IP 协议栈最常采用的路径。应用程序可以使用数据平面开发套件（DPDK）等技术绕过内核网络协议栈，以实现更高的数据包速率和性能。这涉及应用程序在用户空间中实现自己的网络协议，并通过 DPDK 库和内核用户空间 I/O（UIO）或虚拟功能 I/O（VFIO）驱动程序写入网络驱动程序。通过直接访问 NIC 上的内存可以避免复制数据包数据的开销。

eXpress 数据路径（XDP）技术为网络数据包提供了另一条路径：使用扩展 BPF 并集成到现有内核协议栈中而不是绕过它的可编程快速路径[\[Høiland-Jørgensen 18\]](#ch10-ch10ref39)。（DPDK 现在支持 XDP 接收数据包，将一些功能移回内核[\[DPDK 20\]](#ch10-ch10ref54)。）

通过内核网络协议栈旁路，使用传统工具和指标进行插桩不可用，因为它们使用的计数器和跟踪事件也被绕过。这使得性能分析变得更加困难。

除了完全绕过内核协议栈之外，还可以通过一些机制避免拷贝数据的开销：MSG\_ZEROCOPY send(2) 标志，以及通过 mmap(2) [\[Linux 20c\]](#ch10-ch10ref59)[\[Corbet 18b\]](#ch10-ch10ref35) 实现的零拷贝接收。

#### 其他优化

Linux 网络协议栈中还使用其他算法来提高性能。[图 10.11](#ch10-ch10fig11)显示了 TCP 发送路径中的这些算法（其中许多由 tcp\_write\_xmit() 内核函数调用）。

<!-- source-id: ch10#ch10fig11 -->
![图 10.11 TCP 发送路径](../images/10fig11.jpg)

其中一些组件和算法已在前面描述过（套接字发送缓冲区、TSO、[^fn-ch10-ch10-footnote-9] 拥塞控制、Nagle 和 qdisc）；其他包括：

- **调速**：这控制何时发送数据包，分散传输（节奏）以避免可能损害性能的突发。这可能有助于避免 TCP 微突发；这种突发可能导致排队延迟，甚至使网络交换机丢包。当许多端点同时向一个端点传输时，它也可能有助于解决 *incast* 问题[\[Fritchie 12\]](#ch10-ch10ref21)。
- **TCP 小队列（TSQ）**：这控制（减少）网络协议栈排队的数据量，以避免出现缓冲区膨胀等问题（参见 \[Bufferbloat 20\]）。
- **字节队列限制（BQL）**：这些限制会自动将驱动程序队列调整为足够大以避免饥饿，但也足够小以减少排队数据包的最大延迟，并避免耗尽 NIC TX 描述符[\[Hrubý 12\]](#ch10-ch10ref22)。它的工作原理是在必要时暂停向驱动程序队列添加数据包，并于 Linux 3.3 中添加[\[Siemon 13\]](#ch10-ch10ref26)。
- **最早出发时间（EDT）**：这使用定时轮而不是队列来对发送到 NIC 的数据包进行排序。根据策略和速率配置在每个数据包上设置时间戳。这是在 Linux 4.20 中添加的，具有类似 BQL 和 TSQ 的功能[\[Jacobson 18\]](#ch10-ch10ref38)。

这些算法通常结合使用以提高性能。TCP 发送的数据包在到达 NIC[\[Cheng 16\]](#ch10-ch10ref27)之前，可以通过任何拥塞控制、TSO、TSQ、调速和排队规则进行处理。

### 10.5.1 工具方法

工具方法是迭代可用工具、检查它们提供的关键指标的过程。它可能会忽略工具提供的可见性较差或没有可见性的问题，并且执行起来可能非常耗时。

对于网络，工具方法可能涉及检查：

- **`nstat/netstat -s`**：查找高重传率和乱序数据包。什么构成“高”重传率取决于客户端：具有不可靠远程客户端的面向互联网的系统应该比客户端位于同一数据中心的内部系统具有更高的重传率。
- **`ip -s link/netstat -i`**：检查接口错误计数器，包括“错误”、“丢弃”、“溢出”。
- **`ss -tiepm`**：检查重要套接字的限制器标志，以了解其瓶颈是什么，以及显示套接字运行状况的其他统计信息。
- **`nicstat`/`ip -s link`**：检查发送和接收的字节速率。高吞吐量可能受到协商的数据链路速度或外部网络限制的限制。它还可能导致系统上的网络用户之间出现争用和延迟。
- **`tcplife`**：记录 TCP 会话，其中包含进程详细信息、持续时间（生命周期）和吞吐量统计信息。
- **`tcptop`**：实时查看最活跃的 TCP 会话。
- **`tcpdump`**：虽然就 CPU 和存储成本而言，使用该方法可能会很昂贵，但短期使用 tcpdump(8) 可能会帮助您识别异常的网络流量或协议标头。
- **perf(1)/BCC/bpftrace**：检查应用程序和线路之间选定的数据包，包括检查内核状态。

如果发现问题，请检查可用工具中的所有字段以了解更多背景信息。有关每个工具的更多信息，请参阅[第 10.6 节](#ch10-ch10lev6)、[可观测性工具](#ch10-ch10lev6)。其他方法可以识别更多类型的问题。

<!-- source-id: ch10#ch10lev5sec2 -->
### 10.5.2 USE 方法

USE 方法用于快速识别所有组件的瓶颈和错误。对于每个网络接口，以及每个方向（发送 (TX) 和接收 (RX)），检查：

- **利用率**：接口忙于发送或接收帧的时间
- **饱和**：由于接口利用率已达到 100%而导致的额外排队、缓冲或阻塞的程度
- **错误**：对于接收：校验和错误、帧太短（小于数据链路头）或太长、冲突（交换网络中不太可能发生）；对于传输：晚冲突（接线不良）

可以首先检查错误，因为它们通常可以快速检查并且最容易解释。

操作系统或监控工具通常不直接提供利用率（nicstat(1) 是一个例外）。它可以计算为每个方向（RX、TX）的当前吞吐量除以当前协商速度。当前吞吐量应以网络上每秒的字节数来衡量，包括所有协议标头。

对于实施网络带宽限制（资源控制）的环境（如在某些云计算环境中发生的情况），除了物理限制之外，还可能需要根据施加的限制来衡量网络利用率。

网络接口的饱和度很难测量。某些网络缓冲是正常的，因为应用程序发送数据的速度比接口传输数据的速度快得多。可以测量应用程序线程在网络发送上阻塞的时间，该时间应该随着饱和度的增加而增加。还要检查是否有其他与接口饱和度更密切相关的内核统计信息，例如 Linux“溢出”。请注意，Linux 使用 BQL 来调节 NIC 队列大小，这有助于避免 NIC 饱和。

TCP 级别的重传通常可以作为统计数据轻松获得，并且可以作为网络饱和度的指标。但是，它们是通过服务器与其客户端之间的网络进行测量的，并且可能是由任何跃点的问题引起的。

USE 方法还可以应用于网络控制器以及它们与处理器之间的传输。由于这些组件的可观测性工具很少，因此根据网络接口统计数据和拓扑推断指标可能更容易。例如，如果网络控制器 A 容纳端口 A0 和 A1，则网络控制器吞吐量可计算为接口吞吐量 A0 + A1 之和。有了已知的最大吞吐量，就可以计算网络控制器的利用率。

<!-- source-id: ch10#ch10lev5sec3 -->
### 10.5.3 工作负载特征

在进行容量规划、基准测试和模拟工作负载时，表征所应用的负载是一项重要的工作。通过识别可以消除的不必要的工作，它还可以带来一些最大的性能提升。

以下是要衡量的最基本特征：

- **网络接口吞吐量**：RX 和 TX，每秒字节数
- **网络接口 IOPS**：RX 和 TX，每秒帧数
- **TCP 连接速率**：主动和被动、每秒连接数

[第 10.4.1 节](#ch10-ch10lev4sec1)、[协议](#ch10-ch10lev4sec1)的“三次握手”部分中描述了术语“主动”和“被动”。

这些特征可能会随着时间的推移而变化，因为使用模式全天都在变化。[第 10.5.5 节](#ch10-ch10lev5sec5)、[性能监控](#ch10-ch10lev5sec5)中描述了随时间的监控。

下面是一个工作负载描述示例，展示了如何一起表达这些属性：

网络吞吐量因用户而异，并且执行的写入 (TX) 多于读取 (RX)。峰值写入速率为200Mbytes/s、21万包/秒，峰值读取速率为10Mbytes/s、7万包/秒。入站（被动）TCP 连接速率达到 3000 个连接/秒。

除了在系统范围内描述这些特征之外，它们还可以按接口来表达。如果可以观察到吞吐量已达到线路速率，则可以确定接口瓶颈。如果存在网络带宽限制（资源控制），它们可能会在达到线路速率之前限制网络吞吐量。

<!-- source-id: ch10#ch10lev3_26 -->
#### 高级工作负载特征/清单

可能会包含其他详细信息来描述工作负载的特征。此处列出了这些供考虑的问题，也可以作为彻底研究网络问题时的清单：

- 平均数据包大小是多少？接收、发送？
- 每层的协议细分是什么？对于传输协议：TCP、UDP（可以包括 QUIC）。
- 哪些 TCP/UDP 端口处于活动状态？每秒字节数、每秒连接数？
- 广播和组播数据包速率是多少？
- 哪些进程正在积极使用网络？

以下部分回答了其中一些问题。请参阅[第 2 章](#ch02-ch02)、[方法论](#ch02-ch02)，了解此方法的更高级别摘要以及要测量的特征（谁、为什么、什么、如何）。

### 10.5.4 延迟分析

可以研究各种时间（延迟）以帮助理解和表达网络性能。其中一些已在[第 10.3.5 节](#ch10-ch10lev3sec5)、[延迟](#ch10-ch10lev3sec5)中介绍，更长的列表见[表 10.3](#ch10-ch10tab03)。尽可能多地测量这些因素，以缩小延迟的真正来源范围。

<!-- source-id: ch10#ch10tab03 -->
**表 10.3 网络延迟**

| **延迟** | **描述** |
| --- | --- |
| 名称解析延迟 | 通常通过 DNS 解析将主机解析为 IP 地址的时间 — 这是性能问题的常见根源。 |
| Ping 延迟 | 从 ICMP 回显请求到响应的时间。这测量每台主机上数据包的网络和内核协议栈处理情况。 |
| TCP 连接初始化延迟 | 从发送 SYN 到收到 SYN-ACK 的时间。由于不涉及任何应用程序，因此这会测量每个主机上的网络和内核协议栈延迟，类似于 ping 延迟，并对 TCP 会话进行一些额外的内核处理。TCP Fast Open（TFO）可用于减少此延迟。 |
| TCP 第一个字节延迟 | 也称为第一个字节延迟时间 (TTFB)，它测量从建立连接到客户端收到第一个数据字节的时间。这包括主机的 CPU 调度和应用程序思考时间，使其比 TCP 连接延迟更能衡量应用程序性能和当前负载。 |
| TCP 重传 | 如果存在，可能会给网络 I/O 增加数千毫秒的延迟。 |
| TCP TIME\_WAIT 延迟 | 本地关闭的 TCP 会话等待延迟数据包的持续时间。 |
| 连接/会话生命周期 | 网络连接从初始化到关闭的持续时间。某些协议（例如 HTTP）可以使用持久连接（Keep-Alive）策略，使连接保持打开状态并空闲以供将来的请求，以避免重复建立连接的开销和延迟。 |
| 系统调用发送/接收延迟 | 套接字读/写调用（读/写套接字的任何系统调用，包括 read(2)、write(2)、recv(2)、send(2) 和变体）的时间。 |
| 系统调用连接延迟 | 用于连接建立；请注意，某些应用程序将其作为非阻塞系统调用来执行。 |
| 网络往返时间 | 网络请求在端点之间进行往返的时间。内核可以将此类测量与拥塞控制算法结合使用。 |
| 中断延迟 | 从网络控制器为接收的数据包发出中断，到内核处理该中断的时间。 |
| 协议栈处理延迟（inter-stack latency） | 数据包通过内核 TCP/IP 协议栈的时间。 |

延迟可以表示为：

- **每个时间间隔的平均值**：最好按每个客户端/服务器对分别测量，以隔离中间网络中的差异
- **完整分布**：作为直方图或热图
- **每操作延迟**：列出每个事件的详细信息，包括源和目标 IP 地址

问题的一个常见来源是 TCP 重传导致的延迟异常值的存在。这些可以使用完整分布或每个操作延迟跟踪来识别，包括通过过滤最小延迟阈值。

可以使用跟踪工具来测量延迟，对于某些延迟，可以使用套接字选项来测量。在 Linux 上，套接字选项包括用于传入数据包时间的 SO\_TIMESTAMP（以及用于纳秒分辨率的 SO\_TIMESTAMPNS）和用于每个事件时间戳的 SO\_TIMESTAMPING[\[Linux 20j\]](#ch10-ch10ref60)。SO\_TIMESTAMPING 可以识别传输延迟、网络往返时间和协议栈处理延迟；这在分析涉及隧道的复杂数据包延迟时特别有用[\[Hassas Yeganeh 19\]](#ch10-ch10ref49)。

请注意，某些额外延迟的来源是暂时的，仅在系统负载期间发生。为了更真实地测量网络延迟，不仅要测量空闲系统，还要测量负载下的系统，这一点很重要。

<!-- source-id: ch10#ch10lev5sec5 -->
### 10.5.5 性能监控

性能监控可以识别一段时间内的活动问题和行为模式，包括最终用户的日常模式以及包括网络备份在内的计划活动。

网络监控的关键指标是

- **吞吐量**：网络接口每秒接收和传输的字节数，理想情况下每个接口
- **连接数**：每秒 TCP 连接数，作为网络负载的另一个指示
- **错误**：包括丢弃数据包计数器
- **TCP 重传**：对于记录与网络问题的关联也很有用
- **TCP 无序数据包**：也可能导致性能问题

对于实施网络带宽限制（资源控制）的环境，如在某些云计算环境中，还可以收集与所施加的限制相关的统计数据。

<!-- source-id: ch10#ch10lev5sec6 -->
### 10.5.6 数据包嗅探

数据包嗅探（又名“数据包捕获”）涉及从网络捕获数据包，以便可以逐个数据包检查其协议标头和数据。对于可观测性分析，这可能是最后的手段，因为它的 CPU 和存储开销可能非常昂贵。网络内核代码路径通常是针对 CPU 周期数进行优化的，因为它们每秒需要处理多达数百万个数据包，并且对任何额外的开销都很敏感。为了减少这种开销，内核可以使用环形缓冲区通过共享内存映射将数据包数据传递到用户级跟踪工具——例如[^fn-ch10-ch10-footnote-10]，使用 BPF 和 perf(1) 的输出环形缓冲区，并且还使用 AF\_XDP[\[Linux 20k\]](#ch10-ch10ref61)。解决开销的另一种方法是使用带外数据包嗅探器：连接到交换机的“tap”或“mirror”端口的单独服务器。Amazon 和 Google 等公共云提供商将此作为服务提供[\[Amazon 19\]](#ch10-ch10ref43)[\[Google 20b\]](#ch10-ch10ref56)。

数据包嗅探通常涉及将数据包捕获到文件中，然后以不同的方式分析该文件。一种方法是生成日志，其中可以包含每个数据包的以下内容：

- 时间戳
- 整个数据包，包括
    - 所有协议标头（例如以太网、IP、TCP）
    - 部分或全部有效负载数据
- 元数据：数据包数量、丢弃数量
- 接口名称

```text
win 132, options [nop,nop,TS val 328647674 ecr 2313764394], length 336
[...]
```

此输出有一行总结了每个数据包，包括 IP 地址、TCP 端口和其他 TCP 标头详细信息的详细信息。这可用于调试各种问题，包括消息延迟和丢失数据包。

由于数据包捕获可能是一项消耗 CPU 资源的活动，因此大多数实现都具有在过载时丢弃事件而不是捕获事件的功能。丢弃的数据包的计数可能会包含在日志中。

除了使用环形缓冲区来减少开销之外，数据包捕获实现通常还允许用户提供过滤表达式并在内核中执行此过滤。这样可以通过不将不需要的数据包传输到用户级别来减少开销。过滤器表达式通常使用 Berkeley Packet Filter（BPF）进行优化，它将表达式编译为 BPF 字节码，该字节码可以由内核 JIT 编译为机器代码。近年来，BPF 已在 Linux 中扩展为通用执行环境，为许多可观测性工具提供支持：请参阅[第 3 章](#ch03-ch03)、[操作系统](#ch03-ch03)、[第 3.4.4 节](#ch03-ch03lev4sec4)、[扩展 BPF](#ch03-ch03lev4sec4)和[第 15 章](#ch15-ch15)、[BPF](#ch15-ch15)。

### 10.5.7 TCP 分析

除了[第 10.5.4 节](#ch10-ch10lev5sec4)、[延迟分析](#ch10-ch10lev5sec4)中介绍的内容之外，还可以研究其他特定的 TCP 行为，包括：

- TCP（套接字）发送/接收缓冲区的使用
- TCP 连接队列的使用
- 由于连接队列已满而发生的内核丢弃
- 拥塞窗口大小，包括零窗口通告
- 在 TCP TIME\_WAIT 间隔期间收到的 SYN

当一台服务器使用相同的源和目标 IP 地址频繁地连接到同一目标端口上的另一台服务器时，最后一种行为可能会成为可扩展性问题。每个连接的唯一区别因素是客户端源端口（*临时端口*），对于 TCP 来说，它是一个 16 位值，并且可能进一步受到操作系统参数（最小值和最大值）的限制。结合 TCP TIME\_WAIT 间隔（可能为 60 秒），高速率连接（60 秒内超过 65,536 个）可能会遇到新连接冲突。在这种情况下，在该临时端口仍与处于 TIME\_WAIT 状态的先前 TCP 会话关联时发送 SYN，并且如果新 SYN 被错误识别为旧连接的一部分（冲突），则可能会被拒绝。为了避免这个问题，Linux 内核尝试快速重用或回收连接（通常效果很好）。服务器使用多个 IP 地址是另一种可能的解决方案，就像具有较短延迟时间的 SO\_LINGER 套接字选项一样。

### 10.5.8 静态性能调优

静态性能调优重点关注配置环境的问题。对于网络性能，请检查静态配置的以下方面：

- 有多少个网络接口可供使用？目前有多少个正在使用？
- 网络接口的最大速度是多少？
- 网络接口当前协商的速度是多少？
- 网络接口协商为半双工还是全双工？
- 网络接口配置的 MTU 是多少？
- 网络接口是否已聚合？
- 设备驱动程序有哪些可调参数？IP 层？TCP 层？
- 是否有任何可调参数从默认值更改？
- 路由是如何配置的？默认网关是什么？
- 数据路径中网络组件（所有组件，包括交换机和路由器背板）的最大吞吐量是多少？
- 数据路径的最大 MTU 是多少？是否发生 IP 分片？
- 数据路径中是否有无线连接？他们是否受到干扰？
- 是否启用转发？该系统充当路由器吗？
- DNS 是如何配置的？服务器距离多远？
- 网络接口固件版本或任何其他网络硬件是否存在已知的性能问题（错误）？
- 网络设备驱动程序是否存在已知的性能问题（错误）？内核 TCP/IP 协议栈？
- 有哪些防火墙？
- 是否存在软件强加的网络吞吐量限制（资源控制）？这些是什么？

这些问题的答案可能会揭示被忽视的配置选择。

最后一个问题与云计算环境尤其相关，在云计算环境中，网络吞吐量可能受到限制。

### 10.5.9 资源控制

操作系统可以提供控制来限制连接类型、进程或进程组的网络资源。这些可以包括以下类型的控件：

- **网络带宽限制**：由内核应用的不同协议或应用程序允许的带宽（最大吞吐量）。
- **IP 服务质量 (QoS)**：网络流量的优先级，由网络组件（例如路由器）执行。这可以通过不同的方式实现：IP 标头包括服务类型 (ToS) 位，其中包括优先级；此后，这些位已针对较新的 QoS 方案进行了重新定义，包括区分服务（请参阅 IP 标题下的 [第 10.4.1 节](#ch10-ch10lev4sec1)、[协议](#ch10-ch10lev4sec1)）。出于相同的目的，其他协议层可能实现其他优先级。
- **数据包延迟**：额外的数据包延迟（例如，使用 Linux tc-netem(8)），可用于在测试性能时模拟其他网络。

您的网络可能具有可分为低优先级或高优先级的混合流量。低优先级可能包括备份和性能监控流量的传输。高优先级可能是生产服务器和客户端之间的流量。任一资源控制方案都可用于限制低优先级流量，为高优先级流量提供更有利的性能。

这些工作原理取决于实现：请参阅[第 10.8 节](#ch10-ch10lev8)、[调优](#ch10-ch10lev8)。

### 10.5.10 微基准测试

有许多网络基准测试工具。在调查分布式应用程序环境的吞吐量问题时，它们特别有用，以确认网络至少可以达到预期的网络吞吐量。如果不能，可以通过网络微基准测试工具来调查网络性能，该工具通常比应用程序简单得多且调试速度更快。将网络调整到所需的速度后，注意力可以返回到应用程序。

可以测试的典型因素包括：

- **方向**：发送或接收
- **协议**：TCP 或 UDP，以及端口
- **线程数**
- **缓冲区大小**
- **接口 MTU 大小**

更快的网络接口（例如 100 Gbits/s）可能需要多个客户端线程，才能将网络接口驱动到最大带宽。

[第 10.7.4 节](#ch10-ch10lev7sec4)、[iperf](#ch10-ch10lev7sec4)中介绍了一个示例网络微基准测试工具 iperf(1)，[第 10.7 节](#ch10-ch10lev7)、[实验](#ch10-ch10lev7)中列出了其他示例。

### 10.6.1 ss

ss(8) 是一个套接字统计工具，用于汇总打开的套接字。默认输出提供有关套接字的高级信息，例如：

![点此查看代码图片](../images/pg534.jpg)

```text
# ss
Netid State     Recv-Q  Send-Q    Local Address:Port      Peer Address:Port
[...]
tcp   ESTAB     0       0         100.85.142.69:65264    100.82.166.11:6001
tcp   ESTAB     0       0         100.85.142.69:6028     100.82.16.200:6101
[...]
```

此输出是当前状态的快照。第一列显示套接字使用的协议：这些是 TCP。由于此输出列出了所有已建立的连接以及 IP 地址信息，因此它可用于表征当前工作负载，并回答包括打开了多少客户端连接、依赖服务有多少并发连接等问题。

使用较旧的 netstat(8) 工具可以获得类似的每个套接字信息。然而，ss(8) 在使用选项时可以显示更多信息。例如，仅显示 TCP 套接字 (`-t`)，以及 TCP 内部信息 (`-i`)、扩展套接字信息 (`-e`)、进程信息 (`-p`) 和内存使用情况 (`-m`)：

![点此查看代码图片](../images/pg535.jpg)

```text
# ss -tiepm
State     Recv-Q  Send-Q    Local Address:Port      Peer Address:Port

ESTAB     0       0         100.85.142.69:65264     100.82.166.11:6001
 users:(("java",pid=4195,fd=10865)) uid:33 ino:2009918 sk:78 <->
         skmem:(r0,rb12582912,t0,tb12582912,f266240,w0,o0,bl0,d0) ts sack bbr ws
cale:9,9 rto:204 rtt:0.159/0.009 ato:40 mss:1448 pmtu:1500 rcvmss:1448 advmss:14

data_segs_out:294 data_segs_in:1318 bbr:(bw:328.6Mbps,mrtt:0.149,pacing_gain:2.8
8672,cwnd_gain:2.88672) send 11074.0Mbps lastsnd:1696 lastrcv:1660 lastack:1660
pacing_rate 2422.4Mbps delivery_rate 328.6Mbps app_limited busy:16ms rcv_rtt:39.
822 rcv_space:84867 rcv_ssthresh:3609062 minrtt:0.139
[...]
```

以粗体突出显示的是端点地址和以下详细信息：

- **`"java",pid=4195`**：进程名称“java”，PID 4195。
- **`fd=10865`**：文件描述符 10865（对于 PID 4195）。
- **`rto:204`**：TCP 重传超时：204 毫秒。
- **`rtt:0.159/0.009`**：平均往返时间为 0.159 毫秒，平均偏差为 0.009 毫秒。
- **`mss:1448`**：最大段大小：1448 字节。
- **`cwnd:152`**：拥塞窗口大小：152 × MSS。
- **`bytes_acked:347681`**：340 KB 成功传输。
- **`bytes_received:1798733`**：收到 1.72 MB。
- **`bbr:...`**：BBR 拥塞控制统计信息。
- **`pacing_rate 2422.4Mbps`**：调速速率为 2422.4 Mbps。
- **`app_limited`**：显示拥塞窗口未充分利用，表明连接受应用程序限制。
- **`minrtt:0.139`**：最小往返时间（以毫秒为单位）。与平均值和平均偏差（前面列出）进行比较，了解网络变化和拥塞情况。

此特定连接被标记为应用程序限制 (`app_limited`)，到远程端点的 RTT 较低，传输的总字节数较低。 ss(1) 可以打印的可能的“有限”标志是：

- **`app_limited`**：受应用程序限制。
- **`rwnd_limited:Xms`**：受接收窗口限制。包括以毫秒为单位的受限持续时间。
- **`sndbuf_limited:Xms`**：受发送缓冲区限制。包括以毫秒为单位的受限持续时间。

输出中缺少的一个细节是连接建立至今的时间，计算平均吞吐量需要它。我发现的一个解决方法是在 /proc 中的文件描述符文件上使用更改时间戳：对于此连接，我将在 /proc/4195/fd/10865 上运行 stat(1)。

```text
    26550075   273178   0       0       0       0

    link/ether 12:c0:0a:b0:21:b8 brd ff:ff:ff:ff:ff:ff
    RX: bytes  packets  errors  dropped overrun mcast

    TX: bytes  packets  errors  dropped carrier collsns
    573510263433 668110321 0       0       0       0
```

在静态性能调整期间检查所有接口的配置非常有用，可以检查是否存在错误配置。输出中还包含错误指标：对于接收 (`RX`)：接收错误、丢弃和溢出；对于传输 (`TX`)：传输错误、丢包、载波错误和冲突。此类错误可能是性能问题的根源，并且根据错误的不同，可能是由网络硬件故障引起的。这些是全局计数器，显示自接口激活以来的所有错误（用网络术语来说，它被“UP”）。

### 10.6.5 netstat

netstat(8) 命令根据使用的选项报告各种类型的网络统计信息。它就像一个具有多种不同功能的多功能工具。其中包括以下内容：

- **（默认）**：列出已连接的套接字
- **`-a`**：列出所有套接字的信息
- **`-s`**：网络协议栈统计信息
- **`-i`**：网络接口统计信息
- **`-r`**：列出路由表

其他选项可以修改输出，包括 `-n`（不将 IP 地址解析为主机名）以及 `-v`（在可用时提供详细信息）。

间隔（以秒为单位）可以与 netstat(8) 一起使用，以便它在每个间隔连续打印累积计数器。然后可以对该输出进行后处理以计算每个计数器的速率。

创建 udplife(8) 来跟踪 UDP 会话是 *BPF 性能工具*一书中的[第 10 章](#ch10-ch10)练习[\[Gregg 19\]](#ch10-ch10ref45)；我已经发布了一个初始解决方案[\[Gregg 19d\]](#ch10-ch10ref48)。

### 10.6.11 tcpretrans

tcpretrans(8)[^fn-ch10-ch10-footnote-16] 是一个 BCC 和 bpftrace 工具，用于跟踪 TCP 重传，显示 IP 地址和端口详细信息以及 TCP 状态。以下显示了生产实例上来自 BCC 的 tcpretrans(8)：

![点此查看代码图片](../images/pg548.jpg)

```text
# tcpretrans
Tracing retransmits ... Hit Ctrl-C to end
TIME     PID    IP LADDR:LPORT         T> RADDR:RPORT         STATE
00:20:11 72475  4  100.1.58.46:35908   R> 100.2.0.167:50010   ESTABLISHED
00:20:11 72475  4  100.1.58.46:35908   R> 100.2.0.167:50010   ESTABLISHED
00:20:11 72475  4  100.1.58.46:35908   R> 100.2.0.167:50010   ESTABLISHED
00:20:12 60695  4  100.1.58.46:52346   R> 100.2.6.189:50010   ESTABLISHED
00:20:12 60695  4  100.1.58.46:52346   R> 100.2.6.189:50010   ESTABLISHED
00:20:12 60695  4  100.1.58.46:52346   R> 100.2.6.189:50010   ESTABLISHED
00:20:12 60695  4  100.1.58.46:52346   R> 100.2.6.189:50010   ESTABLISHED
00:20:13 60695  6  ::ffff:100.1.58.46:13562 R> ::ffff:100.2.51.209:47356 FIN_WAIT1
00:20:13 60695  6  ::ffff:100.1.58.46:13562 R> ::ffff:100.2.51.209:47356 FIN_WAIT1
[...]
```

此输出显示重传率较低，每秒几次（TIME 列），这主要针对处于 ESTABLISHED 状态的会话。 ESTABLISHED 状态的高速率可能表明存在外部网络问题。 SYN\_SENT 状态的高速率可能表明服务器应用程序过载，无法足够快地消耗其 SYN 队列。

这是通过跟踪内核中的 TCP 重传事件来实现的。由于这些应该很少发生，因此开销应该可以忽略不计。与此相比，历史上如何使用数据包嗅探器捕获所有数据包来分析重传，然后进行后处理以查找重传，这两个步骤都会消耗大量的 CPU 开销。数据包捕获只能看到线路上的详细信息，而 tcpretrans(8) 直接从内核打印 TCP 状态，并且可以根据需要进行增强以打印更多内核状态。

BCC 版本的选项包括：

- **`-l`**：包括尾部丢失探测尝试（为 tcp\_send\_loss\_probe() 添加 kprobe）
- **`-c`**：每个流的重传计数

`-c` 选项更改 tcpretrans(8) 的行为，使其打印计数摘要而不是每个事件的详细信息。

### 10.6.12 bpftrace

bpftrace 是一种基于 BPF 的跟踪器，它提供了一种高级编程语言，允许创建强大的单行代码和短脚本。它非常适合根据其他工具的线索进行自定义网络分析。它可以检查内核和应用程序内的网络事件，包括套接字连接、套接字 I/O、TCP 事件、数据包传输、队列溢出丢弃、TCP 重传和其他详细信息。这些功能支持工作负载表征和延迟分析。

bpftrace 在[第 15 章](#ch15-ch15)中进行了说明。本节展示一些网络分析示例：单行命令、套接字跟踪和 TCP 跟踪。

#### 套接字跟踪

在套接字层跟踪网络事件的优点是负责的进程仍在 CPU 上，从而可以直接识别负责的应用程序和代码路径。例如，统计调用 accept(2) 系统调用的应用程序：

![点此查看代码图片](../images/pg552-6.jpg)

```text
Attaching 1 probe...
^C

@[573, sshd]: 2
@[1948, mysqld]: 41
```

输出显示，在跟踪期间，mysqld 调用了 accept(2) 41 次，sshd 调用了 accept(2) 2 次。

可以包含堆栈跟踪以显示导致 accept(2) 的代码路径。例如，通过用户级堆栈跟踪和进程名称进行计数：

![点此查看代码图片](../images/pg552-7.jpg)

```text
Attaching 1 probe...
^C
@[

    accept+79
    Mysqld_socket_listener::listen_for_connection_event()+283
    mysqld_main(int, char**)+15577
    __libc_start_main+243
    0x49564100fe8c4b3d
```

此输出显示 mysqld 正在通过包含 Mysqld\_socket\_listener::listen\_for\_connection\_event() 的代码路径接受连接。通过将“accept”更改为“connect”，这一行代码将识别通向 connect(2) 的代码路径。我用这样的单行命令来解释神秘的网络连接，并显示调用它们的代码路径。

![点此查看代码图片](../images/pg553-3.jpg)

```text
#!/usr/local/bin/bpftrace

#include <net/sock.h>

kprobe:sock_recvmsg
{
        $sock = (struct socket *)arg0;
        $dport = $sock->sk->__sk_common.skc_dport;
        $dport = ($dport >> 8) | (($dport << 8) & 0xff00);
        @io[comm, pid, "read", $sock->sk->__sk_common.skc_prot->name, $dport] =
            count();
}

kprobe:sock_sendmsg
{
        $sock = (struct socket *)arg0;
        $dport = $sock->sk->__sk_common.skc_dport;
        $dport = ($dport >> 8) | (($dport << 8) & 0xff00);
        @io[comm, pid, "write", $sock->sk->__sk_common.skc_prot->name, $dport] =
            count();
}
```

这是从内核结构（在本例中为 struct socket）获取详细信息的示例，它提供协议名称和目标端口。目标端口是大端字节序，并在包含在 @io 映射之前由工具转换为小端字节序（对于此 x86 处理器）。[^fn-ch10-ch10-footnote-18] 可以修改此脚本以显示传输的字节而不是 I/O 计数。

#### TCP 跟踪

TCP 级别的跟踪提供了对 TCP 协议事件和内部结构以及与套接字无关的事件（例如 TCP 端口扫描）的洞察。

##### TCP 跟踪点

对 TCP 内部结构进行插桩通常需要使用 kprobes，但有一些可用的 TCP 跟踪点。以下来自一个 5.3 内核：

![点此查看代码图片](../images/pg554-1.jpg)

```text
# bpftrace -l 't:tcp:*'
tracepoint:tcp:tcp_retransmit_skb
tracepoint:tcp:tcp_send_reset
tracepoint:tcp:tcp_receive_reset
tracepoint:tcp:tcp_destroy_sock
tracepoint:tcp:tcp_rcv_space_adjust
tracepoint:tcp:tcp_retransmit_synack
tracepoint:tcp:tcp_probe
```

tcp:tcp\_retransmit\_skb 跟踪点由前文的 tcpretrans(8) 工具使用。跟踪点因其稳定性而更可取，但是当它们无法解决您的问题时，您可以在内核 TCP 函数上使用 kprobes。统计这些函数的调用次数：

![点击查看代码图片](../images/pg554-2.jpg)

tcpsynbl(8) 的源代码是：

![点击查看代码图片](../images/pg555-2.jpg)

```text
#!/usr/local/bin/bpftrace

#include <net/sock.h>

BEGIN
{
        printf("Tracing SYN backlog size. Ctrl-C to end.\n");
}

kprobe:tcp_v4_syn_recv_sock,
kprobe:tcp_v6_syn_recv_sock
{
        $sock = (struct sock *)arg0;
        @backlog[$sock->sk_max_ack_backlog & 0xffffffff] =
            hist($sock->sk_ack_backlog);
        if ($sock->sk_ack_backlog > $sock->sk_max_ack_backlog) {
                time("%H:%M:%S dropping a SYN.\n");
        }
}

END
{
        printf("\n@backlog[backlog limit]: histogram of backlog size\n");
}
```

前面打印的分布的形状与 hist() 使用的 log2 尺度有很大关系，其中后来的桶跨越更大的范围。您可以使用以下方法将 hist() 更改为 lhist()：

![点击查看代码图片](../images/pg556.jpg)

```text
            lhist($sock->sk_ack_backlog, 0, 1000, 10);
```

这将为每个存储桶打印一个等宽范围的线性直方图：在本例中，范围为 0 到 1000，存储桶大小为 10。有关更多 bpftrace 编程，请参阅[第 15 章](#ch15-ch15)、[BPF](#ch15-ch15)。

## 10.7 实验

网络性能通常使用执行实验的工具进行测试，而不仅仅是观察系统的状态。此类实验工具包括 ping(8)、traceroute(8) 和 iperf(8) 等网络微基准测试。这些工具可用于确定主机之间的网络运行状况，从而在调试应用程序性能问题时帮助判断端到端网络吞吐量是否存在问题。

<!-- source-id: ch10#ch10lev7sec1 -->
### 10.7.1 ping

ping(8) 命令通过发送 ICMP 回显请求数据包来测试网络连接。例如：

![点此查看代码图片](../images/pg558-2.jpg)

```text
# ping www.netflix.com

bytes
64 bytes from 2620:108:700f::3423:46a1 (2620:108:700f::3423:46a1): icmp_seq=1 ttl=43
time=32.3 ms
64 bytes from 2620:108:700f::3423:46a1 (2620:108:700f::3423:46a1): icmp_seq=2 ttl=43
time=34.3 ms
64 bytes from 2620:108:700f::3423:46a1 (2620:108:700f::3423:46a1): icmp_seq=3 ttl=43 time=34.0 ms

```

输出包括每个数据包的往返时间 (`time`)，并提供显示各种统计信息的摘要。

旧版本的 ping(8) 测量从用户空间的往返时间，由于内核执行和调度程序延迟，时间略有增加。较新的内核和 ping(8) 版本使用内核时间戳支持（SIOCGSTAMP 或 SO\_TIMESTAMP）来提高报告 ping 时间的准确性。

路由器可能会以低于应用程序协议的优先级处理所使用的 ICMP 数据包，并且延迟可能会表现出比平常更高的变化。[^fn-ch10-ch10-footnote-20]

### 10.7.2 traceroute

traceroute(8) 命令发送一系列测试数据包，以通过实验确定到主机的当前路由。这是通过将每个数据包的 IP 协议生存时间（TTL）增加 1 来执行的，从而导致沿途网关通过发送 ICMP 超时响应消息来暴露自身（前提是防火墙不阻止它们）。

例如，测试从加利福尼亚主机到我的网站的当前路由：

### 10.7.3 pathchar

pathchar 与 traceroute(8) 类似，但还会估计跃点之间的带宽。这是通过多次发送一系列不同大小的网络数据包并进行统计分析来确定的。这是示例输出：

### 10.7.4 iperf

iperf(1) 是一个用于测试最大 TCP 和 UDP 吞吐量的开源工具。它支持多种选项，包括使用多个客户端线程的并行模式，这可能是驱动网络达到极限所必需的。iperf(1) 必须在服务器和客户端上执行。

例如，在服务器上执行 iperf(1)：

![点击查看代码图片](../images/pg563.jpg)

```text
$ iperf -s -l 128k
------------------------------------------------------------

TCP window size: 85.3 KByte (default)
------------------------------------------------------------
```

这将套接字缓冲区大小从默认的 8 KB 增加到 128 KB（`-l 128k`）。

在客户端执行如下：

### 10.7.6 tc

流量控制实用程序 tc(8) 允许选择各种排队规则（qdisc）以提高或管理性能。对于实验，还有一些 qdisc 可以限制或扰乱性能，这对于测试和模拟非常有用。本节演示网络模拟器（netem）qdisc。

首先，以下命令列出接口 eth0 的当前 qdisc 配置：

![点击查看代码图片](../images/pg565-1.jpg)

```text
# tc qdisc show dev eth0
qdisc noqueue 0: root refcnt 2
```

现在将添加 netem qdisc。每个 qdisc 支持不同的可调参数。对于此示例，我将使用 netem 的丢包参数，并将丢包率设置为 1%：

![点击查看代码图片](../images/pg565-2.jpg)

```text
# tc qdisc add dev eth0 root netem loss 1%
# tc qdisc show dev eth0
qdisc netem 8001: root refcnt 2 limit 1000 loss 1%
```

eth0 上的后续网络 I/O 现在将遭受 1% 的数据包丢失。

tc(8) 的 `-s` 选项显示统计信息：

![点击查看代码图片](../images/pg566-1.jpg)

```text
# tc -s qdisc show dev eth0
qdisc netem 8001: root refcnt 2 limit 1000 loss 1%
 Sent 75926119 bytes 89538 pkt (dropped 917, overlimits 0 requeues 0)
 backlog 0b 0p requeues 0
```

此输出显示丢弃数据包的数量。

要删除 qdisc：

![点击查看代码图片](../images/pg566-2.jpg)

```text
# tc qdisc del dev eth0 root
# tc qdisc show dev eth0
qdisc noqueue 0: root refcnt 2
```

有关选项的完整列表，请参阅每个 qdisc 的手册页（对于 netem，手册页为 tc-netem(8)）。

## 10.8 调优

网络可调参数通常已经被调整以提供高性能。网络协议栈通常还设计为动态响应不同的工作负载，以提供最佳性能。

在尝试可调参数之前，首先了解网络使用情况是值得的。这还可以识别可以消除的不必要的工作，从而获得更大的性能提升。使用上一节中的工具尝试工作负载表征和静态性能调整方法。

可用的可调参数因操作系统版本而异。请参阅相应的文档。以下部分介绍可用的参数以及调整思路；应将它们视为根据您的工作负载和环境进行修改的起点。

<!-- source-id: ch10#ch10lev8sec1 -->
### 10.8.1 系统范围

在 Linux 上，可以使用 sysctl(8) 命令查看和设置系统范围的可调参数，并将其写入 /etc/sysctl.conf。还可以从 /proc/sys/net 下的 /proc 文件系统读取和写入它们。

例如，要查看当前可用于 TCP 的内容，可以从 sysctl(8) 中搜索参数以查找文本“tcp”：

![点此查看代码图片](../images/pg566-3.jpg)

```text
# sysctl -a | grep tcp
net.ipv4.tcp_abort_on_overflow = 0
net.ipv4.tcp_adv_win_scale = 1
net.ipv4.tcp_allowed_congestion_control = reno cubic
net.ipv4.tcp_app_win = 31
net.ipv4.tcp_autocorking = 1
net.ipv4.tcp_available_congestion_control = reno cubic
net.ipv4.tcp_available_ulp =
net.ipv4.tcp_base_mss = 1024
net.ipv4.tcp_challenge_ack_limit = 1000
net.ipv4.tcp_comp_sack_delay_ns = 1000000
net.ipv4.tcp_comp_sack_nr = 44
net.ipv4.tcp_congestion_control = cubic
net.ipv4.tcp_dsack = 1
[...]
```

在此内核 (5.3) 上，有 70 个名称包含“tcp”的参数，还有更多位于“net.”下的参数。包括 IP、以太网、路由和网络接口的参数。

其中一些设置可以针对每个套接字进行调整。例如，net.ipv4.tcp\_congestion\_control 是系统范围内的默认拥塞控制算法，可以使用 TCP\_CONGESTION 套接字选项为每个套接字设置该算法（请参阅[第 10.8.2 节](#ch10-ch10lev8sec2)、[套接字选项](#ch10-ch10lev8sec2)）。

#### 生产示例

以下显示了 Netflix 如何调整其云实例 [\[Gregg 19c\]](#ch10-ch10ref47)；它在引导期间应用在启动脚本中：

![点击查看代码图片](../images/pg566-4.jpg)

```text
net.core.default_qdisc = fq

net.core.wmem_max = 16777216
net.ipv4.ip_local_port_range = 10240 65535
```

这仅设置了 14 个可能的可调参数，并且作为某一时点的示例提供，而不是配方。Netflix 正在考虑在 2020 年更新其中两个（将 net.core.netdev\_max\_backlog 设置为 1000，将 net.core.somaxconn 设置为 4096）[^fn-ch10-ch10-footnote-21]，有待性能防退化测试验证。

以下部分讨论各个可调参数。

<!-- source-id: ch10#ch10lev3_35 -->
#### 套接字和 TCP 缓冲区

所有协议类型的最大套接字缓冲区大小（对于读取 (`rmem_max`) 和写入 (`wmem_max`)）可以使用以下命令进行设置：

```text
net.core.rmem_max = 16777216
net.core.wmem_max = 16777216
```

该值以字节为单位。这可能需要设置为 16 MB 或更高才能支持全速 10 GbE 连接。

启用 TCP 接收缓冲区的自动调整：

![点此查看代码图片](../images/pg567.jpg)

```text
net.ipv4.tcp_moderate_rcvbuf = 1
```

设置 TCP 读写缓冲区的自动调整参数：

![点此查看代码图片](../images/pg568.jpg)

```text
net.ipv4.tcp_rmem = 4096 87380 16777216
net.ipv4.tcp_wmem = 4096 65536 16777216
```

每个参数都有三个值：要使用的最小字节数、默认字节数和最大字节数。使用的大小是根据默认值自动调整的。要提高 TCP 吞吐量，请尝试增加最大值。增加最小值和默认值将消耗每个连接更多的内存，这可能是没有必要的。

<!-- source-id: ch10#ch10lev3_36 -->
#### TCP 连接队列

第一个连接队列，即 SYN 队列，用于尚未完成握手的连接：

![点击查看代码图片](../images/pg569-2.jpg)

```text
net.ipv4.tcp_max_syn_backlog = 4096
```

第二个连接队列，即监听队列，用于存放等待 accept(2) 接受的已建立连接：

```text
net.core.somaxconn = 1024
```

这两个值可能都需要从默认值增加到例如 4,096 和 1,024 或更高，以更好地处理负载突发。

<!-- source-id: ch10#ch10lev3_37 -->
#### 网络设备接收队列

增加每个 CPU 的网络设备接收队列的长度：

![点此查看代码图片](../images/pg569-3.jpg)

```text
net.core.netdev_max_backlog = 10000
```

对于 10 GbE NIC，这可能需要增加，例如增加到 10,000。

<!-- source-id: ch10#ch10lev3_38 -->
#### TCP 拥塞控制

Linux 支持可插入的拥塞控制算法。列出当前可用的：

![点此查看代码图片](../images/pg569-4.jpg)

```text
# sysctl net.ipv4.tcp_available_congestion_control
net.ipv4.tcp_available_congestion_control = reno cubic
```

有些可能可用但当前未加载。例如添加htcp：

![点击查看代码图片](../images/pg569-5.jpg)

```text
# modprobe tcp_htcp
# sysctl net.ipv4.tcp_available_congestion_control
net.ipv4.tcp_available_congestion_control = reno cubic htcp
```

可以使用以下方式选择当前算法：

![点击查看代码图片](../images/pg570-1.jpg)

```text
net.ipv4.tcp_congestion_control = cubic
```

<!-- source-id: ch10#ch10lev3_39 -->
#### TCP 选项

其他可以设置的 TCP 参数包括：

```text
net.ipv4.tcp_sack = 1
net.ipv4.tcp_fack = 1
net.ipv4.tcp_tw_reuse = 1
net.ipv4.tcp_tw_recycle = 0
```

SACK 和 FACK 扩展可以提高高延迟网络的吞吐量性能，但会增加一些 CPU 负载。

`tcp_tw_reuse` 可调参数允许在安全的情况下重用 TIME\_WAIT 会话。这可以允许两个主机之间（例如 Web 服务器和数据库之间）实现更高的连接速率，而不会因 TIME\_WAIT 会话而达到 16 位临时端口限制。

`tcp_tw_recycle` 是重用 TIME\_WAIT 会话的另一种方法，尽管不如 `tcp_tw_reuse` 安全。

<!-- source-id: ch10#ch10lev3_40 -->
#### ECN

可以使用以下方式控制显式拥塞通知：

```text
net.ipv4.tcp_ecn = 1
```

值为 0 时禁用 ECN，值为 1 时允许传入连接使用 ECN并在传出连接上请求 ECN，值为 2 时允许传入连接使用 ECN，但在传出连接时不请求 ECN。默认值为 2。

还有 net.ipv4.tcp\_ecn\_fallback，默认设置为 1（true）；如果内核检测到连接行为不当，它将禁用该连接的 ECN。

<!-- source-id: ch10#ch10lev3_41 -->
#### 字节队列限制

这可以通过 /sys 进行调整。显示这些限制的控制文件的内容（此输出中截断的路径对于您的系统和接口将有所不同）：

![点此查看代码图片](../images/pg570-2.jpg)

```text
# grep . /sys/devices/pci.../net/ens5/queues/tx-0/byte_queue_limits/limit*
/sys/devices/pci.../net/ens5/queues/tx-0/byte_queue_limits/limit:16654
/sys/devices/pci.../net/ens5/queues/tx-0/byte_queue_limits/limit_max:1879048192
/sys/devices/pci.../net/ens5/queues/tx-0/byte_queue_limits/limit_min:0
```

该接口的限制为 16654 字节，由自动调整设置。要控制该值，请设置 limit\_min 和 limit\_max 以限制可接受的范围。

<!-- source-id: ch10#ch10lev3_42 -->
#### 资源控制

容器组（cgroups）的网络优先级（net\_prio）子系统可用于对进程或进程组的传出网络流量应用优先级。这可用于优先支持高优先级网络流量（例如生产负载），而不是低优先级流量（例如备份或监控）。还有网络分类器（net\_cls）cgroup，用于使用类 ID 标记属于 cgroup 的数据包；然后，这些 ID 可以由排队规则用于应用数据包或带宽限制，也可以由 BPF 程序使用。BPF 程序还可以使用其他信息（例如 cgroup v2 ID）来进行容器感知，并且可以通过将分类、测量和重新标记移至 tc egress hook 来提高可扩展性，从而减轻根 qdisc 锁的压力[\[Fomichev 20\]](#ch10-ch10ref55)。

有关资源控制的更多信息，请参阅[第 11 章](#ch11-ch11)、[云计算](#ch11-ch11)、[第 11.3.3 节](#ch11-ch11lev3sec3)、[资源控制](#ch11-ch11lev3sec3)中关于网络 I/O 的内容。

<!-- source-id: ch10#ch10lev3_43 -->
#### 排队规则

排队规则（qdisc）在[第 10.4.3 节](#ch10-ch10lev4sec3)、[软件](#ch10-ch10lev4sec3)中进行了描述，并在[图 10.8](#ch10-ch10fig08)中进行了图示。它是用于调度、操作、过滤和整形网络数据包的算法。[第 10.7.6 节](#ch10-ch10lev7sec6)、[tc](#ch10-ch10lev7sec6)展示了使用 netem qdisc 来创建数据包丢失。还有各种 qdisc 可以提高不同工作负载的性能。您可以使用以下命令列出系统上的 qdisc：

```text
# man -k tc-
```

每个 qdisc 都有自己的手册页。qdisc 可用于设置数据包速率或带宽策略、设置 IP ECN 标志等。

可以使用以下命令查看和设置默认 qdisc：

![点击查看代码图片](../images/pg570-3.jpg)

```text

net.core.default_qdisc = fq_codel
```

许多 Linux 发行版已经切换到 fq\_codel 作为默认值，因为它在大多数情况下提供了良好的性能。

### 10.8.2 套接字选项

应用程序可以通过 setsockopt(2) 系统调用单独调优套接字。这只有在您正在开发或重新编译软件并且可以修改源代码时才可能实现。[^fn-ch10-ch10-footnote-22]

setsockopt(2) 允许调优不同的层（例如套接字、TCP）。[表 10.8](#ch10-ch10tab08)显示了 Linux 上的一些调优选项。

<!-- source-id: ch10#ch10tab08 -->
**表 10.8 套接字选项示例**

| **选项名称** | **描述** |
| --- | --- |
| SO\_SNDBUF、SO\_RCVBUF | 发送和接收缓冲区大小（这些可以调整到前面描述的系统限制；还有 SO\_SNDBUFFORCE 来覆盖发送限制）。 |
| SO\_REUSEPORT | 允许多个进程或线程绑定到同一端口，允许内核在它们之间分配负载以实现可扩展性（自 Linux 3.9 起）。 |
| SO\_MAX\_PACING\_RATE | 设置最大调速速率，以每秒字节数为单位（请参阅 tc-fq(8)）。 |
| SO\_LINGER | 可用于减少 TIME\_WAIT 延迟。 |
| SO\_TXTIME | 请求基于时间的数据包传输，可以提供截止时间（自 Linux 4.19 起）[\[Corbet 18c\]](#ch10-ch10ref36)（用于 UDP 调速[\[Bruijn 18\]](#ch10-ch10ref34)）。 |
| TCP\_NODELAY | 禁用 Nagle，尽快发送段。这可能会改善延迟，但代价是更高的网络利用率（更多数据包）。 |
| TCP\_CORK | 暂停传输，直到可以发送完整的数据包，从而提高吞吐量。（内核还有一个系统范围的设置来自动尝试 corking：net.ipv4.tcp\_autocorking。） |
| TCP\_QUICKACK | 立即发送 ACK（可以增加发送带宽）。 |
| TCP\_CONGESTION | 套接字的拥塞控制算法。 |

有关可用的套接字选项，请参见 socket(7)、tcp(7)、udp(7) 等的手册页。

还有一些套接字 I/O 系统调用标志可能会影响性能。例如，Linux 4.14 为 send(2) 系统调用添加了 MSG\_ZEROCOPY 标志：它允许在传输期间使用用户空间缓冲区，以避免将其复制到内核空间的开销[^fn-ch10-ch10-footnote-23] \[Linux 20c\]。

<!-- source-id: ch10#ch10lev8sec3 -->
### 10.8.3 配置

以下配置选项也可用于调整网络性能：

- **以太网巨型帧**：如果网络基础设施支持巨型帧，则将默认 MTU 从 1,500 增加到 ~9,000 可以提高网络吞吐量性能。
- **链路聚合**：多个网络接口可以组合在一起，以便它们充当具有组合带宽的一个。这需要交换机支持和配置才能正常工作。
- **防火墙配置**：例如，出口挂钩上的 iptables 或 BPF 程序可用于根据防火墙规则设置 IP 标头中的 IP ToS (DSCP) 级别。这可用于根据端口以及其他用例对流量进行优先级排序。

## 10.9 练习

1. 回答下列有关网络术语的问题：
    - 带宽和吞吐量有什么区别？
    - 什么是 TCP 连接延迟？
    - 什么是首字节延迟？
    - 什么是往返时间？
2. 回答以下概念性问题：
    - 描述网络接口利用率和饱和度。
    - 什么是 TCP 监听队列，它有什么用途？
    - 描述中断合并的优点和缺点。
3. 回答以下更深层次的问题：
    - 对于 TCP 连接，解释网络帧（或数据包）错误如何影响性能。
    - 描述当网络接口工作过载时会发生什么，包括对应用程序性能的影响。
4. 为您的操作系统制定以下过程：
    - 网络资源（网络接口和控制器）的 USE 方法清单。包括如何获取每个指标（例如要执行哪个命令）以及如何解释结果。在安装或使用其他软件产品之前，尝试使用现有的操作系统可观测性工具。
5. 网络资源的工作负载特征检查表。包括如何执行这些任务（可能需要使用动态跟踪）：
    - 测量出站（主动）TCP 连接的第一个字节延迟。
    - 测量 TCP 连接延迟。该脚本应该处理非阻塞 connect(2) 调用。
6. （可选，高级）测量 RX 和 TX 方向的 TCP/IP 协议栈处理延迟（inter-stack latency）。接收方向（RX）测量从中断到套接字读取的时间；发送方向（TX）测量从套接字写入到设备发送的时间。在负载下测试。能否加入更多信息，以解释延迟异常值的成因？

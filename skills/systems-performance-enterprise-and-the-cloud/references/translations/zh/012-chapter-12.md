# 第 12 章 — 基准测试

> *有谎言、该死的谎言，然后还有性能指标。*

—Anon 等人，“交易处理能力的衡量标准”\[Anon 85\]

基准测试以受控方式测试性能，允许在生产中遇到性能限制之前对选择进行比较、识别回归并了解性能限制。这些限制可能是系统资源、虚拟化环境（云计算）中的软件限制或目标应用程序中的限制。前面的章节已经探讨了这些组件，描述了存在的限制类型以及用于分析它们的工具。

前面的章节还介绍了*微基准测试*工具，这些工具使用文件系统 I/O 等简单的人工工作负载来测试组件。还有*宏基准测试*，它模拟客户端工作负载来测试整个系统。宏基准测试可能涉及客户端工作负载模拟或跟踪重放。无论您使用哪种类型，分析基准测试都很重要，这样才能确认实际测量的内容。基准测试只能告诉您系统运行该基准的速度；您需要理解结果，并确定它如何应用于您的环境。

本章的学习目标是：

- 了解微基准测试和宏基准测试。
- 了解要避免的众多基准测试失败。
- 遵循主动基准测试方法。
- 使用基准检查清单来检查结果。
- 提高执行和解读基准测试的准确性。

本章一般性地讨论基准测试，提供建议和方法来帮助您避免常见错误并准确测试您的系统。当您需要解释其他人的结果（包括供应商和行业基准）时，这也是有用的背景。

## 12.1 背景

本节介绍基准测试活动和有效的基准测试，并总结常见错误。

<!-- source-id: ch12#ch12lev1sec1 -->
### 12.1.1 原因

执行基准测试可能出于以下原因：

- **系统设计**：比较不同的系统、系统组件或应用程序。对于商业产品，基准测试可以提供数据来帮助做出购买决策，特别是可用选项的*性能/价格比*。[^fn-ch12-ch12-footnote-1] 在某些情况下，可以使用已发布的*行业基准*结果，从而避免客户自行执行基准测试。
- **概念验证**：在购买或投入生产部署之前测试软件或硬件在负载下的性能。
- **调优**：测试可调参数和配置选项，以确定哪些值得结合生产工作负载进一步研究。
- **开发**：用于产品开发期间的*性能防退化测试*和*极限调查*。性能防退化测试可能是一组定期运行的自动化性能测试，以便及早发现性能回归，并迅速将其与产品变更对应起来。对于极限调查，基准测试可用于在开发过程中将产品推向极限，以确定工程工作应投入哪些方面来提高产品性能。
- **容量规划**：确定容量规划的系统和应用程序限制，为性能建模提供数据，或直接查找容量限制。
- **故障排除**：验证组件是否仍能以最佳性能运行。例如：测试主机之间的最大网络吞吐量，以检查是否存在网络问题。
- **营销**：确定供营销使用的最大产品性能（也称为*基准营销*）。

在企业本地环境中，在概念验证期间对硬件进行基准测试可能是承诺购买大型硬件之前的一项重要工作，并且可能持续数周或数月。这包括运输、机架安装和系统布线，以及测试前安装操作系统所需的时间。当新硬件发布时，这样的过程可能每隔一两年发生一次。

然而，在云计算环境中，资源可以按需提供，无需对硬件进行昂贵的初始投资，并且还可以根据需要快速修改（在不同的实例类型上重新部署）。在选择应用程序编程语言，以及操作系统、数据库、Web 服务器和负载均衡器时，这些环境仍然涉及长期投资。其中一些选择日后可能很难改变。可以执行基准测试来研究各种选项在需要时的扩展能力。云计算模型使基准测试变得容易：可以在几分钟内创建一个大型环境，运行基准测试，然后销毁它，成本很低。

请注意，容错和分布式云环境还使实验变得容易：当新的实例类型可用时，环境可能允许立即使用生产工作负载对其进行测试，从而跳过传统的基准测试评估。在这种情况下，基准测试仍然可以通过比较组件性能来帮助更详细地解释性能差异。例如，Netflix 性能工程团队拥有自动化软件，用于通过各种微基准测试分析新实例类型。这包括自动收集系统统计数据和 CPU 剖析数据，以便分析和解释发现的任何差异。

### 12.1.2 有效的基准测试

基准测试很难做好，而且很容易出现错误和疏忽。正如论文“文件系统和存储基准测试的九年研究”[\[Traeger 08\]](#ch12-ch12ref11) 所总结的：

在本文中，我们调查了 106 篇最新论文中的 415 个文件系统和存储基准。我们发现大多数流行的基准测试都存在缺陷，并且许多研究论文没有提供真实性能的明确指示。

该文件还就应该采取的行动提出了建议；特别是，基准评估应该解释测试的“内容”和“原因”，并且应该对系统的预期行为进行一些分析。

一个好的基准测试的本质也可概括为[\[Smaalders 06\]](#ch12-ch12ref7)：

- **可重复**：便于比较
- **可观测**：便于分析和理解性能
- **可移植**：允许在竞争对手的系统和不同产品版本上运行基准测试
- **易于呈现**：让每个人都能理解结果
- **切合实际**：使测量结果反映客户实际体验
- **可运行**：便于开发人员快速测试变更

在比较不同系统并准备购买时，还必须考虑另一个特征：*性能/价格比*。价格可以量化为设备的五年资本成本\[Anon 85\]。

有效的基准测试还涉及如何应用基准：分析和得出的结论。

<!-- source-id: ch12#ch12lev3_1 -->
#### 基准分析

使用基准测试时，需要了解：

- 正在测试什么
- 限制因素是什么
- 可能影响结果的任何扰动
- 可以从结果中得出什么结论

这些要求需要深入理解基准测试软件的行为、系统的响应方式，以及结果与目标环境的关系。

如果拥有基准测试工具并能访问运行它的系统，最好在基准测试运行期间对系统进行性能分析，以满足这些要求。一个常见的错误是让初级员工执行基准测试，等测试完成后再请性能专家解释结果。最好让性能专家在基准测试期间参与进来，以便在系统仍在运行时分析它。这可能包括深入分析，以解释并量化限制因素。

下面是一个有趣的分析例子：

为了研究最终 TCP/IP 实现的性能，我们在不同机器上的两个用户进程之间传输了 4 MB 数据。传输被划分为 1024 字节的记录，并封装在 1068 字节的以太网数据包中。通过 TCP/IP 将数据从 11/750 发送到 11/780 需要 28 秒，其中包括建立和拆除连接所需的全部时间，用户到用户的吞吐率为 1.2 兆波特。在此期间，11/750 的 CPU 已饱和，而 11/780 约有 30% 的空闲时间。系统处理数据所花的时间分布在以太网处理（20%）、IP 数据包处理（10%）、TCP 处理（30%）、校验和计算（25%）以及用户系统调用处理（15%）之间，没有任何一个处理环节占据系统时间的绝大部分。

这段引文先检查了限制因素（“11/750 的 CPU 已饱和”[^fn-ch12-ch12-footnote-2]），然后解释导致这些限制的内核组件。顺带一提，直到最近，借助火焰图，执行这种分析并概括内核 CPU 时间花在哪里才变得容易。这段话早在火焰图出现之前就已写成：它来自 Bill Joy 于 1981 年对原始 BSD TCP/IP 协议栈的描述 [\[Joy 81\]](#ch12-ch12ref1)！

您可能会发现开发自己的自定义基准测试软件或至少自定义负载生成器更有效，而不是使用给定的基准测试工具。这些可以保持简短，仅关注测试所需的内容，从而使它们能够快速分析和调试。

在某些情况下，例如阅读他人的基准测试结果时，您无法访问基准测试工具或系统。请根据现有材料考虑前面的项目符号列表，此外还要问：系统环境是什么？它是如何配置的？更多问题请参阅 [第 12.4 节](#ch12-ch12lev4)、[基准测试问题](#ch12-ch12lev4)。

### 12.1.3 基准测试失败

以下部分提供了各种基准测试失败（错误、谬误和不当行为）的清单以及如何避免它们。 [第 12.3 节](#ch12-ch12lev3)、[方法论](#ch12-ch12lev3) 描述如何执行基准测试。

<!-- source-id: ch12#ch12lev3_2 -->
#### 1. 草率基准测试

做好基准测试不是一种执行完就可以不再过问的活动。基准工具会提供数字，但这些数字可能并不代表您以为它们代表的内容，因此由此得出的结论可能是错误的。我把它概括为：

草率基准测试：您对 A 进行基准测试，实际测量的是 B，却得出测量了 C 的结论。

做好基准测试需要严谨地检查实际测量的内容，并理解测试对象，才能得出有效结论。

例如，许多工具声称或暗示它们测量磁盘性能，但实际上测试文件系统性能。差异可能是几个数量级，因为文件系统使用缓存和缓冲来用内存 I/O 替代磁盘 I/O。即使基准测试工具可能正常运行并测试文件系统，您对磁盘的结论也将非常错误。

对于初学者来说，理解基准尤其困难，因为他们没有判断数字是否可疑的直觉。如果您买的温度计显示房间温度为 1,000 华氏度（或摄氏度），会立刻知道出了问题。基准测试则不同，它产生的数字可能是您完全不熟悉的。

<!-- source-id: ch12#ch12lev3_3 -->
#### 2. 盲目信仰

人们很容易相信流行的基准测试工具值得信赖，尤其是当它开源且存在已久时。把受欢迎程度等同于有效性的谬误称为*argumentum ad populum*（拉丁语，意为“诉诸群众”）。

分析正在使用的基准测试既耗时，又需要专业知识才能正确完成。而对于流行的基准测试，分析那些“肯定”有效的东西似乎很浪费。

如果一个流行的基准测试由顶尖科技公司之一推广，您会相信它吗？过去确实发生过这种情况：经验丰富的性能工程师都知道，被推广的微基准测试存在缺陷，根本不该使用。没有简单的方法阻止这种事发生（我试过）。

问题甚至不一定出在基准测试软件上——尽管错误确实会发生——而是出在基准测试结果的解释上。

<!-- source-id: ch12#ch12lev3_4 -->
#### 3. 未经分析的数字

没有任何分析细节的基准测试结果，可能表明作者缺乏经验，并想当然地认为结果可信且最终有效。通常，这只是调查的开始——调查最终会发现结果错误或令人困惑。

每个基准数字都应附有对所遇到的限制和所执行的分析的描述。我这样总结了风险：

如果您花了不到一周的时间研究基准结果，那么它可能是错误的。

本书的大部分内容侧重于分析性能，这项工作应该在基准测试期间进行。如果没有时间仔细分析，最好列出尚未检查的假设，并将其随结果一并记录，例如：

- 假设基准测试工具没有错误
- 假设磁盘 I/O 测试实际上测量磁盘 I/O
- 假设基准测试工具按预期将磁盘 I/O 推至极限
- 假设这种类型的磁盘 I/O 与此应用程序相关

如果基准测试结果后来被认为重要到值得投入更多精力，这些内容就可以作为进一步验证的待办事项列表。

<!-- source-id: ch12#ch12lev3_5 -->
#### 4. 复杂的基准测试工具

重要的是，基准测试工具不能因自身的复杂性而妨碍分析。理想情况下，程序应当开源，便于研究；同时足够短，能够快速阅读和理解。

对于微基准测试，建议选择用 C 编写的工具；对于客户端模拟基准测试，建议使用与客户端相同的编程语言，以尽量减少差异。

一个常见问题是“对基准测试本身进行基准测试”——报告的结果其实受基准测试软件本身限制。一个常见原因是基准测试软件采用单线程。复杂的基准测试套件需要理解和分析大量代码，也会使分析变得困难。

<!-- source-id: ch12#ch12lev3_6 -->
#### 5. 测试错误对象

尽管有许多基准测试工具可用于测试各种工作负载，但其中许多工具可能与目标应用程序无关。

例如，一个常见错误是因为有现成的磁盘基准测试工具就去测试磁盘性能，即使目标环境中的工作负载预计完全驻留在文件系统缓存中，不受磁盘 I/O 影响。

类似地，开发产品的工程团队可能会围绕某个基准测试建立标准，并把全部性能工作都用于提高该基准测得的性能。然而，如果它实际上不像客户工作负载，这些工程工作就会针对错误的行为进行优化 \[Smaalders 06\]。

对于现有生产环境，工作负载特征分析方法（前面的章节已介绍）可以测量真实工作负载的组成，从设备 I/O 一直到应用程序请求。这些测量可以指导您选择最相关的基准测试。如果没有可供分析的生产环境，可以建立模拟或模型来分析预期工作负载。还要向基准数据的目标受众确认，他们是否认可这些测试。

基准测试可能曾经测试过适当的工作负载，但如今多年未更新，测试的已经是错误对象。

<!-- source-id: ch12#ch12lev3_7 -->
#### 6. 忽略环境

生产环境和测试环境是否匹配？假设您的任务是评估一个新数据库。您配置测试服务器并运行数据库基准测试，后来才发现错过了一个重要步骤：测试服务器使用默认设置、默认可调参数、默认文件系统等。生产数据库服务器针对高磁盘 IOPS 做过调优，因此在未经调优的系统上测试是不现实的：您没有先了解生产环境。

<!-- source-id: ch12#ch12lev3_8 -->
#### 7. 忽略错误

仅仅因为基准测试工具产生了结果，并不意味着结果反映了一次“成功”的测试。部分甚至全部请求都可能出错。虽然前面的错误类型已经涵盖了这一点，但这个问题非常常见，值得单独指出。

一次 Web 服务器性能基准测试让我想起了这一点。测试人员报告说，Web 服务器的平均延迟对于他们的需求来说太高了：*平均*超过一秒。一秒钟？快速分析很快确定了问题：测试期间 Web 服务器根本没有执行任何操作，因为所有请求都被防火墙阻止了。*所有*请求。显示的延迟其实是基准测试客户端等待超时并报错所花的时间！

<!-- source-id: ch12#ch12lev3_9 -->
#### 8. 忽略方差

基准测试工具，尤其是微基准测试，通常根据一系列现实世界特征测量的“平均值”施加稳定且一致的工作负载，例如一天中不同时间或某个时间间隔内的平均值。例如，磁盘工作负载的平均速率可能是每秒读取 500 次、写入 50 次。基准测试工具随后可以模拟这一速率，或模拟读写比为 10:1 的负载，以便测试更高的速率。

这种方法忽略了*方差*：操作速率可能会变化。操作类型也可能变化，并且某些类型可以彼此独立地发生。例如，写入可能每 10 秒突发一次（异步回写数据刷新），而同步读取保持稳定。写入突发可能在生产环境中造成实际问题，例如让读取排队；但如果基准测试只施加稳定的平均速率，就无法模拟这种情况。

模拟方差的一种可能方案是在基准测试中使用马尔可夫模型：它可以反映一次写入后紧接着另一次写入的概率。

<!-- source-id: ch12#ch12lev3_10 -->
#### 9. 忽略扰动

考虑哪些外部扰动可能影响结果。基准测试运行期间是否会执行定时系统活动（例如系统备份）？监控代理是否每分钟收集一次统计数据？在云环境中，扰动可能来自同一宿主机上不可见的其他租户。

消除扰动的一个常见策略是延长基准测试的运行时间——运行几分钟而不是几秒。通常，基准测试的持续时间不应短于一秒。过短的测试可能会异常地受到设备中断（执行中断服务例程时固定线程）、内核 CPU 调度决策（迁移排队线程以保持 CPU 关联性时的等待）以及 CPU 缓存热身效应的干扰。尝试运行几次基准测试并检查标准差——它应尽可能小。

还要收集数据，以便在存在扰动时对其进行研究。这可能包括收集操作延迟的分布，而不仅仅是基准测试的总运行时间，从而可以发现异常值并记录其细节。

<!-- source-id: ch12#ch12lev3_11 -->
#### 10. 改变多个因素

比较两项测试的结果时，要仔细了解两项测试之间的所有差异因素。

例如，如果通过网络对两台主机进行基准测试，两者之间的网络是否相同？如果一台主机距离更远、网络更慢或更拥堵，又会怎样？任何这类额外因素都可能使基准测试结果失真。

在云中，有时会创建实例、测试它们，然后销毁它们来执行基准测试。这可能引入许多不可见的因素：实例可能创建在更快或更慢的系统上，也可能创建在负载更高、受到其他租户争用的系统上。我建议测试多个实例并取中位数（或者更好的是记录完整分布），以免因测试到一个异常快或异常慢的系统而产生偏差。

<!-- source-id: ch12#ch12lev3_12 -->
#### 11. 基准悖论

潜在客户经常使用基准测试来评估您的产品，但这些基准通常不准确，准确到还不如掷硬币。一位销售人员曾告诉我，他会满足于这样的概率：赢得一半的产品评估就能达到销售目标。但忽视基准测试本身就是一个基准测试陷阱，而实际成功的概率要低得多。我把它概括为：

“如果你的产品赢得基准测试的机会是 50/50，那么你通常会失败。” [\[Gregg 14c\]](#ch12-ch12ref15)

这个看似悖论可以用一些简单的概率来解释。

客户根据性能购买产品时，通常希望确切了解产品的性能。这可能意味着不只运行一个基准测试，而是运行多个基准测试，并希望产品赢得*所有*测试。如果每项基准测试的获胜概率为 50%，则：

赢得三个基准的概率 = 0.5 × 0.5 × 0.5 = 0.125 = 12.5%

基准测试越多——而且必须赢得全部基准测试——成功的机会就越小。

<!-- source-id: ch12#ch12lev3_13 -->
#### 12. 竞争基准测试

您的营销部门希望基准测试结果显示产品如何击败竞争对手。这比听起来困难得多。

顾客挑选产品时，不会只使用五分钟；他们会使用数月。在此期间，他们会分析并调优产品性能，也许在最初几周内就解决最严重的问题。

您没有几周时间去分析和调优*竞争对手*的产品。在有限时间内，您只能收集未经调优、因而并不现实的结果。竞争对手的客户（也就是这场营销活动的目标受众）很可能会看到您发布的这些结果，于是您的公司会失去原本想要赢得的人的信任。

如果必须对竞争对手进行基准测试，就需要投入大量时间调优他们的产品。使用前面章节介绍的技术分析性能；还可以查阅最佳实践、客户论坛和缺陷数据库。甚至可以引入外部专家来调优系统。然后，在最终进行正面对比的基准测试之前，也要为自家产品做同样的准备。

<!-- source-id: ch12#ch12lev3_14 -->
#### 13. 误伤

对自己的产品进行基准测试时，要尽一切努力确保已经测试了性能最佳的系统和配置，并且系统确实达到了极限。发布结果前应与工程团队分享；他们可能发现您遗漏的配置项。如果您是工程团队成员，也要关注公司内部或签约第三方开展的基准测试，并帮助他们完成测试。

有一次，我看到一个工程团队努力开发一款高性能产品。该产品的性能关键在于一项尚未记录的新技术。产品发布时，基准测试团队被要求提供数据；他们不了解这项未记录的新技术，因而配置错误，最终发布了低估产品性能的数据。

有时系统配置正确，却只是没有达到极限。要问的问题是：这个基准测试的瓶颈是什么？瓶颈可能是某个利用率已达 100%、可以通过分析识别的物理资源（例如 CPU、磁盘或互连）。请参见 [第 12.3.2 节](#ch12-ch12lev3sec2)、[主动基准测试](#ch12-ch12lev3sec2)。

另一个误伤问题是：对较旧版本的软件进行基准测试时，较新版本可能已经修复了其中的性能问题；或者只能在手头有限的设备上进行测试，结果并非最佳。潜在客户可能会以为公司发布的任何基准都代表最佳性能，而不是低于最佳水平的产品性能。

<!-- source-id: ch12#ch12lev3_15 -->
#### 14. 误导性基准

误导性的基准结果在行业中很常见。它们可能是由于无意中限制了有关基准实际测量内容的信息，或者故意省略了信息。通常，基准测试结果在技术上是正确的，但随后会向客户歪曲事实。

考虑一下这种假设的情况：供应商通过构建价格昂贵且永远不会出售给实际客户的定制产品获得了惊人的结果。价格并未随基准测试结果一起披露，基准测试结果侧重于非性价比指标。营销部门大方地分享了对结果的模糊总结（“我们的速度快了两倍！”），在客户心目中将其与整个公司或产品线联系起来。这是为了歪曲产品而省略细节的案例。虽然它可能不是作弊——数字不是假的——但它是“通过隐瞒信息说谎”。

此类供应商基准测试仍可作为性能上限，对您有一定用处。您不应期望超过这些数值（不考虑误伤情况）。

考虑这种不同的假设情况：营销部门有预算用于营销活动，并且希望使用良好的基准结果。他们聘请多个第三方来对他们的产品进行基准测试，并从小组中选出最好的结果。这些第三方并不是因为他们的专业知识而被选中的；他们被挑选来提供快速且廉价的结果。事实上，非专业知识可能被认为是有利的：结果偏离现实越大越好——理想情况下，其中一个结果与正方向偏离得很大！

使用供应商结果时，请仔细检查细则，了解被测系统、磁盘的类型和数量、网络接口及其配置，以及其他因素。具体应注意的事项，请参见 [第 12.4 节](#ch12-ch12lev4)、[基准测试问题](#ch12-ch12lev4)。

<!-- source-id: ch12#ch12lev3_16 -->
#### 15. 基准测试专用优化

*基准测试专用优化（benchmark specials）*是指供应商研究流行或行业基准，然后设计产品，使其在该基准上获得良好分数，同时忽略实际客户性能。这也称为“针对基准进行优化”。

“基准测试专用优化”这一术语于 1993 年随 TPC-A 基准出现，如事务处理性能委员会（TPC）的历史页面 [\[Shanley 98\]](#ch12-ch12ref5) 所述：

总部位于马萨诸塞州的咨询公司 Standish Group 指控 Oracle 在其数据库软件中添加了一个特殊选项（离散事务），唯一目的是夸大 Oracle 的 TPC-A 结果。Standish Group 声称 Oracle“违反了 TPC 的精神”，因为典型客户不会使用离散事务选项，因此它属于基准测试专用优化。Oracle 强烈否认这一指控，并有一定道理地表示自己遵守了基准规范的明文规定。Oracle 辩称，既然 TPC 基准规范没有涉及基准测试专用优化，更不用说 TPC 的精神，那么指责其违反任何规定是不公平的。

TPC 增加了一条反基准测试专用优化条款：

禁止所有能够提高基准结果、却不能提高实际性能或改善实际定价的“基准测试专用优化”实现。

由于 TPC 专注于性能/价格比，因此夸大数字的另一种策略是采用“特殊定价”——客户实际上不可能获得的大幅折扣。与特殊软件变更一样，当真实客户购买该系统时，结果就与实际情况不符。TPC 在其价格要求 [\[TPC 19a\]](#ch12-ch12ref19) 中解决了这个问题：

TPC 规范要求总价格必须在客户为配置支付的价格的 2% 以内。

这些例子有助于解释基准测试专用优化的概念，但 TPC 多年前就已在其规范中处理了这些问题，因此如今不一定还会遇到它们。

<!-- source-id: ch12#ch12lev3_17 -->
#### 16. 作弊

基准测试的最后一个失败是作弊：分享虚假结果。幸运的是，这种情况要么很少见，要么根本不存在。即使在最残酷的基准测试战中，我也没有见过纯粹编造的数据被共享的情况。

## 12.2 基准测试类型

根据测试的工作负载，[图 12.1](#ch12-ch12fig01) 描绘了一系列基准测试类型，其中也包括生产工作负载。

<!-- source-id: ch12#ch12fig01 -->
![图 12.1 基准测试类型](../images/12fig01.jpg)

以下部分描述三种基准测试类型：微基准测试、模拟和跟踪/重放；此外还讨论行业标准基准测试。

<!-- source-id: ch12#ch12lev2sec1 -->
### 12.2.1 微基准测试

微基准测试使用人工工作负载来测试特定类型的操作，例如执行单一类型的文件系统 I/O、数据库查询、CPU 指令或系统调用。其优势在于简单：缩小所涉及的组件和代码路径范围，可以更容易地研究目标，并快速找出性能差异的根因。测试通常也具有可重复性，因为其他组件的变化已尽可能排除。微基准测试通常还可以快速在不同系统上运行；而且由于它们是有意构造的人工负载，不容易与真实工作负载模拟混淆。

要使用微基准测试结果，必须将其映射到目标工作负载。微基准测试可以覆盖多个维度，但可能只有一两个维度与目标相关。对目标系统进行性能分析或建模，有助于确定哪些结果适用，以及适用到什么程度。

前面几章中提到的示例微基准工具包括（按资源类型）：

- **CPU**：SysBench
- **内存 I/O**：lmbench（在 [第 6 章](#ch06-ch06)、[CPU](#ch06-ch06) 中）
- **文件系统**：fio
- **磁盘**：具有直接 I/O 的 hdparm、dd 或 fio
- **网络**：iperf

可用的基准测试工具还有很多。不过请记住 \[Traeger 08\] 的警告：“大多数流行的基准测试都有缺陷。”

您也可以自行开发基准测试。应尽量使它们简单，并识别可以单独测试的工作负载属性。（更多信息请参阅 [第 12.3.6 节](#ch12-ch12lev3sec6)、[自定义基准](#ch12-ch12lev3sec6)。）使用外部工具验证它们确实执行了所声称的操作。

<!-- source-id: ch12#ch12lev3_18 -->
#### 设计示例

考虑设计一个文件系统微基准测试，以测试以下属性：顺序或随机 I/O、I/O 大小和方向（读或写）。[表 12.1](#ch12-ch12tab01) 展示了用于研究这些维度的五个示例测试，以及每个测试的目的。

<!-- source-id: ch12#ch12tab01 -->
**表 12.1 文件系统微基准测试示例**

| **#** | **测试** | **意图** |
| --- | --- | --- |
| 1 | 顺序读取 512 字节[^fn-ch12-ch12-footnote-3] | 测试最大（现实可行的）IOPS |
| 2 | 顺序读取 1 MB[^fn-ch12-ch12-footnote-4] | 测试最大读取吞吐量 |
| 3 | 顺序写入 1 MB | 测试最大写入吞吐量 |
| 4 | 随机读取 512 字节 | 测试随机 I/O 的影响 |
| 5 | 随机写入 512 字节 | 测试重写的影响 |

可以根据需要添加更多测试。所有这些测试还要与两个附加因素组合：

- **工作集大小**：正在访问的数据的大小（例如，总文件大小）：
    - 比主内存小得多：使数据完全驻留在文件系统缓存中，从而可以研究文件系统软件的性能。
    - 比主内存大得多：尽量减少文件系统缓存的影响，使基准测试转而测试磁盘 I/O。
- **线程数**：假设工作集大小较小：
    - 单线程：根据当前 CPU 时钟速度测试文件系统性能。
    - 多线程，足以使所有 CPU 饱和：测试系统、文件系统和 CPU 的最大性能。

这些因素很快就会组合成一个大型测试矩阵。可以使用统计分析技术减少所需测试的集合。

创建专注于最高速度的基准测试被称为“晴天”性能测试。为了不忽略问题，还要考虑“阴天”或“雨天”性能测试，即测试包括争用、扰动和工作负载方差在内的非理想情况。

<!-- source-id: ch12#ch12lev2sec2 -->
### 12.2.2 模拟

许多基准测试模拟客户应用程序工作负载；这些有时被称为“宏基准测试”。它们可能根据生产环境的工作负载特征（参见 [第 2 章](#ch02-ch02)、[方法论](#ch02-ch02)）来确定要模拟的特征。例如，您可能会发现生产 NFS 工作负载由以下操作类型和概率组成：读取 40%、写入 7%、获取属性 19%、读取目录 1%，等等。还可以测量并模拟其他特征。

如果模拟得当，模拟可以产生接近客户在真实工作负载下运行情况的结果；即使不完全接近，也可能足够有用。模拟可以涵盖许多因素，而用微基准测试研究这些因素会非常耗时。模拟还可以包含复杂系统交互的影响，而使用微基准测试时可能完全遗漏这些影响。

[第 6 章](#ch06-ch06)、[CPU](#ch06-ch06) 中介绍的 CPU 基准测试 Whetstone 和 Dhrystone 都是模拟示例。Whetstone 于 1972 年开发，用于模拟当时的科学工作负载。Dhrystone 于 1984 年推出，用于模拟当时的整数工作负载。

许多公司使用内部或外部负载生成软件来模拟客户端 HTTP 负载（示例软件包括 wrk [\[Glozer 19\]](#ch12-ch12ref18)、siege [\[Fulmer 12\]](#ch12-ch12ref14) 和 hey [\[Dogan 20\]](#ch12-ch12ref21)）。这些工具可用于评估软件或硬件变更，也可用于模拟峰值负载（例如在线购物平台上的“闪购”），以暴露可供分析和解决的瓶颈。

工作负载模拟可能是“无状态”的，即每个服务器请求都与前一个请求无关。例如，前面描述的 NFS 服务器工作负载可以通过请求一系列操作来模拟，其中每种操作类型都按照测得的概率随机选择。

模拟也可以是“有状态的”，即每个请求都依赖于客户端状态，至少依赖于前一个请求。您可能会发现 NFS 读取和写入往往成组到达，因此写入后紧接写入的概率远高于读取后紧接写入的概率。通过将请求表示为状态并测量状态转换的概率，可以使用“马尔可夫模型”更好地模拟这类工作负载 \[Jain 91\]。

模拟的一个问题是可能忽略方差，如 [第 12.1.3 节](#ch12-ch12lev1sec3)、[基准测试失败](#ch12-ch12lev1sec3) 所述。客户的使用模式也会随时间变化，需要更新并调节模拟以保持相关性。然而，如果已经发布了基于旧版基准测试的结果，就可能遇到阻力，因为这些结果将无法再与新版结果进行比较。

<!-- source-id: ch12#ch12lev2sec3 -->
### 12.2.3 重放

第三种基准测试尝试将跟踪日志重放到目标系统，使用实际捕获的客户端操作测试其性能。这听起来很理想——和在生产环境中测试一样好，对吧？然而它存在问题：当服务器特性和交付延迟发生变化时，捕获的客户端工作负载不太可能自然响应这些差异，因而可能并不比模拟客户工作负载更好。过度相信这种方法，结果可能更糟。

考虑以下假设情况：客户正在考虑升级存储基础设施。当前生产工作负载在新硬件上被跟踪并重放。不幸的是，性能更差，这笔销售也因此未能达成。问题在于跟踪/重放运行在磁盘 I/O 层面：旧系统使用 10K rpm 磁盘，新系统使用速度更慢的 7,200 rpm 磁盘。然而，新系统提供了 16 倍大的文件系统缓存和更快的处理器。真实生产工作负载本应显示性能提升，因为大部分请求会从缓存返回；而重放磁盘事件并没有模拟这一点。

虽然这是测试错误对象的情况，但即使跟踪/重放处于正确层级，其他微妙的时序效应也可能扰乱结果。与所有基准测试一样，分析并理解正在发生的事情至关重要。

<!-- source-id: ch12#ch12lev2sec4 -->
### 12.2.4 行业标准

行业标准基准测试由旨在创建公平且相关基准的独立组织提供。这些基准通常由不同的微基准测试和工作负载模拟组成，定义和文档都很完善，并且必须遵循特定准则执行，才能得到预期结果。供应商可以参与（通常需要付费），并获得用于执行基准测试的软件。其结果通常要求完整披露配置环境，而环境可能接受审计。

对客户来说，这些基准测试可以节省大量时间，因为各种供应商和产品可能已经有现成结果。因此，您的任务是找到与未来或当前生产工作负载最接近的基准测试。对于当前工作负载，可以通过工作负载特征分析来确定。

Jim Gray 等人在 1985 年发表的题为“事务处理能力的衡量标准”的论文中明确了对行业标准基准测试的需求 [\[Anon 85\]](#ch12-ch12ref2)。论文描述了衡量性能/价格比的必要性，并详细介绍了供应商可以执行的三个基准测试：Sort、Scan 和 DebitCredit。它还建议采用基于 DebitCredit 的行业标准每秒事务数（TPS）指标，可以像汽车的每加仑英里数一样使用。Jim Gray 及其工作后来推动了 TPC [\[DeWitt 08\]](#ch12-ch12ref10) 的创建。

除 TPS 外，曾用于相同目的的其他指标包括：

- **MIPS**：每秒百万条指令。虽然它是一种性能指标，但所完成的工作取决于指令类型，因此在不同处理器架构之间可能难以比较。
- **FLOPS**：每秒浮点运算数——作用类似于 MIPS，但用于大量进行浮点计算的工作负载。

行业基准通常根据自身的测试定义定制指标，该指标只适合与同一基准的结果比较。

<!-- source-id: ch12#ch12lev3_19 -->
#### TPC

事务处理性能委员会（TPC）创建并管理专注于数据库性能的行业基准测试，包括：

- **TPC-C**：模拟完整的计算环境，其中一组用户针对数据库执行事务。
- **TPC-DS**：决策支持系统的模拟，包括查询和数据维护。
- **TPC-E**：在线事务处理（OLTP）工作负载，对经纪公司数据库建模，其中客户生成与交易、账户查询和市场研究相关的事务。
- **TPC-H**：决策支持基准，模拟即席查询和并发数据修改。
- **TPC-VMS**：TPC 虚拟测量单一系统，允许为虚拟化数据库收集其他基准测试结果。
- **TPCx-HS**：使用 Hadoop 的大数据基准测试。
- **TPCx-V**：测试虚拟机中的数据库工作负载。

TPC 结果在线共享 [\[TPC 19b\]](#ch12-ch12ref20)，其中包括性能/价格比。

### 12.3.1 被动基准测试

这是基准测试的“执行后不管”策略——运行基准测试，然后直到它完成前都不再关注它。主要目标是收集基准数据。这是基准测试常见的执行方式；为了与主动基准测试比较，这里将其作为一种反面方法论单独描述。

以下是一些被动基准测试步骤示例：

1. 选择一个基准测试工具。
2. 使用多种选项运行它。
3. 把结果制作成演示文稿。
4. 把演示文稿交给管理层。

前面已经讨论过这种方法的问题。总结起来，结果可能是：

- 由于基准测试软件错误而无效
- 受基准测试软件的限制（例如单线程）
- 受到与基准目标无关的组件的限制（例如，拥塞的网络）
- 受配置限制（未启用性能功能，不是最高配置）
- 受到干扰（且不可重复）
- 基准测试完全是错误的事情

被动基准测试容易执行，却容易出错。供应商执行时，可能产生错误警报，浪费工程资源或导致销售损失；客户执行时，则可能导致错误的产品选择，并在日后困扰公司。

<!-- source-id: ch12#ch12lev3sec2 -->
### 12.3.2 主动基准测试

通过主动基准测试，您可以在基准测试运行时（而不是完成后）使用可观测性工具 [\[Gregg 14d\]](#ch12-ch12ref16) 分析性能。您可以确认基准测试确实测量了它声称测量的内容，并理解那究竟是什么。主动基准测试还可以识别被测系统或基准测试本身的真正限制因素。分享结果时，提供所遇限制的具体细节会很有帮助。

此外，这也是提升性能可观测性工具使用技能的好机会。理论上，您检查的是一个“已知负载”，可以通过这些工具观察它呈现出的特征。

理想情况下，可以配置基准测试并使其在稳定状态下运行，以便可以在数小时或数天内执行分析。

在其主页 [\[Coker 01\]](#ch12-ch12ref6) 上：

Bonnie++ 是一个基准测试套件，旨在对硬盘和文件系统性能执行多项简单测试。

第一个测试是“Sequential Output”和“Per Chr”，bonnie++ 报告的得分为 739 Kbytes/sec。

合理性检查：如果这确实是逐字符 I/O，就意味着系统每秒完成 739,000 次 I/O。该基准测试被描述为测试硬盘性能，但我怀疑这个系统能否达到这么高的磁盘 IOPS。

在运行第一个测试时，我使用 iostat(1) 来检查磁盘 IOPS：

![点此查看代码图片](../images/pg658-02.jpg)

```text
$ iostat -sxz 1
[...]
avg-cpu:  %user   %nice %system %iowait  %steal   %idle
          11.44    0.00   38.81    0.00    0.00   49.75
Device             tps      kB/s    rqm/s   await aqu-sz  areq-sz  %util
[...]
```

没有报告磁盘 I/O。

现在使用 bpftrace 对块 I/O 事件计数（请参阅 [第 9 章](#ch09-ch09)、[磁盘](#ch09-ch09)、[第 9.6.11 节](#ch09-ch09lev6sec11)、[bpftrace](#ch09-ch09lev6sec11)）：

![点此查看代码图片](../images/pg658-03.jpg)

```text
# bpftrace -e 'tracepoint:block:* { @[probe] = count(); }'
Attaching 18 probes...
^C

@[tracepoint:block:block_dirty_buffer]: 808225
@[tracepoint:block:block_touch_buffer]: 1025678
```

这也表明没有发出块 I/O（no block:block\_rq\_issue），也没有完成块 I/O（block:block\_rq\_complete）；不过，缓冲区被标记为脏。使用 cachestat(8)（[第 8 章](#ch08-ch08)、[文件系统](#ch08-ch08)、[第 8.6.12 节](#ch08-ch08lev6sec12)、[cachestat](#ch08-ch08lev6sec12)）查看文件系统缓存状态：

     293        0    54299  100.00%           49        361
     658        0   298748  100.00%           49        361
     250        0   602499  100.00%           49        362
[...]
```

bonnie++ 从输出的第二行开始执行；这证实了工作负载是“脏写入”，即写入文件系统缓存。

在 VFS 层检查 I/O 栈中更高层的 I/O（请参阅 [第 8 章](#ch08-ch08)、[文件系统](#ch08-ch08)、[第 8.6.15 节](#ch08-ch08lev6sec15)、[BPF](#ch15-ch15)trace）：

^C

@[kprobe:vfs_open]: 7
@[kprobe:vfs_read]: 13
@[kprobe:vfs_write]: 1176936

这说明 vfs\_write() 的工作量确实很大。使用 bpftrace 进一步深入验证写入大小：

![点此查看代码图片](../images/pg659-02.jpg)

# bpftrace -e 'k:vfs_write /comm == "bonnie++"/ { @bytes = hist(arg2); }'
Attaching 1 probe...
^C

@bytes:
[1]               668839 |@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@|
[2, 4)                 0 |                                                    |
[4, 8)                 0 |                                                    |
[8, 16)                0 |                                                    |
[16, 32)               1 |                                                    |
```

vfs\_write() 的第三个参数是字节数，通常为 1 字节（16 到 31 字节范围内的单次写入可能是关于开始基准测试的 bonnie++ 消息）。

通过分析运行中的基准测试（主动基准测试），我们了解到 bonnie++ 的第一个测试是 1 字节文件系统写入，并且写入被缓存在文件系统缓存中。与 bonnie++ 的描述所暗示的不同，它并不测试磁盘 I/O。

根据手册页，bonnie++ 有一个 `-b` 选项表示“不进行写入缓冲”，会在每次写入后调用 fsync(2)。我将使用 strace(1) 分析这一行为，因为 strace(1) 会以人类可读的形式打印所有系统调用。strace(1) 的开销也很高，因此应丢弃使用 strace(1) 时得到的基准测试结果。

![点此查看代码图片](../images/pg660-01.jpg)

```text
$ strace bonnie++ -b
[...]
write(3, "6", 1)                        = 1
write(3, "7", 1)                        = 1
write(3, "8", 1)                        = 1
write(3, "9", 1)                        = 1
write(3, ":", 1)                        = 1
[...]
```

输出显示 bonnie++ 并未在每次写入后调用 fsync(2)。它还有一个用于直接 I/O 的 `-D` 选项，但该选项在我的系统上失败了。因此无法真正进行逐字符磁盘写入测试。

有人可能会说 bonnie++ 并没有损坏，它确实进行了“Sequential Output”和“Per Chr”测试：这些术语都没有承诺会产生磁盘 I/O。但对于声称测试“硬盘”性能的基准测试来说，这至少具有误导性。

Bonnie++ 并不是一个特别糟糕的基准测试工具；它曾在许多场合很好地服务于用户。我选择它作为这个例子（并选择其中最可疑的测试来研究），是因为它很知名，我以前研究过它，而且这样的发现并不少见。但它只是一个例子。

旧版本的 bonnie++ 在该测试中还有一个问题：它允许 libc 在写入发送到文件系统之前进行缓冲，因此 VFS 写入大小为 4 KB 或更大，具体取决于 libc 和操作系统版本。[^fn-ch12-ch12-footnote-5] 这会误导人们比较使用不同 libc 缓冲大小的不同操作系统上的 bonnie++ 结果。该问题已在近期版本的 bonnie++ 中修复，但又产生了另一个问题：bonnie++ 的新结果无法与旧结果比较。

有关 Bonnie++ 性能分析的更多信息，请参阅 Roch Bourbonnais 的文章《解码 Bonnie++》[\[Bourbonnais 08\]](#ch12-ch12ref9)。

### 12.3.3 CPU 分析

对基准测试目标和基准测试软件进行 CPU 剖析，值得单独作为一种方法论讨论，因为它可以快速发现问题。这通常是主动基准测试调查的一部分。

目的是快速检查所有软件正在做什么，看看是否出现有趣的现象。这还可以将研究范围缩小到最重要的软件组件，即参与该基准测试的组件。

用户级和内核级调用栈都可以进行剖析。[第 5 章](#ch05-ch05)、[应用](#ch05-ch05) 中介绍了用户级 CPU 剖析；[第 6 章](#ch06-ch06)、[CPU](#ch06-ch06) 中介绍了二者，[第 6.6 节](#ch06-ch06lev6)、[可观测性工具](#ch06-ch06lev6) 中还提供了包括火焰图在内的示例。

<!-- source-id: ch12#ch12lev3_22 -->
#### 示例

在一套拟采用的新系统上执行磁盘微基准测试时，结果令人失望：磁盘吞吐量比旧系统更低。我被要求找出问题，大家预期是磁盘或磁盘控制器性能较差，需要升级。

我从 USE 方法开始（[第 2 章](#ch02-ch02)、[方法论](#ch02-ch02)），发现磁盘并不忙，但系统时间（内核）中存在一些 CPU 使用率。

对于磁盘基准测试，您可能不会认为 CPU 是有趣的分析目标。考虑到内核中存在一些 CPU 使用率，我认为值得快速检查一下是否出现有趣现象，尽管原本并未期待这一点。我进行了剖析，并生成了 [图 12.2](#ch12-ch12fig02) 所示的火焰图。

![图 12.2 内核时间的火焰图剖析](../images/12fig02.jpg)

### 12.3.6 自定义基准

对于简单的基准测试，您可能需要自行编写软件。尽量让程序保持简短，避免复杂性妨碍分析。

C 语言通常是微基准测试的不错选择，因为它与实际执行的内容贴近。不过，要仔细考虑编译器优化会如何影响代码：如果编译器认为输出未被使用、因而无需计算，可能会删除简单的基准测试例程。基准测试运行时，始终使用其他工具检查并确认它确实在运行。还可以反汇编编译后的二进制文件，查看实际会执行什么。

涉及虚拟机、异步垃圾回收和动态运行时编译的语言，可能更难以可靠、精确地调试和控制。如果必须模拟用这些语言编写的客户端软件，仍可能需要使用它们来编写宏基准测试。

编写自定义基准测试还可以揭示目标系统的细节，而这些细节以后可能很有用。例如，在开发数据库基准测试时，您可能发现 API 支持各种提高性能的选项，但生产环境目前没有使用这些选项，因为生产环境是在这些选项出现之前开发的。

您的软件可能只负责生成负载（*负载生成器*），把测量工作留给其他工具。一种实现方式是逐步增加负载。

<!-- source-id: ch12#ch12lev3sec7 -->
### 12.3.7 递增负载

这是确定系统可处理最大吞吐量的简单方法：以小增量增加负载，并测量交付吞吐量，直到达到某个限制。可以将结果绘图，展示可扩展性曲线，再通过目视或可扩展性模型研究该曲线（请参阅 [第 2 章](#ch02-ch02)、[方法论](#ch02-ch02)）。

例如，[图 12.3](#ch12-ch12fig03) 展示了文件系统和服务器如何随线程数扩展。每个线程对一个已缓存的文件执行 8 KB 随机读取，线程数逐一增加。

<!-- source-id: ch12#ch12fig03 -->
![图 12.3 递增的文件系统负载](../images/12fig03.jpg)

该系统的峰值读取速度接近每秒 50 万次。通过 VFS 级统计数据检查结果，确认 I/O 大小为 8 KB，峰值传输速度超过 3.5 GB/s。

此测试的负载生成器用 Perl 编写，代码足够短，可以完整列为示例：

![点此查看代码图片](../images/pg663-01.jpg)

```text
#!/usr/bin/perl -w
#
# randread.pl - randomly read over specified file.

use strict;

my $IOSIZE = 8192;                      # size of I/O, bytes
my $QUANTA = $IOSIZE;                   # seek granularity, bytes

die "USAGE: randread.pl filename\n" if @ARGV != 1 or not -e $ARGV[0];

my $file = $ARGV[0];
my $span = -s $file;                    # span to randomly read, bytes
my $junk;

open FILE, "$file" or die "ERROR: reading $file: $!\n";

while (1) {
        seek(FILE, int(rand($span / $QUANTA)) * $QUANTA, 0);
        sysread(FILE, $junk, $IOSIZE);
}

close FILE;
```

为避免缓冲，该程序使用 sysread() 直接调用 read(2) 系统调用。

该程序是为 NFS 服务器微基准测试编写的，在一组客户端上并行执行；每个客户端都对 NFS 挂载的文件进行随机读取。微基准测试结果（每秒读取次数）使用 nfsstat(8) 和其他工具在 NFS 服务器上测量。

所用文件的数量及其总大小受到控制（这构成*工作集大小*），使一些测试可以完全从服务器缓存返回，而其他测试则从磁盘返回。（参见 [第 12.2.1 节](#ch12-ch12lev2sec1)、[微基准测试](#ch12-ch12lev2sec1) 中的设计示例。）

客户端集群中运行的实例数量逐一增加，以递增负载，直到达到限制。实例数和可扩展性曲线一同绘制，并结合资源利用率（USE 方法）进行研究，从而确认某项资源已经耗尽。本例中耗尽的是服务器 CPU 资源，这促成了另一项旨在进一步提升性能的调查。

我使用这个程序和方法找到了 Sun ZFS 存储设备的限制 [\[Gregg 09b\]](#ch12-ch12ref12)。这些限制被作为正式结果——据我们所知，它们创下了世界纪录。我也有一套类似的 C 语言软件，通常会使用它，但本例不需要：客户端 CPU 很充足，虽然改用 C 会降低客户端 CPU 利用率，却不会改变结果，因为目标系统仍达到相同的瓶颈。我们还尝试了更复杂的基准测试和其他语言，但都无法改进这些基于 Perl 的结果。

采用此方法时，要同时测量延迟和吞吐量，尤其要测量延迟分布。系统接近极限时，排队延迟可能显著增加，导致整体延迟上升。如果负载推得过高，延迟可能高到无法合理地将结果视为有效。要问自己：客户能否接受该延迟。

例如：您使用大量客户端将目标系统驱动到 990,000 IOPS，其平均 I/O 延迟为 5 毫秒。您当然希望突破 100 万 IOPS，但系统已经接近饱和。继续增加客户端后，终于超过 100 万 IOPS；然而此时所有操作都严重排队，平均延迟超过 50 毫秒，无法接受！您应向营销部门提供哪个结果？（答案：990,000 IOPS。）

<!-- source-id: ch12#ch12lev3sec8 -->
### 12.3.8 合理性检查

这是一个通过调查是否有任何特征没有意义来检查基准结果的练习。它包括检查结果是否需要某些组件超出其已知限制，例如网络带宽、控制器带宽、互连带宽或磁盘 IOPS。如果超出了任何限制，则值得进行更详细的调查。在大多数情况下，此练习最终会发现基准测试结果是假的。

下面是一个示例：NFS 服务器以 8 KB 读取速度进行基准测试，据报告可提供 50,000 IOPS。它使用单个 1 Gbit/s 以太网端口连接到网络。驱动 50,000 IOPS × 8 KB = 400,000 KB/s 所需的网络吞吐量，加上协议标头。这超过了 3.2 Gbit/s，远远超过了 1 Gbit/s 的已知限制。有问题！

这样的结果通常意味着基准测试已经测试了“客户端缓存”，并且没有将整个工作负载驱动到 NFS 服务器。

我使用此计算来识别许多虚假基准，其中包括单个 1 Gbit/s 接口 [\[Gregg 09c\]](#ch12-ch12ref13) 上的以下吞吐量：

- 120 兆字节/秒（0.96 千兆位/秒）
- 200 兆字节/秒（1.6 吉比特/秒）
- 350 兆字节/秒（2.8 千兆位/秒）
- 800 MB/秒（6.4 Gbit/s）
- 1.15 GB/秒（9.2 Gbit/s）

这些都是单个方向的吞吐量。 120 Mbyte/s 的结果可能还不错——实际上，1 Gbit/s 接口应该达到 119 Mbyte/s 左右。仅当两个方向都有大量流量且将其相加时，才可能得到 200 Mbyte/s 的结果；然而，这些都是单向结果。 350 Mbyte/s 及以上的结果显然是假的。

当您获得要检查的基准结果时，请查找可以对提供的数字执行的任何简单求和，以发现此类限制。

如果您可以访问该系统，还可以通过设计新的观察或实验进一步检验结果。这可以遵循科学方法：当前要检验的问题是基准测试结果是否有效。由此提出假设和预测，再通过测试进行验证。

### 12.3.9 统计分析

统计分析可用于研究基准数据。它分为三个阶段：

1. **选择**基准测试工具、其配置以及要捕获的系统性能指标
2. **执行**基准测试，收集大量结果和指标数据集
3. **解释**数据并进行统计分析，生成报告

主动基准测试侧重于在基准测试运行时对系统进行分析，而统计分析则侧重于分析结果。它也不同于被动基准测试，被动基准测试根本不执行任何分析。

这种方法适用于访问大型系统既受时间限制、成本又高的环境。例如，可能只有一套“最大配置”系统可用，但许多团队希望同时在其上运行测试，包括：

- **销售**：在概念验证期间，运行模拟客户负载以显示最大配置系统可以提供什么
- **营销**：获得营销活动的最佳数字
- **支持**：调查只有在最大配置系统承受重负载时才会出现的异常
- **工程**：测试新功能和代码更改的性能
- **质量**：执行性能防退化测试和认证

每个团队可能只有有限时间在系统上运行基准测试，却有更多时间在事后分析结果。

由于收集指标的成本很高，需要格外确保它们可靠可信，避免发现问题后不得不重新收集。除了检查指标在技术上是如何生成的，还可以收集更多统计属性，以便更早发现问题。这些属性可能包括波动、完整分布、误差范围等的统计数据（请参阅 [第 2 章](#ch02-ch02)、[方法论](#ch02-ch02)、[第 2.8 节](#ch02-ch02lev8)、[统计](#ch02-ch02lev8)）。对代码变更或性能防退化测试进行基准测试时，理解波动和误差范围至关重要，这样才能正确解读一对结果。

还要从运行中的系统收集尽可能多的性能数据（不能因收集开销损害结果），以便事后对这些数据进行取证分析。数据收集可以使用 sar(1) 等工具、监控产品，以及转储所有可用统计数据的自定义工具。

例如，在 Linux 上，自定义 shell 脚本可以在运行前后复制 /proc 计数器文件的内容。[^fn-ch12-ch12-footnote-6] 如有需要，可以把所有可能的数据都包含进来。如果性能开销可接受，这样的脚本也可以在基准测试期间按间隔执行。还可以使用其他统计工具创建日志。

结果和指标的统计分析可以包括*可扩展性分析*和*排队论*，用队列网络对系统建模。这些主题已在 [第 2 章](#ch02-ch02)、[方法论](#ch02-ch02) 中介绍，也是一些独立著作的主题 [\[Jain 91\]](#ch12-ch12ref3) [\[Gunther 97\]](#ch12-ch12ref4) [\[Gunther 07\]](#ch12-ch12ref8)。

### 12.3.10 基准检查清单

受性能箴言清单（[第 2 章](#ch02-ch02)、[方法论](#ch02-ch02)、[第 2.5.20 节](#ch02-ch02lev5sec20)、[性能箴言](#ch02-ch02lev5sec20)）启发，我创建了一份基准测试检查清单，其中的问题可以帮助您验证基准测试的准确性 [\[Gregg 18d\]](#ch12-ch12ref17)：

- 为什么不加倍？
- 是否突破了限制？
- 是不是出错了？
- 它会重现吗？
- 这有关系吗？
- 它真的发生了吗？

更详细地说：

- **为什么不翻倍？** 为什么操作速率没有达到基准结果的两倍？这实际上是在问限制因素是什么。当您发现限制因素不是测试的预期目标时，回答这个问题可以解决许多基准测试问题。
- **它是否突破了限制？** 这是合理性检查（[第 12.3.8 节](#ch12-ch12lev3sec8)、[合理性检查](#ch12-ch12lev3sec8)）。
- **有错误吗？** 出错操作的执行方式与正常操作不同，高错误率会使基准测试结果产生偏差。
- **它能重现吗？** 结果的一致性如何？
- **这重要吗？** 特定基准测试的工作负载可能与您的生产需求无关。一些微基准测试单个系统调用和库调用，但您的应用程序甚至可能没有使用它们。
- **它甚至发生过吗？** [第 12.1.3 节](#ch12-ch12lev1sec3)、[基准测试失败](#ch12-ch12lev1sec3) 中的早期忽略错误标题描述了防火墙阻止基准测试到达目标的情况，并报告了基于超时的延迟作为其结果。

下一节包含更长的问题列表，也适用于您无法访问目标系统、不能自行分析基准测试的情况。

<!-- source-id: ch12#ch12lev4 -->
## 12.4 基准测试问题

如果供应商向您提供基准测试结果，即使无法访问正在运行的基准测试来分析，也可以提出许多问题，以便更好地理解结果并将其应用到您的环境中。目标是确定实际测量的内容，以及结果是否现实、可重复。

- **一般**：
    - 基准测试与我的生产工作负载相关吗？
    - 被测系统的配置是什么？
    - 测试的是单个系统，还是一组系统的结果？
    - 被测系统的成本是多少？
    - 基准测试客户端的配置是什么？
    - 测试持续了多长时间？收集了多少结果？
    - 结果是平均值还是峰值？平均值是多少？
    - 其他分布详细信息是什么（标准差、百分位数或完整分布详细信息）？
    - 基准的限制因素是什么？
    - 操作成功/失败的比率是多少？
    - 操作属性是什么？
    - 是否选择了操作属性来模拟某种工作负载？这些属性是如何选择的？
    - 基准测试是否模拟方差或平均工作负载？
    - 基准测试结果是否使用其他分析工具得到确认？（提供截图。）
    - 可以用基准结果来表示误差幅度吗？
    - 基准测试结果是否可重复？
- 对于 **CPU/内存** 相关基准测试：
    - 使用了什么处理器？
    - 处理器是否超频？是否使用了定制冷却（例如水冷）？
    - 使用了多少个内存模块（例如 DIMM）？它们如何连接到内存插槽？
    - 是否有任何 CPU 被禁用？
    - 系统范围的 CPU 利用率是多少？（轻负载系统可能因更高程度的睿频提升而运行得更快。）
    - 测试的是 CPU 物理核心还是超线程？
    - 安装了多少主内存？什么类型的？
    - 是否使用了任何自定义 BIOS 设置？
- 对于 **存储** 相关基准测试：
    - 存储设备配置是什么（使用了多少个、类型、存储协议、RAID 配置、缓存大小、回写或直写等）？
    - 文件系统配置是什么（类型、数量，以及是否使用日志、如何配置和调优等）？
    - 工作集大小是多少？
    - 工作集有多大比例进入缓存？缓存在哪里？
    - 访问了多少文件？
- 对于 **网络** 相关基准测试：
    - 网络配置是什么（使用了多少个接口、它们的类型和配置）？
    - 网络拓扑结构是怎样的？
    - 使用了什么协议？套接字选项是什么？
    - 调优了哪些网络协议栈设置？TCP/UDP 可调参数是什么？

在研究行业基准时，其中许多问题可以从披露细节中得到答案。

## 12.5 练习

1. 回答以下概念性问题：
    - 什么是微基准测试？
    - 什么是工作集大小，它如何影响存储基准测试的结果？
    - 研究性价比的理由是什么？
2. 选择一个微基准测试并执行以下任务：
    - 调整某个维度（线程数、I/O 大小……），并测量性能。
    - 用图表显示结果（可扩展性）。
    - 使用微基准测试将目标驱动到峰值性能，并分析限制因素。
